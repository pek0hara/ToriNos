# 記事下書き一覧の読み込みと、公開記事の編集の下書き 設計

作成日: 2026-10-13
状態: 実装・自動テスト・Android実機確認済み（2026-10-13、未コミット）
関連: `article-drafts-matometr-design.md`（8章 記事下書きと保存先）、`relay-unavailable-design.md`、`feed-relay-merge-design.md`（3.3）

## 1. 背景

利用者から次の2点の報告があった。

1. 記事の下書き一覧の読み込みが、接続できないリレーがあると遅い。
2. 投稿済みの記事を編集したときも、下書き一覧に追加されてしまう。

## 2. 現状の原因（コードからの推定。実機計測は未実施）

### 2.1 一覧の読み込みが遅い

- `ArticleDraftListScreen` は `ArticleDraftStore.refreshDrafts` が終わるまで一覧を出さない。`ArticleDraftRepository.load` は有限取得（`SubscriptionBehavior.Fetch(10_000)`）の `FetchCompleted` まで待つ。
- 取得先は「有効なリレー＋書き込みリレー」。書き込み専用のリレーは普段つながっていないため、この取得で初めて接続する。
  `relay-unavailable-design.md` 4章のとおり、初回の接続中は「接続できない」に含めないので、応答しないホストでは接続の時間切れ（約10秒）か取得の時間切れ（10秒）まで待つ。
- 一覧を開くたびに取り直し、同じセッションで取得済みの一覧も先に出さない。

### 2.2 公開記事の編集で下書きが増える

- A: 公開記事を開き、何も変えずに戻る・バックグラウンドへ移ると、`ON_STOP` の `saveNow()` → `flush()` で保存される。
  `flush` は未保存（`expectedRevision == null`）の下書きを「保存済みと同じ」と判定しないため、変更がなくても送信する。
- B: 公開前に `flush()` で下書きを保存し、`ArticlePublishAttempt.complete`（全送信先が受理）のときだけ `cleanPublishedDraft` で消す。
  書き込みリレーに接続できないものが1つでもあると一部受理になり、下書きが残る。2.1 と同じ「接続できないリレー」が原因になりうる。
- C: 公開記事の編集を開くたびに新しい draft ID を作るため、同じ記事の下書きが複数できうる。
- D: `torinos` 拡張を復元できない下書き（他クライアントが保存したもの等）は `baseEventId` を持たず、一覧で「通常記事」と表示され、エディタも新規扱いになる。
  ただし `d` は同じなので、公開すると同じ記事を上書きする（最新版との競合確認もされない）。

## 3. 要件

### 3.1 公開記事の編集の保存

| # | 要件 |
| --- | --- |
| R1 | 公開記事を開いただけ・変更せずに戻った・バックグラウンドへ移ったときは下書きを作らない。変更があったときだけ下書きへ保存する |
| R2 | 更新の公開を1つ以上のリレーが受理したら、その revision の下書きを削除する。未受理のリレーへはエディタの「再送」で、メモリ上の署名済みイベントを送り直す。新しい編集 revision がある場合は削除しない（既存の規則を維持） |
| R3 | 同じ記事（`d`）の編集中の下書きがあれば、「編集」から新しく作らずにその下書きを開く。公開版のほうが新しければ、既存の競合表示（`updateConflict`）で知らせる |
| R4 | 下書きの `d` が自分の公開記事（kind 30023）の `d` と一致する場合、`baseEventId` がなくても公開記事の編集（更新）として扱う |

公開前に一度下書きへ保存する仕組み（公開失敗時に入力を失わないため）は残す。1つでも受理すれば R2 で直ちに消える。

### 3.2 一覧の読み込み

フィード・検索の規則（`feed-relay-merge-design.md` 3.3、`app-requirements.md` の投稿検索の失敗表示）にそろえる。

| # | 要件 |
| --- | --- |
| L1 | 最初にリレーが EOSE を返した時点で、それまでに届いた下書きで一覧を表示する。残りのリレーの分は届き次第マージする（`d` ごとに最新版を採用する規則は維持） |
| L2 | 前景の読み込み表示は最初の表示で終える。遅いリレーの取得は時間切れか完了まで続け、取得中であることを控えめに示す |
| L3 | 全リレーの結果がそろったら、EOSE を返さなかったリレーを従来どおり警告として表示する |
| L4 | どのリレーも EOSE を返さずに終わったときは「下書きはありません」と表示せず、エラーと「再取得」を表示する（現状維持） |
| L5 | 同じセッションで取得済みの一覧があれば先に表示し、裏で取り直す |

取得先（有効＋書き込みリレー）と時間切れ（10秒）は変えない。下書きは書き込みリレーに保存するため、取得先を減らすと取りこぼすおそれがある。

### 3.3 一覧で公開記事の編集とわかるようにする

```
┌──────────────────────────────────────┐
│ [更新] 記事タイトル                 ⋮ │
│ 本文の冒頭…                           │
│ [通常記事] #tag · 10/1に公開済み  2時間前│
└──────────────────────────────────────┘
```

| # | 要件 |
| --- | --- |
| V1 | 公開記事の編集には、タイトルの前に種類ラベルとは別の「更新」バッジを付ける。新規の下書きと区別できる色（tertiary 系）にする |
| V2 | 種類ラベル（通常記事／まとめ）は公開記事の編集でも表示する |
| V3 | 元の記事の最初の公開日を「M/dに公開済み」として表示する（`originalPublishedAt`） |
| V4 | 判定は `baseEventId` があるものはすぐ付ける。それ以外は自分の公開記事の `d` の取得が届いた時点で付け足す（R4 と同じ判定） |

## 4. 設計

### 4.1 保存の判定（R1）

- `ArticleEditorViewModel` で、公開記事から開いた直後の下書き（`baseline`、revision 0）を比較の基準にする。
  `flush` は、未保存の下書きでも `saveComparable()` が `baseline` と同じなら送信しない。
- `discard` は、未保存のまま破棄する場合は何もしない（既存の分岐で足りる）。

### 4.2 一部受理での削除（R2）

- `ArticlePublisher` で `cleanPublishedDraft` を呼ぶ条件を `complete` から `accepted`（1つ以上受理）に変える。
- `ArticleDraftStore.cleanPublishedDraft` の `check(attempt.complete)` も `accepted` にそろえる。
- 再送（`retry`）は記事の再送だけを行い、下書きはすでに消えているので何もしない。
- 公開後に記事を開く条件（`publishedArticle`）は従来どおり `complete` のままにする。一部受理ではエディタに留まり、再送できるようにする。

### 4.3 同じ記事の下書きを開く（R3・R4）

- 「編集」から開くとき、`store.read(owner).drafts` から `articleIdentifier == editIdentifier` の下書きを探す。見つかればその draft ID で開き、`checkLatest` で競合を確認する。
- このセッションでまだ一覧を取得していなければ、`refreshDrafts` を待たずに公開版から開く（一覧の取得で編集の開始を遅らせない）。
  そのため、セッションで一度も一覧を取得していない状態では、同じ記事の下書きが重複しうる。R1 により変更したときしか下書きはできないので、これは受け入れる。
- R4 の判定は、一覧画面と下書きを開くときの両方で使う共通関数にする。

### 4.4 一覧の段階表示（L1〜L5）

- `ArticleDraftTransport.load` を、届いた下書きを逐次返す形に変える（例: `Flow<ArticleDraftLoadProgress>`。最初の EOSE 時点と、以降の更新と、完了時の `incompleteRelays` を流す）。
- `ArticleDraftStore.refreshDrafts` は進捗ごとにメモリの `drafts` を更新する。ただし途中経過では、メモリにあって取得結果にない下書きを消さない。消すのは完了時だけにする。
- 一覧画面は `loading`（前景）と `refreshing`（裏の取得中）を分ける。

### 4.5 公開記事の `d` の取得（V4）

- 一覧を開いたとき、自分の kind 30023 を `authors=[自分]` で取得し、`d` の集合を得る。取得先・時間切れは下書きと同じにする。
- 届き次第、`baseEventId` がない下書きにバッジを付け足す。下書き本体は書き換えない（表示上の判定だけ）。

### 4.6 実装時の判断

- R2: 削除後に同じ draft ID で編集を保存すると revision が1からやり直しになる。公開後の削除は revision ではなく、公開時に保存した下書きと内容が一致する場合だけ行う（`ArticleDraftStore.cleanPublishedDraft`）。
- R2: 1つでも受理されて下書きが消えたら、エディタは公開した版を基準（`baseEventId` = 公開したイベント）に戻す。以降の編集は新しい下書きとして保存し、消えた revision へ上書きしようとして競合にならないようにする（`continueAfterPublication`）。
- R2: 一部受理で下書きの削除に失敗したときは失敗を表示し、「同じ版を再送」が削除の再試行も兼ねる。全受理後の失敗では従来どおり「下書きの削除を再試行」を出す。
- R1: 公開の直前の保存は未変更でも行う（`flush(force = true)`）。公開処理は保存済みの下書きから始まるため。
- R4（エディタ）: `baseEventId` がなく `originalPublishedAt` がある下書きだけ公開版を調べる。未公開の新規下書きを開くたびに通信しないため。見つかれば更新として表示し、「確認して同じ記事を更新」を求める（既存の競合表示を使う）。
- L1: リレーごとの EOSE を区切りに一覧を出す。復号は event ID ごとに1回だけ行う。
- L1・L5: 取得中は Store のロックを持たない。取得中にエディタで保存・作成・削除した下書きは、取得結果で上書きしない。
- V1: バッジの文言は「更新」、削除確認では「公開記事の更新」と表示する。

## 5. テスト（実装前に書く）

| 対象 | 確認すること |
| --- | --- |
| R1 | 公開記事を開いて変更せずに `flush`・`saveNow` しても送信しない。1文字変えたら保存する |
| R2 | 送信先2つのうち1つだけ受理で下書きが消える。新しい revision があれば消えない。再送で下書きを作り直さない |
| R3 | 同じ `d` の下書きがメモリにあれば、その draft ID で開く |
| R4・V4 | `baseEventId` なしで `d` が公開記事と一致する下書きを、更新として扱う・バッジを付ける |
| L1・L2 | 偽の購読で1リレーだけ EOSE、もう1つは無応答のとき、最初の EOSE で一覧が出る。後から届いた下書きがマージされる |
| L3・L4 | 完了時の警告。全リレー無応答ではエラーになり、空一覧にならない |
| L5 | 取得済みの一覧がすぐ出て、途中経過で既存の下書きが消えない |

## 6. 実機での確認

- 接続できない書き込みリレーを1つ含む設定で、一覧が出るまでの時間を改修前後で比べる。
- 同じ設定で公開記事を更新し、下書きが残らないことを確かめる。
- 公開記事を開いてすぐ戻り、下書きが増えないことを確かめる。

### 6.1 結果（Android 実機 ASUS_AI2302、2026-10-13）

書き込みリレー6つのうち、r.bitcoinhold.net は名前を引けず、r.ydg.works は応答が遅い（EOSE まで約8秒、または10秒で時間切れ）状態だった。

| 確認 | 結果 |
| --- | --- |
| 一覧の最初の表示 | 0.16〜0.22秒（最初の EOSE）。全リレーの完了は8〜10秒。改修前は完了まで何も出なかった |
| 2回目以降に開いたとき | セッション内の一覧をすぐ表示し、裏で取り直す |
| 一部受理での更新 | 「薬剤師のぼやき」を内容を変えずに更新。5リレーが受理、r.bitcoinhold.net は不明。下書きは削除され、一覧から消えた |
| 更新後に変更せず戻る | 保存処理は未変更と判定し、送信しない |
| 公開記事を開いて変更せず戻る | 下書きは増えない（一覧は3件のまま） |
| `baseEventId` のない下書き（R4） | 10/12 に新規公開で一部受理となり残っていた下書きが、「更新」バッジ付きで表示され、開くと「確認して同じ記事を更新」を求めた。中身は公開版と同一だった |
| R3（既存の下書きを開く） | 実機では未確認（自動テストのみ）。確認には試験用の下書きをリレーに作る必要があるため |

### 6.2 実機で見つけた不具合（修正済み）

有限取得が時間切れで終わると、購読の信号の流れが閉じず、下書きの取得が完了しなかった（「ほかのリレーから取得しています」が出たまま）。

- 原因: `NostrRepository.restartFetchTimeout` のコルーチンが `completeFetch` → `closeActiveSubscription` を呼び、その中の `session.timeoutJob.cancel()` が自分自身を取り消す。
  使われなくなったリレーを閉じる `delay` で処理が打ち切られ、`session.finish()` に届かない。改修前から、時間切れになった取得すべてで起きうる。
- 修正: 時間切れの完了処理を `NonCancellable` で実行する。あわせて記事下書きの取得は `FetchCompleted` を受けた時点で受信を終える（流れが閉じなくても止まらない。回帰テストあり）。
- `NostrRepository` には偽リレーを差し込む口がないため、通信層の修正は実機（r.ydg.works の時間切れ時に10秒で完了）で確認した。
- ほかの受け手で、流れが閉じるまで待つものが同じ影響を受けていたかは未調査。

### 6.3 範囲外で気づいたこと

- 記事タブの「自分」の絞り込みで、yabu.me に受理された自分の記事が「条件に合う記事がありません」になった。今回の変更とは無関係とみられ、未調査。
- 公開記事を開いた直後、保存状態が「未保存」と表示される（変更はなく、下書きも作らない）。
