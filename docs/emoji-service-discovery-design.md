# 絵文字サービスのヘッダー・単一リレー探索・登録人数の設計

作成日: 2026-10-01  
状態: 設計レビューの指摘を反映し、実装済み（2026-10-01）。検証内容・実装上の構成は12章。

## 1. 目的と決定事項

絵文字タブを他のサービスと同じヘッダー構成に揃え、選択した1リレーから取得したセットを、他ユーザーの登録情報に基づいて探せるようにする。

本書の「他ユーザーの取得数」は、直前の議論に沿って「取得できたフォロー先の公開登録情報から数えた、セットごとの登録人数」と解釈する。投稿・リアクションの使用回数や、ネットワーク全体の登録者数ではない。

- ヘッダーはプロフィール / 閲覧リレー選択 / 設定と、その下の4つのサービスタブで構成する。
- 公開セット、フォロー先の登録情報、登録情報が参照するセットの追加取得は、すべて選択中の同じ1リレーを利用する。
- 初期の並び順は「フォロー内の登録順」。切り替えで「新着・更新順」を選べる。
- 登録人数は取得できた各ユーザーの最新 kind 10030 の公開セット参照から集計する。
- 自分のセット登録・お気に入りの同期と送信先は、既存のアカウント設定に従う。
- ピッカーの日本語辞書、投稿の利用頻度集計、全ユーザーのランキングは本改修の対象外。

## 2. 現状と課題

2026-10-01時点の作業ツリーと提示されたスクリーンショットを基準とする。

| 対象 | 現状 | 課題 |
| --- | --- | --- |
| `EmojiServiceHeader` | タイトル「絵文字」、再読み込み、投稿先リレー、設定 | 記事・チャンネル・ステータスの `RelaySelector` 中心の構成と異なる |
| `EmojiSetDiscovery` | 対象指定なしの購読で公開セットを取得 | 有効リレー全体が対象。表示する取得元を選べない |
| 公開セット一覧 | 最新100件を要求し、更新日時降順 | 登録者の多さを反映しない。古いセットが探索対象から漏れる |
| 登録情報 | 自分の kind 10030 を同期 | 他ユーザーの登録人数を保持・表示していない |
| 重複排除 | アドレスに加え作者＋タイトルでも排除 | 登録情報の参照先と一覧の同一性がずれ、別セットの人数が消える可能性がある |

`docs/settings-navigation-design.md` の旧方針「閲覧リレー切り替えを表示しない」を、本書の単一リレー探索に置き換えた。同文書と要件を更新済み。

## 3. ヘッダーと画面

### 3.1 共通構成

他サービスで利用している `AppTopBar` / `RelaySelector` / `ServiceTabRow` を再利用する。

```text
[プロフィール]  relay.example ▾              [設定]
 記事       チャンネル       ステータス       絵文字
────────────────────────────────────────────────
 [フォロー内の登録順 ▾]       125セット  🔍 [更新]
 [登録済みのみ (1)]
────────────────────────────────────────────────
 セット名                                   ＋登録
 絵文字27個 · フォロー中の5人が登録
 作成者名（未取得時は短縮公開鍵）
 [絵文字プレビュー …]
```

- 絵文字だけのタイトル、ヘッダーの更新・クラウドボタンを外し、閲覧リレー選択と設定の位置・色・高さを他サービスに揃える。
- 更新は一覧の操作行へ移す。検索語と選択中の並び順を保持して再取得する。
- リレー選択メニューに「このリレーからセットと公開登録情報を取得します」と補足する。
- サービスからのセット詳細にも共通ヘッダーと4タブを維持する。詳細には独立した「一覧へ戻る」を置く。
- 設定・本文・ピッカーから開く経路は既存の戻る導線を維持し、サービスタブを強制表示しない。
- 「セットを探す / 登録済み」の内側タブは置かない。登録済みの確認は「登録済みのみ」フィルターで行う。
  フィルター中は登録済みセットをすべて出し、選択中のリレーの公開一覧に無いセットも登録時の内容で表示する。
- 検索欄は普段は畳み、操作行の 🔍 で一覧の上に開く。閉じると検索語も消す。検索語付きで開いた場合（本文の絵文字タップなど）は最初から開く。

### 3.2 表示する人数と取得状態

フォロー先の公開登録情報の取得状況（「フォロー120人中84人の公開登録情報を取得」など）は一覧に表示しない。
取得中は操作行の更新ボタンが「取得中」になり、「取得を停止」を出す。リレー設定の読み込み中と閲覧リレー未選択のときだけ操作行の下に案内を出す。

取得人数は kind 10030 を受信した異なる公開鍵の数。空の公開リストを受信した人も取得済みに含める。応答がない人、非公開情報のみの人、古い公開状態しか取得できない人について、現在の登録状況を保証しない。

セット行は「フォロー中の5人が登録」と表示する。取得途中なら「取得済みの情報で5人が登録」とし、人数が暫定であることを伝える。0件は「取得した情報では登録者なし」、集計自体が未実施なら「登録人数未取得」とする。

「125セット」は現在表示条件に一致する取得済みセット数。登録人数やリレー内の総セット数と混同しない。

## 4. 単一リレーの選択と取得範囲

### 4.1 選択状態

- `RelayStore.selectedEmojiRelayUrl` / `setSelectedEmojiRelayUrl` を他サービスと同じ保存方式で追加する。
- 保存値が有効リレーにあれば復元し、なければ有効リレー一覧の先頭を選ぶ。
- 有効リレーがない場合は未選択画面とリレー設定への導線を表示する。
- 未選択・リレー障害でも「登録済み」ページとローカルの詳細・お気に入り操作は利用できる。探索の状態で画面全体をブロックしない。
- 「すべてのリレー」は選択肢に含めない。失敗時にも他リレーへ自動展開しない。
- 切り替え時は旧購読を閉じ、旧リレーの結果を新リレーの結果に混ぜない。
- セット詳細表示中の切り替えは一覧へ戻す。検索語・内側のタブ・並び順は保持し、一覧位置は先頭に戻す。

### 4.2 一覧候補の取得

1. 選択リレーへ kind 30030 の新着100件を要求し、先に一覧を表示する。
2. 同じリレーへフォロー先の kind 10030 を取得する。
3. その公開 `a` タグにある kind 30030 の参照を抽出し、一覧未取得のセットを同じリレーへ追加要求する。
4. 新着セットと参照先セットを `EmojiSetAddress` で統合する。

これにより、古くてもフォロー先が登録しているセットを候補に追加できる。追加取得できなかったセットは参照と人数を保持するが、通常のセット行にはせず、取得できなかった件数も表示しない。架空のタイトルやプレビューを生成しない。

同じ作者・同じタイトルでもアドレスが異なれば別セットとして表示する。重複排除をアドレスだけに変更し、kind 10030 の参照と正確に対応させる。

公開一覧に関連するセット詳細取得とピッカーの公開候補も、同じリレー別カタログを参照する。設定・本文・ピッカーの入口でも保存済みの絵文字閲覧リレーを利用する。自分の kind 10030 同期やその参照解決は、単一リレー探索とは別処理として既存の方針を維持する。

本文から渡されたアドレスのセットを選択リレーで取得できない場合、一覧へ黙って戻さず「このリレーではセットを取得できませんでした」と再試行・閲覧リレー変更の導線を表示する。自分の登録済みセットに一致する場合はローカル情報で詳細を開ける。アドレスがある場合、コード名だけ一致する別セットを自動的に開かない。

## 5. 登録人数の集計

### 5.1 対象と同一性

- 集計対象は現在のアカウントのフォロー先。自分自身を除き、公開鍵を重複排除する。
- フォロー情報は既存のアカウント状態を使う。探索処理が別途 kind 3 を全リレーから取得しない。
- `FollowRepository.loaded` が false の間は「フォロー情報を読み込み中」とし、「フォローなし」に分類しない。集合の内容が変わった時だけ集計世代を更新する。
- ユーザーごとに最新の有効な kind 10030 を1件だけ採用する。
- `created_at` が同じならイベントIDの辞書順が小さい方を採用する。
- 公開 `a` タグを `EmojiSetAddress.parse` で検証し、kind 30030 の有効な参照だけを採用する。
- 1ユーザーが同じセットを何回参照しても1人と数える。
- インライン `emoji` のみの登録は、画像・コードが同じでもセット登録人数に加えない。所属セットを推測しない。
- 暗号化されたリスト内容は集計しない。

```text
登録人数(set) = 最新の公開リストに set の参照がある、取得済みフォロー先の人数
```

新しいリストを受信したら、旧参照から人数を減らし、新参照へ加える。登録解除による人数減少も反映する。件数を単純に加算し続けない。

### 5.2 取得方式と制限

初期値はフォロー先50人ずつ、同時購読2本、各購読10秒の一時取得とする。すべて `RelayTarget.Single(selectedRelayUrl)` を明示し、`SubscriptionBehavior.Fetch` を利用する。

受信には `SubscriptionSession.signals` を使い、`FetchCompleted.outcomes` の選択リレーの結果が `RelayOutcome.Eose` の時だけ正常終了とする。`TimedOut`・`Closed`・`Unavailable` は、イベントを一部受信していても一部取得として扱う。例外・キャンセル時も `finally` でセッションを閉じる。

今回取得した人数は、`SubscriptionSignal.Event.relayUrl` が選択リレーと一致する受信だけで数える。既存APIは `CACHE_RELAY_URL` からイベントを再生するため、新設の一時取得では `deduplicateEvents = false` とし、キャッシュ再生が後続の実リレー応答を抑制しないようにする。実リレー受信後は受信側でIDを重複排除し、kind・作者・要求条件・署名とイベントIDの検証を通過したものだけ採用する。探索キャッシュはこの検証済みの結果を保持する。

kind 10030 は `authors` を指定して取得する。セットの `#a` だけで絞る方式は採用しない。参照を削除した最新リストが検索に一致せず、旧登録を残す恐れがあるため。

各バッチの `limit` は対象人数を初期値とし、要求上限に達したまま未取得ユーザーが残った場合は、そのユーザーを小さいバッチに分けて1回再要求する。応答のないユーザーを無制限に再試行しない。EOSEは取得終了を意味し、全ユーザーの情報が揃った保証ではない。

セット追加取得は最大20アドレスずつの正確なフィルターで要求する。作者集合と `d` 集合を一括で組み合わせず、アドレスごとの作者＋`d` フィルターを使う。取得後も要求アドレスとの一致を確認する。

フォロー先は全員を対象とし、処理を分割して進捗表示する。初回のセット表示予算は新着を含む1,000件とし、新着に加える参照先は登録人数の多い順で解決する。残りは件数を表示し「さらに読み込む」で100件ずつ追加する。1,000件は初回取得量の上限であり、メモリ上限とは呼ばない。未取得参照と取得失敗参照を別に数え、読み込んでいないセットを取得失敗と表示しない。

バッチ間はキャンセル可能とし、フォロー先が多い場合は「取得を停止」を表示する。停止後も取得済みで一覧を利用できる。表示セットの累積上限は3,000件とし、到達時は明示して追加取得を止める。非表示のリレー別カタログはLRUで最大2リレー分、アカウント依存キャッシュはセッション終了時に破棄する。各公開リストの参照解析も最大1,000アドレスとし、超過分は黙って省く（表示はしない）。全体の人気順位が確定したとは表示しない。

## 6. 並び順・検索・安定性

| 選択 | 比較順 |
| --- | --- |
| フォロー内の登録順（初期値） | 登録人数降順 → 更新日時降順 → セット名 → アドレス |
| 新着・更新順 | 更新日時降順 → セット名 → アドレス |
| 検索中 | 一致度降順 → 選択中の比較順 |

検索一致度は、セット名または絵文字コードの完全一致、前方一致、部分一致の順。コロン除去・大小文字などの正規化を一覧と詳細で共通化する。

未ログイン・フォローなし・公開登録情報を1件も取得できない場合は、新着・更新順に切り替え、理由を表示する。取得済みの公開リストがすべて空の場合は集計済み0件として扱い、登録順の同率を更新日時で解決する。

取得途中に行が頻繁に移動しないよう、件数は更新しても現在の行順を保持する。候補の追加は末尾へ置き、取得完了時または上限に達して一旦停止した時点で並び替える。スクロール中なら「並び順を更新」ボタンで適用し、先頭表示中なら自動適用する。ページ追加・登録情報更新でも同じ規則を使う。

「登録済み」ページは自分の管理用。フォロー内の登録人数で順番を変えず、セット名順を維持する。

## 7. 状態所有とキャッシュ

`EmojiSetDiscovery` のプロセス全体の単一状態に、アカウント依存の登録人数を追加しない。

| 所有者（新設名は案） | 状態・役割 |
| --- | --- |
| `EmojiCatalogRepository` | リレー別の公開セット、新着・参照先取得、キャッシュ |
| `EmojiAdoptionRepository` | アカウント・リレー・フォロー集合ごとの最新公開リストと登録人数 |
| `EmojiDiscoveryViewModel` | 検索、並び順、取得進捗、表示順の確定、選択リレー |
| 既存 `CustomEmojiRepository` | 自分の登録・お気に入り・履歴・同期 |

集計キーは `(accountPubkey, relayUrl, followSetVersion)`。カタログはリレー別。別リレーで取得したイベントをキャッシュから再生しても、そのリレーでの観測結果として集計しない。イベントID・取得元リレー・取得時刻を保持する。

- キャッシュ有効期間の初期値は5分。戻る操作では有効キャッシュを再利用する。
- 更新時は既存一覧を残して取得する。今回受信したユーザーのリストはイベントの新旧比較で更新し、空の公開リストを受信した場合はそのユーザーの旧参照を取り除く。受信のなかったユーザーの旧リストは正常EOSEでも削除せず、前回の情報として保持する。タイムアウトや応答なしを登録解除と解釈しない。
- 失敗したバッチの旧データを残す場合は「前回取得した情報を含む」と表示する。最新取得人数とキャッシュ人数を別に保持する。
- リレー切り替え・アカウント切り替え・フォロー変更時は世代を更新し、旧処理の結果を無視する。
- 画面離脱時は一覧と集計の購読を閉じる。購読共有中は利用者参照数を管理し、最後の利用者が離れた時点で閉じる。
- 一覧から同画面内の詳細へ移る操作は画面離脱としない。詳細の早期returnで一覧の購読所有者を破棄しないよう、状態とライフサイクルの管理を画面の共通部分に置く。別サービスタブへの移動・ナビゲーションでの離脱では停止する。
- 各ページの `LazyListState` は詳細表示の分岐より上で保持する。順位適用時もキーとオフセットで表示位置を維持する。サービスを離れて戻る場合は同じナビゲーションエントリの保存状態から検索・タブ・並び順を復元する。
- 更新の連打は実行中要求にまとめ、キャッシュ・接続を無制限に増やさない。

## 8. 失敗時の動作

- 一覧取得失敗: 同じリレーの前回一覧があれば残して再試行を表示。キャッシュなしならエラー表示。
- 集計取得失敗: 取得済みの範囲で人数を表示し、一部取得の状態を保持する。
- 新着取得のみ成功: セットは利用できる。人数は未取得とし、新着順で表示する。
- 参照セット取得失敗: 登録情報は失わず、取得できなかったセット数を表示する。
- リレー切断・拒否: EOSEと区別して失敗状態にする。別リレーへの切り替えはユーザー操作に委ねる。
- 自分の登録操作: 一覧の登録済み表示は即時反映するが、他ユーザー登録人数には加算しない。

## 9. 実装順と受け入れ条件

1. 閲覧リレー選択の保存・共通ヘッダー・単一リレーのカタログ取得を導入する。
2. フォロー先の公開リスト取得、最新イベント置換、登録人数の純粋な集計ロジックを導入する。
3. 参照先セットの追加取得とアドレス単位の重複排除を導入する。
4. 行の人数表示、並び順、取得進捗、失敗表示、スクロール中の並び替え制御を導入する。
5. 既存ピッカー・設定経路の共有を移行し、関連する要件・設計書を更新する。

受け入れ確認:

- iOS・Android・Webで、他サービスと同じヘッダー構成になる。
- 一覧・集計・参照先追加取得のREQが選択した1リレーだけへ送信される。
- 自分の登録情報同期・送信先が閲覧リレー変更で変わらない。
- 旧リレー・旧アカウント・旧フォロー集合の遅延イベントが一覧や人数に混ざらない。
- 同一ユーザーの重複イベント・重複タグで人数が増えない。
- 新しいリストによる登録解除と、同時刻イベントIDの優先規則をテストする。
- 最新100件にないセットも、フォロー先の参照から取得して表示できる。
- 同名の別アドレスを別セットとして集計する。
- 未取得・集計中・集計済み0件・一部失敗を区別する。
- フォロー初期読み込み中をフォローなしと判定しない。
- キャッシュ再生後に同じイベントを実リレーから受け取っても、今回取得人数に正しく含まれる。
- 更新時にイベントを受け取れなかったユーザーの旧参照を削除せず、空の最新公開リストを受け取った場合だけ解除を反映する。
- リレー未選択・障害時も登録済みセット管理と詳細表示を利用できる。
- スクロール中に人数が更新されてもタップ対象の位置が勝手に変わらない。
- 詳細から戻ると検索・タブ・並び順・一覧位置が復元される。

## 10. 初期値と調整事項

実装を進めるための初期値は新着100件、ユーザー50人/バッチ、同時2購読、10秒、キャッシュ5分、セット初回1,000件・累積3,000件とする。これらはプロトコルの保証値ではなく、実端末と選択リレーでの応答サイズ・取得時間を見て調整する。

最初から全ユーザーの登録人数を収集する設計にはしない。将来追加する場合も「選択リレーで観測した人数」として、フォロー内人数とは別の指標・並び順にする。

## 12. 実装とレビュー結果（2026-10-01）

- 公開カタログのクラス名は `EmojiSetDiscovery` を維持し、単一リレー・2リレー分のキャッシュ・利用者参照数を追加した。ピッカーと管理画面の既存共有を維持するため、別名のカタログリポジトリへの置き換えは行っていない。
- `EmojiAdoptionRepository` は `AccountSession` に追加し、終了時にキャンセル・破棄する。公開リストの取得と集計をUIから分離した。要求IDにはセッションIDのハッシュを使い、公開鍵を含む長いセッションIDで64文字制限を超えないようにした。
- UIの検索・並び順・表示順は画面で保持する。専用ViewModelは新設せず、既存ナビゲーションの保存状態と `rememberSaveable` / `rememberLazyListState` を利用する。セット詳細に切り替えても共通の状態・購読所有者を保持する。
- `EmojiDiscoveryTransport` が単一リレーのFetchを作り、署名・イベントID・要求条件を検証する。キャッシュ応答と別リレー応答は今回取得人数に含めず、正常終了と部分取得を区別する。
- レビューで、応答なしによる旧参照の削除、登録済みページのリレー依存、初回取得予算とメモリ上限の混同、キャッシュ再生による人数の誤集計を修正した。
- 実装レビューで、購読ID長、参照取得による新着キャッシュ期限の延長、古い応答が来た際のキャッシュ使用表示、取得中の追加行の順序固定を修正した。
- 実リレーのブラウザ確認は未ログイン状態で実施。サービスヘッダー、スマートフォン幅、公開セット取得、検索、詳細から戻る際の検索保持を確認した。ログインしたアカウントの登録人数表示は、偽の通信応答による自動テストで検証する。ユーザーの鍵入力・登録状態の変更は行っていない。

自動テストには、人数の重複排除、登録解除、同時刻のイベント選択、無応答時の旧情報保持、キャッシュ／別リレー応答の除外、タイムアウト・キャンセル、リレー切り替え、検索順位、同名別アドレスの保持を含む。

検証結果: `:composeApp:iosSimulatorArm64Test` は879件すべて成功。`:composeApp:compileAndroidMain` と `:composeApp:wasmJsBrowserDistribution` も成功。`git diff --check` は問題なし。iOS・Androidの実機表示とログインアカウントでの実リレー集計は未確認。
