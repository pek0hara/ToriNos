# フィードの起動時キャッシュ 設計

作成日: 2026-10-16
状態: 設計（未実装）。
関連: `profile-cache-design.md`（永続キャッシュは今後の実装対象）、`cache-performance-refactor-design.md`、`feed-skeleton-design.md`、`feed-initial-reveal-design.md`、`feed-relay-merge-design.md`、`Torinos_NIP28_channel_spec.md` 第22章（Room の撤去）

## 1. 目的と範囲

アプリを起動した直後に、前回見ていたホームのフィードをすぐ表示する。新しい投稿はその後リレーから取り、前回の表示に重ねる。

今は起動のたびに、フォロー一覧 → 最新30件の取得 → 表示、の順に待ち、その間はスケルトンを出している（`feed-skeleton-design.md`）。本設計はこの待ち時間そのものをなくす。

| 対象 | 内容 |
| --- | --- |
| **対象** | ホームのフォローフィードとグローバルフィードの、先頭の投稿（スナップショット）。その投稿の作者・リポストした人・引用先の作者のプロフィール（kind 0） |
| 対象外 | リアクション・返信・リポストの件数（毎回取り直す）、スレッド、プロフィール画面の投稿一覧、チャンネル、記事、検索、通知、リンクプレビュー |

非目標: すべてのイベントを保存するローカル DB。オフラインでの閲覧。

## 2. 前提: Room を撤去した判断との関係

2026-09-23 に、チャンネルのメッセージ全履歴を Room に保存する仕組みを撤去した（`Torinos_NIP28_channel_spec.md` 第22章）。理由は「リレーが一次ストアとして存在する以上、全履歴の複製はコストに見合わない」ことと、migration・prune・複数のリレー集合テーブル・キャッシュとライブ受信の重複排除の整合という維持コストだった。

本設計はこの判断に従う。

- 保存するのは**表示を速くするための小さな使い捨ての写し**だけで、上限を決める（§5.2）。正しい内容は常にリレーから取り直す。
- 形式が変わったら、移行せずに捨てる。migration は書かない。
- 保存したイベントを取得の代わりには使わない。取得のカーソルや重複排除の仕組み（`FeedHistoryStore`、リレー別の履歴カーソル）には混ぜない（§5.5）。

DB を使わない理由: 必要な読み書きは「起動時に1回まとめて読む」「バックグラウンドに移るときに1回まとめて書く」だけで、検索も部分更新もない。1つのファイルに JSON で書けば足りる。

## 3. 現状

| 項目 | 現状 |
| --- | --- |
| フォロー一覧 | `FollowRepository` が kind 3 を `LocalSettingsStorage` に保存済み。起動時はこれを先に使う |
| フィード | `FeedController.startSubscriptions()` から取得を始め、最初のページが届くまで投稿は0件。保持はメモリの `FeedHistoryStore`（上限5,000件） |
| プロフィール | `ProfileCache` はメモリだけ。永続化は `profile-cache-design.md` で「今後の実装対象」 |
| 画像 | Coil のディスクキャッシュがある（`cache-performance-refactor-design.md` §10） |
| 復帰 | バックグラウンドが10分を超えたら、フィードを捨てて最新30件を取り直す（`FeedResumePolicy`） |
| 保存先 | `LocalSettingsStorage` は Android が DataStore Preferences、iOS が `NSUserDefaults`、Web が `localStorage` |

`LocalSettingsStorage` には載せない。どの実装も保存内容をまとめてメモリに読み込む作りで、数百 KB のデータを置く場所ではない（Web の `localStorage` は他の設定や鍵と合わせて約 5MB の上限がある）。

## 4. 他クライアント

Nostrism は、受け取ったイベントをすべて SQLDelight の DB に保存し、画面は DB を読む（cache-first）。起動直後から前回の内容が出る一方、DB スキーマと migration（1〜8）、6,000 行の Repository を抱えている。本設計は、起動直後の表示という効果だけを、小さな写しで得る。

## 5. 設計

### 5.1 保存するもの

```kotlin
@Serializable
data class FeedSnapshot(
    val version: Int = 1,
    val accountPubkey: String,
    val feedKey: String,                // §5.6
    val savedAt: Long,
    val events: List<NostrEvent>,       // 表示していた先頭の投稿（新しい順、最大100件）
    val reposts: List<NostrEvent>,      // events のうちリポストで表示していたものの kind 6
    val quotedEvents: List<NostrEvent>, // 引用先（最大50件）
    val relayUrls: Map<String, List<String>>, // イベントID → 受信したリレー（所在の表示用）
)
```

- 署名つきのイベントをそのまま保存する。表示用に加工した値（`ParsedNoteContent` など）は保存せず、読み込み後に作り直す。
- 件数はリアクションなどを除いた、画面に並べていた投稿の数で数える。

プロフィールは `ProfileStore` として別のファイルに保存する（`profile-cache-design.md` の構成図にある `ProfileStore` をここで実装する）。

```kotlin
@Serializable
data class ProfileStoreFile(
    val version: Int = 1,
    val entries: List<StoredProfile>,   // 最後に使った順、最大1,000件
)

@Serializable
data class StoredProfile(val event: NostrEvent, val fetchedAt: Long, val lastUsedAt: Long)
```

### 5.2 保存先と上限

新しく `CacheFileStorage`（expect/actual、キー → バイト列）を作る。

| プラットフォーム | 保存先 | 上限 |
| --- | --- | --- |
| Android | `context.cacheDir/torinos_cache/` | スナップショット 100件、プロフィール 1,000件 |
| iOS | `NSCachesDirectory/torinos_cache/` | 同上 |
| Web | `localStorage`（キーの接頭辞 `torinos_cache_`） | スナップショット 50件、プロフィール 300件、合計 512KB |

- OS が容量不足のときに消せる場所（Caches）に置く。消えても次の起動が遅くなるだけで、データは失われない。iOS で再取得できるものを Caches に置く方針は `cache-performance-refactor-design.md` §5.5 と同じ。
- 1件あたり、投稿は約1KB、プロフィールは約0.6KB と見込む。ネイティブで合計約 0.8MB、Web で 512KB 以内。実際の大きさは計測して見直す（§7）。
- 書き込みは一時ファイルに書いてから名前を変える（途中で落ちても壊れたファイルを残さない）。Web は1回の `setItem` で済む。
- 読めないファイル（形式の違い、壊れた JSON、`version` の不一致）は消して、キャッシュなしとして起動する。

### 5.3 書き込むとき

- アプリがバックグラウンドに移ったとき（`FeedResumePolicy` が使っている時刻の記録と同じ場所）。
- 起動後、最初の新しいページを表示してから 5 秒後に1回（起動直後に落ちたときに古いスナップショットが残り続けないように）。
- 上のどちらも、前回の書き込みから 30 秒以内なら書かない。ライブ受信のたびには書かない。
- 書き込みはバックグラウンドのスレッドで行い、画面の更新を止めない。
- その時点でリストの先頭にいなくても、保存するのは常に**一番新しい側から**100件とする（起動時は先頭から表示するため。§5.4）。

### 5.4 起動時の表示

1. アカウントのセッションが始まったら、`feedKey` が一致するスナップショットと `ProfileStore` を読み込む。
2. `ProfileStore` の内容を `ProfileCache` に入れる。`fetchedAt` は保存時の値のままにするので、古いものは `CacheFirst` の規則で取り直される。
3. スナップショットの投稿に、**今の**ミュート・NG ワード・フォロー一覧を当てて表示する。フォローを外した人の投稿は出さない。
4. 表示は先頭（一番新しい投稿）から。スケルトンは出さない。
5. 画面の上端に、取得中であることを小さく示す（例: 「更新中…」とプルリフレッシュの印）。投稿の内容を、新しく取ったものと区別して描き分けることはしない。
6. リアクションなどの件数は、スナップショットの投稿にも普段どおり取得を始める（`EngagementFetcher` に投稿 ID を渡す）。

### 5.5 新しいページが届いたとき

スナップショットは `FeedHistoryStore` に入れず、「前回の続き」として別に持つ（`snapshotTail`）。表示するリストは、新しく取った投稿と `snapshotTail` を合わせて時刻順に並べたものにする。

```
新しく取った投稿（最新30件）      ← 取得のカーソルはここから古い方へ進む
──────────────────
（隙間：まだ取っていない期間）      ← 重なっていればこの部分はない
────── ここから前回の表示 ──────
snapshotTail（前回の先頭100件）
```

- **重なっているとき**（スナップショットの一番新しい投稿が、新しく取った一番古い投稿より新しい）: 隙間はない。重なった投稿は ID で1つにする。
- **重なっていないとき**: 隙間の位置に「ここから前回の表示」の区切りを出す。区切りが画面に入ったら、今と同じ「もっと読み込む」で古い方へ取得を進める。取ったものは時刻順に区切りより上へ入る。
- 履歴のカーソルがスナップショットの一番新しい投稿より古くなったら、区切りを消す。カーソルがスナップショットの一番古い投稿より古くなったら、`snapshotTail` を捨てる（以後は普段の取得結果だけになる）。
- 新しいページが届いた時点で利用者がまだ先頭にいて、重なっていない場合は、`snapshotTail` をその場で捨てる（隙間の下に古い投稿が残っても見ないため）。
- 履歴の取得は今までどおり `FeedHistoryStore` とリレー別のカーソルで動き、スナップショットの存在を知らない。代わりに、スナップショットと同じ範囲を取り直す分だけ通信が増える。段階2でカーソルを引き継ぐかを決める（§10）。

### 5.6 フィードの鍵（`feedKey`）

`feedKey` は、フィードの種類（フォロー・グローバル）、選択中のリレーの集合、表示する kind の集合から作る。リレーの選択を変えたら、前のスナップショットは使わない（別のリレーで取った写しを混ぜないため）。

### 5.7 アカウント

- スナップショットとプロフィールはアカウントごとのファイルにする（ファイル名に pubkey のハッシュを使う）。
- ログアウトとアカウント削除で、そのアカウントの分を消す。誰をフォローしているか、何を見ていたかが端末に残らないようにする。
- アカウントを切り替えたら、切り替え先のスナップショットを読む。切り替え前の書き込みは、セッションを閉じる前に済ませる（`AccountSession.prepareTransition()` の中で行う）。

### 5.8 検証

- 保存するイベントは、受信時に署名を検証済みのものだけ。読み込み時には署名を検証し直さない。100件の検証は Web（`@noble/curves`）では起動を目に見えて遅らせるため。
- 端末のファイルや `localStorage` を書き換えられる攻撃者は、すでに秘密鍵（Web）や画面そのものを操作できる立場にあるので、ここで守る意味が薄い。この判断は §8 R5 に残す。

## 6. 起動の順序と計測

| 時点 | 今 | 本設計 |
| --- | --- | --- |
| セッション開始 | スケルトン | スナップショットを表示 |
| フォロー一覧（キャッシュ） | 取得開始 | 取得開始（変わらない） |
| 最初のページ | 投稿を表示 | 前回の表示に重ねる |

`StartupTrace`（ホームのフィードの `startupTraceName`）に `snapshot.loaded` と `snapshot.shown` を足し、Android 実機のコールドスタートで「投稿が最初に出るまで」を今と比べる。目標は、`paneComposed` から 300ms 以内にスナップショットが出ること。

## 7. テスト

| 対象 | 主なケース |
| --- | --- |
| `CacheFileStorage` | 書き込みと読み込みの往復、一時ファイルからの置き換え、壊れたファイルを消す |
| `FeedSnapshot` | 上限の100件・50件、新しい側から保存する、`version` が違えば捨てる |
| 表示 | 今のミュート・NG ワード・フォロー一覧で絞り込む、`feedKey` が違えば使わない |
| 合流（§5.5） | 重なっている・重なっていない、先頭にいるときは捨てる、区切りの表示と消え方、カーソルが通り過ぎたら捨てる、ID の重複を1つにする |
| `ProfileStore` | 最後に使った順で1,000件、`createdAt` が古いもので上書きしない（`ProfileCache` の規則） |
| アカウント | ログアウト・削除で消える、切り替え前に書き込みが済む |
| Web | 512KB を超えるときに件数を減らす、`localStorage` の容量超過で失敗しても起動できる |

実機では、Android のコールドスタートを録画し（`feed-skeleton-design.md` と同じ手順）、スナップショットの有無で比べる。キャッシュファイルの実際の大きさも記録する。

## 8. 設計レビュー

| # | 指摘 | 対応 |
| --- | --- | --- |
| R1 | Room を撤去した判断（全履歴の複製はコストに見合わない）と矛盾しないか | §2 のとおり、上限のある使い捨ての写しに限る。migration・prune・取得への混入はない |
| R2 | スナップショットを `FeedHistoryStore` に入れると、カーソルや重複排除の前提が崩れる | §5.5 で別に持ち、表示のときだけ合わせる |
| R3 | 前回から長く空くと、新しい投稿との間に隙間ができる | §5.5 で区切りを出し、「もっと読み込む」で埋める。先頭にいれば捨てる |
| R4 | フォローを外した人や、ミュートした人の投稿が出る | §5.4 で今の条件を当ててから表示する |
| R5 | 保存したイベントを読み込み時に検証しない | §5.8。受信時に検証済みで、保存先を書き換えられる攻撃者には別の手段がある |
| R6 | 何を見ていたかが端末に残る | §5.7 でログアウト・削除時に消す |
| R7 | `LocalSettingsStorage` に入れると、設定の読み込みが重くなる | §3・§5.2 で別の保存先にする |
| R8 | 前回の後に削除された投稿が、取り直すまで表示される | 許容する。`snapshotTail` は履歴の取得が追いつけば捨てる |

## 9. 実装順序

1. `CacheFileStorage`（3プラットフォーム）とテスト。
2. `ProfileStore` と `ProfileCache` への読み込み。プロフィールの表示が起動直後から出ることを確かめる。
3. `FeedSnapshot` の保存（バックグラウンドへの移行時、最初のページの後）。
4. 起動時の表示と、`snapshotTail` の合流（§5.5）。
5. `StartupTrace` での計測と、上限の見直し。
6. `profile-cache-design.md` の「永続キャッシュ」の記述と、`app-requirements.md` のデータ保存要件を更新する。
