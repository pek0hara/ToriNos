## 1. 目的と範囲

NIP-17（Private Direct Messages）で、1対1のメッセージを送受信できるようにする。メッセージの中身・送り手・受け手・送った時刻を、リレーや第三者から読めない形で扱う。

| 段階 | 内容 |
| --- | --- |
| 段階0（前提） | NIP-42 のリレー認証。`signer-abstraction-design.md` の段階1（相手を指定した NIP-44 暗号化） |
| **段階1（本書の主対象）** | 1対1のテキストの送受信、会話一覧と会話画面、DM リレー（kind 10050）の設定、未読、知らない人からの「リクエスト」 |
| 段階2 | 旧形式の DM（NIP-04、kind 4）の読み出し、グループの会話、返信の引用表示、件名（`subject`） |
| 段階3 | 画像などのファイル（kind 15）、消えるメッセージ（`expiration`）、プッシュ通知（別のプライバシー設計） |

非目標: 旧形式（kind 4）での送信。送信済みメッセージの編集・取り消し（NIP-17 では仕組み上できない）。

## 2. 仕様の確認（NIP-17・NIP-59・NIP-44）

### 2.1 3重の包み

```
kind 14  rumor（中身）   未署名。content=本文、tags=[["p", 相手], …]、created_at=送った時刻
   ↓ 自分の鍵で相手宛てに NIP-44 暗号化
kind 13  seal（封）      自分の鍵で署名。tags は空。created_at はずらす
   ↓ 使い捨ての鍵で相手宛てに NIP-44 暗号化
kind 1059 gift wrap（包装）使い捨ての鍵で署名。tags=[["p", 相手]]。created_at はずらす
```

- rumor は署名しないので、漏れても「本人が書いた」証明にならない（否認できる）。
- seal は署名するので、受け取った人は送り手を確かめられる。**seal の pubkey と rumor の pubkey が一致しなければならない**（なりすまし対策）。
- gift wrap は使い捨ての鍵で署名するので、リレーからは送り手が分からない。分かるのは `p` タグの受け手だけ。
- seal と gift wrap の `created_at` は、過去 2 日以内のランダムな時刻にずらす（時刻から相手を推測させないため）。表示に使う時刻は rumor の `created_at`。
- 送るときは、相手宛てと**自分宛ての写し**の2つの gift wrap を作る（他の端末で自分の送信を読むため）。

### 2.2 DM リレー（kind 10050）

- 受け取りに使うリレーを `["relay", "wss://…"]` タグで公開する置換可能イベント。
- 送り手は、相手の kind 10050 のリレーへ送る。**相手の kind 10050 がなければ、その相手は NIP-17 の DM を受け取る準備ができていないとみなし、送らない**。
- DM 用のリレーは、kind 1059 を受け手本人にしか渡さないよう、NIP-42 の認証を求めるものが多い。

### 2.3 復号の手間

1件の受信に、gift wrap の復号と seal の復号で、**自分の鍵での NIP-44 復号が2回**要る。外部 signer（NIP-46）では、これが署名器との往復2回になる。

## 5. 受信

### 5.1 段階0: NIP-42

- リレーから `["AUTH", <challenge>]` を受け取ったら、そのリレーが「DM の受信に使うリレー」のときだけ、kind 22242（`relay`・`challenge` タグ）に署名して返す。それ以外のリレーでは今までどおり認証しない（不要な署名と、どのリレーを使っているかの露出を避ける）。
- 認証が済んだら、`auth-required:` で拒否された購読を張り直す。
- 外部 signer では接続ごとに署名が要るので、チャットタブを開くまで（§8.4.4）、または未読を確認する時まで、認証の必要なリレーへの接続を遅らせる（`signer-abstraction-design.md` §7.4）。

### 5.2 購読

- 対象は自分の kind 10050 のリレー。まだ公開していなければ、自分の読み込みリレーで代用し、会話一覧の上に「DM の受信先を設定してください」と出す（§7.3）。
- フィルターは `kinds=[1059] #p=[自分]`。
- 初回: `limit=200` で最新の分を取り、会話一覧を作る。古い分は会話一覧の下端で「さらに読み込む」を押したときに `until` で取る。
- 2回目以降: `since = 最後に受け取った gift wrap の created_at − 2日 − 1時間`。gift wrap の時刻は最大2日ずらされるので、これより短いと取りこぼす（Nostrism と同じ）。
- 処理済みの gift wrap の ID を覚えておき（§6）、同じものは復号しない。

### 5.3 開封と検証

1. gift wrap（署名は受信時に検証済み）の `p` が自分であることを確かめる。
2. `nip44Decrypt(wrap.content, wrap.pubkey)` で seal を取り出す。kind 13、署名が正しい、tags が空であることを確かめる。
3. `nip44Decrypt(seal.content, seal.pubkey)` で rumor を取り出す。kind 14、ID が内容から計算した値と一致、`rumor.pubkey == seal.pubkey` であることを確かめる。
4. 会話の相手は「rumor の pubkey と `p` タグの集合から自分を除いたもの」。段階1では相手が1人のものだけを会話にし、複数のもの（グループ）は「グループの会話には未対応です」の行として一覧に出す。
5. 同じ rumor（自分宛ての写しと、複数のリレーから届いたもの）は rumor の ID で1つにする。

どこかで失敗した gift wrap は、ID を「処理済み・失敗」として覚えて、再び復号しない。失敗の件数は開発者向けのログにだけ出す。

### 5.4 外部 signer での開封

- 1件に2回の往復が要るので、新しいものから順に開封し、開封できたものから表示する。
- 同時に開封する件数は4件まで（`signer-abstraction-design.md` §7.2 の同時要求の上限と同じ）。
- 初回の 200 件の開封には時間がかかる。会話一覧に「n / 200 件を開封中」と出す。
- 開封した内容は §6 で保存するので、2回目以降は新しく届いた分だけを開封する。

## 6. 保存

**2026-11-17 に変更: 開封した内容は端末に保存しない（すべてのプラットフォームでメモリーだけ）。** 以下の 6.1〜6.3 は当初の案として残す。

- 端末に置くのは、会話ごとの既読の時刻（`dm.lastRead.<pubkey>`）と、初めて受信した時刻（`dm.readBaseline.<pubkey>`、これより前の分を未読にしない）だけ。どちらも `LocalSettingsStorage`。
- アプリを起動するたびに gift wrap を取り直して開封する（1回の取得で 200 件まで、§5.2）。同じ起動の中では、処理済みの gift wrap を覚えて開封し直さない。
- 外部 signer の人は、起動するたびに開封の往復がかかる。待ち時間が問題になれば、改めて保存を検討する（§13）。

### 6.1 方針と、Room を撤去した判断との関係

チャンネルでは「リレーが一次ストアなので、全履歴を端末に複製しない」と決めた（`Torinos_NIP28_channel_spec.md` 第22章）。DM はこの判断の例外にする。理由は次のとおり。

- DM は、取り直すたびに1件2回の復号が要る。外部 signer では、1,000 件の取り直しが署名器との往復 2,000 回になり、現実的でない。
- gift wrap は `p` タグでしか絞り込めないので、「この相手との会話だけ」をリレーに問い合わせることができない。会話を開くたびに取り直す方法がない。

ただし、チャンネルの撤去理由だった維持コストは避ける。DB は使わず、上限のある暗号化ファイルにし、形式が変わったら捨てて取り直す。

### 6.2 保存するもの

| ファイル | 内容 | 上限 |
| --- | --- | --- |
| 会話一覧 | 会話ごとの相手、最後のメッセージの時刻、既読の時刻、「リクエスト」かどうか | 500 会話 |
| 会話ごとの履歴 | 開封した rumor（ID、送り手、時刻、本文、タグ）、送信の状態 | 1 会話 2,000 件。超えたら古いものから捨てる（リレーから読み直せる） |
| 処理状態 | 処理済みの gift wrap の ID（成功・失敗）、最後に受け取った gift wrap の時刻 | ID は 20,000 件、古い順に捨てる |

- 一覧に出すプレビュー（最後のメッセージの先頭）は保存しない。会話一覧を開くときに、会話ごとの履歴から作る。
- 会話ごとにファイルを分け、変わった会話のファイルだけを書き直す。

### 6.3 暗号化

| プラットフォーム | 保存先 | 鍵 |
| --- | --- | --- |
| Android | アプリ専用の領域（`filesDir`。Caches には置かない） | Keystore の AES-GCM 鍵（DM 専用の alias を新しく作る） |
| iOS | Application Support | Keychain に置いた AES-256 鍵（このデバイスのみ、iCloud で同期しない） |
| Web | 保存しない（メモリだけ） | — |

- 端末を盗まれたり、バックアップを読まれたりしても中身が読めないようにする。
- Web では、平文を `localStorage` に置かない。パスキーで保護したログイン（`signer-abstraction-design.md` §6）の場合に、その鍵で暗号化して保存するかは §12 で決める。
- ログアウトでは、DM のファイルと鍵を消す（再ログインで取り直す）。アカウント削除でも消す。

## 7. 送信

### 7.1 流れ

1. 相手の kind 10050 を取る（キャッシュは 10 分）。なければ送らず、「この人は DM の受け取り先を設定していません」と出す。
2. rumor（kind 14）を作る。`p` は相手、`created_at` は今。カスタム絵文字は投稿と同じく `emoji` タグを付ける。
3. 相手宛てと自分宛ての2つについて:
   - seal: `nip44Encrypt(rumorJson, 宛先)`、kind 13、tags なし、`created_at` を過去2日以内でずらし、自分の鍵で署名。
   - gift wrap: 使い捨ての鍵（毎回新しく作る）で `Nip44.encrypt(sealJson, 使い捨ての鍵, 宛先)`、kind 1059、`["p", 宛先]`、`created_at` をずらし、使い捨ての鍵で署名。
4. 相手宛ては相手の DM リレーへ、自分宛ては自分の DM リレーへ送る。相手の DM リレーは利用者のリレー設定に入っていないことが多いので、一時接続を使う。
5. 送信の状態は「送信中 → 送信済み（相手の DM リレーの1つ以上が受理）／失敗」。失敗したらメッセージに「再送」を出す。再送は同じ gift wrap をもう一度送る（作り直さない。作り直すと相手に2通届く）。

外部 signer では、1通の送信に、暗号化2回と署名2回で往復が4回要る。送信中の表示をその間続ける。

### 7.2 送る前の確認

- 本文の上限は投稿と同じ `MAX_POST_CHARS`（800 文字）とし、入力欄も投稿と同じ部品を使う。
- 相手をミュートしていたら、送信欄の上に「ミュート中の相手です」と出す（送ることはできる）。

### 7.3 自分の DM リレー

- 設定 › DM に「受け取りに使うリレー」を置き、kind 10050 を公開する。
- 初期値の候補は、自分の書き込みリレーのうち NIP-42 に対応しているもの（NIP-11 の `limitation.auth_required` などで判断）。公開する前に、利用者に確認してもらう。
- kind 10050 を公開していないと他のクライアントから DM を送ってもらえないことを、会話一覧の案内で伝える。

### 8.2 会話一覧

```
┌───────────────────────────────┐
│ DM                 [リクエスト 3] │
├───────────────────────────────┤
│ 〔アイコン〕 表示名        10:42 │
│            最後のメッセージ…   ● │
│ 〔アイコン〕 表示名        昨日  │
│            最後のメッセージ…     │
└───────────────────────────────┘
```

- 最後のメッセージの新しい順。未読は ● で示す。
- **リクエスト**: 自分がフォローしていない相手で、自分がまだ一度も返信していない会話は、別の一覧「リクエスト」に分ける。開いても既読を相手に知らせる仕組みはないので、開くこと自体の危険はない。リクエストの一覧では画像のプレビューを出さない（段階3）。
- ミュートした相手の会話は出さない。NG ワードは DM には当てない（自分宛ての私的なメッセージを勝手に隠さないため）。

### 8.3 会話画面

- 吹き出しで、自分は右、相手は左。時刻は rumor の `created_at`。
- 送信中・失敗の印と「再送」。
- 画面を開いている間に表示したメッセージまでを既読にする（既読の時刻はこの端末にだけ保存し、相手には知らせない）。
- 入力欄はチャンネルと同じ部品（絵文字の選択）を使う。画像の添付は段階3。

### 8.4 チャットタブへの統合（2026-11-17 追記・同日改訂）

NIP-17 の会話をチャットタブに出す。この節は §8.1・§8.2 の「独立した DM 画面」を置き換える（会話の中身と会話画面 §8.3 はそのまま使う）。

#### 8.4.1 ねらい

- チャットタブはフッターに初期状態で出る（`FooterConfig.kt` の `Chat`）。ところが NIP-29（標準・Buzz）を使う人は少なく、多くの人にとっては空のタブになっている。
- NIP-17 の DM を出せば、グループを使わない人にとってチャットタブは「DM の画面」になり、フッターに置いておく理由ができる。
- 一方で、グループに入っている人にとってはグループが主役。DM を足したことで、グループの一覧が押し下げられたり、見た目が変わったりしないようにする。
- そこで、**グループの有無で見せ方を変える**。

| | グループが無い人（大半） | グループがある人 |
| --- | --- | --- |
| 主役 | DM | グループ（今のまま） |
| 「すべて」の中身 | DM の会話一覧（§8.2 の中身） | 参加中のグループ（今のまま）。DM は入れない |
| DM への入口 | 「すべて」そのもの | ヘッダーの DM アイコン（未読の点つき） |
| ＋ボタン | 「新しい DM」を直接開く | 今のメニューに「新しい DM」を足す |

「グループがある」は、kind 10009 の標準グループ（承認待ちを含む）か Buzz コミュニティが1つ以上あること（`ChatTabUiState.relays` が空でない）とする。

#### 8.4.2 今のチャットタブ（2026-11-17 時点のコード）

| 項目 | 今の動き（`ui/chat/ChatTabViewModel.kt`、`ChatTabScreen.kt`） |
| --- | --- |
| リレーの一覧 | `publish()` で、kind 10009 に載った標準 NIP-29 グループのリレーと、Buzz コミュニティを合わせたもの（`state.relays`） |
| 「すべて」 | 上のリレーの参加中の行を、リレー・コミュニティごとの見出しでまとめる（`groupRowsByRelay`） |
| 読み込み | `refreshJoined()`。10009 のグループも Buzz も無ければ、何も読まずに終わる |
| 見出し | 「すべて ▾」と補足「n リレー」。メニューは「すべて」、リレー、「グループに参加…」 |
| ＋ボタン | 作成先が無ければ参加シート。あれば「新しい DM」（Buzz のみ）・「新しいチャンネル」などのメニュー |
| Buzz の DM | Buzz コミュニティの中の非公開グループ（`GroupLayout.Direct`）。暗号化されない。そのコミュニティの見出しの下に並ぶ |
| NIP-42 | `ChatAccount.authAllowedRelays`（同意したリレー、10009 のリレー、Buzz）でだけ応答する |

#### 8.4.3 そのまま足したときの問題

1. **取りこぼす。** NIP-17 の DM は自分の kind 10050 のリレー（§5.2）に届き、10009 とは関係がない。チャットタブのリレー（10009・Buzz）から kind 1059 を読む作りにすると、たまたまそのリレーに届いた DM しか出ない。
2. **10009 が空だと何も出ない。** グループに参加していない人（＝主な利用者）は、`refreshJoined()` の早期終了で DM も読まれない。
3. **露出が増える。** グループのリレーに `#p=[自分]` の 1059 を問い合わせると、DM の受け手であることと NIP-42 の署名を、DM と関係のないリレーに渡すことになる（§5.1 で DM リレーに限った理由と同じ）。
4. **グループの人の一覧が崩れる。** 「すべて」に DM を混ぜると、グループに入っている人の一覧が押し下げられる。DM はどのリレーの見出しの下にも置けない。
5. **2種類の「DM」を取り違える。** 暗号化される NIP-17 の DM と、暗号化されない Buzz の DM が同じ画面に並ぶ。

#### 8.4.4 読み込み

**読み込みを2つに分ける。** チャットタブは「グループ」と「DM」の2つの入力を受け取って並べるだけにし、DM の購読と開封はチャットタブの外（`dm/DmInbox`、仮称）が持つ。

```
グループ系（今のまま）            DM 系（新規）
 kind 10009 のリレー ┐             自分の kind 10050 のリレー
 Buzz コミュニティ   ┴→ refreshJoined()   （無ければ読み込みリレー、§5.2）
                      │                   ↓ 1059 #p=[自分]
                      │             DmInbox: 開封・検証・保存（§5.3・§6）
                      ↓                   ↓ 会話一覧（StateFlow）
                ChatTabViewModel.publish() で画面を組み立てる
```

- `ChatTabViewModel` は kind 1059 を読まない。`DmInbox` の会話一覧を購読するだけにする。
- DM の購読は、10009 や Buzz の有無と関係なく動く。`refreshJoined()` の早期終了はグループ系だけに掛ける。
- グループのリレーには 1059 を問い合わせない。NIP-42 の署名器はアカウントに1つしか登録できない（`ChatAccount` が登録する）ので、`ChatAccount` に「チャット以外で認証を許すリレー」（`extraAuthRelays`）を渡し、`DmInbox.dmRelays` を足す（2026-11-17 実装）。`authAllowedRelays`（チャットの許可）そのものは変えない。

**受信を始める時期。** DM が主な用途になる人には、タブを開く前からフッターに未読の点を出したい。一方、外部 signer では開封のたびに署名器との往復が要る。

| ログインの種類 | 受信を始める時期 | 補足 |
| --- | --- | --- |
| 自分の鍵（端末に秘密鍵） | アプリの起動時 | 開封は端末の中で済むので、起動直後の負荷が小さい。フッターの未読の点を起動時から出せる |
| 外部 signer（NIP-46 など） | チャットタブを初めて開いたとき | 開封した内容は保存しない（§6）ので、起動ごとに開封し直す。開封中は件数を出す（§5.4） |
| Web | 上の2つと同じ | 保存しない（§6.3）ので、読み込み直すたびに開封し直す。外部 signer では待ち時間が長くなる |

#### 8.4.5 画面: グループが無い人（主な形）

```
┌──────────────────────────────────┐
│ (自分)  すべて ▾                   │ ← 見出しは今と同じ形（グループに入ったときに形が変わらないように）
│         DM 5                       │
├──────────────────────────────────┤
│ リクエスト 3                     › │
│ 〔アイコン〕 表示名          10:42 ● │
│            最後のメッセージ…        │
│ 〔アイコン〕 表示名          昨日    │
│            最後のメッセージ…        │
│                                    │
│                              [＋]  │ ← 「新しい DM」を直接開く
└──────────────────────────────────┘
```

- 「すべて」に §8.2 の会話一覧をそのまま出す。件数で切らない。上に「リクエスト n」の行を出す（0件なら出さない）。
- 見出しの補足は「DM m」（m は「リクエスト」を除いた会話数）。メニューは「すべて」と「グループに参加…」だけ。ヘッダーの DM アイコンは出さない（押しても同じ画面になるため）。
- ＋ボタンは「新しい DM」のシートを直接開く。グループへの参加は見出しのメニューから行う。
- 空のときの案内は DM を中心にする。
  - DM の受信先（kind 10050）が未設定: 「DM を受け取るには、受信先のリレーを設定してください」と［設定する］（§7.3）。
  - 会話が0件: 「DM はまだありません」と［新しい DM］。その下に小さく「NIP-29 のグループに参加する」。
  - 開封中（外部 signer）: 一覧の上に「DM を開封中 n / m」の1行。
- ログインしていない（署名できない）ときは、「ログインすると DM を使えます」と出す。

#### 8.4.6 画面: グループがある人

```
┌──────────────────────────────────┐
│ (自分)  すべて ▾          ✉• ⚙    │ ← DM アイコン。未読があれば点
│         3リレー                    │
├──────────────────────────────────┤
│ relay.example.com                  │ ← 今と同じ。DM は混ぜない
│   # グループ名               9:10   │
│ Community  [Buzz]                  │
│   # チャンネル名             8:55   │
│   〔アイコン〕 表示名 暗号化なし     │ ← Buzz の DM
└──────────────────────────────────┘
```

- 「すべて」とリレーを選んだときの一覧は、今のままにする。NIP-17 の DM は混ぜない。見出しの補足も今の「n リレー」のまま。
- ヘッダーの右（設定の左）に DM アイコンを置く。NIP-17 の未読の会話があれば点を付ける。どのリレーを選んでいても見える。
- アイコンを押すと選択を「DM」（`ChatSelection.Direct`）に切り替え、§8.4.5 と同じ会話一覧とリクエストを出す。選択中はアイコンを強調し、見出しは「DM」にする。もう一度押すか、見出しのメニューで選び直すと、前の選択に戻る。見出しのメニューには「DM」を足さない（メニューはグループの切り替えに専念する）。
- Buzz の DM の行には「暗号化なし」を付ける（`chat-create-design.md` の、DM 画面の「DM（暗号化なし）」と合わせる）。NIP-17 の DM はアイコンの先にしか出ないので、一覧の上で混ざることはない。
- ＋メニューの先頭に「新しい DM」（NIP-17）を足す。Buzz の DM は、Buzz コミュニティがあるときだけ「Buzz の DM（暗号化なし）」という名前で残す。

**形の切り替わり。** 初めてグループに参加すると §8.4.6 の形になる（ヘッダーに DM アイコンが現れ、「すべて」はグループの一覧になる）。最後のグループを抜けると §8.4.5 に戻る。「DM」の選択を保存したままグループが無くなったら、「すべて」に戻す。

#### 8.4.7 状態とコード

- `ChatSelection` に `Direct` を足す。選ぶ手段はヘッダーの DM アイコンだけ。選択の保存（`encodeChatSelection`）に「DM」を表す値を足す。前の版で保存した値はそのまま読める。
- `ChatTabUiState` に、グループの行（`joinedRows`）とは別に次を持つ。
  - `directConversations`（会話の要約）、`directRequestCount`、`directUnread`（ヘッダーとフッターの点）
  - `dmStatus`（受信先が未設定／開封中 n / m／準備済み）
  - `hasGroups`（`relays` が空でない。§8.4.5 と §8.4.6 の切り替え）
- `ChatGroupRow` は `GroupRef` が前提（既読の鍵・`markRead`・画面遷移）なので、DM の会話を混ぜない。
- 未読の点は、フッターのチャットタブのアイコンにまとめる（グループの未読と同じ点）。
- 会話を開くと §8.3 の会話画面へ移る（チャットタブの中の画面遷移）。

## 9. 安全とプライバシー

- 中身・送り手・時刻はリレーから見えない。見えるのは「この公開鍵宛てに何かが届いた」ことと、その大まかな時刻（2日以内のずれ）。
- 相手の DM リレーへの接続で、自分の IP アドレスがそのリレーに伝わる。
- 開封した内容をログに出さない。`FetchTrace` などには、kind 1059 の件数だけを出す。
- 端末の保存は §6.3 のとおり暗号化する。
- プッシュ通知は扱わない。通知サーバーが kind 1059 を見ても中身は読めないが、「誰宛てにいつ届いたか」が通知サーバーに集まるので、別に設計する（`push-notification-durable-object-design.md` §8.1）。

## 10. テスト

| 対象 | 主なケース |
| --- | --- |
| 包みと開封 | 固定の鍵での往復、自分宛ての写し、`created_at` のずれが2日以内 |
| 検証 | seal の署名が不正、seal の tags が空でない、rumor の ID が不一致、**seal と rumor の pubkey が違う**、`p` が自分でない、kind が違う |
| 重複 | 同じ rumor を自分宛ての写しと複数のリレーから受け取っても1件 |
| 取得 | 2回目以降の `since` が「最後の時刻 − 2日 − 1時間」、処理済みの gift wrap を開封しない |
| 送信 | 相手の kind 10050 がないと送らない、再送で gift wrap を作り直さない、送信の状態の遷移 |
| 既読 | 初めての受信より前の分を未読にしない、既読の時刻を設定に保存する（開封した内容は保存しない） |
| NIP-42 | DM リレーでだけ認証する、認証後に購読を張り直す |
| 会話の分類 | リクエストへの振り分け、返信したら通常の会話に移る、ミュートした相手を出さない |
| 外部 signer | 開封の同時実行が4件まで、新しいものから開封する |
| チャットタブ（§8.4） | 10009・Buzz のリレーに 1059 を問い合わせない。グループが無い: 「すべて」に DM の全件とリクエストの行、補足「DM m」、DM アイコンを出さない、＋が「新しい DM」を直接開く、空・未設定・開封中の案内。グループがある: 「すべて」とリレーの一覧に NIP-17 の DM が混ざらない、DM アイコンの未読の点、アイコンで「DM」に切り替えて戻せる、Buzz の DM に「暗号化なし」。切り替わり: 初めての参加・最後の退出で形が変わる、グループが無くなったら保存した「DM」の選択を「すべて」に戻す、前の版の保存値も読める。受信の開始: 自分の鍵は起動時、外部 signer はタブを開いたとき |

実機では、自分の2つのアカウントの間で送受信し、Amethyst・Nostrism など他のクライアントとも相互に送受信できることを確かめる。

## 11. 実装順序

1. ~~前提: `signer-abstraction-design.md` の段階1（suspend 化と相手指定の NIP-44）。~~ 実装済み（`AccountSigner.nip44Encrypt` / `nip44Decrypt`、2026-11-17 に確認）。
2. ✅ NIP-42（DM リレーでだけ応答）。`ChatAccount` の `extraAuthRelays` に `DmInbox.dmRelays` を渡す。
3. ✅ 包みと開封、検証の純粋関数とテスト（`dm/Nip17.kt`、`Nip17Test`）。
4. ~~暗号化ファイルの保存（`dm/DmStore`）。~~ 保存しないことにした（§6）。
5. ✅ 受信と会話の組み立て（`dm/DmInbox.kt`・`dm/DmConversations.kt`、`DmInboxTest`・`DmConversationsTest`）。取得は有限取得で、起動時（自分の鍵）・チャットタブを開いたとき・アプリが前面に戻ったときに読み直す。常時の購読はまだ無い。
6. ✅ チャットタブへの統合（§8.4）: グループが無い人の「すべて」（DM の会話一覧）、グループがある人のヘッダーの DM アイコンと `ChatSelection.Direct`、案内。会話画面は読むだけ（`ui/chat/DmConversationScreen.kt`）。＋ボタンはまだ今のまま（送信が無いため）。
7. ✅ 送信（`DmInbox.send` / `retry`、`DmInboxTest`）と会話画面の入力欄・送信中／失敗・再送、＋ボタン（グループが無い人は「新しい DM」を直接開く）と＋メニューの「新しい DM」（NIP-17）・「Buzz の DM（暗号化なし）」。宛先はフォロー中の人から名前で探すか npub を貼る（1対1、自分へのメモも可）。
   - 相手の kind 10050 は、自分の読み込みリレーと、端末に控えのある相手の NIP-65 の書き込みリレーで探す（10 分覚える）。見つからなければ送らない。
   - 相手宛ては相手の DM リレーへ一時接続で送り、OK を待つ（自分の NIP-65 の read 専用の設定には縛られない）。相手全員のどれかのリレーが受理したら「送信済み」。
   - 自分宛ての写しは自分の DM リレー（無ければ読み込みリレー）へ送り、その gift wrap は処理済みにして、後で取得しても開封し直さない。
   - 送ったメッセージは受理を待たずに会話に出す。端末に保存しないので、アプリを終了すると再送の控えも消える。
   - 書き込みに NIP-42 を求めるリレー（`auth-required:` で拒否）は、認証を許したリレー（自分の DM リレーなど）に限り、管理している接続で認証してから1回だけ送り直す（`NostrRepository.publishAfterAuth`、2026-11-17 にエミュレーターで auth.nostr1.com への受理を確認）。相手の DM リレーには認証しない（公開鍵を知らせない）ので、相手のリレーがすべてこの種類だと送れない。
   - 未実装: kind 10050 の設定画面。
10. ✅ 届いた分から開封する（2026-11-17、ASUS 実機で発見）: 読み込みにも NIP-42 を求める DM リレー（r.kojira.io）の認証待ちで、gift wrap の取得全体が約8〜10秒終わらず、そのあいだ一覧に何も出なかった。取得で届いたそばから4件ずつ開封して一覧に出す（`DmInbox.openAsArrived`）。同じ gift wrap が複数のリレーから届いても1回だけ開封する。実機で、取得開始から最初の DM の表示まで約1.1〜1.3秒（取得全体は約8秒）になった。
9. ✅ グループのある人の形の保持（2026-11-17、エミュレーターで発見）: 起動直後に kind 10009 が時間切れで読めないと、グループのある人も DM が主役の画面になっていた。`ChatAccount` が「前回グループがあった」を端末に控え（`chat.knownGroups.<pubkey>`）、読めないあいだはその控えで画面の形を決める。答えがそろわず見つからなかったときは 5・15・45 秒後に読み直す。控えがあって一覧がまだ無いときは「参加中のグループを読み込んでいます」を出す。
8. フッターのチャットタブのアイコンへの未読の点。常時の購読（届いたらすぐ一覧に出す）。
9. `app-requirements.md` の NIP-17/59・NIP-42 と、Nostr イベント要件の表（13、14、1059、10050、22242）を更新する。
