# DM（ダイレクトメッセージ）機能設計

作成日: 2026-10-16
状態: 設計（未実装）。
関連: `signer-abstraction-design.md`（前提）、`app-requirements.md`（NIP-04・NIP-17/59・NIP-42 は未対応）、`push-notification-durable-object-design.md` §8.1（DM は別のプライバシー設計）、`footer-customization-design.md`、`feed-startup-cache-design.md`、`zap-feature-design.md`（NIP-04 の実装を共有）

## 1. 目的と範囲

NIP-17（Private Direct Messages）で、1対1のメッセージを送受信できるようにする。メッセージの中身・送り手・受け手・送った時刻を、リレーや第三者から読めない形で扱う。

| 段階 | 内容 |
| --- | --- |
| 段階0（前提） | NIP-42 のリレー認証。`signer-abstraction-design.md` の段階1（相手を指定した NIP-44 暗号化） |
| **段階1（本書の主対象）** | 1対1のテキストの送受信、会話一覧と会話画面、DM リレー（kind 10050）の設定、未読、知らない人からの「リクエスト」 |
| 段階2 | 旧形式の DM（NIP-04、kind 4）の読み出し、グループの会話、返信の引用表示、件名（`subject`） |
| 段階3 | 画像などのファイル（kind 15）、消えるメッセージ（`expiration`）、プッシュ通知（別のプライバシー設計） |

非目標: 旧形式（kind 4）での送信。送信済みメッセージの編集・取り消し（NIP-17 では仕組み上できない）。

## 2. 仕様の確認（NIP-17・NIP-59・NIP-44）

### 2.1 3重の包み

```
kind 14  rumor（中身）   未署名。content=本文、tags=[["p", 相手], …]、created_at=送った時刻
   ↓ 自分の鍵で相手宛てに NIP-44 暗号化
kind 13  seal（封）      自分の鍵で署名。tags は空。created_at はずらす
   ↓ 使い捨ての鍵で相手宛てに NIP-44 暗号化
kind 1059 gift wrap（包装）使い捨ての鍵で署名。tags=[["p", 相手]]。created_at はずらす
```

- rumor は署名しないので、漏れても「本人が書いた」証明にならない（否認できる）。
- seal は署名するので、受け取った人は送り手を確かめられる。**seal の pubkey と rumor の pubkey が一致しなければならない**（なりすまし対策）。
- gift wrap は使い捨ての鍵で署名するので、リレーからは送り手が分からない。分かるのは `p` タグの受け手だけ。
- seal と gift wrap の `created_at` は、過去 2 日以内のランダムな時刻にずらす（時刻から相手を推測させないため）。表示に使う時刻は rumor の `created_at`。
- 送るときは、相手宛てと**自分宛ての写し**の2つの gift wrap を作る（他の端末で自分の送信を読むため）。

### 2.2 DM リレー（kind 10050）

- 受け取りに使うリレーを `["relay", "wss://…"]` タグで公開する置換可能イベント。
- 送り手は、相手の kind 10050 のリレーへ送る。**相手の kind 10050 がなければ、その相手は NIP-17 の DM を受け取る準備ができていないとみなし、送らない**。
- DM 用のリレーは、kind 1059 を受け手本人にしか渡さないよう、NIP-42 の認証を求めるものが多い。

### 2.3 復号の手間

1件の受信に、gift wrap の復号と seal の復号で、**自分の鍵での NIP-44 復号が2回**要る。外部 signer（NIP-46）では、これが署名器との往復2回になる。

## 5. 受信

### 5.1 段階0: NIP-42

- リレーから `["AUTH", <challenge>]` を受け取ったら、そのリレーが「DM の受信に使うリレー」のときだけ、kind 22242（`relay`・`challenge` タグ）に署名して返す。それ以外のリレーでは今までどおり認証しない（不要な署名と、どのリレーを使っているかの露出を避ける）。
- 認証が済んだら、`auth-required:` で拒否された購読を張り直す。
- 外部 signer では接続ごとに署名が要るので、DM 画面を開くまで、または未読を確認する時まで、認証の必要なリレーへの接続を遅らせる（`signer-abstraction-design.md` §7.4）。

### 5.2 購読

- 対象は自分の kind 10050 のリレー。まだ公開していなければ、自分の読み込みリレーで代用し、会話一覧の上に「DM の受信先を設定してください」と出す（§7.3）。
- フィルターは `kinds=[1059] #p=[自分]`。
- 初回: `limit=200` で最新の分を取り、会話一覧を作る。古い分は会話一覧の下端で「さらに読み込む」を押したときに `until` で取る。
- 2回目以降: `since = 最後に受け取った gift wrap の created_at − 2日 − 1時間`。gift wrap の時刻は最大2日ずらされるので、これより短いと取りこぼす（Nostrism と同じ）。
- 処理済みの gift wrap の ID を覚えておき（§6）、同じものは復号しない。

### 5.3 開封と検証

1. gift wrap（署名は受信時に検証済み）の `p` が自分であることを確かめる。
2. `nip44Decrypt(wrap.content, wrap.pubkey)` で seal を取り出す。kind 13、署名が正しい、tags が空であることを確かめる。
3. `nip44Decrypt(seal.content, seal.pubkey)` で rumor を取り出す。kind 14、ID が内容から計算した値と一致、`rumor.pubkey == seal.pubkey` であることを確かめる。
4. 会話の相手は「rumor の pubkey と `p` タグの集合から自分を除いたもの」。段階1では相手が1人のものだけを会話にし、複数のもの（グループ）は「グループの会話には未対応です」の行として一覧に出す。
5. 同じ rumor（自分宛ての写しと、複数のリレーから届いたもの）は rumor の ID で1つにする。

どこかで失敗した gift wrap は、ID を「処理済み・失敗」として覚えて、再び復号しない。失敗の件数は開発者向けのログにだけ出す。

### 5.4 外部 signer での開封

- 1件に2回の往復が要るので、新しいものから順に開封し、開封できたものから表示する。
- 同時に開封する件数は4件まで（`signer-abstraction-design.md` §7.2 の同時要求の上限と同じ）。
- 初回の 200 件の開封には時間がかかる。会話一覧に「n / 200 件を開封中」と出す。
- 開封した内容は §6 で保存するので、2回目以降は新しく届いた分だけを開封する。

## 6. 保存

### 6.1 方針と、Room を撤去した判断との関係

チャンネルでは「リレーが一次ストアなので、全履歴を端末に複製しない」と決めた（`Torinos_NIP28_channel_spec.md` 第22章）。DM はこの判断の例外にする。理由は次のとおり。

- DM は、取り直すたびに1件2回の復号が要る。外部 signer では、1,000 件の取り直しが署名器との往復 2,000 回になり、現実的でない。
- gift wrap は `p` タグでしか絞り込めないので、「この相手との会話だけ」をリレーに問い合わせることができない。会話を開くたびに取り直す方法がない。

ただし、チャンネルの撤去理由だった維持コストは避ける。DB は使わず、上限のある暗号化ファイルにし、形式が変わったら捨てて取り直す。

### 6.2 保存するもの

| ファイル | 内容 | 上限 |
| --- | --- | --- |
| 会話一覧 | 会話ごとの相手、最後のメッセージの時刻、既読の時刻、「リクエスト」かどうか | 500 会話 |
| 会話ごとの履歴 | 開封した rumor（ID、送り手、時刻、本文、タグ）、送信の状態 | 1 会話 2,000 件。超えたら古いものから捨てる（リレーから読み直せる） |
| 処理状態 | 処理済みの gift wrap の ID（成功・失敗）、最後に受け取った gift wrap の時刻 | ID は 20,000 件、古い順に捨てる |

- 一覧に出すプレビュー（最後のメッセージの先頭）は保存しない。会話一覧を開くときに、会話ごとの履歴から作る。
- 会話ごとにファイルを分け、変わった会話のファイルだけを書き直す。

### 6.3 暗号化

| プラットフォーム | 保存先 | 鍵 |
| --- | --- | --- |
| Android | アプリ専用の領域（`filesDir`。Caches には置かない） | Keystore の AES-GCM 鍵（DM 専用の alias を新しく作る） |
| iOS | Application Support | Keychain に置いた AES-256 鍵（このデバイスのみ、iCloud で同期しない） |
| Web | 保存しない（メモリだけ） | — |

- 端末を盗まれたり、バックアップを読まれたりしても中身が読めないようにする。
- Web では、平文を `localStorage` に置かない。パスキーで保護したログイン（`signer-abstraction-design.md` §6）の場合に、その鍵で暗号化して保存するかは §12 で決める。
- ログアウトでは、DM のファイルと鍵を消す（再ログインで取り直す）。アカウント削除でも消す。

## 7. 送信

### 7.1 流れ

1. 相手の kind 10050 を取る（キャッシュは 10 分）。なければ送らず、「この人は DM の受け取り先を設定していません」と出す。
2. rumor（kind 14）を作る。`p` は相手、`created_at` は今。カスタム絵文字は投稿と同じく `emoji` タグを付ける。
3. 相手宛てと自分宛ての2つについて:
   - seal: `nip44Encrypt(rumorJson, 宛先)`、kind 13、tags なし、`created_at` を過去2日以内でずらし、自分の鍵で署名。
   - gift wrap: 使い捨ての鍵（毎回新しく作る）で `Nip44.encrypt(sealJson, 使い捨ての鍵, 宛先)`、kind 1059、`["p", 宛先]`、`created_at` をずらし、使い捨ての鍵で署名。
4. 相手宛ては相手の DM リレーへ、自分宛ては自分の DM リレーへ送る。相手の DM リレーは利用者のリレー設定に入っていないことが多いので、一時接続を使う。
5. 送信の状態は「送信中 → 送信済み（相手の DM リレーの1つ以上が受理）／失敗」。失敗したらメッセージに「再送」を出す。再送は同じ gift wrap をもう一度送る（作り直さない。作り直すと相手に2通届く）。

外部 signer では、1通の送信に、暗号化2回と署名2回で往復が4回要る。送信中の表示をその間続ける。

### 7.2 送る前の確認

- 本文の上限は投稿と同じ `MAX_POST_CHARS`（800 文字）とし、入力欄も投稿と同じ部品を使う。
- 相手をミュートしていたら、送信欄の上に「ミュート中の相手です」と出す（送ることはできる）。

### 7.3 自分の DM リレー

- 設定 › DM に「受け取りに使うリレー」を置き、kind 10050 を公開する。
- 初期値の候補は、自分の書き込みリレーのうち NIP-42 に対応しているもの（NIP-11 の `limitation.auth_required` などで判断）。公開する前に、利用者に確認してもらう。
- kind 10050 を公開していないと他のクライアントから DM を送ってもらえないことを、会話一覧の案内で伝える。

## 8. 画面

### 8.1 入口

- フッターの機能に「DM」を足す（`footer-customization-design.md` の仕組みで、表示・並び順を変えられる）。初期状態では表示する。
- 未読がある会話の数を、フッターのアイコンに点で示す（件数は出さない）。

### 8.2 会話一覧

```
┌───────────────────────────────┐
│ DM                 [リクエスト 3] │
├───────────────────────────────┤
│ 〔アイコン〕 表示名        10:42 │
│            最後のメッセージ…   ● │
│ 〔アイコン〕 表示名        昨日  │
│            最後のメッセージ…     │
└───────────────────────────────┘
```

- 最後のメッセージの新しい順。未読は ● で示す。
- **リクエスト**: 自分がフォローしていない相手で、自分がまだ一度も返信していない会話は、別の一覧「リクエスト」に分ける。開いても既読を相手に知らせる仕組みはないので、開くこと自体の危険はない。リクエストの一覧では画像のプレビューを出さない（段階3）。
- ミュートした相手の会話は出さない。NG ワードは DM には当てない（自分宛ての私的なメッセージを勝手に隠さないため）。

### 8.3 会話画面

- 吹き出しで、自分は右、相手は左。時刻は rumor の `created_at`。
- 送信中・失敗の印と「再送」。
- 画面を開いている間に表示したメッセージまでを既読にする（既読の時刻はこの端末にだけ保存し、相手には知らせない）。
- 入力欄はチャンネルと同じ部品（絵文字の選択）を使う。画像の添付は段階3。

## 9. 安全とプライバシー

- 中身・送り手・時刻はリレーから見えない。見えるのは「この公開鍵宛てに何かが届いた」ことと、その大まかな時刻（2日以内のずれ）。
- 相手の DM リレーへの接続で、自分の IP アドレスがそのリレーに伝わる。
- 開封した内容をログに出さない。`FetchTrace` などには、kind 1059 の件数だけを出す。
- 端末の保存は §6.3 のとおり暗号化する。
- プッシュ通知は扱わない。通知サーバーが kind 1059 を見ても中身は読めないが、「誰宛てにいつ届いたか」が通知サーバーに集まるので、別に設計する（`push-notification-durable-object-design.md` §8.1）。

## 10. テスト

| 対象 | 主なケース |
| --- | --- |
| 包みと開封 | 固定の鍵での往復、自分宛ての写し、`created_at` のずれが2日以内 |
| 検証 | seal の署名が不正、seal の tags が空でない、rumor の ID が不一致、**seal と rumor の pubkey が違う**、`p` が自分でない、kind が違う |
| 重複 | 同じ rumor を自分宛ての写しと複数のリレーから受け取っても1件 |
| 取得 | 2回目以降の `since` が「最後の時刻 − 2日 − 1時間」、処理済みの gift wrap を開封しない |
| 送信 | 相手の kind 10050 がないと送らない、再送で gift wrap を作り直さない、送信の状態の遷移 |
| 保存 | 暗号化ファイルの往復、上限で古いものから捨てる、形式が違えば捨てる、ログアウトで消える |
| NIP-42 | DM リレーでだけ認証する、認証後に購読を張り直す |
| 会話の分類 | リクエストへの振り分け、返信したら通常の会話に移る、ミュートした相手を出さない |
| 外部 signer | 開封の同時実行が4件まで、新しいものから開封する |

実機では、自分の2つのアカウントの間で送受信し、Amethyst・Nostrism など他のクライアントとも相互に送受信できることを確かめる。

## 11. 実装順序

1. 前提: `signer-abstraction-design.md` の段階1（suspend 化と相手指定の NIP-44）。
2. NIP-42（DM リレーでだけ応答）。
3. 包みと開封、検証の純粋関数とテスト（`dm/Nip17.kt`）。
4. 暗号化ファイルの保存（`dm/DmStore`）。
5. 受信（購読、開封、会話の組み立て）と会話一覧。
6. 送信と会話画面、kind 10050 の設定画面。
7. フッターへの追加、未読の表示。
8. `app-requirements.md` の NIP-17/59・NIP-42 と、Nostr イベント要件の表（13、14、1059、10050、22242）を更新する。

## 13. 未確定事項

- Web で、パスキーで保護したログインのときに DM を暗号化して保存するか。
- 会話の上限（500 会話・1会話 2,000 件）の妥当性。実際の利用者の件数で見直す。
- 件数が上限を大きく超える利用者が多ければ、SQLite（暗号化つき）を再検討するか。
- 既読をほかの端末と同期するか（NIP-17 には仕組みがない。kind 30078 のアプリデータで同期する方法がある）。
- 段階2のグループの会話を、何人まで扱うか。
