# チャットタブ（NIP-29）と Buzz コミュニティ対応 設計

- 作成日: 2026-11-15（同日、Buzz のソース調査と標準 NIP-29 との共存方針に基づき改訂）
- ステータス: 段階1〜4を実装・レビュー済み（実機・実在のリレーでの確認は未実施）
- 目的: フッターに「チャット」タブを追加し、NIP-29 のグループ（標準の NIP-29 リレーと Buzz コミュニティ）に参加して、チャットとフォーラムを読み書きできるようにする。
- 調査対象: [block/buzz](https://github.com/block/buzz)（リレー、Rust）、[block/buzz-app](https://github.com/block/buzz-app)（クライアント、TypeScript/Tauri）の main ブランチ（2026-11-15 時点）。`buzz-` で始まるファイル参照はこの2リポジトリのもの。
- 参照仕様（2026-11-15 に本文を確認）: [NIP-29](https://github.com/nostr-protocol/nips/blob/master/29.md)、[NIP-C7](https://github.com/nostr-protocol/nips/blob/master/C7.md)、[NIP-51](https://github.com/nostr-protocol/nips/blob/master/51.md)（kind 10009）、[NIP-42](https://github.com/nostr-protocol/nips/blob/master/42.md)、[NIP-98](https://github.com/nostr-protocol/nips/blob/master/98.md)、[Blossom BUD-01](https://github.com/hzrd149/blossom/blob/master/buds/01.md)。いずれも draft。

## 1. 標準の NIP-29（共通の土台）

### 1.1 グループの識別

- グループは「リレー + グループID（任意の文字列）」で決まる。
- 共有の正式な形は、kind 39000 への naddr（pubkey = リレーの `self` 鍵、`d` = グループID、relay hint = リレー）。招待コードは `naddr1…?invite=<code>` と後ろに付ける。
- `<host>'<group-id>` は現行の NIP-29 本文には無いが、既存のクライアント（Chachi、0xchat など）が使っている。入力としては受け付け、共有には naddr を使う。

### 1.2 グループ情報（リレーが署名）

kind 39000〜39005 はリレーの `self` 鍵だけが署名する（NIP-11 の `self` と照合し、他の署名は捨てる）。`d` = グループID。

| kind | 内容 |
| --- | --- |
| 39000 | `name`、`picture`、`banner`、`about`、フラグ（下表）、`supported_kinds`、`parent` / `child`（サブグループ） |
| 39001 | 管理者 `["p", pubkey, role…]` |
| 39002 | メンバー `["p", pubkey]`（省略・一部だけのことがあり、完全な一覧とみなさない） |
| 39003 | 役割 |
| 39005 | ピン留め |

| フラグ | 意味 | 無いとき |
| --- | --- | --- |
| `private` | メンバーだけが読める | 誰でも読める |
| `restricted` | メンバーだけが書ける | 誰でも書ける |
| `hidden` | メンバー以外にはグループ情報も見せない | 誰でも情報を取れる |
| `closed` | 招待コード無しの参加要求を受け付けない | 参加要求を受け付ける |

### 1.3 参加・退出とメンバーの判定

- 参加要求: kind 9021、`["h", g]`、招待コードがあれば `["code", c]`、content は任意の理由。
- 受け付けられると、リレー（または管理者）が kind 9000（put-user、`p` = 自分）を出す。すぐ出るとは限らず、管理者の判断待ちのこともある。拒否理由は「確定」「審査待ち」「支払いが必要」を区別して返すべきとされている。既にメンバーなら `duplicate:` で拒否される。
- 退出: kind 9022。リレーが kind 9001（remove-user）を出す。
- **メンバーかどうかは、自分を対象にした 9000 と 9001 のうち新しいほうで判定する**（どちらも無ければ非メンバー）。

### 1.4 メッセージ

- グループへ送るイベントは `["h", g]` を1つ持つ。kind はそれぞれの NIP の定義どおり（`supported_kinds` で制限されることがある）。
- チャット: kind 9（NIP-C7）。返信は kind 9 に `["q", 返信先ID, relay, pubkey]` を付け、本文の先頭に `nostr:nevent1…` を置く。チャット表示は kind 9 だけを取る。
- スレッド: kind 11 を使うリレー・クライアントがある（39000 の `supported_kinds` の例に 11）。NIP-29 本文には定義が無いので、段階1では表示だけ対応し、コメントは NIP-22（kind 1111）の形で読む。
- タイムライン参照: `["previous", 先頭8文字, …]`。そのリレーで見た直近50件から3件以上入れるのが推奨。リレーは自分の DB に無い参照を含むイベントを拒否してよい。
- 古い `created_at` の投稿（遅れた公開）はリレーに拒否されることがある。
- 管理系: 9000〜9020（9005 = 管理者による削除、9009 = 招待作成 など）。

### 1.5 参加中グループの一覧（kind 10009）

NIP-51 の「Simple groups」。`["group", <グループID>, <relay URL>, <名前（任意）>]` と、使っているリレーごとの `["r", url]`（フィールドの並びは NIP-51 の表の説明からの推定。実装前に既存クライアントの実物で確認する）。公開タグか、NIP-44 で暗号化した content に入れられる。ToriNos は公開タグで読み書きし、暗号化された項目も読む。

### 1.6 読み取りと AUTH

NIP-29 本文には AUTH の規定は無い。`private` のグループは、リレーが NIP-42 AUTH でメンバー確認をするのが一般的。公開グループは AUTH 無しで読めることが多い。ToriNos は「求められたら（参加済みのリレーなら）AUTH する」方式で両方に対応する（5.3）。

## 2. Buzz の調査結果

Buzz は NIP-29 を土台に、コミュニティ（ドメイン）単位のメンバー制と独自の kind を足したもの。標準との違いは 2.8 にまとめる。

### 2.1 コミュニティとリンク

- コミュニティはドメイン単位。WebSocket は `wss://<host>`、REST とメディアは `https://<host>` で同じホストを使う。リレーは接続先ホストからコミュニティを決める。
- **投稿リンクはコミュニティを含まない。** `buzz://message?channel=<UUID>&id=<イベントID>[&thread=<ルートID>]`、`buzz://channel/<UUID>[/<イベントID>]`。受け取った側が選んでいるコミュニティで解釈する（`buzz-app/src/features/messages/message-copy.ts`、`navigation/buzz-links.ts`）。nevent / naddr は作らない。
- 参加の入力として受け付ける形（`buzz-app/src/features/communities/invite-link.ts` の `parsePastedInvite`）:

| 入力 | 例 | 意味 |
| --- | --- | --- |
| 招待ページURL | `https://png.communities.buzz.xyz/invite/v2.<43文字>` | コミュニティ + 招待コード |
| アプリ招待リンク | `buzz://join?relay=https://<host>&code=<コード>` | 同上 |
| コード無しリンク | `buzz://connect?relay=…`、`buzz://add-community?relay=…` | コミュニティのみ |
| アドレス | `wss://png.communities.buzz.xyz`、`png.communities.buzz.xyz` | コミュニティのみ（スキーム無しは wss とみなす） |
| コードだけ | `v2.<43文字>` | 拒否し「招待リンク全体を貼ってください」 |

招待コードは `v2.` + 32バイトの base64url（43文字）。`v2.` 以外は旧形式（HMAC 検証）として扱われる。

### 2.2 参加の流れ（REST）

`buzz-app/src/features/communities/join.ts` の `admitCommunity` と、リレーの `buzz-relay/src/router.rs`、`api/invites.rs`。

1. `GET /api/join-policy` → `{ policy: { version, terms_markdown?, privacy_markdown?, age_attestation_required } }` または `{}`。不正な形はエラー扱い（規約が無いとみなさない）。
2. 規約があれば利用規約・プライバシーポリシーを表示し、同意（必要なら年齢確認）を得る。
3. `POST /api/invites/accept-policy` `{ code, policy_version, age_confirmed }` → `{ receipt }`。
4. `POST /api/invites/claim` `{ code, policy_receipt }`。**参加する鍵で NIP-98（kind 27235）署名した Authorization ヘッダーが必要**。応答 `status` が `joined` / `already_member` なら成功。
5. WebSocket で AUTH し、自分の kind 0 を読めることで参加を確認する（Buzz アプリは `inspectProfile`）。

コード無しの入力（`wss://…` など）は 1〜4 を飛ばして 5 だけ行う。既にメンバーなら接続でき、メンバーでなければ AUTH が `restricted: not a relay member` で拒否される。

### 2.3 認証

- **REQ / EVENT / COUNT は常に NIP-42 AUTH が必要。** 未認証は `CLOSED auth-required: not authenticated`（`buzz-relay/src/handlers/req.rs`）。匿名閲覧はできない。
- **本番はコミュニティのメンバーでないと AUTH できない。** `BUZZ_REQUIRE_RELAY_MEMBERSHIP` はコードの既定値は false だが、本番用の `deploy/compose/.env.example` と helm `values.yaml`（"production default"）は true。拒否理由は `restricted: not a relay member`（`handlers/auth.rs`）。
- 接続直後にリレーから `["AUTH", challenge]` が届く。
- `BUZZ_REQUIRE_AUTH_TOKEN` は REST API 用で、WebSocket とは無関係。

### 2.4 イベント

| kind | 用途 | 備考 |
| --- | --- | --- |
| 9 | チャットメッセージ（人） | `h` 必須。返信は `["e", root, "", "root"]`（親がルートのときは省略）+ `["e", parent, "", "reply"]`（標準の `q` ではない） |
| 40002 | チャットメッセージ（エージェント） | content は JSON、`content` フィールドが本文 |
| 40003 | 編集 | `h`、`["e", 対象]`、新しい本文、`imeta`。同じ作者の削除されていない最新の編集で本文と添付を差し替える（`buzz-app/src/features/relay/fold.ts`） |
| 40008 | メッセージ差分 | 表示対象外 |
| 45001 | フォーラム投稿（スレッドのルート） | |
| 45002 | フォーラム投稿への投票 | |
| 45003 | フォーラムのコメント | |
| 7 | リアクション | ライブ配信は `#h` 付き購読にしか流れない |
| 5 / 9005 | 本人削除 / 管理者削除 | 両方を反映する |
| 39000〜39002 | チャンネル情報・管理者・メンバー | リレー鍵の署名。`d` = チャンネルUUID。最初の `t` がチャンネル種別（stream / forum / dm / workflow / system）。標準のフラグに加え `join_role`、`auto_join` など |
| 9021 / 9022 | チャンネル参加 / 退出 | open チャンネルのみ |
| 40099、48100、48103 ほか | システム通知、ハドル（音声通話）など | 表示対象外（40099 は1行の通知として出す） |

- **作者**: リレー鍵で署名されたイベントは `actor` タグ（無ければ先頭の `p` タグ）が本当の作者（`fold.ts` の `messageAuthor`）。
- **本文は Markdown**。添付は本文に `![名前](<url>)` で入り、`imeta` タグにも載る。`||ネタバレ||` やメンションのリンク表記もある。
- **重複**: スレッドの返信をチャンネルへ送ったコピーは `["buzz:copy-of", 元ID]` と `["buzz:sent-from-thread", root, 見出し]` を持つ。
- 読み取りは、メンバーのチャンネルと open チャンネルが対象。unlisted・system チャンネルは `#h`（39000〜39003 は `#d`）で名前を指定しないと返らない。1フィルター500件まで。
- `previous` タグは使っていない。

### 2.5 メディア

`GET /media/{sha256.ext}` は Blossom 認証（kind 24242 を base64 にして `Authorization: Nostr …` に付ける）とメンバー確認が必要（`buzz-relay/src/api/media.rs` の `get_blob`）。ToriNos の通常の画像表示（URL を直接読む）では表示できない。

### 2.6 鍵

Buzz アプリの鍵は、自動生成か nsec の取り込み。NIP-46 には対応していない。ToriNos で参加するときは ToriNos のアカウントの鍵がそのままメンバーの鍵になる。Buzz アプリで別の鍵で参加済みでも、ToriNos の鍵は未参加扱いになる。

### 2.7 NIP-11 で分かること（参加前の判定）

`GET https://<host>/`（`Accept: application/nostr+json`）。2026-11-15 に `png.communities.buzz.xyz` で確認した値を併記する。

| 項目 | 意味 | png.communities.buzz.xyz |
| --- | --- | --- |
| `supported_nips` に 29 | NIP-29 グループのリレー | あり |
| `supported_nips` に 43 | コミュニティのメンバー制が有効（招待制） | あり |
| `limitation.auth_required` | AUTH 必須（Buzz は常に true） | true |
| `requires_nip_fi` | 外部 ID 連携（NIP-FI、IdP が発行した JWT を `Nostr-Federated-Identity` ヘッダーで送る）が必須 | false |
| `supported_extensions` に `buzz-*` | Buzz のリレー | あり |
| `self` | リレー鍵（39000〜39002 の署名者） | あり |

`requires_nip_fi: true` のコミュニティは、ToriNos では外部 ID サービスの証明を得られないため対象外とし、参加前に案内する（`docs/nips/NIP-FI.md`）。

### 2.8 標準の NIP-29 と Buzz の違い

| 項目 | 標準の NIP-29 | Buzz |
| --- | --- | --- |
| 参加の単位 | グループごと（kind 9021） | コミュニティ（ドメイン）ごと（REST の招待） |
| 未参加での閲覧 | `private` でなければ読める | 読めない |
| 共有の形 | kind 39000 の naddr（`?invite=`）、`host'id` | 招待リンク、`wss://`、`buzz://` |
| 参加中の保存 | kind 10009（他クライアントと同期） | 端末に保存し、10009 の暗号化項目の `r` で ToriNos 同士を同期 |
| 返信 | `q` タグ | `e` タグ（reply マーカー） |
| `previous` | 推奨 | 不要 |
| フォーラム | 無し（kind 11 スレッドの実装はある） | 45001 / 45003 |
| 編集 | 無し | 40003 |
| 画像 | 外部ホスト | Blossom 認証付き |
| 本文 | プレーンテキスト | Markdown |

## 3. 対象範囲と段階

| 段階 | 内容 |
| --- | --- |
| 1. NIP-29 の共通部分 | チャットタブ、NIP-42 AUTH、入力の解析（naddr・`host'id`・`wss://`）、グループ一覧（39000）、チャット（kind 9）、返信（`q`）、スレッド表示（11 / 1111）、リアクション、参加・退出（9021 / 9022）とメンバー判定、kind 10009 の読み書き、kind 9 の投稿（`h`・`previous`）。標準の NIP-29 リレーで検証する |
| 2. Buzz 固有部分 | Buzz の判定（NIP-11）、招待リンクの解析、規約同意と招待の利用（REST・NIP-98）、コミュニティの保存、表示の集約（作者・編集・削除・40002）、Markdown 表示、認証付き画像、フォーラム（読み取り）、Buzz 形式の返信（`e`）、コミュニティ内の `buzz://` リンク |
| 3. 投稿の拡充 | 画像の添付（Buzz は Blossom アップロード、標準は既存の画像アップローダー）、フォーラムの投稿・コメント、自分の投稿の編集（Buzz）・削除 |
| 4. 外部リンク | ToriNos の通常投稿や DM に貼られた NIP-29 の naddr と `buzz://message` を、チャットタブで開く |

対象外: OS からの `buzz://` 受け取り（公式アプリと取り合いになるため）、グループ・コミュニティの作成と管理（9000〜9020 の送信）、DM、ハドル・LiveKit、ワークフロー、エージェント関連、投票（45002）、Buzz コミュニティからの退会、サブグループの階層表示（`parent` / `child` は段階1では平らに並べる）。

## 4. UI 設計

### 4.1 方針

- フッターに **「チャット」タブ** を追加する（`FooterItem.Chat`、storageId `chat`、`ServiceTab.Chat`、アイコンは吹き出し）。標準の NIP-29 と Buzz の両方を扱う。
- 既存の「チャンネル」タブ（NIP-28）とは分ける。仕組み（参加の要否、AUTH、編集の反映）が違い、混ぜると「なぜこのチャンネルは読めないのか」が分からなくなるため。
- 画面の型は既存のチャンネルタブにそろえる。ヘッダーの左がアバター、中央が切り替え、右が設定。
- 既定は **非表示**（`defaultVisible = false`、ステータス・絵文字タブと同じ）。フッター設定で表示を選べる。最初のグループ参加を完了したら自動で表示に切り替える（設定に反映し、元に戻せる）。
- メッセージの見た目は吹き出しではなく、アバター + 名前 + 本文の行形式。同じ人の5分以内の連続投稿はアバターと名前を省いてまとめる。
- 標準と Buzz の違いは画面を分けずに、表示する要素の有無で吸収する（参加ボタン、フォーラム、編集済み表示など）。用語は画面上「グループ」に統一し、Buzz のチャンネルも「グループ」と表示する（Buzz の一覧の見出しだけ「チャット」「フォーラム」で区切る）。

### 4.2 画面遷移

```text
チャットタブ
 ├─ 参加中のグループが無い → 空の状態 →「参加する」→ 参加シート
 └─ グループ一覧（ヘッダーで「すべて」／リレー・コミュニティを切り替え）
      ├─ チャットのグループ → チャット画面 → スレッド画面
      ├─ フォーラム（Buzz） → 投稿一覧 → 投稿の詳細
      ├─ スレッド型（kind 11） → スレッド一覧 → スレッド画面
      └─ ヘッダーの切り替え → 「参加する…」→ 参加シート
                              「管理」→ 設定のチャット管理
```

横長画面（タブレット・Web の広い表示）では、グループ一覧を左、チャット画面を右に並べる2ペインにする（`web-wide-side-panels-design.md` の型に合わせる）。

### 4.3 グループ一覧（タブの最初の画面）

「すべて」（既定）:

```text
┌──────────────────────────────────────────┐
│ (●)  すべて ▾                         ⚙ │
├──────────────────────────────────────────┤
│  #  general        png (Buzz)    12:40  3│ ← 名前・どこのグループか・時刻・未読
│     tanaka: 今日のリリース…               │
│  #  nostr-jp       groups.0xchat… 12:10  │
│  ▤  ideas          png (Buzz)    11/02   │ ← フォーラム
│  #  kotlin-dev     relay.groups…  11/14  │
│  ⏳ design-team    relay.groups…  承認待ち│ ← 参加要求を送って 9000 待ち
└──────────────────────────────────────────┘

切り替えメニュー
  ✓ すべて
    png.communities.buzz.xyz   [Buzz]
    groups.0xchat.com          [NIP-29]
    relay.groups.nip29.com     [NIP-29]
    ──────────
    参加する…
    管理
```

個別のリレー・コミュニティを選んだとき:

```text
┌──────────────────────────────────────────┐
│ (●)  groups.0xchat.com ▾              ⚙ │
├──────────────────────────────────────────┤
│ 参加中                                    │
│  #  nostr-jp                    12:10    │
│ そのほかのグループ                        │ ← 公開グループ（未参加）。ここから探せる
│  #  bitcoin-ja       メンバー 120   [参加]│
│  🔒 dev-private      招待制               │ ← closed
│ ［グループを探す（名前で絞り込み）］        │
└──────────────────────────────────────────┘
```

- 「すべて」は参加中のグループだけを最終発言の新しい順に並べる。各行の右にリレー（Buzz はコミュニティ名）を小さく出す。
- 個別のリレーでは、参加中と、未参加の公開グループ（`hidden` でないもの）を分けて出す。Buzz では「チャット」「フォーラム」で区切り、dm・workflow・system は出さない。
- 未読数は端末内で数える（既存の `ChannelUnreadTracker` と同じ考え方）。フッターのチャットタブには、参加中グループの未読があれば点を付ける。
- 接続状態はリレー名の横に小さく出す: 接続中（スピナー）、ログイン失敗（赤い点、タップで理由）。
- 行の長押し: 「グループ情報」「リンクをコピー」（標準は naddr、Buzz は `buzz://channel/<id>`）、「退出」。

## 5. 段階1: NIP-29 の共通部分

### 5.1 構成

`chat` パッケージ（新設）に置き、NIP-28 の `ui/channel` とは共有しない。共有するのは投稿カードの部品、プロフィール、画像表示、履歴の「最新へ」ボタン、スレッド画面の型。

```kotlin
/** リレーの種類ごとの違いを閉じ込める。 */
interface GroupRelayAdapter {
    val kind: GroupRelayKind                       // Standard / Buzz
    fun groupListFilters(): List<NostrFilter>
    fun messageFilters(groupId: String): List<NostrFilter>
    fun replyTargetId(event: NostrEvent): String?  // 標準は q、Buzz は e(reply)
    fun buildMessage(groupId: String, text: String, replyTo: NostrEvent?, previous: List<String>): UnsignedEvent
    suspend fun join(ref: GroupRef, code: String?): JoinResult
    fun fold(events: Collection<NostrEvent>): List<GroupMessage>   // 標準はほぼそのまま、Buzz は編集・作者解決
}
data class GroupRef(val relayUrl: String, val groupId: String)
```

種類の判定は NIP-11（2.7）。`buzz-*` 拡張があれば Buzz、`supported_nips` に 29 があれば標準。どちらでもなければ「NIP-29 に対応していないリレーです」。

### 5.2 入力の解析（`chat/GroupInput.kt`）

```kotlin
sealed interface GroupInput {
    data class Group(val ref: GroupRef, val inviteCode: String?) : GroupInput   // naddr(39000)、host'id
    data class Relay(val relayUrl: String) : GroupInput                         // wss://、ホスト名
    data class BuzzInvite(val host: String, val code: String) : GroupInput      // 段階2
    data object BareBuzzCode : GroupInput
    data object Invalid : GroupInput
}
```

- naddr は kind 39000 だけを受け付け、relay hint が無ければ Invalid。`?invite=` を招待コードとして取り出す。既存の `decodeNaddr` を使う。
- `host'id` は `wss://host` + id。
- Buzz の形式（2.1）は段階2で足す。段階1では `wss://` を Relay として扱い、種類の判定は NIP-11 に任せる。

### 5.3 NIP-42 AUTH（`model/RelayMessage.kt`、`network/NostrRelay.kt`）

- `RelayMessage.Auth(challenge)` を追加する。既存テスト `RelayMessageTest.parse_unknownType_returnsUnknown` は AUTH を「不明」とみなす前提なので、AUTH を解析するテストに置き換える。
- 接続ごと（`RelayOutbox` の接続世代ごと）に `RelayAuthState`（None / Challenged / Authenticating / Authenticated(pubkey) / Failed(reason)）を持ち、切断で None に戻す。
- `RelayAuthenticator`（`NostrRepository` 側）は、チャレンジを受けたリレーが **AUTH 許可リスト**に入っているときだけ kind 22242（`relay`、`challenge` タグ）に署名して送り、`OK` を待つ。許可リストは「参加中のグループがあるリレー」「参加中の Buzz コミュニティ」「参加・閲覧のためにユーザーが確認ダイアログで許可したリレー」。それ以外では AUTH しない（公開鍵を知らせないため）。
- 未参加のグループを［中を見る］で開いて `auth-required:` が返ったら、「このリレーはログインが必要です。公開鍵を伝えてログインしますか？」を出し、許可したら許可リストへ入れる。
- `CLOSED auth-required:` は既に `classifyClosedReason` で `RetryDisposition.RetryAfterAuth` に分類されている。許可リストのリレーに限り、認証完了後に同じ接続世代で REQ を送り直す。それ以外は従来どおり（有限取得は Stop）。フィードなど既存の画面の挙動は変えない。
- 接続時の REQ 再送と AUTH は並行して走るので、REQ が先に着いて拒否されることがある。これも送り直しで回収する。
- `OK false auth-required:`（投稿）は AUTH 後に1回だけ再送する。
- アカウント切り替え時は、認証済みの接続を切って張り直す（`AccountTransitionEffect`）。

### 5.4 取得

すべて該当リレーだけに送る（`RelayTarget.Explicit(setOf(relayUrl))`）。グループのイベントはユーザーの read リレーに問い合わせず、通常のフィードのキャッシュにも入れない。

- グループ一覧: `{kinds:[39000], authors:[self]}`。参加中のグループは `{kinds:[39000,39001], authors:[self], #d:[参加中のID]}` で名前を取る。
- メンバー判定: `{kinds:[9000,9001], #h:[g], #p:[自分]}` の新しいほう（1.3）。39002 は補助としてだけ使う。
- チャット: `{kinds:[9], #h:[g], limit:50}` を遡って取得し、同じ `#h` でライブ購読も張る。リアクションと削除は `{kinds:[7,5,9005], #h:[g]}`。
- スレッド型: `{kinds:[11], #h:[g]}`、コメントは `{kinds:[1111], #h:[g], #E:[root]}`。
- `previous` 用に、グループごとに直近50件の ID を保持する。

### 5.5 参加中グループの保存（kind 10009）

- 標準の NIP-29 の参加中グループは kind 10009 に保存し、ユーザーの write リレーへ出す（他のクライアントと同期できる）。読み込みは既存のリスト系（`RelayListSynchronizer`、`FollowEventEditor` など）と同じ「最新版を取り、未知のタグを保ったまま編集する」方式にする。
- 参加の流れ: 9021 送信 → 9000 を確認 → 10009 に `["group", id, relay, name]` を追加。承認待ちの間は端末にだけ「承認待ち」として持つ。
- 退出: 9022 送信 → 10009 から外す。
- Buzz のコミュニティは公開タグには入れず、暗号化項目に `["r", <リレー>]` として入れる（6.4、[buzz-community-sync-design.md](buzz-community-sync-design.md)）。

### 5.6 投稿（段階1の範囲）

- kind 9、`["h", g]`、`previous`（直近の ID から3件以上、無ければ0件）、返信は `["q", id, relay, pubkey]` と本文先頭の `nostr:nevent1…`、メンションは `p`、カスタム絵文字は `emoji`。
- リアクション（kind 7、`e`・`p`・`k`・`h`）、自分の投稿の削除（kind 5、`h`）。
- 送信先は該当リレーだけ。送信処理に「宛先リレーと kind の組み合わせ」を検査する関数を置き、グループのイベントが他のリレーへ、通常の投稿（kind 1 など）がグループのリレーへ出ないことをテストで固定する。
- `supported_kinds` に無い kind は送らない。

## 6. 段階2: Buzz 固有部分

### 6.1 招待リンクの解析

5.2 の `GroupInput` に、2.1 の表の形式を足す。`https` の招待URLは https のみ受け付け、ユーザー名・パスワード・クエリ・フラグメント付きは拒否する（Buzz と同じ規則）。`ws://` と `http://` はローカル検証用に限って許可する設定を設ける（通常は拒否）。

### 6.2 参加処理（`chat/buzz/BuzzJoinService.kt`）

2.2 の手順を実装する。HTTP は既存の `HttpClientFactory` を使う。NIP-98 署名は `AccountSigner` で kind 27235（タグ `u` = 完全なURL、`method` = POST、`payload` = 本文の SHA-256）を作る。NIP-46 の要求権限には 27235 が既に入っている。

- 参加前の判定: 2.7 の NIP-11 を先に読み、`requires_nip_fi: true` なら「外部 ID 連携が必要なため ToriNos では参加できません」、コード無しの入力で `supported_nips` に 43 があれば「招待制です。招待リンクを貼ってください」と、AUTH で拒否される前に案内する。
- 規約画面: `terms_markdown` / `privacy_markdown` を既存の記事用 Markdown 表示で出し、同意チェックと（必要なら）年齢確認を付ける。
- 拒否理由ごとの表示（`buzz-app/src/features/communities/join.ts` の `CLAIM_REFUSALS` と同じ区分）:

| 理由 | 表示 |
| --- | --- |
| `invite_expired` | 招待の期限が切れています。新しい招待リンクをもらってください |
| `invite_exhausted` | 招待の利用回数の上限に達しています |
| `invite_invalid` | このコミュニティでは使えない招待です |
| `join_policy_required` / `join_policy_not_accepted` | 規約が更新されました。もう一度確認してください（規約画面へ戻す） |
| AUTH の `restricted: not a relay member` | 参加できていません。招待リンクが必要です |

- 招待コードは秘密情報として扱う。ログ（`networkTraceLog`、`appLog`）に出さず、保存もしない（標準の NIP-29 の `code` も同じ扱い）。
- claim の応答が失われた場合に備え、claim の前に「参加処理中」（journal）を保存し、再開時はまず AUTH で参加済みかを確かめてから claim し直す（Buzz の `JoinJournal` と同じ考え方）。

### 6.3 取得の違い

- チャンネル一覧: `{kinds:[39000], authors:[self]}`。最初の `t` で stream / forum を分け、dm・workflow・system は出さない（**要確認**: `#d` 無しで何が返るか）。
- チャット: `{kinds:[9,40002], #h:[g]}`。編集・削除・リアクションは `{kinds:[40003,5,9005,7], #h:[g]}`。
- フォーラム: `{kinds:[45001], #h:[g]}`、詳細では `{kinds:[45003], #h:[g], #e:[post]}`。
- スレッド: `{kinds:[9,40002,45003], #h:[g], #e:[root]}`。
- Buzz は「履歴の取得より先か同時にライブ購読を張る」ことを求めている。既存の購読セッションの仕組みがこの順序になっているか確認する。

### 6.4 コミュニティの保存（`chat/buzz/BuzzCommunityStore.kt`）

アカウントごとに参加コミュニティ（host、表示名、参加日時、規約の同意版）を `LocalSettingsStorage` に保存する。kind 10002 と 10009 の公開タグには入れない（10002 の印の無い `r` は読み書き両方の意味になり、ほかのクライアントが投稿を送ってしまうため。公開すると所属が他の人に見えるため）。

端末を替えても復元できるよう、kind 10009 の暗号化項目（NIP-44 で自分宛て）に `["r", <リレー>]` を入れ、チャットタブを開いたときに合わせる（2026-11-19 改訂）。詳細は [buzz-community-sync-design.md](buzz-community-sync-design.md)。

### 6.5 表示用の集約（`chat/buzz/BuzzMessageFold.kt`、純粋ロジック）

Buzz の `fold.ts` に相当する処理を、テスト可能な純粋関数として作る（`GroupRelayAdapter.fold` の Buzz 版）。

1. 作者の解決: リレー鍵が署名したイベントは `actor` → 先頭の `p`（`h` があるとき）→ pubkey。
2. 削除: kind 5（本人）と 9005（管理者）で対象を消す。kind 5 は作者一致を確認する。
3. 編集: 同じ作者の、削除されていない 40003 のうち最新（`created_at` 降順、同時刻は ID 昇順）で本文を差し替える。`imeta` を持つ最新の編集で添付も差し替える。
4. 40002 は JSON の `content` を本文にする。
5. `buzz:copy-of` を持つコピーは「スレッドから送信」と表示する。
6. 表示対象外の kind は除外する。

### 6.6 本文と画像

- 本文は Markdown として表示する。記事用の Markdown 表示（`ArticleMarkdownContent`）をメッセージ向けに軽くした版を作るか、既存の本文表示に Markdown のサブセット（強調、コード、リンク、画像、引用、`||ネタバレ||`）を足す。どちらにするかは実装前に既存部品の重さを測って決める。
- 画像: コミュニティのホストの `/media/` を指す URL は、Blossom 認証ヘッダー付きで取得する画像ローダーを使う。kind 24242（`t` = get、`x` = sha256、`expiration`、サーバーのホスト）に署名して付ける。
  - 署名回数: Blossom の認証イベントを画像間で使い回せるか確認する（**要確認**。`buzz-app/src-tauri/src/relay.rs` の `blossom_auth` は「スクリプトが使い回せる読み取り証明を作れないように」とあり、ハッシュごとの署名が前提の可能性が高い）。ハッシュごとなら、秘密鍵ログインでは自動で署名し、外部署名アプリでは画像を自動で読まずタップで読み込む。
  - 他のホストの画像は通常どおり表示する。

### 6.7 コミュニティ内の `buzz://` リンク

`buzz://message?...`、`buzz://channel/...` を、表示中のコミュニティのものとしてアプリ内で開く。それ以外の `buzz://`（プラグイン、設定、エージェントなど）はリンクとして表示するだけにする。

### 6.8 Buzz の投稿の違い

- 返信は `["e", root, "", "root"]`（親がルートのときは省略）+ `["e", parent, "", "reply"]`。`q` と `previous` は付けない。
- リアクションは `e` と `h`。

リレーの受け付け条件（`buzz-relay/src/handlers/event.rs`、`ingest.rs`）と、それに合わせた ToriNos 側の扱い:

| 条件・拒否理由 | ToriNos 側 |
| --- | --- |
| 署名者と AUTH した鍵が一致（`invalid: event pubkey does not match authenticated identity`） | 投稿は必ず AUTH 済みのアカウントで署名する。アカウント切り替え中は送らない |
| `h` 必須（`invalid: channel-scoped events must include an h tag`） | 組み立て関数で必ず付ける |
| 知らない kind は拒否（`restricted: unknown event kind`） | 9、45001、45003、7、5、40003、9021、9022 以外を送らない |
| `restricted: not a channel member` / `only members can post in this channel` | 投稿欄を無効にし、open チャンネルなら［参加して投稿］を出す |
| `invalid: channel is archived` | 投稿欄を無効にする |
| `restricted: you are timed out until …` | 解除時刻を表示する |
| 返信先・リアクション先がリレーに無い | 送る前に対象がそのコミュニティのイベントか確認する |
| リアクションの絵文字は64文字まで、カスタム絵文字のショートコードは小文字の正規形 | 絵文字ピッカーで条件外を選べないようにする |

表現の違い:

- 本文は Buzz で Markdown として表示される。投稿欄に「Markdown が使えます」の表示とプレビューを付ける。
- メンションは `p` タグと Buzz のリンク表記にする。ToriNos の `nostr:npub…` のままでは Buzz で文字列として見える。

## 11. 懸念とリスク

- **規約同意（Buzz）**: 参加にはコミュニティの利用規約・年齢確認への同意が必要。ToriNos で同意画面を正しく出さないと、ユーザーが内容を見ずに同意したことになる。
- **画像の署名回数（Buzz）**: 画像ごとに署名が要る場合、外部署名アプリでは実用的でない（6.6）。
- **AUTH による公開鍵の通知**: 許可リスト方式にし、未参加のリレーでは確認を挟む（5.3）。
- **`previous` の拒否**: リレーが自分の DB に無い参照を拒否するので、そのリレーから受け取ったイベントだけを参照に使う。
- **参加の承認待ち**: 9000 がいつ届くか分からない。承認待ちの表示と、届いたときの切り替えを用意する。
- **仕様の変化**: NIP-29・NIP-C7・NIP-51 はいずれも draft。Buzz も活発に開発されており、独自 kind やタグが増え続けている。表示対象を絞り、知らない kind は無視する。
- **共有接続**: `RelayTarget.Explicit` の接続は同じ URL の他の購読と共有される。グループのリレーをユーザーが通常のリレーにも登録していると、その接続も AUTH 済みになる。アカウント切り替え時の切断対象に含める。
- **鍵の扱い（Buzz）**: ToriNos のアカウントの鍵でコミュニティに参加することになる。Buzz アプリで同じアカウントを使うには nsec を取り込む必要があり、その案内が要る。

- E2E で見つけた問題: ViewModel の `init` より後に宣言したプロパティを、`init` のコルーチンが先に使い Wasm で null 参照になった（Android・iOS でも同じ順序の問題）。宣言を `init` より前へ移した。一覧のプレビューが古いまま、認証を求めるリレーで参加前にグループ情報を読めない、も修正。
- 実装レビュー2（10件）: 画面側の再購読による送り直しの重複（リポジトリだけで送り直す）、認証待ちの上限が署名器の承認待ちを打ち切る、`restricted` を閲覧のみと誤判定、NIP-11 の `pubkey` を署名者として使う誤り、同じアカウントの再登録で認証中のまま止まる、古いページのリアクション・削除の欠落、読み込み失敗で過去を読めなくなる、参加の保存の重複、古い接続の切断で新しい接続の認証状態を消す、を修正。フッターの自動表示が働かない点は未解決として上に記載。
- 段階2〜4の実装中の E2E で見つけた問題: 外部署名ではない Web のパスキーを「確認が要る署名器」と扱っていた、画像の許可の後に読み直されない、フォーラムのチャンネルのリンクがチャットで開く、通常の投稿の折りたたみで naddr が途中で切れてリンクにならない、グループのリンクからの移動でタブのスタックを壊しホームに戻れない。すべて修正。kind 0 を直接購読しない規則（`verifyNoDirectProfileSubscriptions`）に合わせ、参加確認は kind 39000 で行う。
- 実装レビュー3（段階2〜4、10件）: メッセージのリンクが任意のスキーム（javascript: など）を開く、`buzz://` の検出が日本語の続く文で失敗する、流儀が決まる前の参加で Buzz のチャンネルを 10009 に書く、NIP-11 を読めないと参加済みの Buzz を標準として扱う、スレッドのルートを `#h` 無しで読む、リンクの処理を渡すたびに画面全体を作り直す、招待の後の認証の失敗でコミュニティを外す、リレーの鍵が分からないときのメンバー一覧を信じる、重複した関数、を修正。フォーラムへの置き換えは既知の課題として残した。
- 実装レビュー4（全体、10件）: 通常の投稿の `buzz://` リンクの処理が受け取りの直後に取り消される、過去の遡りが表示中の最古を起点にして進まなくなる（`OlderPager` に分離）、チャレンジを送らないリレーで認証待ちが失敗にならない（`authWaitVerdict`）、遡りの判定に古い件数を使う、単語の途中の `_` を斜体にする、既読位置を読み込む前の保存でほかのグループの分を消す、参加シートがリンクの鍵を NIP-11 の `self` より優先する、画像の署名が同時に何件も走る、参加グループの数だけフィルターを1つの要求に詰める、行ごとの全件走査、を修正。
- 改訂5（2026-11-19、Buzz コミュニティの同期）: 端末を替えると Buzz コミュニティが出ない問題に対し、kind 10002 は使わず（印の無い `r` は読み書き両方の意味になる）、kind 10009 の暗号化項目に `r` を入れて、チャットタブを開いたときに NIP-11 と AUTH で確かめて復元する方針にした。5.5・6.4 を改訂し、詳細を [buzz-community-sync-design.md](buzz-community-sync-design.md) に分けた。
