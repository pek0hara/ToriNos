# フィードの読み込み中をスケルトン表示にする

## 目的
起動直後や10分以上空けて戻ったときの「投稿が出るまで」を短く感じさせる。待ち時間そのものは変えない。

今の見え方（Android 実機の録画より）:
1. フォロー一覧を待つ間は、画面中央に「読み込み中...」
2. 取得中は回転アイコン
3. 取得開始から2.5秒たつと「リレーから取得中…」に変わる（遅れていると伝えてしまう）
4. 投稿が0.15秒のフェードで出る

文言とアイコンが2〜3回切り替わり、最後に画面全体が投稿に入れ替わる。

## 方針
- 待っている間は、投稿カードと同じ形の灰色の枠（スケルトン）を、画面の高さぶん並べる。
- 起動から投稿が出るまで、スケルトンの見た目を変えない。上の1〜3はすべて同じスケルトンにする。
- 投稿に切り替わるとき、各行の位置がほぼ同じになるよう、寸法は投稿カードに合わせる。

## 対象
- `NoteListItems.kt` の `Loading` と `Slow` の表示。
  - `NoteTimeline` を使う画面すべてに入る: ホームのフォロー・グローバル、自分と他人のプロフィールの投稿一覧。
  - `NoteTimeline` の段階表示で投稿を隠している間（`presentedState` が `Loading` 扱い）もスケルトンになる。
- `FeedScreen.kt` のフォロー一覧待ちの「読み込み中...」。
- 対象外: スレッド、チャンネル、記事。見た目が違うので別に考える。

変えないもの:
- `Failed` の「ポストを取得できませんでした」と再試行の導線。
- `Empty` の「ポストがありません」。
- `InitialFeedState.Slow` という状態そのもの。見た目だけ `Loading` と同じにする。状態は空状態の判定（`NoteTimeline` の段階表示）にも使っている。

## 見た目
1行（`NoteSkeletonRow`）は `NoteCard` の配置に合わせる。

縦の位置は、本文2行の投稿を Android 実機（440dpi）の録画で測った値に合わせる。行の高さは 142dp（実測 391px）。

| 部分 | 寸法 | 合わせる先 |
|---|---|---|
| 行の余白 | 左右16dp、上下8dp、列の間10dp | `NoteCard` の外側の `Row` |
| アイコン | 直径42dpの円 | `AvatarCircle(size = 42)` |
| 時刻 | 幅28dp・高さ10dpの棒、アイコンの下9dp | 時刻の `labelSmall`（実測 行頭から59〜69dp） |
| 名前 | 幅35%・高さ14dpの棒、上17dp | 名前の行（実測 23〜38dp） |
| 本文 | 高さ12dpの棒を2行（幅100%と70%）、上20dp・12dp | 本文（実測 57〜72dp、81〜95dp） |
| リアクション欄 | 幅40%・高さ14dpの棒、上16dp、下9dp | アクション行（実測 109〜127dp） |
| 区切り線 | 投稿の間と同じ `HorizontalDivider` | `noteListItems` |

- 棒の角は4dp、色は `MaterialTheme.colorScheme.onSurface` の透明度12%。点滅で半分まで薄くなっても、ダークで見える濃さにする。
- 行数は6行。端末の高さに合わせて増やすことはしない。6行あれば一般的なスマホの高さを埋め、余りは下が空くだけで済む。

## 動き
- 全体の透明度を 0.5 ↔ 1.0 の間で、1回900msでゆっくり往復させる。
- 点滅の位置はフレームの時刻（`withFrameMillis`）から計算する。`rememberInfiniteTransition` だと、フォロー一覧待ちの画面から一覧へ切り替わるときに点滅が最初からやり直しになり、明るさが跳ぶため。
- 光が横に流れる表現はしない。描画が重く、目立ちすぎるため。
- 透明度は描画の段階でだけ読む（`graphicsLayer { alpha = ... }`）。毎フレームの再コンポーズを起こさない。

## 切り替え
- スケルトンの行は `LazyColumn` の項目として出す（キーは `"skeleton-0"`〜`"skeleton-5"`、`contentType = "skeleton"`）。
- 投稿が出るときは、スケルトンを `Modifier.animateItem(fadeInSpec = null, placementSpec = null, fadeOutSpec = tween(150))` で消し、投稿は今の0.15秒のフェードで出す。2つが重なって入れ替わるので、背景だけが見える瞬間ができない。
- 失敗・空のときも、同じくスケルトンをフェードで消してから文言を出す。
- 投稿は「透明のまま組み立てる → 先頭へ移動 → フェードで出す」の順なので、スケルトンが消え始めるのは投稿が見え始める1〜2フレーム前になる。0.15秒どうしなので重なりは保たれる。

## 読み上げ
- スケルトン全体を1つの要素にまとめ、「投稿を読み込み中」と読ませる。各行の中身は読ませない（`clearAndSetSemantics`）。
- 6行のうち先頭の行にだけ説明を付け、残りは読み上げの対象から外す。

## 実装の分け方
1. `ui/components/NoteSkeleton.kt` を新しく作る: `NoteSkeletonRow(alpha: () -> Float, modifier)`、共有の点滅を返す `rememberSkeletonAlpha()`、`LazyListScope.noteSkeletonItems(count = 6)`。
2. `NoteListItems.kt`: `Loading` と `Slow` の分岐を `noteSkeletonItems()` に置き換える。
3. `FeedScreen.kt`: フォロー一覧待ちの `Box` を、スケルトン6行を並べた `Column` に置き換える（`LazyColumn` の外なのでフェードは `AnimatedVisibility` を使う）。
4. 使わなくなる文言「リレーから取得中…」を消す。

## テスト
- 表示の分岐は関数に切り出してテストする: `InitialFeedState` と投稿の有無から「スケルトン / 失敗 / 空 / 投稿」のどれを出すかを返す `timelinePlaceholder(...)`。
  - Loading・Slow で投稿なし → スケルトン
  - Failed → 失敗の文言、Empty → 空の文言
  - 投稿あり → 投稿（状態によらない）
- 見た目は実機で確かめる: ダークとライトの両方で、コールドスタートを録画し、スケルトンから投稿への切り替えで行の位置が大きく動かないこと、文言が途中で切り替わらないことを見る。

## 設計レビューで見つけたこと
1. 画面の切り替えで点滅がやり直しになる → フレームの時刻から点滅を計算する（「動き」に反映）。
2. 8%では点滅で薄くなったときにダークで見えにくい → 12%にする（「見た目」に反映）。
3. 投稿への切り替えの順序 → 重なりは保たれることを確認（「切り替え」に追記）。
4. 通信できないときは過去ページの取得が再試行を続けて `Failed` にならず、スケルトンが出続ける。今の「リレーから取得中…」も同じで、今回の変更では悪くならない。別の課題として残す。

## 実装レビューで見つけたこと
1. `NoteTimeline` は空の文言を出す前に `emptyStateDelayMillis`（フィードは500ms）待ち、その間は状態を `Slow` として渡す。このためスケルトンが500ms続いてから「ポストがありません」に替わる。読み込み中から空への切り替わりが一度で済むので、このままにする。

2. 最初の実装（棒を等間隔で並べたもの）は1行94dpで、実際の投稿（1行の本文で125dp、2行で142dp）より低く、投稿に替わると行の位置が大きくずれた。実機の録画で各部の位置を測り直し、2行の投稿と同じ142dpにした（実測 394px）。

## 実機での確認（Android、コールドスタートの録画）
- フォロー一覧待ち → 一覧の読み込み中 → 投稿、の間に文言や回転アイコンが出ず、スケルトンが続く。
- フォロー一覧待ちから一覧へ切り替わっても、スケルトンの位置と明るさは変わらない。
- 投稿が出る瞬間は、スケルトンが消えながら投稿が重なって出る。背景だけが見える瞬間はない。
- アプリの起動直後（アカウントの読み込み中）に出る回転アイコンは、`FeedScreen` より前の表示なので今回の対象外。

## 決めていないこと
- 画面の向きやタブレットで行数を変えるか（今回は固定6行）。
- システムの「アニメーションを削除」設定に合わせて点滅を止めるか。Compose が自動では合わせないので、合わせるなら別途対応が要る。
