# 投稿検索のレビューとリファクタ設計

## 1. 対象と結論

2026-10-02時点の作業ツリーをレビューした設計案。実装変更は行っていない。
対象は `ui/search/SearchViewModel.kt`、`SearchScreen.kt` と、その通信・プロフィール・集計境界。
ユーザー検索は投稿検索と共有する検索語、タブ、画面ライフサイクルの互換性を守るために確認した。

推奨は、**ページ取得の状態機械と有限購読の所有権を先に整理し、付随情報の取得・集計を分離する**こと。
ファイルを分割するだけでは、部分ページの扱いや復帰時の欠落は解消しない。

現行の選択タブだけの検索、未取得タブの遅延取得、検索世代による結果分離、
EOSE/タイムアウトによる終了、100msのUI更新集約、iOSのフォーカス解除は維持する。
`search-performance-fix-plan.md` は以前の性能改善と計測の記録であり、
本設計はそこに残る状態管理・テスト容易性・ページ取得の正確性を扱う。
既存のiOSスクロール低下を今回の構造問題が引き起こしたと断定しない。

## 2. 現行の構造

```text
SearchScreen
  └─ SearchViewModel
       ├─ 投稿ページ: temporary relay + events/eose + 独自10秒タイマー
       ├─ ユーザー: ProfileRepository.searchProfiles
       ├─ プロフィール: キャッシュ監視 + 500ms待機 + ensureProfiles
       ├─ 付随情報: SubscriptionSession.Fetch + 独自集計
       └─ 可変の結果/Map/Setを100msごとにUiStateへ転記
```

ViewModelは約630行で、検索操作、ページ境界、ネットワーク終了、プロフィール、
返信・リアクション・リポスト、表示用スナップショットを所有する。
同じ概念が `postsLoadState`、`loadingMore`、`activePageSubId`、`pageProgress`、
`oldestCreatedAt` に分散し、それぞれの更新条件が異なる。

## 3. レビュー所見

行番号はレビュー時点のもの。確定した分岐上の問題と、追加検証が必要なリスクを区別する。

| 優先度 | 所見と根拠 | 影響 |
| --- | --- | --- |

| P2 | 投稿とEOSEを別のcollectorで処理する (257–273) | 終了時にイベントcollectorを取消すため、EOSE以前のイベントがすべて適用済みであることを検索側で保証できない。実際の欠落頻度は未計測 |

| P3 | `appendEvent()` は受信ごとに全結果をソート (336–340)。集計もMap/Listを都度コピーする | UI発行は100msに抑えていても、受信処理の割当・ソートは毎回発生する。性能影響は計測が必要 |

### ページ境界の制約

次ページに `oldestCreatedAt - 1` を使うため、ページ末尾と同秒に未取得投稿があると飛ばす。
これはリレー検索に時刻以外のカーソルがないことも関係し、クライアント側のIDソートだけでは解消しない。
同秒境界の重複取得は改善策だが、同秒の投稿数がリレーの上限を超える場合の完全取得までは保証できない。

### 既存テストの限界

`SearchPageProgressTest` は境界保持と再取得時のページ件数を検証しているが、
ViewModelの追加取得→stop→resumeの接続を検証していない。
`SearchScreenTest` はSpotify URI変換とフィルター上限のテストで、画面の状態遷移を検証していない。
依存先がobjectへ直結しているため、終了順序・旧世代・取消を偽通信で制御しにくい。

## 4. 責務と依存関係

| 要素 | 所有するもの | 所有しないもの |
| --- | --- | --- |
| `SearchViewModel` | 検索語、選択タブ、ユーザー検索状態、画面操作の仲介 | フィルター構築、購読ID、返信タグ解析 |
| `PostSearchController` | 検索世代、ページ状態、結果ID索引、確定カーソル、検索の子scope | Compose、具体的なリレーAPI |
| `PostSearchTransport` | 1ページの有限取得、終了理由の変換、finallyによるclose | 検索全体の結果、ページ送りの可否 |
| `SearchResultEnricher` | プロフィール監視、未送信キュー、付随情報の取得対象と完了状態 | 投稿ページのカーソル |
| `SearchEngagementAccumulator` | 対象別のイベント索引と集計、受理後の重複排除 | 購読開始/終了、画面のロード状態 |
| `SearchScreen` / `PostSearchResults` | 入力、表示、スクロール位置、イベント通知 | 検索取得の判断 |

プロフィールは小さな注入可能な `SearchProfileSource` で既存 `ProfileRepository` を包む。
Clock、検索設定、ID生成、CoroutineScope/Dispatcherもテストから差し替え可能にする。
初期移行ではController内部に集計を残し、Enricher/Accumulatorは次段階で抽出してよい。

`SubscriptionSession`、`SubscriptionBehavior.Fetch`、`RelayTarget.Explicit(setOf(searchRelayUrl))`
を投稿取得にも使用する。これらは既に実装済み。
投稿/EOSE/終了を1本の `signals` で順番に扱い、独自タイマーとtemporary購読管理を撤去する。
閉じる処理はキャンセル中でも完了するよう `withContext(NonCancellable) { session.close() }` をfinallyで実行する。
リレー側拒否、接続不可、タイムアウトは `FetchCompleted.outcomes` を含めて判定する。
基盤のキャッシュ再生・共有接続・終了時のバッファ処理が検索にも適合することを移行テストで確認する。

既存の `SubscriptionOwner` は複数セッションの所有が必要なら再利用できる。
1ページだけなら子Jobとfinallyで足り、Job配列や別の購読レジストリを重ねない。
IDは所有者ごとの一意prefix + 世代 + 用途 + 連番とし、VM間で衝突しない。

### 集計の再利用方針

`EngagementAccumulator` は `FeedViewModel.UiState` に依存し、
`EngagementReducer` / `NoteEngagementCoordinator` は送信操作の楽観更新用なので、検索へ直接導入しない。
既存の `replyTargetId`、絵文字解析、`ReactionEventReducer` など適合するイベント単位のロジックは再利用する。
検索の取得集計をまず独立させ、フィードとの共通化は状態モデルが一致する部分だけ後続で行う。

## 5. 状態モデルと遷移

投稿一覧の存在と、初回/追加ページの取得状態を独立させる。
`loadingMore` を別Booleanで保持せず、操作可否とローディングをページ状態から導く。

```kotlin
data class PostSearchState(
    val events: List<NostrEvent>,
    val page: PageState,
    val nextCursor: PageCursor?, // 正常完了したページからのみ更新
    val hasMore: Boolean,
)

sealed interface PageState {
    data object Idle : PageState
    data class Loading(val request: PageRequest) : PageState
    data class Interrupted(val request: PageRequest) : PageState
    data class Incomplete(val request: PageRequest, val reason: PageFailure) : PageState
    data class Complete(val end: PageEnd) : PageState
}
```

上記は設計用の型案。`PageRequest` は世代、requestId、初回/追加の区別、取得境界、
初回の検索上限時刻を含む。受信件数・ページ最古時刻は実行中ページだけで数え、
表示済みIDとの重複とページ内の重複を別々に判定する。

| 入力/結果 | 遷移・動作 |
| --- | --- |
| 新しい検索/明示的な再検索 | 世代更新、旧子scopeを停止、結果を初期化、選択タブのみ取得 |
| LoadMore | CompleteかつhasMoreならLoadingへ同期的に遷移してからJobを起動。連打でも1ページのみ |
| ページのイベント | 世代とrequestIdを照合。結果へIDでマージ。確定カーソルは動かさない |
| 正常EOSE | 保留イベントを適用してComplete。ページ件数とページ境界から次カーソルを確定 |
| Timeout / Closed / Unavailable / 上限による打切り | 部分結果を保持してIncomplete。カーソルを確定せず、同じrequestを再試行できる |
| 画面非表示 | 実行中ページは初回/追加どちらもInterrupted。付随情報と監視を停止し、全保留状態をUIへ反映 |
| 画面復帰 | 選択タブのInterruptedページだけ同じrequestで再開。完了済みページは再検索しない。プロフィール監視を再接続 |
| タブ変更 | 未取得/中断のタブだけ開始。取得済み結果を再取得しない。非選択タブの既開始の有限取得は完了してよい |
| 取得中の例外 | CancellationExceptionは伝播。他の例外はログだけにせず、対象ページ/付随取得の失敗状態へ反映 |

再開した初回ページも同じ上限時刻で取得できるよう、最初の要求時に `until` を固定する。
検索を実行した時点の履歴を対象とし、新着確認は明示的な再検索とする動作変更を要件に反映する。
画面停止でも取得済みイベント・プロフィール・集計をまとめてflushする。
取消だけに頼らず、旧世代/旧requestの通知をすべての非同期経路で無視する。
更新は1つのdispatcherまたは直列のイベント処理へ集約し、状態と副作用を複数collectorから直接書き換えない。

### 同秒境界への対応

責務抽出中は現行境界を維持し、境界変更は独立した変更として検証する。
改善段階では `until=boundarySecond` で境界秒を重ね、IDで重複排除する。
一意受信件数には既表示IDも含めるが、新規ID数・境界の前進も別に記録する。
同じ境界で進まないときは設定された有限回数/件数の範囲で取得幅を増やし、
なお進まなければ「取得範囲の上限」として終了する。無限再試行や完全取得の表示は行わない。
この対応が必要な高密度の検索語については、リレーの実応答で有効性を評価する。

## 6. 付随情報、保持上限、UI

- 500msの待機は新イベントで無限に延ばさず、最初の未送信追加から固定期間でflushする。
  プロフィールの `referencedPubkeys` と `queuedPubkeys` を分け、依頼済みと未送信を判別する。
- プロフィール監視はページ取得から独立し、画面表示中に1つだけ維持する。
  完了済み画面の復帰ではキャッシュを再読込し、画面停止で未送信になった対象だけを予約する。
  共有ProfileFetchCoordinatorへ依頼済みの通信は共有所有であり、他画面の取得を止めない。
  検索専用通信の完全取消が必要なら所有者leaseの設計を別途追加する。現行要件の所有範囲も明記する。
- 付随情報は新たに追加した対象の差分を有限バッチで取得する。完了済み対象を追加ページごとに再取得しない。
  中断した付随バッチは同じ対象で復帰時に再開し、保持したイベント索引で再計上を防ぐ。
- 対象は当初「最新の追加対象100件」という現行範囲を維持する。可視範囲優先は計測後の別施策とする。
  対象外になってもカードの集計スナップショットは残し、今後の再取得と正確性の扱いを明示する。
- 累積カウントを残して重複IDだけ捨てない。対象ごとの集計済みイベント索引と件数を同じ寿命で保持し、
  予算到達時は対象を取得済み/打切りとして固定する。追い出した対象を再取得する場合はその対象の集計全体を再構築する。
- 設定へPAGE_SIZE=30、投稿10秒、付随5秒、90日、各フィルター200件、1購読800件、
  追跡100件、プロフィール500ms、UI100msを移す。値の変更は計測を伴う別変更にする。
  投稿ページはアプリ側でも一意受理件数に上限を持ち、上限超過の応答を記録する。
  30件に達しただけで正常完了にせず、追加受理を止めてEOSEを待つ。
  過剰送信の安全予算でEOSE前に閉じた場合はIncompleteとして扱う。
  検索全体の最大ページ数/保持件数も設定可能にし、到達時の表示を設ける。具体値は実機計測で決める。
- イベントIDの索引を内部で更新し、ソートと不変スナップショット生成を100msのflush/完了時へ集約する。
  同時刻の表示順をIDで安定化し、バッチ内のイベントも互いに重複排除する。
- 初回検索、追加読込、追加失敗を分けて描画する。部分結果/追加失敗でも既存カードを保持し、
  リスト末尾に進捗と同じページの再試行を置く。通信失敗を「結果なし」と表示しない。
- `SearchScreen` はRouteとContentへ分け、結果一覧を独立Composableにする。
  投稿/ユーザー別のスクロール位置を保持する。Spotify URI処理、キーボードとフォーカス解除は維持する。

保持・集計上限はアプリの処理量を制限するもので、リレーが送信する総バイト数の厳密な上限ではない。
共有のlossless Fetchキューの制限は、検索側の件数制限と分けて評価する。

## 7. 段階的な移行

1. **現行動作の固定**: 通信/プロフィール/Clock/ID生成を注入可能にする。
   タブ分離、旧世代排除、EOSE後closeを偽通信で固定し、上記の不具合経路を回帰ケースとして用意する。
2. **ページ状態を統合**: PostSearchControllerを抽出。初回/追加のLoading、確定カーソル、
   中断requestを一本化し、追加取得中のstop/resumeを修正する。
3. **有限購読を統一**: 投稿をSubscriptionSession.Fetchへ移す。
   終了理由を型で保持し、Timeout/CLOSEDを成功から分離。既存結果を残す再試行UIを接続する。
4. **付随取得を分離**: Enricherと集計索引を抽出。復帰時の監視再接続、未送信queue、差分取得、上限を整理する。
5. **表示と性能を整理**: 状態バッチ化、一覧Composable分離、スクロール保持を導入し実機計測する。
   同秒境界の改善はこの構造を使って別変更として適用する。

各段階で動作変更と機械的な抽出をレビュー上区別する。ユーザー検索の通信APIまで同時に作り直さない。
要件のTimeout/部分結果、復帰時の付随取得、初回境界、共有プロフィールの所有範囲を
`app-requirements.md` と `search-performance-fix-plan.md` に実装と同じ変更セットで反映する。
本書は未実装の提案であり、現行仕様を上書きしない。実装完了後は残す境界をアーキテクチャ文書へ移し、本書を整理する。

## 8. 検証と受け入れ条件

Coroutineの仮想時間と偽Transportを使い、実リレーなしで再現可能にする。

| 検証 | 期待結果 |
| --- | --- |
| ユーザー検索→タブ往復 | 投稿/付随購読は投稿初選択時だけ。取得済みタブの再検索0回 |
| 30件→EOSE | 30件保持、ページclose、追加読込可。次ページ中も既存一覧を表示 |
| 追加ページを1件受信→stop→resume | 同じ境界を再使用、ページ内件数を数え直し、表示IDは重複しない |
| 0件/1件/満杯でTimeout | 空結果の成功にしない、確定カーソル不変、同じrequestへ再試行可能 |
| CLOSED/Unavailable/例外 | 理由を保持し失敗表示、closeが完了する |
| イベント連続到着→直後EOSE | 終了以前に受理した全イベントを反映後にページを確定する |
| 新検索後の旧結果/古い付随バッチの完了 | 新しい状態を書き換えない |
| 完了済み結果→離脱→プロフィールキャッシュ更新→復帰 | 投稿再検索0回、プロフィールは最新、監視は1本 |
| 500ms待機中の離脱/付随取得中の離脱 | 未送信と中断を保持し、復帰後に再開。再計上しない |
| 500msを超える連続受信 | バッチが定期的に実行され、末尾到着まで無期限に待たない |
| 2,000件を超える付随取得→既対象の再応答 | 忘れたIDによる累積カウント増加がない。保持予算を守る |
| 2つのControllerを同時検索 | 購読ID/closeが互いに干渉しない |
| LoadMore連打/画面STOP連続/取消中close | 同時ページ最大1、close冪等、検索所有セッションが残らない |
| 同秒の末尾/境界で前進なし | 重複排除、有限再試行、上限到達の表示。完全取得を誤表示しない |

手動UI検証はAndroid/iOS/Webと、通常画面/サイドパネルの両方を対象にする。
プロフィール/スレッドへの遷移後の復帰、バックグラウンド、入力中の離脱、初期クエリの再適用を確認する。
実機ではページ件数・終了理由・活動中購読数・付随バッチ数・保持イベント数・UI発行数を記録し、
