# フォローフィードのリレー読み込み 修正方針

## 1. 位置づけ

2026-10-03の静的レビューで確認した問題と、修正の順序をまとめる。Phase A〜Cは実装・単体テスト済みで、
実機確認と全体設計への反映（7章の順序4）が残っている。実装時の判断は9章に記録する。

全体の設計は [`feed-relay-merge-design.md`](./feed-relay-merge-design.md)、製品要件は
[`app-requirements.md`](./app-requirements.md) を参照する。この文書は両者を置き換えず、
レビューで見つかった取得漏れの修正に範囲を絞る。修正完了後は必要な判断を全体設計へ反映し、
この修正計画は削除する。

## 2. 現行実装と修正対象

フォローフィードはread有効な全リレーへ、フォロー中ユーザーをauthorsとする履歴REQを送る。
通常の画面ではkind 1とkind 6が対象で、返信は表示から除外する。NIP-65のOutbox方式による
投稿者別の取得先選択は行っていない。

- 履歴は `RelayFeedHistoryCoordinator` がリレー・フィルター別のカーソルで取得する。
- 初回の基準時刻を固定し、それ以前の履歴と、それ以降のライブ購読を並行して開始する。
- 1フィルター30件を要求し、同一秒に集中する場合は要求数を最大3,840件まで増やす。
- 正常完了したリレーだけカーソルを進め、遅いリレーを表示境界の決定から外せる。
- 復帰・手動更新・ライブ切断後の補完は、通常履歴とは別のcoordinatorで行う。
- 生投稿の保持は最大2,000件、画面へ渡す一覧は最大800件。

| 優先度 | 問題 | 現行の挙動 | 修正後の挙動 |
|---|---|---|---|
| P1 | 短い非空ページで取得終了 | 要求数未満なら `exhausted` にする | 空ページ＋EOSEだけを終端にする |
| P1 | 差分取得失敗後の未取得区間消失 | 連続失敗で同期状態を削除する | 通信を終了しても未取得区間を保留する |
| P2 | 表示前の投稿が保持上限で消失 | 受信順に古い投稿を削除する | ページ全体を保存してからカーソルを進める |

部分取得・未解決境界・端末の保持上限は、それぞれ取得終了と区別して画面へ伝える。

## 3. 守る性質

1. 応答しないリレーがあっても、正常なリレーの取得を続けられる。
2. 空ページとEOSEを受信したフィルターだけを `exhausted` にする。
3. タイムアウト、切断、CLOSED、保存失敗で取得カーソルを進めない。
4. 取得判定はリレー・フィルター別の受信IDで行い、表示件数や全体の重複排除件数に依存しない。
5. 通信を止めることと、未取得範囲を捨てることを別の操作にする。
6. 保存とカーソル更新を整合させ、保存できていないイベントを取得済み扱いにしない。
7. 画面の待機時間・自動取得回数・保持件数には上限を設ける。

## 4. Phase A：短いページの終端判定を修正する

主な対象：
[`RelayFeedHistoryCoordinator.kt`](../composeApp/src/commonMain/kotlin/com/nostr/torinos/ui/feed/RelayFeedHistoryCoordinator.kt)
の `advanceCursor()`。

### 方針

- `timestamps.size < requested.limit` による終端判定を削除する。
- 非空ページ＋EOSEでは、受信した最古時刻を次の包含 `until` とする。
- 同じ境界秒しか返らない場合は、短いページでも要求数を拡張する。
- 拡張しても進めない境界は未解決として記録し、前の秒へ進む。
  その秒を完全取得済みとは扱わない。複数の未解決境界を1つの時刻で上書きしない。
- 表示から除外された投稿だけが続く場合もカーソルは進める。自動継続には全体設計の
  `MAX_AUTO_SKIP_EMPTY_HISTORY_PAGES`（初期値5ページ）を適用し、上限後は明示操作で再開する。

単に終端判定を削除すると、同じ境界秒の再取得や表示0件ページが繰り返され得る。
境界の進行・未解決状態・自動継続上限までを同じ変更で確認する。

### 確認するケース

- 30件要求に対し20件＋EOSEが返り、続く古い投稿も取得できる。
- 空ページ＋EOSEだけが該当フィルターを終端にする。
- 複数フィルターのうち片方が空でも、他方の取得を継続できる。
- 同一秒の短いページで要求数を拡張し、上限後は穴を残して古い秒へ進める。
- ミュート・NGワード・返信除外で表示0件が続いても、自動REQが無限に続かない。
- 既存テストの「短いページで終了する」という前提を修正し、疑似リレーから空ページまで取得する。

## 5. Phase B：失敗した差分区間を保持する

主な対象：
[`FeedController.kt`](../composeApp/src/commonMain/kotlin/com/nostr/torinos/ui/feed/FeedController.kt)
の `startFeedSync()`、`recoverLiveGap()`、`finishFeedSync()`。

### 方針

- リレー・フィルター別に `PendingGap` を持ち、固定の `since`、次に要求する包含 `until`、
  要求数、停止理由を保存する。通常履歴のカーソルへは反映しない。
- 一定回数の失敗で自動取得を止めることは許容するが、未取得区間を成功扱いで削除しない。
- 保留区間の再試行は、最後に正常完了した位置から始める。
  最新の表示投稿の時刻を、全リレー共通の取得完了位置として使わない。
- 新しい補完区間は既存区間を包含する範囲へ統合する。
  同じリレー・フィルターの保留件数を1件に抑え、要求が進行中なら古い結果が広げた範囲を消さないよう
  要求時スナップショットと世代を検証する。
- 再試行契機は手動更新、前景復帰、接続復旧などとし、一時失敗にはバックオフを適用する。
  認証待ち・構造的拒否は既存設計の再開条件に従う。
- 通常履歴、全リレーの差分同期、リレー単位の切断補完を共通のリレー別arbiterで直列化する。
- 前景の更新表示は、通信の終了時に消してよい。保留区間が残る場合は部分取得を表示する。

保留区間は同じフィードスコープのメモリ内に保持する。フォロー一覧変更、長時間復帰による
明示的リセット、アカウント切り替え、ViewModel破棄ではスコープとともに破棄する。
アプリ再起動をまたぐ永続化は今回の対象に含めない。

24時間の補完対象期間や件数予算を超えた場合も、期間外・予算到達による打ち切りと正常完了を区別する。
打ち切った区間を、全件取得済みとして表示しない。

### 確認するケース

- リレーAが成功し、Bが3回失敗して通信を終了しても、Bの保留区間が残る。
- Aからさらに新しい投稿が届いた後、Bの復旧で以前の欠落投稿を回収できる。
- 複数フィルターで成功・失敗が分かれた場合、成功分だけを進める。
- タブを繰り返し切り替えても保留区間が狭まらず、購読が重複しない。
- 通常履歴・手動更新・切断補完が重なっても、同じリレーの有限取得は同時に1件以下。
- フォロー一覧やアカウントの変更後、旧スコープの結果を新しいフィードへ反映しない。

## 6. Phase C：保存と表示ウィンドウを分離する

主な対象：`FeedController`、`HeldFeedEvents`、履歴ページの受信・完了処理。
型と責務は全体設計9.4節の `FeedHistoryStore` と `FeedPresentationIndex` に合わせる。

### 方針

- 履歴イベントはページ単位で集計し、ストアへの保存成功後にカーソルを更新する。
  不完全ページを保存する場合も、取得完了とは扱わない。
- 保存は要求IDとスコープで冪等にし、旧スコープの保存を拒否する。
- 履歴ストアは表示待ち・表示範囲外・除外中の生イベントも保持する。
  画面の最大800件は表示ウィンドウの上限とし、ストアの上限と切り離す。
- ソフト上限は全体設計に合わせて初期値5,000件とする。開始済みページは途中で捨てず全件保存し、
  上限到達後は新しい通常履歴REQを止めて保持上限を表示する。
- ストア容量を増やすだけで完了とはしない。開始済みページによる一時超過とライブ受信時の扱いも
  全体設計に従い、無制限にメモリを増やさない。
- 画面末尾では、保存済みの次のウィンドウを先に表示し、不足する場合だけネットワーク取得する。
- リポストのsource IDと元投稿のdisplay IDを区別し、ウィンドウ変更や遅着時も表示位置を維持する。
- 同一秒の未解決境界、停止リレー、認証待ち、保存失敗、保持上限を終端と区別して表示する。

### 確認するケース

- 同一秒に3,840件あるページを保存し、最初に受信した投稿もウィンドウを切り替えて閲覧できる。
- 複数リレーの同時完了で上限を超えても、開始済みページを途中で捨てない。
- 保存失敗時はカーソルが進まず、再試行後にイベントが重複しない。
- 画面の表示上限到達だけを理由に、リレーへ同じページを再要求しない。
- リポスト・ミュート・NGワードによる表示変換後も、投稿と付随情報を保持できる。

## 7. 実装の進め方

| 順序 | 変更 | 完了条件 |
|---|---|---|
| 1 | Phase A | 短いページの取りこぼしを再現するテストが通り、同秒境界・表示0件でも停止条件がある |
| 2 | Phase B | 失敗したリレーの保留区間を復旧後に回収し、同一リレーの有限取得を直列化できる |
| 3 | Phase C | 保存成功とカーソル更新が整合し、保存済み投稿を表示ウィンドウで閲覧できる |
| 4 | 実機確認・文書整理 | 遅延、停止、復旧、大量投稿で表示と読み込み操作を確認し、全体設計へ導入状況を反映する |

既存の `FeedControllerAsyncRegressionTest`、`FeedRelayMergeGapTest`、`HeldFeedEventsTest` を
基礎に、取得漏れ・復旧・保存失敗を再現するテストを追加する。新しい状態機械とストアには
仮想時間およびFake gateway／storeを使い、実リレーの応答に依存せず確認できるようにする。

## 9. 実装時の判断

- 境界秒だけの短いページは、そのフィルターで以前により多くの件数を受信していれば、境界秒を取りきったとみなし
  前の秒へ進む。履歴の末尾で既知の境界秒だけが返るたびに要求数を拡張し、未取得範囲と誤表示しないためである。
  以前の最大件数以上の短いページはリレーの返却上限とみなし、拡張せずに未解決境界として記録して前の秒へ進む。
- 要求数を超えて返すリレーの応答は保存せず、そのリレーの一時失敗として再試行する。保存失敗とは表示を分ける。
- 表示0件ページの自動継続は、ミュート・NGワードで隠れた投稿を表示件数に数えない。差分同期の件数予算は、
  隠れた投稿も含む保持件数で数える。
- 長時間の離脱で最新ページだけを取る場合は、保留区間を引き継がない。保留区間を統合するときは、
  補完対象期間（24時間）より古い部分を打ち切る。
- 保存済みウィンドウは先頭へ戻ると固定を外し、手動更新でも最新から表示する。
