作成日: 2026-10-09

関連: `app-requirements.md`（NIP-57 は未対応）、`subscription-architecture-design.md` §11.3、`engagement-fetch-redesign.md`、`profile-cache-design.md`、`nip-compatibility-design.md`

## 1. 目的と範囲

ポストカードの操作欄で、リアクション数の右にライトニング（⚡）のアイコンを置き、その投稿の作者へ Zap（NIP-57）を送れるようにする。
受け取った Zap の合計額（sats）をアイコンの右に出す。

お金を持つのは常に外部のウォレットで、アプリはウォレットにならない。支払いは「ウォレットアプリに渡す」か「NWC でウォレットに頼む」のどちらか。

| 段階 | 内容 |
| --- | --- |
| **第1段階（本書の主対象）** | ⚡ボタン、額の選択（ポップアップ）と詳細シート、LNURL 解決、Zap リクエスト（kind 9734）の作成と請求書の取得・検査、外部ウォレットアプリへの受け渡し（`lightning:` URI）、送った Zap の受領確認、フィード・スレッドでの合計額の表示、Zap の設定（額の選択肢、⚡を出さない） |
| 第2段階 | NWC（NIP-47）によるアプリ内の支払い（取り消せる5秒の待ち付き）、送った人・額・コメントの内訳パネル |
| 第3段階 | Zap の分配（`zap` タグ）、記事（kind 30023、`a` タグ）とプロフィールへの Zap、受け取った Zap の通知、ウォレットアプリの選択、Web 版の WebLN、請求書の QR 表示 |

非目標: 匿名・非公開の Zap（Damus・Amethyst にはあるが、現行の NIP-57 本文に定義がない）、ウォレット機能そのもの（残高・受け取り・履歴）。

## 2. 仕様の確認（2026-10-09、NIP-57・NIP-47 の最新本文）

### 2.1 NIP-57 の流れ

1. 受け取り先の LNURL を決める。投稿に `zap` タグがあればそれを優先し（Appendix G）、なければ作者の kind 0 の `lud16` を LNURL の規則で URL にする。
   `lud06` は NIP-57 本文に記載がないが、LUD-01 の bech32 `lnurl` として Damus・Amethyst とも扱うため対応する。
2. その URL を GET し、`allowsNostr == true` かつ `nostrPubkey` が正しい 64 桁の16進なら Zap に対応している。`callback`・`minSendable`・`maxSendable`（msats）を使う。
3. kind 9734（Zap リクエスト）を作って署名する。**リレーには送らない。**
4. `callback` に `amount`（msats）・`nostr`（イベントの JSON を URL エンコード）・`lnurl`（bech32 `lnurl`）を付けて GET し、`pr`（BOLT11 請求書）を受け取る。
5. 請求書を支払う（ウォレットアプリに渡す、または NWC で頼む）。
6. 受け取り側の LNURL サーバーが、支払い後に kind 9735（Zap レシート）を Zap リクエストの `relays` へ送る。

kind 9734 のタグ:

| タグ | 必須 | 値 |
| --- | --- | --- |
| `relays` | 必須 | `["relays", "wss://a", "wss://b", …]`（入れ子にしない） |
| `amount` | 推奨 | msats の文字列。クエリーの `amount` と一致させる |
| `lnurl` | 推奨 | 受け取り先の bech32 `lnurl` |
| `p` | 必須 | 受け取る人の公開鍵（1つだけ） |
| `e` | 投稿へ送るとき必須 | 対象イベントID（0か1つ） |
| `a` | 任意 | 置換可能イベントの座標（記事、第3段階） |
| `k` | 任意 | 対象イベントの kind の文字列 |

`content` は任意のコメント。レシートの `description` に入るため**公開される**。

### 2.2 Zap レシートの検証（Appendix F、MUST）

- レシートの `pubkey` は、受け取り先の LNURL サーバーの `nostrPubkey` と一致しなければならない。
- `bolt11` の請求額は、Zap リクエストの `amount` タグ（あれば）と一致しなければならない。
- Zap リクエストの `lnurl` タグ（あれば）は受け取り先の lnurl と一致すべき（SHOULD）。
- `SHA256(description)` は請求書の description hash と一致すべき（Appendix E、SHOULD。サーバー側の規定）。
- レシートは支払いの証明ではない（「誰かが請求書を取得した」ことの記録）。

### 2.3 NIP-47（第2段階）

- kind 13194（ウォレットの情報、置換可能）、23194（要求）、23195（応答）。通知の kind は本体から外れ、別リポジトリの拡張仕様になった。
- 接続 URI は `nostr+walletconnect://<ウォレットの公開鍵>?relay=…&secret=<32バイト16進>[&lud16=…]`。`secret` で要求に署名し、内容を暗号化する。
- 暗号化は NIP-44（`nip44_v2`）を優先する。NIP-04 は非推奨だが後方互換として残っており、情報イベントに `encryption` タグがなければ NIP-04 だけの対応とみなす。
- `pay_invoice` の結果は `preimage`（と任意の `fees_paid`）。エラーは `PAYMENT_FAILED`、`INSUFFICIENT_BALANCE`、`QUOTA_EXCEEDED`、`RATE_LIMITED`、`RESTRICTED`、`UNAUTHORIZED`、`UNSUPPORTED_ENCRYPTION`、`NOT_IMPLEMENTED`、`INTERNAL`、`OTHER`。

## 3. 既存クライアントの実装（2026-10-09 時点の main）

Damus（`damus-io/damus`、Swift）と Amethyst（`vitorpamplona/amethyst`、Kotlin）のソースを読んで比べた。

| 項目 | Damus | Amethyst | 本設計 |
| --- | --- | --- | --- |
| ⚡のタップ | 既定額を**すぐ送る**（`NoteZapButton.tap`） | 額の選択肢をポップアップで出す。選択肢が1つならすぐ送る（`zapClick`） | Amethyst に合わせてポップアップ（§5.2） |
| 長押し | 額・コメント・種類を選ぶシート（`CustomizeZapView`） | 額の選択肢の編集。ダブルタップで任意の額 | 額とコメントのシート |
| 額の選択肢 | 既定額1つ（設定で変更） | 選択肢のリスト（設定で編集、同期設定に保存） | 選択肢のリスト（端末内、アカウントごと） |
| 送信中の表示 | 送信中から自分の Zap として数え、アイコンを塗る | アイコンの中に2段階の進み具合を出す。済んだら塗った⚡ | 送信中はアイコンに進み具合。合計にはレシートまたは NWC の成功で足す |
| 合計の書式 | `format_msats_abbrev` | 1万未満はそのまま（`2100`）、以上は `12k`・`1.2M`（四捨五入） | Amethyst に合わせる |
| 合計が 0 | 数字を出さない | 数字を出さない | 出さない |
| `relays` タグ | 自分のリレーの先頭10個 | 自分のリレー＋作者（と分配先）の inbox リレー | 自分の読み込みリレー＋作者の read リレー、最大10個 |
| 請求書の検査 | 額が一致しなければ捨てる | 額が一致しなければエラー（sats に丸めて比較） | 額・ネットワーク・期限。description hash は見るが止めない（§7.4） |
| `allowsNostr` がない | — | Zap リクエストを付けずに普通の LNURL 支払いをする | 普通の支払いとして送れる。シートで「件数に出ません」と出す |
| コメント | Zap リクエストの `content` | `content` と LUD-12 の `comment` パラメーターの両方 | 両方 |
| レシートの `pubkey` 検証 | 受け取る人ごとに LNURL を取り、`zapper` を覚えて照合（`process_zap_event`） | 同じ。キャッシュ1000件、同じ URL の同時取得は1回にまとめ、失敗は覚えない（`LnurlEndpointCache`） | 同じ形（§9.2） |
| 照合できないとき | 数えない | 受け取り先の LNURL がプロフィールに無ければ署名だけで数える。取得に失敗したら数えない | 数えない |
| `lnurl` タグの不一致 | — | 数える（SHOULD のため） | 数える |
| 額なしの請求書のレシート | 捨てる | — | 捨てる |
| 外部ウォレット | `lightning:` かウォレットごとの URL（設定で既定のウォレットを選ぶ） | Android の Intent。`<queries>` で受け手の有無を事前に調べる | `lightning:`。Android は `<queries>` を宣言して受け手の有無を調べる |
| NWC | 対応。**送る前に5秒待ち、その間は⚡で取り消せる** | 対応。既定の支払い元に設定すると自動で使う | 第2段階で対応。5秒の取り消しも入れる |
| NWC の暗号化 | NIP-04 のみ | ウォレットが `nip44_v2` を出していれば NIP-44、なければ NIP-04 | Amethyst に合わせる |
| Zap の種類 | 公開・匿名・非公開・Zap にしない | 同じ | 公開だけ |
| 分配 | — | 対応 | 第3段階 |
| ⚡を出さない設定 | あり（`nozaps`） | — | あり |

## 4. 現状のコード

| 項目 | 現状 | Zap に必要な変更 |
| --- | --- | --- |
| プロフィール | `NostrProfile` は `name`・`display_name`・`picture`・`banner`・`about`・`nip05` だけ。kind 0 の content から `ignoreUnknownKeys` で読む | `lud16`・`lud06` を足す。キャッシュは kind 0 イベントから読み直すので移行は要らない |

| 件数の集計 | `TargetEngagement` → `EngagementSummary` → `NoteEngagementState` | `zaps` と Zap の合計を足す |
| ハンドラーの受け渡し | `LocalQuotePostHandler` を `AppSessionCoordinator` の `CompositionLocalProvider` で渡している | `NoteCard` の呼び出し元は7ファイルあるため、Zap の開始も同じ場所から CompositionLocal で渡す |

## 5. UI と操作

### 5.1 操作欄

```
 ✉ 3   ⟲ 1   ♥ 12   ⚡ 2100        ✉ 3   ⟲ 1   ♥ 12   ⚡ 12k
```

- 並びは 返信・リポスト・リアクション・**Zap**。間隔は既存の `spacedBy(12.dp)` に合わせ、アイコンの大きさ・数字の書式も `EngagementCount` を使う。
- 数字は受け取った Zap の合計額（sats）。0 なら数字を出さない（Damus・Amethyst と同じ）。書式は 1万未満はそのまま、以上は `12k`・`1.2M`（四捨五入、Amethyst と同じ）。
- アイコン: 通常は線の⚡（`onSurfaceVariant`）。自分が Zap 済みなら塗った⚡（アンバー `0xFFF5A623`）。送信中は⚡の中に進み具合（請求書の取得 → 支払い）を出す。
- 出す条件: `showEngagement` が true、ログイン中、設定で「⚡を出さない」にしていない。**自分の投稿**は合計額だけ出し、押せない。
- 受け取り先が分からない（プロフィール未取得、`lud16`/`lud06` なし）ときもアイコンは出す（行の幅を投稿ごとに変えない）。押すと「この人は Zap の受け取り先を設定していません」と出す。
- リポストのカードでは、リポストした人ではなく元の投稿と作者へ送る（`NoteCard` の `event` が元の投稿）。
- ミュート中の人の投稿には出さない。
- 数字を押したときの内訳パネルは第2段階。第1段階では数字は押せない。

### 5.2 タップ: 額のポップアップ

```
            ┌──────────────────────────┐
            │  ⚡100   ⚡500   ⚡1,000  │
            └──────────────────────────┘
 ✉ 3   ⟲ 1   ♥ 12   ⚡ 2100
```

- ⚡をタップすると、設定の額の選択肢を⚡の上にポップアップで出す（Amethyst の `ZapAmountChoicePopup` と同じ）。選択肢を押すと、その額でコメントなしで送る。
- **⚡のタップだけでは送らない。** Damus はタップで既定額をすぐ送るが、スクロール中の誤タップで実際に支払いが始まる（このアプリではフィードの誤タップでリアクションを送った実例がある）。額を選ぶ2回目のタップを必ず挟む。
- 選択肢の初期値は 100 / 500 / 1,000 sats。設定で 1〜6 個に変えられる。
- ポップアップの外を押すか、スクロールすると閉じる。

### 5.3 長押し: 詳細シート

⚡を長押しすると、額とコメントを指定できるボトムシートを開く（Damus の `CustomizeZapView` と同じ位置づけ）。

```
┌─────────────────────────────────┐
│ ⚡ Zap を送る                     │
│ 〔アイコン〕 表示名                │
│   name@example.com               │
│                                   │
│ [100] [500] [1,000] [その他…]    │
│                                   │
│ コメント（公開されます）           │
│ ┌─────────────────────────────┐ │
│ └─────────────────────────────┘ │
│                                   │
│        [ 1,000 sats を送る ]       │
└─────────────────────────────────┘
```

- 額の初期値は前回シートで送った額。「その他」は数字入力。LNURL の `minSendable`〜`maxSendable` の範囲外は送るボタンを押せなくし、範囲を下に出す。シートを開いたときに LNURL を取りに行き、範囲が分かるまでボタンは押せない。
- コメントは最大 280 文字。LNURL 応答の `commentAllowed` が 280 より小さければそれに合わせる（§7.3 の `comment` パラメーターのため）。
- 受け取り先が Zap に対応していない（`allowsNostr` がない）ときは「この受け取り先は Zap に対応していません。送ることはできますが、件数には出ません」と出したうえで送れる（Amethyst と同じ）。ポップアップから送ったときも同じ文言をトーストで出して止め、シートを開かせる（知らずに Zap でない支払いをしないように）。
- 10,000 sats を超える額は確認ダイアログを挟む（桁の打ち間違い対策）。

### 5.4 送信の流れと結果

- 送る → ⚡の中に進み具合 → ウォレットアプリが開く。アプリに戻ると「支払いを確認しています」を⚡の進み具合のまま出し、レシートが届けば塗った⚡にして合計に足す。
- ウォレットアプリが開けなかった（受け手がない）ときは、請求書をコピーするボタン付きのダイアログに「Lightning ウォレットのアプリが見つかりません」と出す。
- エラーは §7 の表の文言でトーストに出す。
- 支払い待ちの投稿でもう一度⚡を押すと「支払いを確認中です。もう一度送りますか」と聞く（二重払い対策）。

### 5.5 設定（設定 › Zap）

| 項目 | 既定 | 内容 |
| --- | --- | --- |
| ⚡を表示する | オン | オフで⚡と合計を出さない（Damus の `nozaps`） |
| 額の選択肢 | 100 / 500 / 1,000 | 1〜6 個、1〜1,000,000 sats |
| ウォレットの接続（第2段階） | なし | NWC の接続 URI |

アカウントごとに端末内に保存する。他の端末との同期はしない。

## 6. アーキテクチャ

新しいパッケージ `com.nostr.torinos.zap` に通信と判定を置き、UI は `ui/zap` に置く。判定はすべて純粋関数にしてテストする。

| ファイル | 役割 |
| --- | --- |
| `zap/LightningAddress.kt` | `lud16`（`name@domain`）と `lud06`（bech32 `lnurl`）から LNURL-pay の URL を作る。`lnurl` タグ用の bech32 も作る |
| `zap/LnurlPay.kt` | LNURL-pay 応答の読み取りと検証（`PayEndpoint`）。取得は関数を差し込める形にする |
| `zap/LnurlPayRepository.kt` | 受け取り先の URL ごとの `PayEndpoint` の取得とキャッシュ。同じ URL への同時取得を1回にまとめる |
| `zap/ZapRequest.kt` | kind 9734 のタグの組み立てと callback URL の組み立て |
| `zap/Bolt11.kt` | 請求書の解析（ネットワーク、額、payment hash、description hash、発行時刻、有効期限） |
| `zap/ZapReceipt.kt` | kind 9735 の読み取りと検証、合計額の集計 |
| `zap/ZapSender.kt` | 送信の状態機械（§8.1）。アカウントのセッションの寿命に従う |
| `zap/PendingZapWatcher.kt` | 支払い待ちのレシートの確認（§8.2） |
| `zap/ZapSettingsStore.kt` | ⚡の表示、額の選択肢、シートの前回の額 |
| `ui/zap/ZapButton.kt` | 稲妻の `ImageVector`（線・塗り）、進み具合、操作欄のボタン |
| `ui/zap/ZapAmountPopup.kt` | 額のポップアップ |
| `ui/zap/ZapSheet.kt` | 詳細シート |

`NoteCard` への受け渡し:

- `zapSummary: ZapSummary? = null` を1つだけ足す（`totalMsats`、`count`、`isZappedByMe`）。引数を細かく増やさない。`ZapSummary` は `@Immutable` の data class にし、`feed-recomposition-design.md` の方針どおり変わらなければ再描画しない。
- 送信の開始は `LocalZapHandler = compositionLocalOf<ZapHandler?> { null }` で渡す。`LocalQuotePostHandler` と同じ `AppSessionCoordinator` の `CompositionLocalProvider`（3か所）で提供する。null のとき（未ログイン、設定で非表示、Web 版で無効にしたときなど）はボタンを出さない。
- 送信中・支払い待ちの状態は `ZapSender` が `StateFlow<Map<eventId, ZapProgress>>` で持ち、ボタンは自分の投稿IDの分だけを読む。

## 7. 送信の詳細

### 7.1 受け取り先の決定

1. 投稿に `zap` タグがある → 第1段階では送らず「分配の Zap には未対応です」と出す（作者へ送ると、分配を指定した人の意図と違う相手に払うため）。
2. 作者の `lud16` → `https://<domain>/.well-known/lnurlp/<name>`。`name` は小文字にし、`a-z0-9-_.+` 以外を含む場合は使わない。
3. なければ `lud06` を bech32 で解いて URL にする。
4. どちらもなければ受け取り先なし。

プロフィールはキャッシュを使うが、⚡を押したときに取得から10分以上たっていれば kind 0 を取り直す（受け取り先の変更に追いつくため）。

### 7.2 LNURL-pay 応答の検証

| 項目 | 条件 | 満たさないとき |
| --- | --- | --- |
| URL | `https`（`.onion` は対象外）。リダイレクトは `https` のみ | 「受け取り先に接続できません」 |
| 応答 | 64KB 以内の JSON。`status == "ERROR"` なら `reason` を出す | 同上 |
| `tag` | `payRequest` | 「受け取り先の設定が正しくありません」 |
| `callback` | `https` の URL | 同上 |
| `minSendable`/`maxSendable` | 正の整数（msats、`Long`）、min ≤ max | 同上 |
| `allowsNostr`/`nostrPubkey` | true かつ 64 桁の16進 | Zap でない普通の支払いとして扱う（§5.3） |
| `commentAllowed` | 任意。0 以上の整数 | コメントの上限に使う |

キャッシュは受け取り先の URL ごと（メモリ、上限 1,000 件、30 分）。同じ URL の同時取得は1回にまとめ、待っていた呼び出し側にも同じ結果を返す（Amethyst の `LnurlEndpointCache` と同じ）。失敗は覚えず次の呼び出しで取り直すが、同じ URL への取得は1分に1回までにする（連打や、レシートが続けて届いたときに相手のサーバーへ繰り返し送らないため）。

### 7.3 Zap リクエストと callback

```
kind 9734
content: <コメント>
tags:
  ["relays", <自分の読み込みリレー>…, <作者の read リレー>…]
  ["amount", "<msats>"]
  ["lnurl", "<bech32 lnurl>"]
  ["p", "<作者>"]
  ["e", "<投稿ID>"]
  ["k", "<投稿の kind>"]
```

- `relays` は、自分の有効な読み込みリレー（レシートを自分が受け取れる場所。件数の取得先と同じ）を先に、作者の NIP-65 read リレー（キャッシュにある分）を後に並べ、重複を除いて最大 10 個（Damus と同じ上限）。`wss://` 以外は入れない。
- チャンネルのメッセージ（kind 42）は `k=42`。チャンネルの推奨リレーも `relays` に足す（レシートがチャンネル画面の取得先に届くように）。
- callback の URL は Ktor の `URLBuilder` でパラメーターを足す。`callback` がすでに `?` を含む場合も壊さない（Amethyst も `&` でつなぐ）。
  - `amount`: msats。
  - `nostr`: 署名済みイベントの JSON を全体エンコードする（NIP の例は `encodeURI` だが、`&` や `#` を含むコメントで壊れるため。Amethyst も全体エンコード）。`allowsNostr` がない受け取り先には付けない。
  - `lnurl`: bech32。
  - `comment`: コメントがあれば付ける（LUD-12。Zap でない支払いのときにコメントを届けるため。Amethyst と同じ）。
- URL 全体が 8,000 文字を超える場合は送らずに「コメントを短くしてください」と出す。
- 応答は `{"pr": "lnbc…"}`。`status == "ERROR"` なら `reason` を出す。

### 7.4 請求書の検査（支払いの前に必ず行う）

NIP-57 は送信側の請求書の検査を定めていないが、支払う前に次を確かめる。

| 検査 | 満たさないとき | 理由 |
| --- | --- | --- |
| 接頭辞が `lnbc`（メインネット） | 渡さない | テストネットの請求書を渡さない |
| 額が指定され、送ると決めた額（msats）と一致する | 渡さない | サーバーの不具合や改ざんで別の額を払わせない（Damus・Amethyst とも行う） |
| 有効期限内 | 渡さない | 期限切れをウォレットに渡さない |
| description hash（`h`）が `SHA256(callback に送った JSON 文字列)` と一致する | **渡す**。不一致をログに出す | 一致しないとレシートが作られない可能性があるが、Damus・Amethyst とも検査しておらず、サーバーの実装差で正しい Zap を止める危険のほうが大きい |

BOLT11 は署名の検証まではしない（ウォレットが行う）。bech32 部分は 90 文字の制限なしで解き、タグ付きフィールドから `p`（payment hash）・`h`・`x`（期限、既定 3600 秒）を読む。

### 7.5 支払い（第1段階）

- `LocalUriHandler.openUri("lightning:<請求書>")`。例外なら §5.4 のコピーのダイアログを出す。
- Android は `Intent.ACTION_VIEW` で開くので、受け手が複数ならアプリの選択が出る。Android 11 以降は `AndroidManifest.xml` に `<queries>` で `lightning` スキームを宣言し、受け手がなければ最初からコピーのダイアログを出す（Amethyst の `PayToAppAvailability` と同じ）。
- iOS は `lightning:` を受けるアプリがあれば開く。開けたかどうかは `openURL` の結果で分かるので `LSApplicationQueriesSchemes` は要らない。ウォレットごとの URL を選ぶ設定（Damus の既定ウォレット）は第3段階。
- Web 版は `lightning:` の受け手がない環境が多い。第1段階はコピーを主にし、WebLN は第3段階。

## 8. 状態と受領確認

### 8.1 送信の状態機械

```
Idle → ResolvingEndpoint → RequestingInvoice → InvoiceReady(invoice)
     → AwaitingPayment(since) → Confirmed(receipt)
                              ↘ Unconfirmed（タイムアウト）
   （各段階から）↘ Failed(reason)
第2段階の NWC: InvoiceReady → Countdown(5秒、取り消し可) → PayingViaNwc → Paid(preimage) → Confirmed
```

- ⚡の中の進み具合は `ResolvingEndpoint`・`RequestingInvoice` を前半、`AwaitingPayment`・`PayingViaNwc` を後半として出す（Amethyst の2段階の表示）。
- `ResolvingEndpoint` と `RequestingInvoice` はシートを閉じても続ける（ポップアップから送ったときはシートがないため）。⚡をもう一度押すと取り消せる。`AwaitingPayment` 以降はウォレットへ移ったあとなので取り消さない。
- アカウントを切り替える・ログアウトするときは、`AccountSession` のスコープごと止める。支払い待ちの記録も捨てる（別アカウントのカードに出さない）。
- `Failed` の理由は §7 の表の文言。callback を再び呼ぶと新しい請求書になるが、未払いなので問題ない。
- 同じ投稿で `AwaitingPayment` が残っている間の再送は確認を挟む（§5.4）。

### 8.2 支払い待ちの確認

- `AwaitingPayment` に入ったら、`kinds=[9735] #e=[投稿ID] #p=[作者] since=<請求書の発行時刻 − 60>` を Zap リクエストの `relays` へ購読する（`RelayTarget.Explicit`、未接続のリレーは一時接続）。
- 受け取ったレシートの `description` の Zap リクエストの ID が自分の送ったものと一致し、§9 の検証を通れば `Confirmed`。件数の取得とは独立して、そのレシートを件数のストアへも入れる（すぐ合計に反映する）。
- 3分で `Unconfirmed` にして購読を閉じ、⚡を元に戻す。トーストで「支払いを確認できませんでした。ウォレットで支払いが済んでいれば、後で件数に反映されます」と出す。アプリがバックグラウンドの間は時間を数えない（ウォレットで操作している間に切れないように）。
- Zap でない支払い（`allowsNostr` なし）はレシートが来ないので、ウォレットを開いた時点で終える。
- 支払い待ちは同時に最大 3 件。超えたら古いものから `Unconfirmed` にする。

## 9. 件数の取得と検証

### 9.1 取得

- フィード: `EngagementPartition` に `Zap` を足す（`NostrFilter(kinds = listOf(9735), eTags = ids, …)`）。既存の購読に入るので REQ は増えない。ライブ追跡・履歴のバックフィル・リレーの絞り込み（`sourceRelays`）も既存の区分と同じ扱い。
- スレッド: `ThreadController` の件数取得に同じフィルターを足す。
- 検索・ジャーナル・チャンネル・通知は第2段階以降（そこでは ⚡ の数字を出さず、送信だけ可能にする）。
- `limit` はリアクションと同じ値。レシートは1件が大きい（`description` に Zap リクエスト全体を含む）ので、受信量は FetchTrace の kinds 内訳で確かめる（§12）。

### 9.2 検証（Appendix F）

レシートごとに次を確かめ、すべて通ったものだけを数える。

1. `bolt11` と `description` のタグがあり、`description` が kind 9734 の署名つきイベントとして読める（署名を検証する）。
2. Zap リクエストの `p` がカードの作者、`e` がカードの投稿ID。
3. `bolt11` に額があり（額なしは捨てる。Damus と同じ）、Zap リクエストの `amount`（あれば）と一致。数える額は請求書の額。
4. Zap リクエストの `lnurl`（あれば）が作者の現在の受け取り先と違っても数える（SHOULD のため。Amethyst と同じ）。
5. **レシートの `pubkey` が作者の LNURL サーバーの `nostrPubkey` と一致。**

5 には作者の LNURL-pay 応答が要る。Damus・Amethyst と同じく、受け取る人ごとに取りに行く。

- 1〜4 を通ったレシートを「未確認」として作者ごとに保留する。
- **レシートが1件以上ある作者だけ**、LNURL-pay 応答を取りに行く（§7.2 のキャッシュと同時取得のまとめを共用、同時 2 本、表示中の投稿の作者を優先）。結果の `nostrPubkey` は作者ごとに 24 時間覚える。
- `nostrPubkey` が分かったら、その作者の保留分を確定または破棄する。
- 受け取り先が分からない作者（プロフィールなし、`lud16`/`lud06` なし、サーバー停止）のレシートは数えない。Amethyst はプロフィールに受け取り先がなければ署名だけで数えるが、偽のレシートで合計を大きく見せられるのを避けるため、ここは Damus に合わせる。

### 9.3 集計

- 重複は Zap リクエストの ID で除く（同じ支払いのレシートを複数のリレーや複数回の発行で受け取ることがある）。
- `ZapSummary.totalMsats` は確定したレシートの請求額の合計。表示は sats に切り捨ててから §5.1 の書式にする。
- `isZappedByMe` は Zap リクエストの `pubkey`（`P` タグがあれば一致を確かめる）が自分。
- 削除（kind 5）は対象外。レシートは受け取り側のサーバーが出すので、送った人が消すものではない。

## 10. 安全とプライバシー

- ⚡のタップだけでは支払いを始めない（§5.2）。額を選ぶ操作を必ず挟む。
- コメントと送った人の公開鍵は、レシートの `description` として誰でも読める。シートに「コメントは公開されます」と出す。
- Zap リクエストは受け取り先の LNURL サーバーに送られ、送った人の公開鍵・指定したリレー・IP アドレスが伝わる。
- 請求書・NWC の secret はログに出さない（`FetchTrace` などに URL を出すときは `nostr=` 以降を伏せる）。
- HTTP は `https` のみ、10 秒で打ち切り、応答は 64KB まで。

## 11. 第2段階: NWC と内訳（概要）

### 11.1 NWC

- 設定 › Zap に「ウォレットを接続」を置き、`nostr+walletconnect://` を貼り付ける（QR の読み取りは後で）。接続したら情報イベント（kind 13194）を取り、`pay_invoice` があるかを確かめる。
- 接続があれば、ポップアップ・シートのどちらから送っても NWC で払う（Amethyst の既定の支払い元と同じ）。外部ウォレットへ渡すのは接続がないときだけ。
- `secret` は支払いの権限そのものなので、アカウントごとに OS の安全な保存先（iOS は Keychain、Android は Keystore で暗号化した保存）に置く。`KeyStorage` と同じ expect/actual の形にする。Web 版では NWC を使わない。
- 暗号化は、情報イベントの `encryption` に `nip44_v2` があれば NIP-44、なければ NIP-04（Amethyst と同じ。Damus は NIP-04 だけなので、NIP-04 だけのウォレットもまだある）。NIP-04 の AES-256-CBC は Android は `javax.crypto`、iOS は CommonCrypto で actual を書く。
- **送る前に5秒待ち、その間は⚡を押すと取り消せる**（Damus と同じ）。ポップアップで額を押した直後の「しまった」に間に合わせる。
- `pay_invoice` の要求（kind 23194）には `expiration`（現在 + 60 秒）と `encryption` を付ける。応答の購読（`#e=[要求ID] authors=[ウォレット]`）は要求を送る前に始め、60 秒待つ。接続先のリレーはユーザーのリレー設定に含まれないことが多いので一時接続を使う。
- **応答がないときに自動で再送しない**（二重払いになりうる）。「結果が分かりません」とし、レシートの確認（§8.2）に任せる。
- `preimage` を受け取ったら `SHA256(preimage) == payment hash` を確かめて成功とし、レシートを待たずに塗った⚡にする。合計への反映はレシートで行う。エラーコードは日本語の文言に対応させる。

### 11.2 内訳パネル

- ⚡ の数字を押すと、リアクションと同じ `EngagementDetailsPanel` に「Zap」の欄を開く。額の大きい順に、送った人のアイコン・額・コメントを並べる。

| R22 | 合計の書式は `999`・`1.2k`・`12k` | 1万未満はそのまま、以上は `12k`・`1.2M`（§5.1） | Amethyst と同じ。4桁は省略しないほうが額が分かる |
| R23 | 送信中・支払い待ちはアイコンを半透明にする | ⚡の中に2段階の進み具合、済んだら塗った⚡（§5.1・§8.1） | Amethyst と同じ。どこまで進んだか分かる |
| R24 | ⚡は常に出す | 設定で出さないようにできる（§5.5） | Damus の `nozaps`。iOS の審査で求められたときにもこの経路で止められる |
| R25 | 失敗した LNURL の取得を1分覚える | 失敗は覚えず、同じ URL への取得は1分に1回まで。同時取得は1回にまとめる（§7.2） | Amethyst の `LnurlEndpointCache`。レシートが続けて届いたときに相手のサーバーへ繰り返し送らない |
| R26 | 受け取り先が分からない作者のレシートの扱いは未記載の比較 | 数えない（Damus と同じ）。Amethyst の「署名だけで数える」は採らない（§9.2） | 偽のレシートで合計を大きく見せられるのを避ける |
| R27 | 額なしの請求書のレシート | 捨てる（§9.2-3） | Damus と同じ。額が決まらない |
| R28 | Android で受け手の有無を調べない | `<queries>` で `lightning` を宣言して調べ、なければ最初からコピーを出す（§7.5） | Amethyst の `PayToAppAvailability`。Android 11 以降は宣言しないと調べられない |

### 未確定事項

- **iOS の App Store 審査。** 2023年6月、Apple は Damus の投稿への Zap を「デジタルコンテンツの販売」とみなし、外すよう求めた（プロフィールへの Zap は残った）。その後 Damus は「新しい App Store ガイドラインで認められた」として投稿への Zap を戻している（App Store の変更履歴）。そのため投稿への Zap は出せる見込みとして進める。どのガイドラインの改定で認められたのか、地域による違いがあるのかはまだ確かめていないので、iOS のリリース前に 3.1.1 の現行の文面を確認する。審査で指摘されたときに備え、iOS だけ投稿の ⚡ を出さない設定（`LocalZapHandler` を null にする）は残しておく。
