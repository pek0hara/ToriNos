# アカウント切り替え時の ViewModel 初期化仕様

## 1. 目的

アカウント切り替え時に、旧アカウントの状態や非同期処理が新アカウントへ混入しないことを保証する。

画面や ViewModel ごとにリセット処理を追加する方式を廃止し、アカウントセッションの終了と開始によって、アカウント依存の ViewModel、Repository、購読、編集中状態を一括して管理する。

## 2. 背景と現状の課題

現在の実装では、次の仕組みが混在している。

- `SettingsViewModel` が `KeyStorage` のアクティブアカウントを変更し、コールバックで App に変更を通知している。
- App が `ownPubkey`、プロフィール、ドロワー、投稿シート、返信・引用情報などを個別に初期化している。
- `accountStateResetKey` を更新し、一部の Compose state を再生成している。
- ViewModel key にアカウントを含む画面と、含まない画面がある。
- 一部の ViewModel は `init` で `loadPublicKey()` を実行し、その時点のアカウントを内部変数に保持している。
- 一部の Repository／Store はシングルトンとしてアカウント依存状態を保持している。
- ミュート・NGワードなど、アカウント別であるべきキャッシュの一部が共通キーで保存されている。

この構成には、次の問題がある。

- リセット対象を追加し忘れる可能性がある。
- 旧 ViewModel が生存し続け、新しい秘密鍵を参照する可能性がある。
- 旧アカウント向けの通信結果が、切り替え後に反映される可能性がある。
- 画面ごとに ViewModel key の規則が異なり、初期化の保証が難しい。
- アカウントを往復した際に、アカウント別キャッシュを正しく復元できない。
- 起動、アカウント追加、切り替え、ログアウト、削除で初期化経路が異なる。

## 3. 基本方針

1. アクティブアカウントは `AccountSessionManager` が一元管理する。
2. アカウント切り替えを、公開鍵の差し替えではなく `AccountSession` の終了と開始として扱う。
3. アカウント依存 ViewModel はセッション単位の `ViewModelStoreOwner` 配下で生成する。
4. セッション終了時に、配下の ViewModel とアカウント依存 CoroutineScope をすべて破棄する。
5. ViewModel は `KeyStorage` から現在アカウントを直接読み込まない。
6. アカウント別データは公開鍵を含むキーで永続化する。
7. 公開データのキャッシュは、アカウントから独立した共有キャッシュとして保持できる。
8. 起動、追加、切り替え、ログアウト、削除は同じセッション遷移経路を使用する。

## 4. 用語

### 4.1 アカウント

保存済みの秘密鍵と、その秘密鍵から導出される公開鍵で識別される利用者単位。

### 4.2 アカウントセッション

アプリが特定のアカウントとして動作している期間。

同じ公開鍵へログインし直した場合でも、以前のセッションとは別の `sessionId` を発行する。

### 4.3 匿名セッション

アクティブな秘密鍵がなく、公開情報の閲覧だけが可能な状態。

## 5. セッション状態

セッション状態は、概念上次のモデルとする。

```kotlin
sealed interface AccountSessionState {
    data object Loading : AccountSessionState

    data class Active(
        val session: AccountSession,
    ) : AccountSessionState

    data class Anonymous(
        val sessionId: String,
    ) : AccountSessionState

    data class Switching(
        val fromPubkey: String?,
        val toPubkey: String?,
    ) : AccountSessionState
}

data class AccountSession(
    val sessionId: String,
    val pubkey: String,
    val signer: AccountSigner,
)
```

`AccountSession` は秘密鍵文字列を公開しない。署名が必要な処理には、セッションに紐づいた `AccountSigner` を使用する。

## 6. AccountSessionManager の責務

`AccountSessionManager` をアクティブアカウントの唯一の管理主体とする。

主な責務は次のとおり。

- 起動時に保存済みアカウントを復元する。
- アカウント切り替え要求を直列化する。
- `KeyStorage` のアクティブアカウントを変更する。
- セッションごとに一意な `sessionId` を発行する。
- アカウント依存 Repository と CoroutineScope を生成する。
- 旧セッションの処理をキャンセルし、終了を待つ。
- セッション状態を `StateFlow` として公開する。
- ログアウト、アカウント削除後の遷移先を決定する。
- 初期化失敗時に旧セッションを復元する。

画面および個別の ViewModel は、`KeyStorage.switchAccount()`、`KeyStorage.logout()`、`KeyStorage.deleteKey()` を直接呼び出さない。

## 7. ViewModel のスコープ

### 7.1 構成

```text
App
├── グローバルスコープ
│   ├── 公開プロフィールキャッシュ
│   ├── 公開イベントキャッシュ
│   ├── チャンネルキャッシュ
│   └── 端末共通設定
└── AccountSessionHost(sessionId)
    ├── FeedViewModel
    ├── ThreadViewModel
    ├── ChannelViewModel
    ├── NotificationsViewModel
    ├── PostViewModel
    ├── JournalViewModel
    ├── アカウント依存 Repository
    └── アカウント依存 CoroutineScope
```

`AccountSessionHost` は、セッションごとの `ViewModelStoreOwner` を提供する。

`sessionId` が変わった場合は、旧 `ViewModelStore` を `clear()` し、新しい `ViewModelStore` を生成する。これにより、旧セッションに属する全 ViewModel の `onCleared()` が呼ばれることを保証する。

### 7.2 ViewModel の生成規則

アカウント依存 ViewModel は、コンストラクタで `AccountSession` または必要最小限のアカウント依存インターフェースを受け取る。

```kotlin
class FeedViewModel(
    private val account: AccountContext,
    private val feedRepository: FeedRepository,
) : SafeViewModel()
```

次の処理は禁止する。

- ViewModel の `init` で `loadPublicKey()` を呼ぶ。
- ViewModel から `KeyStorage.loadPrivateKey()` を呼ぶ。
- 操作実行時にグローバルなアクティブアカウントを再取得する。
- ViewModel key に手作業で公開鍵やリセットカウンターを追加して、セッション破棄の代用とする。

### 7.3 ViewModel の分類

#### アカウント依存 ViewModel

次のいずれかに該当する ViewModel は、アカウントセッション配下に置く。

- 投稿、削除、リアクション、リポストなど署名操作を行う。
- 自分の公開鍵によって表示内容が変わる。
- フォロー、ミュート、NGワードを参照する。
- 自分の通知、既読状態を保持する。
- 自分が行ったリアクションやリポストを保持する。
- アカウント別の下書きや入力状態を保持する。

#### アカウント非依存 ViewModel／Repository

次の情報だけを扱うものは、グローバルスコープに置ける。

- 公開プロフィール
- 署名済み公開イベント
- 公開チャンネル情報
- URLやイベントIDだけで決まる共有キャッシュ

ただし、自分との関係、操作可否、ミュート状態などを含めた時点でアカウント依存となる。

## 8. 状態とキャッシュの保存範囲

| 状態 | 保存範囲 | 切り替え時の動作 |
| --- | --- | --- |
| 公開プロフィール | 全アカウント共通 | 維持する |
| 公開イベント | 全アカウント共通 | 維持する |
| チャンネルキャッシュ | 全アカウント共通 | 維持する |
| フォロー一覧 | 公開鍵別 | 新アカウントのキャッシュを読み込む |
| ミュート一覧 | 公開鍵別 | 新アカウントのキャッシュを読み込む |
| NGワード | 公開鍵別 | 新アカウントのキャッシュを読み込む |
| 通知、既読状態 | 公開鍵別 | 新アカウントの状態を読み込む |
| 自分のリアクション、リポスト | セッション／公開鍵別 | ViewModel を再生成する |
| NIP-65 リレーリスト | 公開鍵別 | 新アカウントのキャッシュを読み込む |
| 画面ごとの選択リレー | 公開鍵別 | 新アカウントの選択を復元する |
| 投稿、返信、引用の編集中状態 | セッション内 | 破棄する |
| ドロワー、ダイアログ表示状態 | セッション内 | 閉じる |
| フィードのスクロール位置 | セッション内 | リセットする |
| 年齢確認、テーマなど | 端末共通 | 維持する |

アカウント別の永続化キーには、必ず公開鍵を含める。

```text
follow_list_cache_{pubkey}
private_mute_list_cache_{pubkey}
notifications_{pubkey}
relay_entries_{pubkey}
selected_global_relay_{pubkey}
```

旧形式の共通キャッシュが存在する場合は、現在アカウントのキャッシュとして一度だけ移行する。別アカウントへ複製しない。

## 9. アカウント切り替えシーケンス

### 9.1 正常系

1. 切り替え要求を受け付ける。
2. 切り替え先が現在アカウントと同じ場合は、何も変更せず成功とする。
3. 状態を `Switching` に変更する。
4. 投稿、フォロー、ミュート変更など、アカウント依存操作を無効化する。
5. 旧セッションの購読、通信、保留中の書き込み処理をキャンセルする。
6. 旧セッションの終了を待つ。
7. `KeyStorage` のアクティブアカウントを変更する。
8. 新しい `sessionId` を発行する。
9. 新アカウント用 Repository と CoroutineScope を生成する。
10. 新アカウントのローカルキャッシュを読み込む。
11. セッション状態を `Active` に変更する。
12. `AccountSessionHost` が旧 ViewModelStore を破棄し、新しい ViewModel を生成する。
13. ナビゲーションをフィードへ戻す。
14. リレーからの最新情報取得をバックグラウンドで開始する。

ネットワーク同期の完了は、`Active` への遷移条件にしない。ローカルキャッシュの読み込み後に画面を表示し、通信結果は後から反映する。

### 9.2 失敗時

- `KeyStorage` の変更前に失敗した場合は、旧セッションを再開する。
- `KeyStorage` の変更後に新セッションの生成へ失敗した場合は、可能な限り旧アカウントへロールバックする。
- 旧セッションを復元できない場合は `Anonymous` へ遷移する。
- UIには切り替え失敗を表示する。
- 新アカウントの一部状態だけを表示してはならない。

### 9.3 多重実行

- 切り替え処理は Mutex 等で直列化する。
- `Switching` 中の追加要求は受け付けない。
- UI上のアカウント操作ボタンを無効化する。

## 10. 非同期処理の安全性

アカウント依存の非同期処理は、開始時の `sessionId` を保持する。

次のいずれかを満たさない結果は破棄する。

- 処理開始時と結果反映時の `sessionId` が一致する。
- 処理を所有するセッションの CoroutineScope が有効である。

特に次の処理を対象とする。

- フォロー一覧の取得と更新
- ミュート、NGワードの取得と公開
- 通知購読
- リアクション、リポストの照合
- プロフィール編集
- 投稿、記事、チャンネル、ステータスの公開
- リレーリスト同期

購読IDにも `sessionId` を含めるか、セッション所有の購読管理オブジェクトで一括管理する。

## 11. 投稿などの書き込み操作

書き込み操作は、操作開始時の `AccountSession` に固定する。

- 署名途中でアクティブアカウントを再取得しない。
- 切り替え開始時に未完了の書き込みをキャンセルする。
- キャンセルできない外部送信が完了した場合でも、新セッションの UI 状態へ成功結果を反映しない。
- 楽観的更新は、処理開始時と現在の `sessionId` が一致する場合だけ確定する。

これにより、Aアカウント用に開始した操作をBアカウントの鍵で署名することを防止する。

## 12. UI仕様

### 12.1 切り替え中

- アカウント一覧の選択操作を無効化する。
- 投稿、フォロー、リアクションなどのアカウント依存操作を無効化する。
- 切り替え中であることが分かる進行表示を出す。
- 旧アカウントの画面を操作可能な状態で残さない。

### 12.2 切り替え完了時

- プロフィールドロワーを閉じる。
- 通知ドロワーを閉じる。
- クイック設定を閉じる。
- 投稿、返信、引用、ステータス作成画面を閉じる。
- 選択中のメモとローカル下書きを破棄する。
- ナビゲーションをフィードへ戻す。
- 初期表示タブはグローバルとする。
- スクロール位置を先頭へ戻す。
- 新アカウントのキャッシュが読み込まれるまで、旧アカウントの情報を表示しない。

### 12.3 切り替え失敗時

- 元のアカウントを継続利用できる状態へ戻す。
- 「アカウントを切り替えられませんでした」を表示する。
- 切り替えボタンを再度操作可能にする。

## 13. 起動・ログアウト・削除

### 13.1 アプリ起動

1. `Loading` から開始する。
2. `KeyStorage` からアクティブアカウントを取得する。
3. アカウントがあれば通常のセッション開始処理で `Active` へ遷移する。
4. アカウントがなければ `Anonymous` へ遷移する。

起動時だけの特別な ViewModel 初期化経路は作らない。

### 13.2 ログアウト

- 現在セッションを終了する。
- 保存済みアカウントを削除しないログアウト仕様の場合は、`Anonymous` へ遷移する。
- UIと ViewModel は通常のセッション終了処理で破棄する。

### 13.3 アカウント削除

- 現在セッションを終了してから秘密鍵を削除する。
- 保存済みアカウントが残っている場合は、選択された次アカウントで新セッションを開始する。
- 保存済みアカウントがない場合は `Anonymous` へ遷移する。
- 削除後の遷移先は、画面側の推測ではなく `AccountSessionManager` の結果を使用する。

## 14. エラー処理

- セッション切り替えエラーは、画面固有の ViewModel state ではなくセッション管理層から通知する。
- エラーには、利用者向けメッセージとログ用原因を分けて保持する。
- キャッシュ読み込みの一部失敗は、空状態でセッションを開始し、ネットワーク更新を継続できる。
- 秘密鍵の読み込み、署名機能の生成、アクティブアカウント変更に失敗した場合は `Active` にしない。

## 15. 受け入れ条件

### 15.1 ViewModel

- AからBへ切り替えたとき、すべてのアカウント依存 ViewModel が別インスタンスになる。
- 旧 ViewModel の `onCleared()` が呼ばれる。
- 新 ViewModel はBの `AccountSession` だけを参照する。
- ViewModel から `loadPublicKey()` と `KeyStorage.loadPrivateKey()` の直接利用がなくなる。

### 15.2 データ分離

- Aのフォロー、ミュート、NGワード、通知がBに表示されない。
- AからB、再度Aへ切り替えたとき、Aのローカルキャッシュを復元できる。
- 公開プロフィールや公開イベントの共有キャッシュは切り替え後も利用できる。

### 15.3 非同期処理

- Aで開始した通信結果が、Bの ViewModel state に反映されない。
- Aで開始した署名処理がBの秘密鍵を使用しない。
- 切り替え中に投稿やフォロー操作を開始できない。
- 古い購読が切り替え完了後も残らない。

### 15.4 遷移

- 同じアカウントへの切り替えは no-op になる。
- 切り替え失敗時は元のアカウントを利用できる。
- ログアウト後は匿名セッションになる。
- アカウント削除後、残存アカウントがあればそのアカウントの新セッションが開始される。
- 残存アカウントがなければ匿名セッションになる。

## 16. 必要なテスト

### 16.1 AccountSessionManager 単体テスト

- 起動時の Active／Anonymous 遷移
- AからBへの正常切り替え
- 同一アカウントへの切り替え
- 切り替え多重実行の拒否
- `KeyStorage` 変更失敗時の復元
- 新セッション生成失敗時のロールバック
- ログアウト
- アカウント削除後の次アカウント選択

### 16.2 ViewModel スコープテスト

- `sessionId` 変更による旧 ViewModelStore の破棄
- 旧 ViewModel の CoroutineScope キャンセル
- 新セッションでの ViewModel 再生成
- 旧セッションからの遅延イベント破棄

### 16.3 Repository テスト

- 公開鍵別キャッシュの分離
- A→B→Aでのキャッシュ復元
- generation／`sessionId` 不一致結果の破棄
- セッション終了時の購読解除

### 16.4 UIテスト

- 切り替え中の操作無効化と進行表示
- 完了後のフィード遷移
- ドロワー、投稿シート、編集中状態の破棄
- 失敗メッセージと旧アカウントへの復帰
- 旧アカウント情報が一瞬表示されないこと

## 17. 移行方針

一度に全 ViewModel を変更せず、次の順序で移行する。

1. `AccountSessionManager` とセッション状態を導入する。
2. 起動、切り替え、ログアウト、削除を Manager 経由に統一する。
3. `AccountSessionHost` とセッション単位の ViewModelStore を導入する。
4. `FeedViewModel`、`ThreadViewModel`、`ChannelViewModel` から `loadPublicKey()` を除去する。
5. 投稿・編集系 ViewModel から `KeyStorage.loadPrivateKey()` を除去し、`AccountSigner` へ移行する。
6. フォロー、ミュート、NGワード、通知、リレー設定をアカウント別 Repository へ移行する。
7. アカウント別キャッシュキーへ移行する。
8. `accountStateResetKey` と画面固有のアカウントリセット処理を削除する。
9. ViewModel key に含めていた `ownerKey` や公開鍵を、必要な画面識別用途を除いて整理する。

移行期間中も、アクティブアカウントを変更する入口は `AccountSessionManager` のみに限定する。

## 18. 今回の決定事項

- アカウント切り替え時、編集中の投稿・返信・引用は破棄する。
- 切り替え後はフィードのグローバルタブへ戻す。
- フィードのスクロール位置は引き継がない。
- NIP-65 リレーリストと画面ごとの選択リレーはアカウント別に保存する。
- 公開プロフィールと公開イベントのキャッシュは全アカウントで共有する。
- ネットワーク同期完了を待たず、ローカルキャッシュ読み込み後に新セッションを表示する。
