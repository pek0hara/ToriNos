# 記事下書き・投稿画面改善・Matometr 統合設計

作成日: 2026-10-01。状態: 実装・自動テスト・コードレビュー完了。端末での操作確認は12.2に記載。
更新日: 2026-10-03。ユーザー指定により記事下書きをリレーに保存する方式へ変更。専用の端末内DB・公開履歴の永続化を撤回し、実装とテストを更新。

## 1. 目的と要件の基準

記事を書きかけのまま保存・再開できるようにし、投稿画面を長文編集に適したUIへ改善する。同じエディタを使って、フィード・ジャーナル・マイプロフィール・ユーザープロフィール・検索の投稿を複数選択し、各投稿の `nevent` をまとめた `#matometr` 記事を公開できるようにする。以降、この5画面を「対象画面」と呼ぶ。

本書では **Matometr = 複数のNostr投稿を、順序と編集者の文章を付けて紹介するまとめ記事** と定義する。外部のMatometr固有仕様は今回の検索では確認できていないため、ユーザーの依頼とNostrの標準仕様を基準にしたToriNosの設計案である。既存サービスとの完全互換を保証するものではない。固有仕様が提示された場合は公開形式を照合する。

| 区分 | 内容 |
| --- | --- |
| 依頼に基づく必須要件 | 記事下書き、投稿UI改善、対象5画面共通の複数選択、ヘッダー直下の選択投稿表示、neventをまとめた記事、`#matometr` |
| 本書で提案する初期仕様 | 自己暗号化した記事下書きのリレー保存、アカウント別取得、kind 1・kind 1111の選択、並べ替え、kind 30023で公開 |
| 初期リリース後の拡張 | 暗号化リレー下書き同期、kind 1・kind 1111以外の選択、引用通知のオプション |

本書の要件を実装した。設計上の型名と実装上の配置の対応、検証済み範囲、残る操作確認は12.2を参照する。

## 3. Matometrの機能要件

| ID | 要件 | 初期仕様 |
| --- | --- | --- |
| M01 | 対象画面からまとめ作成を開始 | 各画面のメニュー「投稿を選んでまとめる」、各投稿メニュー「まとめに追加」 |
| M02 | 複数選択 | タップで選択／解除。ヘッダー直下の固定欄に選択投稿を表示。スクロール・ページ追加・画面切替後も保持 |
| M03 | 対象投稿 | 公開kind 1・kind 1111。旧形式のkind 1返信とNIP-22のkind 1111返信・引用投稿を含む。返信は親ではなく返信投稿自体を選び、リポストは元投稿を選択。DM・非公開投稿は対象外 |
| M04 | 重複防止 | nevent文字列ではなくevent IDで一意化。同じ投稿の複数リレー受信・リポスト表示を統合 |
| M05 | 選択順序 | 選択した順。取り込み後は上下移動とドラッグで変更可能。表示順は本文の順序に反映 |
| M06 | 件数 | 初期値は最大50件。1件でも作成可。0件では引用投稿・記事作成の両操作を無効化 |
| M07 | nevent生成 | event IDを必須、著者と取得元リレーを可能な範囲で付与。1投稿につき1つのURIを独立段落で配置 |
| M08 | 記事編集 | タイトル、導入本文、引用ごとの説明、カバー、概要、トピックを編集できる |
| M09 | Matometr識別 | 公開イベントに`["t", "matometr"]`を1つ付ける。本文への自動追加は行わない（2026-10-06変更） |
| M10 | 下書き | 選択した投稿・順序・説明を通常記事と同じ下書きとして保存・復元できる |
| M11 | 閲覧 | 記事本文の引用位置で投稿カードを表示し、元投稿へ移動できる |
| M12 | 取得不能 | 元投稿が取得できなくても参照を保持。neventのコピーと再取得導線を表示し、公開を阻止しない |
| M13 | 投稿方法の選択 | ヘッダー下に「引用投稿」「記事作成」を表示し、同じ選択投稿・順序を各投稿画面に引き継ぐ |

上限50件はToriNosの初期提案であり、Nostrの規定ではない。MVPではAI要約、投稿全文の転載、元投稿の再配信、まとめ用kind 1の同時投稿、専用Matometrサービス画面は追加しない。記事タブの既存トピックフィルターから`matometr`を選べるようにする。

## 4. 利用フロー

### 4.1 通常記事・下書き

1. 記事一覧の「記事を書く」から新規作成。
2. 入力変更を記事下書きとして自己暗号化し、リレーへ自動保存。タイトル・本文の一方が未入力でも保存できる。何も入力していない新規下書きは残さない。
3. 戻る操作では最新revisionを保存して記事一覧へ戻る。失敗した場合は画面に留まり、再保存／編集継続／明示的な破棄を選べる。
4. 記事一覧の「下書き（件数）」から再開。タイトル未入力は「無題の記事」、更新日時、通常／Matometr／公開記事の編集を表示する。
5. 公開条件を満たしたら公開。受理状況に応じて公開完了または再送待ちへ進む。

下書き削除は一覧メニューから確認して行う。自動保存したデータも削除対象になる。「入力を破棄」は今回開いた時点へ戻す操作で、既存下書き自体の削除とは区別する。新規下書きでは作成前の空状態へ戻し、空の新規下書きは一覧に残さない。

### 4.2 対象画面から投稿方法を選ぶ

1. 「投稿を選んでまとめる」で選択モードへ入り、対象画面を閲覧しながら選ぶ。
2. ヘッダー直下に「N件選択中／引用投稿／記事作成」と横一列の選択投稿カードを固定表示。ヘッダーは選択モード中固定する。
3. 「記事作成」で選択集合から新規Matometr下書きを作成し、保存成功後にエディタへ移動する。「引用投稿」を選んだ場合は4.6の通常投稿フローへ進む。
4. タイトル・導入・引用ごとの説明を記入し、引用の順序や不要な投稿を調整する。
5. プレビューで引用カードを確認し、`#matometr`を付けた記事として公開する。

保存や遷移に失敗した場合は選択集合を維持する。成功時は同じdraft IDへ遷移するため、連打で下書きが増えない。選択UIの開始ボタンを再度押すと選択を保持して通常表示へ戻り、開き直すと同じ投稿・順序・追加先を復元する。不要な投稿は個別のチェックボックスまたは選択一覧の「解除」で外す。全選択解除ボタンは表示しない。記事追加モードの「キャンセル」は選択と追加先を破棄する。エディタから「投稿を追加」で選択画面を開く場合は、対象draft IDを保持して対象画面のどこからでも既存引用へ重複なく追加する。

選択中も通常の投稿カードを表示し、時刻下のチェックボックスで選択を変更する。カードタップで投稿を開き、画像・引用・リアクション・返信などの通常操作も利用できる。対象画面間の移動、フィードタブ変更、リレー切替、ジャーナルの日付・月・種類フィルター変更、プロフィールの表示ユーザー・投稿タブ変更後も同じアカウント内の選択を保持する。プロフィールの著者アイコンから別ユーザーへ移動でき、通常の戻る操作では選択を解除しない。アカウント切替時は選択をクリアする。

### 4.3 ヘッダー下の共通選択欄

```text
対象画面のヘッダー
────────────────────────────────────────────
3件選択中                 [引用投稿] [記事作成]
[① 著者アイコン 本文冒頭… ×] [② 本文冒頭… ×] →
────────────────────────────────────────────
ジャーナルの日付・カレンダー・種類フィルター
またはフィードの投稿一覧
```

- `MatometrSelectionBar`を対象5画面で再利用し、同じ選択集合を表示する。選択モード中は0件でも操作欄を表示し、「引用投稿」「記事作成」を両方無効化する。通常表示時は選択欄を出さない。全選択解除ボタンは固定欄・選択一覧のどちらにも置かない。開始ボタンの再タップは表示だけを閉じ、選択集合・順序・追加先・引き継ぎ識別子を保持する。記事追加モードの「キャンセル」は追加操作を終了する。取り込み中は開閉・選択解除を無効にする。
- 選択カードは横スクロールで、選択順番号・著者アイコン・本文冒頭・解除ボタンを表示する。縦に積み上げない。
- カードタップで投稿プレビューを開く。件数タップで選択全件のモーダルボトムシートを開き、並べ替え・個別解除・選択UIの開閉を行える。各投稿の左端には投稿者のユーザーアイコンを表示し、その右に選択順番号と本文冒頭を置く。アイコンと本文のどちらを押しても投稿プレビューを開く。一覧はスクロール可能にし、狭い画面でも見出しと閉じる操作を残す。0件は空状態を表示し、閉じる・スワイプによるシートの解除でも選択を保持する。並べ替えは先頭の「上へ」と末尾の「下へ」を無効化し、取り込み確定後の編集操作も無効化する。固定欄は狭幅の場合、引用投稿・記事作成を次の行に表示する。変更は全対象画面と各投稿画面への取り込み順に即時反映する。
- 件数は左詰め、投稿操作は右詰めにする。表示ラベルは「引用投稿」「記事作成」とし、押した時点では公開しない。件数ラベルの1行分の必要幅を折り返し判定に使い、大きい文字設定等で横並びが収まらない場合は件数と操作を2段に分け、折り返した操作も右詰めにしてラベルを切り詰めない。記事追加モードの「N件追加／キャンセル」も同じ配置にする。
- 投稿一覧は通常の投稿カードを維持し、選択モード中だけ時刻の下にチェックボックスと選択順番号を追加する。本文・画像・引用・返信・リアクション・メニューをそのまま利用でき、選択変更はチェックボックスで行う。kind 1とkind 1111の選択可否は投稿メニュー・チェックボックス・Coordinatorで共通の判定を使う。同一投稿が複数画面に現れた場合も番号・選択状態は共通。ジャーナルのリポスト・いいねも通常のアクティビティ行の時刻下にチェックボックスを置き、元kind 1・kind 1111投稿を選ぶ。元投稿未取得ではチェックを無効化して「未取得」と表示する。
- ジャーナルでは主ヘッダー直下、日付・カレンダー・種類フィルターより上に配置する。カレンダー開閉やフィルター操作で選択欄を隠さない。
- プロフィールでは画面上部の固定操作ヘッダー直下に配置し、バナー・自己紹介・投稿タブより上に保持する。既存の折りたたみヘッダーのフェード／重なりに選択欄を含めず、スクロール中も選択カードと2つの投稿操作を表示する。
- 検索ではヘッダー直下、検索入力欄とタブより上に固定選択欄を配置する。ヘッダーの開始ボタンで選択表示を開閉でき、検索結果の時刻下にもチェックボックスを表示する。クエリ変更・再検索・追加読み込み・ユーザータブへの切替でも選択を保持し、通常の検索画面とWebサイドパネルで同じ選択集合・引用投稿・記事作成・ボトムシート操作を使う。未ログイン時は共通コンポーネントの判定に従って選択UIを表示しない。
- 選択集合はAccountSession所有の共通Coordinatorで保持する。画面のViewModel破棄や取得リストの更新で選択を消さない。開閉では選択を保持し、個別解除・取り込み完了・記事追加の明示キャンセルで選択を消す。記事へ取り込む前の選択はメモリ内であり、プロセス終了後の復元対象にはしない。

### 4.4 ジャーナルの選択対象

ジャーナルは投稿そのものと、リポスト・いいねのアクティビティを混在表示するため、選択対象を正規化する。

| ジャーナルの行 | まとめへ追加する対象 |
| --- | --- |
| 投稿・kind 1の返信・kind 1111の返信 | 表示している投稿。返信の親投稿へ置き換えない |
| リポスト | リポスト先の元kind 1・kind 1111投稿 |
| したいいね・もらったいいね | いいね対象の元kind 1・kind 1111投稿。kind 7イベント自体は追加しない |
| その他のkind | 対象外。選択可能なチェックを出さず、対象外であることを示す |
| 参照先未取得のリポスト・いいね | 元投稿取得後に選択可能。取得中・失敗を表示し、未解決のまま追加しない |

元投稿の解決は既存の参照取得とキャッシュを再利用する。行のアクティビティIDではなく解決した元event IDで重複排除するため、フィードで選んだ投稿をジャーナルのいいね行から選んでも件数は増えない。非同期取得が完了しても、利用者がキャンセルした選択操作を後から追加しない。自分・他ユーザーのジャーナルで同じ選択規則を適用し、作成する記事の所有者は現在のログインアカウントとする。

### 4.5 マイプロフィール・ユーザープロフィール

両プロフィールの「投稿」「投稿と返信」タブから選択できる。公開kind 1・kind 1111は自分・他ユーザーを問わず同じ規則で追加し、リポストは元投稿を選ぶ。返信は返信投稿自体のevent ID・著者・本文を取り込み、親やルートのkindを追加対象の判定に使わない。プロフィール情報、ステータス、フォロー一覧自体は選択対象にしない。

フィードで2件選択→ユーザープロフィールで1件追加→マイプロフィールで1件追加→ジャーナルで1件追加、という移動でも1つの選択集合として5件を保持する。画面内に現在表示されていない選択投稿も固定欄に残す。閲覧先のユーザー変更はアカウント切替とは区別し、記事の著者・下書き所有者は常に現在のログインアカウントとする。

未ログインでユーザープロフィールを閲覧できる現行導線は維持する。まとめ作成の開始はログイン後とし、プロフィール閲覧だけでアカウント所有の選択状態を生成しない。Webのサイドパネル等で複数の対象画面を同時表示する場合もCoordinatorは1つとし、各画面の固定欄は同じ状態を観測する。取り込み中の無効化と二重作成防止も共有する。

### 4.6 引用投稿

「引用投稿」は通常の投稿シートを開き、選択順に引用データを取り込む。参照URLを入力欄へ直接挿入せず、通常の単一引用と同じ「引用」枠で各投稿の本文冒頭を表示する。複数引用のプレビュー欄は高さを制限してスクロール可能にし、文章の入力欄を残す。プレビュー用本文は1件500文字まで保持し、空本文は投稿IDで識別する。利用者は文章を追加・修正してから、通常投稿の公開操作でkind 1として送信する。送信時に選択順の`nostr:nevent...`を独立段落として本文へ組み立て、プレビュー文は送信しない。Matometr用の`#matometr`・`t=matometr`は自動付与しない。引用タグ等の送信規則は通常投稿の既存方針と整合させ、記事の引用通知方針とは別に扱う。

既存の通常投稿の引用入力は単一投稿用のため、順序付き複数参照を渡せる入力契約へ拡張する。選択結果は操作開始時にスナップショット化し、通常投稿シートへ一度だけ引き継ぐ。正常に入力状態へ取り込めた後に選択モードを終了し、起動・取り込み失敗時は選択を残す。起動中は「引用投稿」「記事作成」の両方を無効化し、異なる投稿画面の二重起動を防ぐ。

すでに通常投稿の入力・下書きがある場合は、それを無断で上書きしない。既存入力への参照追加または別投稿の作成を選べるようにし、同一event IDを重複挿入しない。取り込み後の離脱・保存は通常投稿の下書き方針に従う。引用データとプレビューもリレー下書き・セッション内の保留入力・絵文字設定からの復帰で保持する。引用だけの投稿も送信・下書き保存が可能で、下書き一覧には引用件数と本文冒頭を表示する。文字数表示・送信可否・取り込み時の検証には引用参照を含めた生成後本文の800文字上限を適用し、上限超過時に参照を黙って切り捨てない。

「既存入力へ追加」は既存の投稿種別・返信先・チャンネル・公開先を維持する。返信／チャンネルの入力である場合は「返信に追加」「チャンネル投稿に追加」と行き先を示し、kind 1の新規投稿と混同させない。「別投稿を作成」は常に返信先・チャンネルを持たない新規kind 1とする。

別投稿へ切り替える前に`ComposerSnapshot`をアカウントセッションのメモリへ退避する。本文、画像URLとメタデータ、絵文字、内容警告、返信・ルート・チャンネル参照、引用、選択リレー、元下書きID、カーソルを所有者付きで保持する。保存完了までは`clearPostContext`やViewModelのresetを呼ばない。失敗時は元入力・選択投稿を保持する。アップロード中・未アップロード画像あり・投稿送信中は入力切替を停止し、完了／再試行／画像削除後に操作できる。

退避した入力がある場合は、同じセッションで投稿シート・簡易コンポーザーを開いたときに確認ダイアログを表示し、「適用」「破棄」を選べる。「保留入力」の専用ボタンは置かない。複数ある場合は対象を選び、適用では本文・画像・返信先・チャンネル・引用・公開先・カーソルを復元し、破棄では選んだ保留入力だけを削除する。現在編集中の入力・引き継ぎ処理中の入力・リレー下書きは確認対象に含めない。アプリ終了やアカウント切替後の再開が必要な通常投稿は、既存のリレー下書き保存を使う。適用・破棄を選ぶまでは現在の入力を置き換えない。復帰時にも現在の入力があれば先に退避し、失敗時は切り替えない。退避レコードは元のリレー下書きを削除せず、復帰データがViewModelへ取り込まれた後に削除する。通常のリレー下書き一覧とは区別する。

引き継ぎには`handoffId`と対象の入力IDを付け、同一handoffを適用済みなら再挿入しない。新規引用入力の一時スナップショットと引き継ぎ済み記録を同じメモリ操作で確定してから選択を消費する。保存失敗では選択を残し、画面遷移失敗では同じ入力IDを再度開く。退避・復帰・取り込みは共通の操作ロックで直列化する。通常投稿の一時スナップショットはリレー下書きと区別し、自動でリレーへ送らない。

記事エディタの「投稿を追加」はエディタ上にシートを開く。貼り付けた文章からURL内・`nostr:`有無を問わないnote/nevent（16進IDは入力全体の場合のみ）を拾い、利用者のリレー、見つからなければneventのリレーヒント（最大2件）から取得する。取得でき、kind 1/1111で、まだ含まれていない投稿だけを「N件追加」の対象にし、naddr・npub・nprofileは対象外として件数を示す。取得できない投稿は追加しない。追加は編集操作として下書きに反映し、エディタを離れない。シートの「タイムラインから選ぶ」は以下の選択モードを開始してフィードへ移り、選択欄に追加先の記事名を表示し、「キャンセル」で元の下書きへ戻る。
選択モードからの追加は既存記事への追加専用として扱う。その場合は「N件追加／キャンセル」を表示し、新規の引用投稿・記事作成とは分ける。開始前に元記事を保存し、対象draft IDとrevisionを固定する。追加結果は重複除去・合計50件・本文長・Markdown境界を検証し、revisionが一致した場合のみ原子的に保存する。不一致では競合を表示し、再読込してやり直す。キャンセルしても元記事の文章・引用・順序を変更しない。

自由Markdownではコード・画像内を除いた既存参照を解析し、未挿入のURIだけを独立段落として追記する。本文中の手入力のハッシュタグは保持する。既存本文全体の再生成は行わず、6.1の検証に失敗した場合は本文も選択も変更しない。

## 5. 記事投稿画面のUI設計

添付画像では固定高の本文欄が画面の大半を占め、保存状況が表示されず、カバー・概要・トピックの確認に長いスクロールが必要になる。以下の構成へ変更する。

```text
← 記事を書く                         …   公開
  アカウント表示     下書きを保存しました 22:55
       編集                     プレビュー
────────────────────────────────────────────
タイトル *                            0/200
本文 *                Markdown      全画面編集
[見出し] [太字] [リンク] [画像]
本文を入力…              内容に応じた高さの編集欄
                                    0/10,000

引用した投稿（Matometrの場合）       ＋投稿を追加
  1  投稿カード   説明欄       ↑ ↓ 削除
  2  投稿カード   説明欄       ↑ ↓ 削除

タグ（常時表示・任意）
  [#matometr ×] [#nostr ×] [＋タグを追加]
  追加入力欄の先頭に固定の「#」を表示

記事の設定                            展開／閉じる
  カバー画像・概要・公開先
────────────────────────────────────────────

```

- ヘッダーの主操作は「公開／更新」。狭い画面では保存時刻を2段目に出し、リレー設定は「…」または記事の設定に移す。
- 本文欄は空時に6〜8行程度。内容に応じて増やし、画面高を超える長文は全画面編集へ移れる。420dp固定を廃止する。
- Markdown操作は選択文字列／カーソル位置へ挿入する。本文文字列とカーソル・選択範囲を保持する編集状態を分ける。
- カバー・概要・公開先は折りたたみ可能。エラーを含む設定項目は自動で展開する。
- タグは本文・引用一覧の下に常時表示し、設定の折りたたみ対象から外す。登録済みタグは`#`付きチップで表示し、`#matometr`を含めて削除ボタンで外せる。まとめ記事の`#matometr`は初期表示するが、削除後は下書きの再読み込み・プレビュー・公開で自動復活させない。削除しても引用と編集形式を保持し、本文末尾へのハッシュタグの自動追加はタグ登録の有無にかかわらず行わない。利用者が文章中に入力した同名ハッシュタグは保持する。
- 「タグを追加」で入力欄を開く。先頭に固定の`#`を表示し、追加ボタン・Enter・空白・カンマで確定する。自動付与についての案内文は表示しない。日本語変換中の空白では確定しない。入力途中も既存のトピック入力として下書きに保存し、公開・画面離脱・プレビュー切替で失わない。タグは最大20個、入力は合計500文字まで。プレビューと公開タグも同じ生成処理を使う。
- プレビューは編集と同じ入力スナップショットから生成し、詳細画面と同じMarkdown・引用描画を使う。5.1の引用取得Controllerを接続し、空Mapだけで描画する現行実装を置き換える。切替後もカーソル・スクロール位置を保つ。
- 公開不能の理由を「タイトルを入力してください」「本文を入力してください」「投稿先リレーを設定してください」等で表示する。必須入力と保存可否を結び付けない。
- 保存状態は「未保存／保存中／保存済み（時刻）／保存できませんでした」。ネットワーク接続状態とは別に表示する。
- 画像アップロード中は公開を停止し、操作中の表示を出す。下書きには完了したURLのみ保存する。下書き保存と外部への画像アップロードは別操作であり、保存だけではアップロードしない。
- Android・iOSではキーボードとセーフエリアを避ける。Webの広い画面では編集／プレビューの2列表示を提供する。
- タップ対象は原則48dp、アイコンには読み上げラベルを付ける。並べ替えはドラッグ以外に上下ボタンも用意する。

### 5.1 編集プレビューの引用取得

`ArticleQuotePreviewController`をエディタのAccountSessionに結び付け、本文の非コード領域から抽出した参照集合を観測する。選択時に検証済みの元イベントをメモリ内で引き継いで即時表示し、下書き再開時はキャッシュから表示して未取得分を取得する。元投稿全文は下書きStoreには保存しない。

event IDをキーに`Loading / Ready / Unavailable`を保持し、著者プロフィールは既存Repositoryから取得・観測する。未取得分は短いdebounce後にまとめてFetchし、1投稿ごとの常時購読を作らない。本文から除外されたIDの取得を停止し、取得世代を比較して古い応答を現在の参照へ混ぜない。詳細・プレビューは同じ参照抽出と取得方針を使い、ミュート・削除の表示規則も共有する。

取得失敗はnevent表示・コピー・再試行を出す。未取得だけを理由に公開を止めない。プレビューを閉じた場合、本文全画面編集へ移った場合、エディタを離脱した場合、セッションが変わった場合は購読とプロフィール観測を停止する。プレビューを再度開けばキャッシュから再開する。カードから元投稿・著者へ遷移できるコールバックを接続する。

## 6. 本文と引用の編集モデル

初期版のMatometrは **導入Markdown + 順序付き引用ブロック** の構造にする。通常記事は自由なMarkdown本文のみ。Matometrの本文欄には導入文章を表示し、引用と引用ごとの説明は下の一覧で編集する。

```text
serializeArticleContent(draft):
  導入Markdown
  空行 + nostr:nevent（投稿1）+ 空行 + 投稿1の説明Markdown
  空行 + nostr:nevent（投稿2）+ 空行 + 投稿2の説明Markdown
  …
  空行 + #matometr
```

投稿の並べ替えで説明も一緒に移動する。削除は当該参照と説明を削除し、導入文章に触れない。本文を自動生成してから手編集した内容を再生成で上書きする実装は避ける。保存・プレビュー・公開で同じserializerを使い、生成後の全体文字数を検証する。

公開済みMatometrの編集時はネットワーク上の本文を正とする。同じセッション内の編集アーカイブ参照が指す公開event IDが取得した最新版と一致し、構造から生成した本文・タグも一致する場合に限り、保存した構造を新しい編集下書きへ復元する。アーカイブがない・ID不一致・整合性検証失敗の場合は自由Markdownとして読み込み、他クライアントの本文を推測して構造化しない。最新版を確認できない場合は編集を下書きとして保存できるが、構造の採用と更新公開は確認できるまで保留する。

`#matometr`をタグ欄から削除していない場合に限り、`t=matometr`を維持する。削除状態は下書きの`matometrTagEnabled`に保存し、編集形式の切替でも保持する。自由編集（画面上は「本文に直接書く」）へ切り替える場合は生成結果を一度コピーして本文を正とする。「カードで並べる」へ戻す操作では、非コード領域で参照だけの行を引用、最初の引用より前を導入文、各引用の後ろを説明として分解する。文中・リスト・引用ブロック内の参照や同じ投稿の重複参照がある場合、または分解後の描画結果が元と一致しない場合は、行番号付きの理由を示して変換しない（`toStructuredMatometr`）。同じセッション内の公開後アーカイブも自由Markdownモードで更新し、古い構造を復元しない。本文へのハッシュタグの自動追加は行わず、利用者が入力したハッシュタグは末尾行を含めて削除しない。

構造化モードで引用が0件になった場合、Matometrとしての公開を止める。「通常記事に変更」で導入本文と設定を保持し、引用一覧と自動ハッシュタグを外せる。自由MarkdownのMatometrも公開時に本文の有効なイベント参照が1件以上あることを検証する。コードブロック内のURIは引用件数に含めない。

### 6.1 Markdownと引用の境界検証

引用追加・プレビュー・公開は、同じ`ArticleMarkdownBoundaryValidator`と参照抽出器を使用する。現行パーサーのコードフェンス判定もこの契約へ合わせる。行頭最大3空白のバッククォート／チルダ3個以上を開始フェンスとし、同じ文字で開始長以上のフェンスを閉じとして扱う。インデントコード・インラインコード・画像内のURIは自動引用候補に含めない。

構造化モードでは導入文と各説明を個別検証し、閉じていないフェンスがあれば、対象入力に「コードブロックを閉じてください」を表示する。生成結果でも、管理対象の全参照が意図した順序で非コードの独立段落として解析できることを検証する。導入文・説明が本文末尾にあっても同じ規則とする。通常記事は手動引用を含め既存の自由編集を維持する。

自由Markdownへの追加はまず既存本文のフェンスが閉じていることを検証し、追加後に各新規URIが非コード領域へ出現することを確認する。失敗時は追記を行わず、修正可能なエラーを返す。コードを自動で閉じたり利用者の文章を黙って書き換えたりしない。

途中の未閉じフェンスを含む編集内容も下書き保存できる。構造化プレビューでは本文の検証エラーを表示し、引用一覧のカードは別領域で表示する。公開・引用の追加確定は検証が通るまで止める。本文中の取得不能URIと、構文によってコードに巻き込まれたURIは別の状態として扱う。

## 7. Nostr公開形式

### 7.1 記事イベント

公開は通常記事と同じkind 30023を使用する。Matometr専用kindや独自リレーは導入しない。記事の編集先は`30023:<pubkey>:<d>`。新規下書き作成時に記事用`d`を確定し、公開失敗・再試行でも変更しない。更新は既存`d`と初回`published_at`を維持する。[NIP-23](https://github.com/nostr-protocol/nips/blob/master/23.md)

```json
{
  "kind": 30023,
  "content": "今週気になった投稿を紹介します。\n\nnostr:nevent1...\n\nこの投稿についての説明。\n\nnostr:nevent1...\n\n#matometr",
  "tags": [
    ["d", "torinos-<stable-identifier>"],
    ["title", "今週のNostrまとめ"],
    ["summary", "気になった投稿をまとめました"],
    ["published_at", "<first-published-unix-seconds>"],
    ["t", "matometr"],
    ["client", "ToriNos"]
  ]
}
```

上記は形式を示す例で、neventと時刻はプレースホルダー。署名・ID・pubkey・created_atは既存の署名処理で設定する。トピックは`#`を除いて保存する。`matometr`が有効な場合は先に確保して残り19枠をユーザー入力へ割り当て、削除済みの場合は20枠すべてを使える。重複除去後に上限を適用する。

### 7.2 neventと引用タグ

本文は`nostr:nevent...`形式とする。nevent内部はevent IDを必須とし、著者と取得元リレーを任意情報として扱う。タグや取得フィルターでevent IDを扱う場合はhexを使用する。[NIP-19](https://github.com/nostr-protocol/nips/blob/master/19.md) / [NIP-27](https://github.com/nostr-protocol/nips/blob/master/27.md)

- リレーヒントは実際に元イベントを取得した公開リレーから最大2つを選ぶ。記事の投稿先を元投稿の所在として推測しない。
- hintがない場合もevent IDと著者だけで生成できる。TLVに入れられない長いURLは省略し、記事生成そのものを失敗させない。
- 初期版では元著者への大量通知を避けるため、自動の`p`・`q`・返信用`e`タグは付けない。本文だけで引用を表示できる。
- 将来引用通知を追加する場合は、ユーザーが有効にした参照だけへ`q`を付ける。本文で削除した参照のタグを残さない。

引用取得はキャッシュ優先、続いて有効な閲覧リレーへevent IDをまとめて問い合わせる。本文のhintは参照情報として保持し、通常リレーで未取得のものだけ、利用者の接続方針に従って追加取得する。50件それぞれに常時購読・無制限接続を作らない。取得済みイベントはID・署名を検証し、author hintだけを本人性の根拠にしない。

## 8. 記事下書きと保存先

記事下書きそのものをリレーに保存する。専用のSQLite・IndexedDB・ファイル保存は追加しない。この方針は「保存は記事側の下書きにすれば端末での永続化は不要」というユーザー指定を優先したもので、旧版の端末内DB案を置き換える。

`ArticleDraft`は所有者、draft ID、安定した記事識別子、リレー下書きの識別子、編集開始時の公開event ID、初回公開時刻、モード、タイトル・概要・本文・カバー・トピック、引用の順序と説明、更新時刻とrevisionを扱う。編集中の比較用baselineはViewModelのメモリだけに保持する。

### 8.0 リレーへの下書き保存

[NIP-37](https://github.com/nostr-protocol/nips/blob/master/37.md)に沿って、署名前のkind 30023記事をJSONにし、既存の`AccountSigner.encryptToSelf`で自己宛NIP-44暗号化してkind 31234のcontentへ入れる。

```text
kind: 31234
タグ: d=<記事下書きの固定識別子>, k=30023, client=ToriNos
content: 自己暗号化した署名前の記事JSON
  pubkey / created_at / kind=30023 / tags / content
  torinos: 本文・引用説明を除いたArticleDraftの編集メタデータ
  torinosContentLayout: contentから導入文・引用説明を復元する範囲情報
```

- 通常投稿用kind 31234と記事用を`k=30023`およびpayload形式で区別する。通常投稿の下書き一覧では記事を解釈しない。
- 保存先は現在のアカウントで書き込みが許可されるリレー。取得は同じアカウントの有効リレーと書き込みリレーから行う。kind 10013の専用private relay設定への対応は今後の拡張とする。
- 1件以上のリレーからOK受理を確認したときにだけ保存済みと表示する。全拒否・タイムアウト・接続障害では入力を保持し、保存失敗を表示する。
- 入力が10秒止まったら保存を開始し、入力が続いても最初の未保存変更から60秒以内に保存する。保存済みの内容と同じなら送信しない。「今すぐ保存」、離脱、バックグラウンド移行、アカウント切替前にもflushする。未閉じMarkdownや未入力タイトルは下書き保存を阻止しない。
- 同じ下書きの更新は同じ外側dを使い、created_atを前回より大きくする。同秒内なら次秒まで待ち、時刻異常では送信を中止する。
- 一覧は作者・kind 31234・k=30023で取得し、dごとの最新版を採用する。1件以上のリレーでEOSEまで取得できれば一覧を出し、取得できなかったリレーは一覧上に警告として示す（そこにだけある下書きは欠けるか古い可能性がある）。どのリレーでも取得が完了しない場合は空一覧と断定せずエラーにする。最大取得件数は1,000件。
- 削除は同じdへ空contentの最新版を送る。新しい空contentを優先し、古い本文が別リレーから届いても一覧へ復活させない。
- 本文・引用説明は標準contentに一度だけ保存し、範囲情報と省略された改行・空白から編集入力を復元する。本文を重複保存する旧payloadも読み込める。暗号化前にUTF-8のJSONがNIP-44の65,535バイト以内であることを確認し、超過時は入力を保持して保存エラーを表示する。
- 復号・復元できない下書きは個別に一覧のエラーとして表示し、正常な下書きの取得・再開を続ける。壊れた元イベントは削除しない。
- `torinos`拡張を復元した本文・タグとの一致を検証して引用順・説明を復元する。他クライアントの標準unsigned記事下書きも読み込み、構造情報がなければ自由Markdownとして扱う。既存の外側dを維持して更新する。
- 元投稿全文、プロフィール、秘密鍵、画像の未アップロードbytesは下書きへ複製しない。画像はアップロード済みURLだけ保存する。

### 8.1 セッション内の一時状態

`ArticleDraftStore`はAccountSession所有のメモリ状態を直列化する。下書きの追加・変更・削除だけを`ArticleDraftRepository`経由でリレーに反映し、受理確認後にメモリを更新する。次の状態は端末内へ永続化せず、リレー下書きpayloadにも含めない。

| 状態 | 用途 | 保持範囲 |
| --- | --- | --- |
| 公開試行 | 署名済み記事・対象revision・リレー別の受理結果・Superseded | 同じAccountSession内 |
| 編集アーカイブ参照 | 受理済み試行を参照し、その場で構造化再編集する | 同じAccountSession内 |
| 記事Identity・公開lock | 初回公開時刻・既知の版の時刻・同じ記事の同時送信防止 | 同じAccountSession内。初回公開時刻は記事下書きにも反映 |
| 通常投稿の退避・handoff | 別投稿への切替と、重複取り込み防止 | 同じAccountSession内 |

メモリ内revisionの比較で同じセッションの古い保存を防ぐ。リレーは端末間のCASや分散lockを提供しないため、別タブ・別端末の同時編集にはNostrの最新版選択規則が適用される。端末内DBを使った排他・容量管理・ローカル保存データ削除画面は追加しない。

### 8.2 アカウント切替と再開

切替・ログアウト・削除の前に入力を凍結し、開始済みの画像アップロード・公開処理を待ち、記事下書きをリレーへflushする。保存失敗・待機タイムアウトなら元のActiveセッション、入力、選択を保ち、凍結を解除する。旧所有者の下書きを新所有者へ保存しない。

切替成功やアプリ終了後の復元元は、リレーに保存できた記事下書きである。公開待ちイベント・通常投稿の保留入力・メモリ内アーカイブは復元対象にしない。既存の通常投稿下書き保存は維持する。

公開記事の更新では、編集開始時のbaseEventIdと取得した最新版を比較する。相違・取得不能では下書きを保持し、最新版を見る／別記事にする／確認して更新する、を選べる。通常のログアウト・鍵の削除で、記事下書きの削除イベントを一括送信しない。

## 9. 公開・再送

1. 本文・Markdown境界・必須項目・カバーHTTPS・HTML禁止・公開先を検証し、記事下書きの保存を確認する。
2. 安定したdで記事を署名する。初回published_atを記事下書きへ反映し、署名済み記事と送信先はセッションのメモリへ保持してから送信する。
3. リレー別に`Pending / Accepted / Rejected / Unknown`を表示する。受理が不明なら未公開と断定しない。
4. 同じセッション内の再送は同じ署名済みイベントを使う。現在書き込みが許可される未受理リレーへだけ送る。
5. 受理結果と編集アーカイブ参照を先にメモリへ確定する。その後、全対象が受理した場合、別操作で対応revisionの記事下書きへ空contentを送って削除する。新しい編集revisionがある場合は削除しない。一部公開では下書きを残す。
6. 公開後の下書き削除が失敗しても、記事の受理済み記録とアーカイブ参照をメモリで保持し、「公開済み・下書き削除失敗」と表示する。「下書きの削除を再試行」は削除だけを行い、記事を再署名・再送しない。新しい編集revisionは再試行でも削除しない。

応答不明後も編集を続けられる。修正版を公開するときは同じセッションのaddress lockを取得し、旧試行をSupersededにして旧版の新しい再送を止める。旧版の遅い完了は新版の状態を巻き戻さない。公開先と、旧版が残る可能性のある除外先を確認画面に表示する。

修正版のcreated_atは既知の最大時刻より大きくし、次秒まで待つ。初回published_atは記事下書きに保持した値を再利用する。セッション終了後は署名済み試行を保持しないため、再開は記事下書きから行い、再公開では新しく署名する。公開済み記事の再編集ではリレー上の本文を正とし、メモリ内の一致する編集構造がなければ自由Markdownを使う。

### 12.1 レビューで修正した点

- 保存完了時に追加入力があれば「保存済み」にしない。debounce取消しで実行中の保存を中断しない。
- 保存・取得を記事のリレー下書きへ集約し、端末内の二重保存をしない。
- リレー取得が不完全な場合を空一覧と扱わない。復号不能な下書きは個別に表示し、正常な下書きの一覧を妨げず、元イベントを削除しない。
- 全受理の記事は下書き削除より先に受理結果を保持する。削除失敗の再試行は記事を再送せず、新しい編集も消さない。
- 保存済みの通常記事を空入力にした際の削除失敗は保存エラーとして表示し、離脱を止める。削除中の追加入力は消さない。
- 空contentをdごとの最新版選択に含め、削除後に古い版を復元しない。
- 標準unsigned記事の読み込みと、整合したToriNos編集構造の復元を分ける。
- 初回公開時刻を記事下書きに反映し、アプリ終了後の再開でも維持する。
- アカウント削除の既存プロフィール公開は、入力保存の成功後に実行する。
- 応答不明の再送拒否で前回の結果を未公開と断定しない。
- 通常本文の字下げを保持し、自由Markdownにも50件上限と未閉じフェンス検証を適用する。
- 古いプレビュー取得の完了が新しい取得表示を消さない。
