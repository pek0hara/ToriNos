# 記事下書き・投稿画面改善・Matometr 統合設計

作成日: 2026-10-01。状態: 要件・設計案、未実装。
更新日: 2026-10-02。共通選択欄の2操作を確定し、レビュー指摘7点に対する保存・復旧・公開・入力引き継ぎの契約を追加。

## 1. 目的と要件の基準

記事を書きかけのまま保存・再開できるようにし、投稿画面を長文編集に適したUIへ改善する。同じエディタを使って、フィード・ジャーナル・マイプロフィール・ユーザープロフィールの投稿を複数選択し、各投稿の `nevent` をまとめた `#matometr` 記事を公開できるようにする。以降、この4画面を「対象画面」と呼ぶ。

本書では **Matometr = 複数のNostr投稿を、順序と編集者の文章を付けて紹介するまとめ記事** と定義する。外部のMatometr固有仕様は今回の検索では確認できていないため、ユーザーの依頼とNostrの標準仕様を基準にしたToriNosの設計案である。既存サービスとの完全互換を保証するものではない。固有仕様が提示された場合は公開形式を照合する。

| 区分 | 内容 |
| --- | --- |
| 依頼に基づく必須要件 | 記事下書き、投稿UI改善、対象4画面共通の複数選択、ヘッダー直下の選択投稿表示、neventをまとめた記事、`#matometr` |
| 本書で提案する初期仕様 | 端末内自動保存、アカウント別保存、kind 1の選択、並べ替え、kind 30023で公開 |
| 初期リリース後の拡張 | 暗号化リレー下書き同期、kind 1以外の選択、引用通知のオプション |

実装は本依頼の対象外。本書は実装時の判断、状態境界、受け入れ条件をまとめる。

## 4. 利用フロー

### 4.1 通常記事・下書き

1. 記事一覧の「記事を書く」から新規作成。
2. 入力変更を端末に自動保存。タイトル・本文が未入力でも保存できる。
3. 戻る操作では最新revisionを保存して記事一覧へ戻る。失敗した場合は画面に留まり、再保存／編集継続／明示的な破棄を選べる。
4. 記事一覧の「下書き（件数）」から再開。タイトル未入力は「無題の記事」、更新日時、通常／Matometr／公開記事の編集を表示する。
5. 公開条件を満たしたら公開。受理状況に応じて公開完了または再送待ちへ進む。

下書き削除は一覧メニューから確認して行う。自動保存したデータも削除対象になる。「入力を破棄」は今回開いた時点へ戻す操作で、既存下書き自体の削除とは区別する。新規下書きでは作成前の空状態へ戻し、空の新規下書きは一覧に残さない。

### 4.2 対象画面から投稿方法を選ぶ

1. 「投稿を選んでまとめる」で選択モードへ入り、対象画面を閲覧しながら選ぶ。
2. ヘッダー直下に「N件選択中／引用投稿／記事作成」と横一列の選択投稿カードを固定表示。ヘッダーは選択モード中固定する。
3. 「記事作成」で選択集合から新規Matometr下書きを作成し、保存成功後にエディタへ移動する。「引用投稿」を選んだ場合は4.6の通常投稿フローへ進む。
4. タイトル・導入・引用ごとの説明を記入し、引用の順序や不要な投稿を調整する。
5. プレビューで引用カードを確認し、`#matometr`を付けた記事として公開する。

保存や遷移に失敗した場合は選択集合を維持する。成功時は同じdraft IDへ遷移するため、連打で下書きが増えない。選択モードをキャンセルすると選択を破棄する。エディタから「投稿を追加」で選択画面を開く場合は、対象draft IDを保持して対象画面のどこからでも既存引用へ重複なく追加する。

選択中のカードタップは選択操作とし、リアクション・返信などの通常操作は選択UIから外す。メニュー「元投稿を開く」で閲覧は可能。対象画面間の移動、フィードタブ変更、リレー切替、ジャーナルの日付・月・種類フィルター変更、プロフィールの表示ユーザー・投稿タブ変更後も同じアカウント内の選択を保持する。プロフィールの著者アイコンから別ユーザーへ移動でき、通常の戻る操作では選択を解除しない。アカウント切替時は選択をクリアする。

### 4.3 ヘッダー下の共通選択欄

```text
対象画面のヘッダー
────────────────────────────────────────────
3件選択中                 [引用投稿] [記事作成]
[① 著者アイコン 本文冒頭… ×] [② 本文冒頭… ×] →
────────────────────────────────────────────
ジャーナルの日付・カレンダー・種類フィルター
またはフィードの投稿一覧
```

- `MatometrSelectionBar`を対象4画面で再利用し、同じ選択集合を表示する。選択モード中は0件でも操作欄を表示し、「引用投稿」「記事作成」を両方無効化する。通常表示時は選択欄を出さない。
- 選択カードは横スクロールで、選択順番号・著者アイコン・本文冒頭・解除ボタンを表示する。縦に積み上げない。
- カードタップで投稿プレビューを開く。件数タップで選択全件の一覧シートを開き、並べ替え・個別解除・全選択解除・選択モード終了を行える。固定欄には全選択解除のボタンを置かず、2つの投稿操作を優先する。変更は全対象画面と各投稿画面への取り込み順に即時反映する。
- 表示ラベルは「引用投稿」「記事作成」とし、押した時点では公開しない。大きい文字設定等で横並びが収まらない場合は件数と操作を2段に分け、ラベルを切り詰めない。
- 投稿一覧内の選択済み投稿にもチェックと番号を表示する。同一投稿が複数画面に現れた場合も番号・選択状態は共通。
- ジャーナルでは主ヘッダー直下、日付・カレンダー・種類フィルターより上に配置する。カレンダー開閉やフィルター操作で選択欄を隠さない。
- プロフィールでは画面上部の固定操作ヘッダー直下に配置し、バナー・自己紹介・投稿タブより上に保持する。既存の折りたたみヘッダーのフェード／重なりに選択欄を含めず、スクロール中も選択カードと2つの投稿操作を表示する。
- 選択集合はAccountSession所有の共通Coordinatorで保持する。画面のViewModel破棄や取得リストの更新で選択を消さない。取り込み完了または明示キャンセルで終了する。記事へ取り込む前の選択はメモリ内であり、プロセス終了後の復元対象にはしない。

### 4.4 ジャーナルの選択対象

ジャーナルは投稿そのものと、リポスト・いいねのアクティビティを混在表示するため、選択対象を正規化する。

| ジャーナルの行 | まとめへ追加する対象 |
| --- | --- |
| 投稿・kind 1の返信 | 表示している投稿 |
| リポスト | リポスト先の元kind 1投稿 |
| したいいね・もらったいいね | いいね対象の元kind 1投稿。kind 7イベント自体は追加しない |
| kind 1111の返信・その他のkind | 初期版は対象外。選択可能なチェックを出さず、対象外であることを示す |
| 参照先未取得のリポスト・いいね | 元投稿取得後に選択可能。取得中・失敗を表示し、未解決のまま追加しない |

元投稿の解決は既存の参照取得とキャッシュを再利用する。行のアクティビティIDではなく解決した元event IDで重複排除するため、フィードで選んだ投稿をジャーナルのいいね行から選んでも件数は増えない。非同期取得が完了しても、利用者がキャンセルした選択操作を後から追加しない。自分・他ユーザーのジャーナルで同じ選択規則を適用し、作成する記事の所有者は現在のログインアカウントとする。

### 4.5 マイプロフィール・ユーザープロフィール

両プロフィールの「投稿」「投稿と返信」タブから選択できる。公開kind 1は自分・他ユーザーを問わず同じ規則で追加し、リポストは元投稿を選ぶ。kind 1111など初期対象外の投稿は選択不可とする。プロフィール情報、ステータス、フォロー一覧自体は選択対象にしない。

フィードで2件選択→ユーザープロフィールで1件追加→マイプロフィールで1件追加→ジャーナルで1件追加、という移動でも1つの選択集合として5件を保持する。画面内に現在表示されていない選択投稿も固定欄に残す。閲覧先のユーザー変更はアカウント切替とは区別し、記事の著者・下書き所有者は常に現在のログインアカウントとする。

未ログインでユーザープロフィールを閲覧できる現行導線は維持する。まとめ作成の開始はログイン後とし、プロフィール閲覧だけでアカウント所有の選択状態を生成しない。Webのサイドパネル等で複数の対象画面を同時表示する場合もCoordinatorは1つとし、各画面の固定欄は同じ状態を観測する。取り込み中の無効化と二重作成防止も共有する。

### 4.6 引用投稿

「引用投稿」は通常の投稿シートを開き、選択順に並べた`nostr:nevent...`を独立段落として取り込む。利用者は文章を追加・修正してから、通常投稿の公開操作でkind 1として送信する。Matometr用の`#matometr`・`t=matometr`は自動付与しない。引用タグ等の送信規則は通常投稿の既存方針と整合させ、記事の引用通知方針とは別に扱う。

既存の通常投稿の引用入力は単一投稿用のため、順序付き複数参照を渡せる入力契約へ拡張する。選択結果は操作開始時にスナップショット化し、通常投稿シートへ一度だけ引き継ぐ。正常に入力状態へ取り込めた後に選択モードを終了し、起動・取り込み失敗時は選択を残す。起動中は「引用投稿」「記事作成」の両方を無効化し、異なる投稿画面の二重起動を防ぐ。

すでに通常投稿の入力・下書きがある場合は、それを無断で上書きしない。既存入力への参照追加または別投稿の作成を選べるようにし、同一event IDを重複挿入しない。取り込み後の離脱・保存は通常投稿の下書き方針に従う。生成後本文に既存の通常投稿の入力上限・送信検証を適用し、上限超過時に参照を黙って切り捨てない。

「既存入力へ追加」は既存の投稿種別・返信先・チャンネル・公開先を維持する。返信／チャンネルの入力である場合は「返信に追加」「チャンネル投稿に追加」と行き先を示し、kind 1の新規投稿と混同させない。「別投稿を作成」は常に返信先・チャンネルを持たない新規kind 1とする。

別投稿へ切り替える前に`ComposerSnapshot`を8章の専用Storeへ保存する。本文、画像URLとメタデータ、絵文字、内容警告、返信・ルート・チャンネル参照、引用、選択リレー、元下書きID、カーソルを所有者付きで保持する。保存完了までは`clearPostContext`やViewModelのresetを呼ばない。失敗時は元入力・選択投稿を保持する。アップロード中・未アップロード画像あり・投稿送信中は入力切替を停止し、完了／再試行／画像削除後に操作できる。

退避した入力は通常投稿の「保留中の入力」から復帰でき、アプリ再起動後も復元する。新しい引用投稿の取消・公開後に復帰導線を表示するが、別の入力を自動で置き換えない。復帰時にも現在の入力があれば先に退避し、失敗時は切り替えない。退避レコードは元のリレー下書きを削除せず、復帰データがViewModelへ取り込まれた後に削除する。通常のリレー下書き一覧とは区別する。

引き継ぎには`handoffId`と対象の入力IDを付け、同一handoffを適用済みなら再挿入しない。新規引用入力の復旧用スナップショットと引き継ぎ済み記録を原子的に保存してから選択を消費する。保存失敗では選択を残し、画面遷移失敗では同じ入力IDを再度開く。退避・復帰・取り込みは共通の操作ロックで直列化する。アカウント切替の事前保存対象にはこれらの通常投稿スナップショットも含める。

記事エディタから開始した「投稿を追加」は既存記事への追加専用として扱う。その場合は「N件追加／キャンセル」を表示し、新規の引用投稿・記事作成とは分ける。開始前に元記事を保存し、対象draft IDとrevisionを固定する。追加結果は重複除去・合計50件・本文長・Markdown境界を検証し、revisionが一致した場合のみ原子的に保存する。不一致では競合を表示し、再読込してやり直す。キャンセルしても元記事の文章・引用・順序を変更しない。

自由Markdownではコード・画像内を除いた既存参照を解析し、未挿入のURIだけを独立段落として追記する。自動管理している末尾`#matometr`行がある場合はその直前へ挿入する。既存本文全体の再生成は行わず、6.1の検証に失敗した場合は本文も選択も変更しない。

## 5. 記事投稿画面のUI設計

添付画像では固定高の本文欄が画面の大半を占め、保存状況が表示されず、カバー・概要・トピックの確認に長いスクロールが必要になる。以下の構成へ変更する。

```text
← 記事を書く                         …   公開
  アカウント表示     下書きを保存しました 22:55
       編集                     プレビュー
────────────────────────────────────────────
タイトル *                            0/200
本文 *                Markdown      全画面編集
[見出し] [太字] [リンク] [画像]
本文を入力…              内容に応じた高さの編集欄
                                    0/100,000

引用した投稿（Matometrの場合）       ＋投稿を追加
  1  投稿カード   説明欄       ↑ ↓ 削除
  2  投稿カード   説明欄       ↑ ↓ 削除

記事の設定                            展開／閉じる
  カバー画像・概要・トピック・公開先
  #matometr（まとめ記事に自動で付与）
────────────────────────────────────────────
公開できない理由／保存エラーがあればここに表示
```

- ヘッダーの主操作は「公開／更新」。狭い画面では保存時刻を2段目に出し、リレー設定は「…」または記事の設定に移す。
- 本文欄は空時に6〜8行程度。内容に応じて増やし、画面高を超える長文は全画面編集へ移れる。420dp固定を廃止する。
- Markdown操作は選択文字列／カーソル位置へ挿入する。本文文字列とカーソル・選択範囲を保持する編集状態を分ける。
- カバー・概要・トピック・公開先は折りたたみ可能。エラーを含む設定項目は自動で展開する。
- プレビューは編集と同じ入力スナップショットから生成し、詳細画面と同じMarkdown・引用描画を使う。5.1の引用取得Controllerを接続し、空Mapだけで描画する現行実装を置き換える。切替後もカーソル・スクロール位置を保つ。
- 公開不能の理由を「タイトルを入力してください」「本文を入力してください」「投稿先リレーを設定してください」等で表示する。必須入力と保存可否を結び付けない。
- 保存状態は「未保存／保存中／保存済み（時刻）／保存できませんでした」。ネットワーク接続状態とは別に表示する。
- 画像アップロード中は公開を停止し、操作中の表示を出す。下書きには完了したURLのみ保存する。下書き保存と外部への画像アップロードは別操作であり、保存だけではアップロードしない。
- Android・iOSではキーボードとセーフエリアを避ける。Webの広い画面では編集／プレビューの2列表示を提供する。
- タップ対象は原則48dp、アイコンには読み上げラベルを付ける。並べ替えはドラッグ以外に上下ボタンも用意する。

### 5.1 編集プレビューの引用取得

`ArticleQuotePreviewController`をエディタのAccountSessionに結び付け、本文の非コード領域から抽出した参照集合を観測する。選択時に検証済みの元イベントをメモリ内で引き継いで即時表示し、下書き再開時はキャッシュから表示して未取得分を取得する。元投稿全文は下書きStoreには保存しない。

event IDをキーに`Loading / Ready / Unavailable`を保持し、著者プロフィールは既存Repositoryから取得・観測する。未取得分は短いdebounce後にまとめてFetchし、1投稿ごとの常時購読を作らない。本文から除外されたIDの取得を停止し、取得世代を比較して古い応答を現在の参照へ混ぜない。詳細・プレビューは同じ参照抽出と取得方針を使い、ミュート・削除の表示規則も共有する。

取得失敗はnevent表示・コピー・再試行を出す。未取得だけを理由に公開を止めない。プレビューを閉じた場合、本文全画面編集へ移った場合、エディタを離脱した場合、セッションが変わった場合は購読とプロフィール観測を停止する。プレビューを再度開けばキャッシュから再開する。カードから元投稿・著者へ遷移できるコールバックを接続する。

## 6. 本文と引用の編集モデル

初期版のMatometrは **導入Markdown + 順序付き引用ブロック** の構造にする。通常記事は自由なMarkdown本文のみ。Matometrの本文欄には導入文章を表示し、引用と引用ごとの説明は下の一覧で編集する。

```text
serializeArticleContent(draft):
  導入Markdown
  空行 + nostr:nevent（投稿1）+ 空行 + 投稿1の説明Markdown
  空行 + nostr:nevent（投稿2）+ 空行 + 投稿2の説明Markdown
  …
  空行 + #matometr
```

投稿の並べ替えで説明も一緒に移動する。削除は当該参照と説明を削除し、導入文章に触れない。本文を自動生成してから手編集した内容を再生成で上書きする実装は避ける。保存・プレビュー・公開で同じserializerを使い、生成後の全体文字数を検証する。

公開済みMatometrの編集時はネットワーク上の本文を正とする。8章の`ArticleEditArchive`の公開event IDが取得した最新版と一致し、構造から生成した本文・タグも一致する場合に限り、保存した構造を新しい編集下書きへ復元する。アーカイブがない・ID不一致・整合性検証失敗の場合は自由Markdownとして読み込み、他クライアントの本文を推測して構造化しない。最新版を確認できない場合は編集を下書きとして保存できるが、構造の採用と更新公開は確認できるまで保留する。

`t=matometr`と末尾ハッシュタグを維持する。自由編集へ切り替える場合は生成結果を一度コピーして本文を正とし、引用一覧への自動逆変換は行わない。公開後のアーカイブも自由Markdownモードで更新し、古い構造を復元しない。自動ハッシュタグは独立した末尾行として管理し、利用者が文章中に入力した同名ハッシュタグは削除しない。

構造化モードで引用が0件になった場合、Matometrとしての公開を止める。「通常記事に変更」で導入本文と設定を保持し、引用一覧と自動ハッシュタグを外せる。自由MarkdownのMatometrも公開時に本文の有効なイベント参照が1件以上あることを検証する。コードブロック内のURIは引用件数に含めない。

### 6.1 Markdownと引用の境界検証

引用追加・プレビュー・公開は、同じ`ArticleMarkdownBoundaryValidator`と参照抽出器を使用する。現行パーサーのコードフェンス判定もこの契約へ合わせる。行頭最大3空白のバッククォート／チルダ3個以上を開始フェンスとし、同じ文字で開始長以上のフェンスを閉じとして扱う。インデントコード・インラインコード・画像内のURIは自動引用候補に含めない。

構造化モードでは導入文と各説明を個別検証し、閉じていないフェンスがあれば、対象入力に「コードブロックを閉じてください」を表示する。生成結果でも、管理対象の全参照が意図した順序で非コードの独立段落として解析できることを検証する。導入文・説明が本文末尾にあっても同じ規則とする。通常記事は手動引用を含め既存の自由編集を維持する。

自由Markdownへの追加はまず既存本文のフェンスが閉じていることを検証し、追加後に各新規URIが非コード領域へ出現することを確認する。失敗時は追記を行わず、修正可能なエラーを返す。コードを自動で閉じたり利用者の文章を黙って書き換えたりしない。

途中の未閉じフェンスを含む編集内容も下書き保存できる。構造化プレビューでは本文の検証エラーを表示し、引用一覧のカードは別領域で表示する。公開・引用の追加確定は検証が通るまで止める。本文中の取得不能URIと、構文によってコードに巻き込まれたURIは別の状態として扱う。

## 7. Nostr公開形式

### 7.1 記事イベント

公開は通常記事と同じkind 30023を使用する。Matometr専用kindや独自リレーは導入しない。記事の編集先は`30023:<pubkey>:<d>`。新規下書き作成時に記事用`d`を確定し、公開失敗・再試行でも変更しない。更新は既存`d`と初回`published_at`を維持する。[NIP-23](https://github.com/nostr-protocol/nips/blob/master/23.md)

```json
{
  "kind": 30023,
  "content": "今週気になった投稿を紹介します。\n\nnostr:nevent1...\n\nこの投稿についての説明。\n\nnostr:nevent1...\n\n#matometr",
  "tags": [
    ["d", "torinos-<stable-identifier>"],
    ["title", "今週のNostrまとめ"],
    ["summary", "気になった投稿をまとめました"],
    ["published_at", "<first-published-unix-seconds>"],
    ["t", "matometr"],
    ["client", "ToriNos"]
  ]
}
```

上記は形式を示す例で、neventと時刻はプレースホルダー。署名・ID・pubkey・created_atは既存の署名処理で設定する。トピックは`#`を除いて保存し、自動`matometr`を先に確保して残り19枠をユーザー入力へ割り当てる。重複除去後に上限を適用し、末尾切り捨てで自動タグが落ちないようにする。

### 7.2 neventと引用タグ

本文は`nostr:nevent...`形式とする。nevent内部はevent IDを必須とし、著者と取得元リレーを任意情報として扱う。タグや取得フィルターでevent IDを扱う場合はhexを使用する。[NIP-19](https://github.com/nostr-protocol/nips/blob/master/19.md) / [NIP-27](https://github.com/nostr-protocol/nips/blob/master/27.md)

- リレーヒントは実際に元イベントを取得した公開リレーから最大2つを選ぶ。記事の投稿先を元投稿の所在として推測しない。
- hintがない場合もevent IDと著者だけで生成できる。TLVに入れられない長いURLは省略し、記事生成そのものを失敗させない。
- 初期版では元著者への大量通知を避けるため、自動の`p`・`q`・返信用`e`タグは付けない。本文だけで引用を表示できる。
- 将来引用通知を追加する場合は、ユーザーが有効にした参照だけへ`q`を付ける。本文で削除した参照のタグを残さない。

引用取得はキャッシュ優先、続いて有効な閲覧リレーへevent IDをまとめて問い合わせる。本文のhintは参照情報として保持し、通常リレーで未取得のものだけ、利用者の接続方針に従って追加取得する。50件それぞれに常時購読・無制限接続を作らない。取得済みイベントはID・署名を検証し、author hintだけを本人性の根拠にしない。

## 8. 下書きデータ・永続化

```kotlin
data class ArticleDraft(
    val schemaVersion: Int,
    val draftId: String,              // ローカル下書きID
    val ownerPubkey: String,
    val articleIdentifier: String,    // 公開用の安定したd
    val editingAddress: String?,      // 新規ならnull
    val baseEventId: String?,         // 編集開始時の公開版
    val originalPublishedAt: Long?,
    val mode: ArticleDraftMode,       // Regular / MatometrStructured / MatometrMarkdown
    val title: String,
    val summary: String,
    val bodyMarkdown: String,         // Structuredでは導入、それ以外は全文
    val coverImageUrl: String,
    val topics: List<String>,
    val references: List<MatometrReference>,
    val createdAt: Long,
    val updatedAt: Long,
    val revision: Long,
    val activePublishAttemptId: String?, // 公開履歴そのものは別レコード
)

data class MatometrReference(
    val eventId: String,
    val authorPubkey: String?,
    val relayHints: List<String>,
    val commentaryMarkdown: String,
)
```

型は設計例。専用Storeでは次のレコードを分離し、編集中本文が過去の公開イベントを上書きしない構成とする。元投稿全文やプロフィールを永続payloadへ複製せず、プレビューは通常のキャッシュとメモリ内引き継ぎを使う。編集時の比較に必要な初期状態もbaselineとして保持する。

| レコード | キー・内容 | 保持と削除 |
| --- | --- | --- |
| `ArticleDraft` | owner + draft ID。現在の編集内容・revision | 公開済みrevisionだけを条件付き削除。より新しい編集revisionは残す |
| `ArticleEditArchive` | owner + article address。公開event ID、公開した本文・タグ、編集構造、初回公開時刻 | 一部／全受理時に更新し、下書き削除後も保持。公開記事は消さずにローカル編集データだけ明示削除できる |
| `ArticlePublishAttempt` | owner + attempt ID。署名済みイベント、対象revision、編集スナップショット、リレー別結果、後続版ID | `Prepared / Active / Completed / Superseded`。未完・応答不明は再起動後も再送可能。完了履歴はアーカイブ保存後に署名本文を整理できる |
| `ArticleIdentity` | owner + article address。固定d、固定published_at、既知の最大created_at | 下書き・アーカイブ・未完attemptのどれかが参照する間は保持 |
| `ComposerSnapshot` / `ComposerHandoff` | owner + input ID／handoff ID。通常投稿の退避・復旧入力・適用済み記録 | 4.6の引き継ぎ・復帰が成功した後に整理する |

### 8.0 専用Storeの保存契約

Android・iOSはSQLite、WebはIndexedDBを初期保存先に決定する。既存の`LocalSettingsStorage`は設定専用のままとし、記事本文・索引・公開試行の保存には使わない。SQLite用の依存・各プラットフォームの接続実装は新設する。Store APIは`load / list / save(expectedRevision) / delete(expectedRevision) / transaction`を提供し、結果を`Success / NotFound / Conflict / StorageFailure / CorruptRecord`に分ける。読み取り失敗を未保存・0件として扱わない。

本文更新・一覧メタデータ・revision・容量カウンターを1トランザクションでコミットする。下書き一覧は同じDBのメタデータから取得し、別キーの索引更新へ依存しない。レコードはキーで列挙でき、メタデータ整合性検査時も本文から復旧できる。公開準備、受理結果とアーカイブ更新、下書き削除、通常投稿の退避と引き継ぎ記録もそれぞれ原子的な単位にする。

`expectedRevision`はDB内で比較してから更新し、UI側の比較だけに依存しない。Webの複数タブも同じ比較契約を使う。IndexedDBの完了イベント／SQLiteのcommit成功を保存完了とする。プロセス中断・transaction abortでは旧レコードが残り、成功表示にしない。OSやブラウザ自体のデータ消去は復元保証の対象外である。

- 保存キーは`ownerPubkey + draftId`。一覧もアカウント別。アカウントを跨ぐ単一の「現在の下書き」は作らない。
- 入力後750msのdebounceで保存し、「今すぐ保存」、離脱、バックグラウンド移行、アカウント切替前には可能な範囲でflushする。
- 保存処理はアカウント所有のRepositoryで直列化し、Storeのrevision比較を使う。古い保存完了が新しい入力の保存表示を「保存済み」に変えない。
- 保存成功はストレージへの書き込み完了時。中断直前のdebounce内の入力は強制終了で失われる可能性があるため、UIは未保存状態を正しく示す。終了時だけの保存には依存しない。
- プロセス再起動後は保存済みrevisionを復元。アップロード中・公開中のspinnerをそのまま復元せず、未完操作として再開可能な状態にする。
- `schemaVersion`で移行する。読めないレコードを自動削除しない。エラーを表示し、他の下書きは利用可能にする。
- 一覧メタデータと本文を分け、全下書き全文をUI stateに載せない。初期はアカウントごとに記事下書き最大100件、下書き・アーカイブ・公開試行・通常投稿スナップショットのJSON payload合計10MiBをアプリ側上限とする。DBの物理サイズとは区別し、UTF-8 byte数で更新前後を計算する。
- 編集アーカイブ・署名済み本文も容量計算に含める。超過時は下書き／ローカル編集データ／保留入力を選んで明示削除する導線を出し、未送信内容・未完attemptを自動削除しない。公開準備用スナップショットが保存できなければ送信を開始しない。受理後は保存済みattemptのスナップショットをアーカイブへ移管でき、本文をさらに複製せず容量上限で公開後処理が詰まらない構成にする。
- DBやブラウザの実際のquota・書き込み失敗はアプリ側上限とは別に扱い、必ず保存エラーを通知する。
- 端末内保存は暗号化リレー同期と区別する。初期版は端末・ブラウザごとの保存で、ストレージ消去やアプリ削除による復元は保証しない。秘密鍵は下書きpayloadへ入れない。

### 8.1 アカウントと編集競合

エディタ・Repository・署名処理は同じAccountSessionに結び付ける。`AccountSessionManager`に中断可能な`prepareTransition`を導入し、**Switchingへ遷移する前、lease失効・scope cancel・ViewModel破棄より前**に入力凍結とflushを行う。現行の`resources.onBeforeClose`だけへ保存を登録して済ませない。このフックはlease失効後に実行され、finallyでsessionJobを停止するため、失敗後の入力保持契約には使えない。

1. 切替・ログアウト・アカウント削除の要求を共通ロックで直列化し、旧セッションの入力変更・新しいアップロード・送信開始を凍結する。開始済み画像アップロードと公開結果の反映を待つ。
2. 記事の最新revision、通常投稿の復旧スナップショット、公開試行結果をflushする。すべての編集入口と非同期更新が同じ凍結境界を通る。
3. 保存失敗・競合・待機タイムアウト時は状態をActiveのまま維持し、旧lease・scope・ViewModelを残して凍結を解除する。「保存できないため切り替えられません。再試行または編集を続けてください」を表示する。未保存内容を破棄する場合だけ別の明示操作とする。
4. 保存成功後にSwitchingへ入り、旧セッションを終了して鍵・セッションを切り替える。保存後の通常の切替失敗は、永続化済みデータから旧アカウントへ復旧する。

通常のログアウト・鍵の削除では端末内の下書き・編集アーカイブ・保留入力を自動削除しない。アカウント削除画面で「端末内の下書き等も削除する」を選んだ場合だけ、保存準備後に明示削除する。旧所有者のデータを新所有者へ移して保存・公開しない。未取り込みの選択集合は通常の切替成功時にクリアし、切替失敗時は維持する。

公開済み記事の編集下書きは`baseEventId`を保存する。再開・更新前に取得した最新版と異なる場合は「別の場所で記事が更新されています」を表示し、最新版を見る／自分の編集を別記事にする／確認して同じ記事を更新する、を選べる。取得できない場合は確認不能と表示し、下書きを保持する。同じdraft IDを同時編集した際のrevision不一致も上書きせず競合として扱う。

### 8.2 将来のリレー同期

初期版は端末内保存のみとする。端末間同期は[NIP-37](https://github.com/nostr-protocol/nips/blob/master/37.md)のkind 31234、自己宛NIP-44暗号化、`k=30023`のunsigned記事イベントを検討する。旧kind 30024は採用しない。既存の通常投稿用kind 31234 payloadとの互換性は別途検証し、kind番号が同じという理由だけで流用しない。

## 9. 公開・再送の状態設計

編集UI: `Editing → Saving → Signing → Publishing → Published / PartiallyPublished / RetryableFailure / PublicationUnconfirmed`

公開試行: `Prepared → Active → Completed`、後続版へ移行した旧試行は`Superseded`。編集UIの状態・draft revisionと公開試行の状態は分けて管理する。

1. 現在のrevisionを固定し、生成後本文・Markdown境界・必須入力・HTML禁止・カバーHTTPS・署名可否・公開先を検証する。公開先は開始時のスナップショットとして固定する。
2. 当該revisionを保存してから署名し、署名済みイベント・編集スナップショット・送信予定リレー・記事Identityを1トランザクションで保存する。コミット前はネットワークへ送信しない。新規記事の`published_at`は最初に保存した署名済み版の値で固定し、受理確認が失われても変更しない。
3. `awaitAcceptance=true`相当の処理でOK応答を確認する。リレー別状態を`Pending / Accepted / Rejected(reason) / Unknown(reason)`とし、タイムアウト・送信後切断・強制終了は「未公開」と断定しない。明らかな接続前失敗も再試行可能として理由を保存する。
4. 全対象Acceptedは公開完了。1件以上Acceptedは一部公開として記事を開ける。0件Acceptedかつ送信後Unknownありは「公開結果を確認できません」、応答不明なしの全失敗は再試行可能な失敗とする。Unknownを含む試行は履歴に残す。
5. 同じ版の再送は保存した同じ署名済みイベントを失敗／未確認リレーへ送る。署名し直さず、event ID・d・published_atを変更しない。再送開始時にも現在の書き込み許可を検証し、解除された宛先へ黙って送信しない。再送対象から明示的に外す場合は除外履歴を保存し、「一部公開」を「全リレー受理」に読み替えない。
6. 1件以上の受理を記録するとき、対応event ID・編集構造を`ArticleEditArchive`へ原子的に移管する。全対象受理なら、アーカイブ保存・試行完了・当該revisionの下書き削除を同じトランザクションで確定する。新しい編集revisionがある場合は削除しない。一部公開では下書きと再送履歴を残す。
7. 結果保存に失敗した場合は公開済みと断定せず「公開結果の保存に失敗しました」と表示する。保存済みの署名イベントを残し、再起動後の再送／取得確認で回復する。画面遷移失敗では同じ公開結果から記事を開き直し、公開処理を繰り返さない。

### 9.1 応答不明・一部公開後の編集

送信処理中は入力変更・二重公開を停止する。試行がタイムアウト等で終了した後は、結果を残したまま新しいdraft revisionを編集できる。編集中の変更で旧attemptの署名イベントを更新しない。

- **同じ版を再送**: 旧イベントをそのまま使う。現在の未公開編集は別revisionとして保持し、旧版の再送成功で削除しない。
- **修正版を公開**: 同じ記事addressのロックを取り、旧版の再送開始を止め、開始済み送信が終了するまで待つ。旧attemptの全宛先（受理・拒否・不明を含む）と現在の公開先の和集合から、現在書き込みが許可されるリレーを提示する。除外先には旧版が残る可能性を表示する。
- **新しい記事にする**: 元の試行履歴を残して別draft ID・別dを発行する。元記事の再送履歴を新記事へ移さない。

修正版の`created_at`は、旧試行・既知のリレー最新版・Identityの最大時刻より大きい値とする。端末時刻がそれを超えるまで待ち、待機が長引く場合は公開を中止して下書きを保持する。未来の時刻を任意に生成しない。同秒内更新は次秒まで待つ。初回`published_at`は固定値を再利用する。

同じ記事addressの公開ロックはStore内の所有者・期限・世代番号付きleaseとして取得し、同じブラウザの別タブからの同時送信も停止する。準備コミット・受理結果反映時にlease世代を照合する。失効したPublisherは新しい送信を開始せず、回復側は前試行の署名イベントとUnknown状態を検査してから再送／新版公開を選ぶ。他クライアントからの同時更新はこのロックでは制御できないため、8.1の最新版競合確認を引き続き行う。

新版の署名イベントを保存するトランザクションで、旧attemptへ`Superseded`と新版IDを記録する。このコミット前は旧試行の終了処理を行わず、コミット後は旧版を再送しない。新版が全失敗しても旧版がリレーから消えたとは扱わない。Superseded履歴は後続版の結果が確定するまで保持し、遅れて届いた旧版の応答は履歴だけを更新して現在の編集／公開状態を巻き戻さない。

### 9.2 再起動時の回復

Prepared／Activeの試行はプロセス終了で受理確認を失っている可能性がある。保存済みのevent IDで取得を試み、一致するイベントを取得できた場合は確認元リレーの受理済み相当として記録する。未取得は未公開の証明にせず、同じ署名イベントの再送を選べる。Supersededの旧試行は送信せず後続版を開く。アーカイブ作成とdraft削除は同じトランザクションのため、回復時に片方だけが確定した状態を作らない。

## 11. 検証・受け入れ条件

| 分類 | 条件 |
| --- | --- |
| 保存・復元 | 未完成の記事、Matometr順序・説明、公開記事編集を再起動後に復元できる |
| 保存障害 | quota超過・書き込み失敗で保存済みと表示せず、離脱で本文を失わない |
| 保存の原子性 | 本文・メタデータ更新途中の強制終了／transaction abortで旧版が残る。読み取り障害をNotFoundとして扱わない |
| 保存競合 | debounceとflushの順序が入れ替わっても最新revisionが残る |
| 複数タブ | Store内のexpectedRevision比較により競合を検出し、別タブの下書きを上書きしない |
| 公開ロック | 同じaddressの別タブ公開を停止し、lease失効後の旧Publisherが新しい公開状態を上書きしない |
| アカウント | 切替・ログアウト・古い非同期処理の完了で別アカウントの保存・公開が起きない |
| 切替失敗 | prepareTransitionの保存失敗・競合・待機タイムアウト時にActive・lease・入力・選択が残り、再試行できる |
| 選択 | 同一event IDの重複、リポスト、ページ追加、0／1／50／51件、解除・再選択を正しく扱う |
| 共通選択 | 対象4画面間の移動で件数・番号・順序を保持し、どの画面で解除しても反映する |
| ジャーナル | 日付・月・種類変更でも選択を保持。いいね・リポストは元投稿を追加し、未取得・対象外kindは追加しない |
| プロフィール | 表示ユーザー・投稿タブの変更と戻る操作で選択を保持。記事所有者は閲覧先ユーザーに変わらない |
| 選択欄 | ヘッダー下に固定表示し、横スクロール・プレビュー・全件一覧・並べ替えを対象4画面で同じように操作できる。プロフィールヘッダーの折りたたみで消えない |
| 取り込み | 保存・遷移失敗で選択を維持し、連打で複数下書きを作らない |
| 投稿方法 | 同じ選択順を引用投稿・記事作成に引き継ぐ。通常投稿にはMatometrタグを自動付与せず、どちらも画面を開くだけでは公開しない |
| 通常投稿の入力保護 | 既存本文・下書きを上書きせず、参照の重複・文字数超過・二重起動を防ぐ |
| 通常投稿の退避 | 本文・画像・警告・絵文字・返信／チャンネル・公開先を保存後にだけ切り替える。保存失敗・再起動・復帰時の既存入力でも内容を失わない |
| 引き継ぎの一意性 | 同じhandoff IDで遷移を再試行しても参照を二重挿入せず、取り込み失敗では選択を消費しない |
| 既存記事への追加 | 追加専用表示、合計50件上限、キャンセル時の元記事保持、自由Markdown本文への追記を検証する |
| nevent | round-tripで元IDと著者・hintが復元でき、hintなし・長いhintでも生成できる |
| 本文生成 | 順序・説明が一致し、100,000文字上限とmatometrタグ枠を守る |
| Markdown境界 | 導入・説明の未閉じバッククォート／チルダ、フェンス長、コード中のURIを検証する。失敗時も保存可能だが追加・公開は止め、既存本文を変更しない |
| 引用表示 | 編集プレビューと公開詳細で同じ順序。未取得・削除・ミュート投稿は既存方針に沿い、参照URIを残す |
| プレビュー取得 | 引き継ぎイベントを即時表示し、再開時はバッチ取得する。参照削除・タブ切替・離脱で停止し、古い応答で表示を戻さない |
| 自由編集 | 公開済み本文を構造化再生成で上書きしない。コードブロックのURIを引用扱いしない |
| 公開 | 全受理・一部受理・全失敗・応答不明を区別し、再送で同じevent ID／dを維持する |
| 公開後再編集 | 全受理後に下書きを削除してもアーカイブから引用順序・説明を復元できる。ネットワーク版不一致なら自由Markdownで開く |
| 不明結果からの修正 | 旧版再送と新版公開を直列化し、初回公開時刻を維持する。旧版の遅延応答で新版状態を戻さず、新しい編集revisionを削除しない |
| 公開後保存失敗 | Accepted後のDB失敗でも準備済み署名イベントが残り、同一イベントの再送・取得確認で回復できる |
| 公開後処理 | 下書き削除や遷移が失敗しても二重公開しない |
| UI | Android・iOS・Webで長文・大きい文字・キーボード表示時も本文／公開操作へ到達できる |

純粋ロジック・偽Store・偽Publisherを使うcommonTestを中心に追加する。現行`ArticleEditorViewModelTest`、`ArticleMarkdownParserTest`、`NostrUriTest`を拡張する。プラットフォーム保存とUIは対象端末で手動検証し、リレー受理は制御可能なテストリレーで確認する。

## 12. 導入順序と未確定事項

1. **保存・復旧基盤**: SQLite／IndexedDB、Storeの原子的保存・revision比較、記事下書き・アーカイブ・公開履歴・通常投稿退避、切替前の保存ゲート、復元・下書き一覧、公開IDの固定。
2. **投稿UI改善**: 保存状態、可変高・全画面本文編集、ツールバー、折りたたみ設定、公開理由表示、プレビュー取得Controller。
3. **選択と投稿方法**: AccountSession所有の共通選択Coordinator、対象4画面の固定選択欄、元投稿解決、引用一覧、Markdown境界検証、serializer、`matometr`タグ、通常投稿への複数引用引き継ぎ・既存入力退避と復帰。
4. **公開の堅牢化**: OK受理、署名済みイベント永続化、一部公開・同一イベント再送、応答不明時の修正版公開、アーカイブからの再編集、更新競合。
5. **統合検証**: 各プラットフォームの保存障害、アカウント切替、引用取得、長文、公開再送。

段階4まで揃うまでは公開成功に連動した下書きの自動削除を有効にしない。

以下は初期提案として実装可能だが、外部仕様・製品判断に応じて調整する。

- 外部Matometrとの互換要件: 現在は`kind 30023 + nostr:nevent + t=matometr + 本文#matometr`を採用。
- 選択上限・保存容量: 現在の提案は50投稿、アカウントごとに100記事下書き、関連レコードのpayload合計10MiB。実端末で検証し、8章の原子的保存・明示削除の契約を維持する。
- 引用対象拡張: kind 1111・30023などは初期対象外。addressable eventではneventによる特定版とnaddrによる最新版のどちらを扱うか別途決める。
- 端末間同期: 初期対象外。NIP-37との互換、private relay設定、既存通常投稿下書きとの識別を含めて設計する。
- 自動引用通知: 初期は無効。通知ありの外部Matometr互換が必要な場合に見直す。
