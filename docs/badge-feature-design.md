# バッジ機能設計

作成・仕様確認日: 2026-10-01。実装・再確認日: 2026-10-02。状態: 初期版実装済み。

設計更新日: 2026-10-02。保存・同期とタップ領域のレビュー指摘を反映し、ポストカードの配置を名前の右側へ変更。

## 1. 目的と採用方針

ユーザーが選んだNostrバッジをポストカードの投稿者名の右側、プロフィールの名前の下に横並びで表示する。

指定された配置以外の件数・サイズ・操作・初期範囲は本書の提案。初期版では他クライアントで授与されたバッジの閲覧、本人による表示選択・解除・並べ替えを実装する。バッジの作成・授与、セットの作成・編集は後続とする。

表示するのは「投稿者が現在選んでいるプロフィールバッジ」。投稿そのものへの授与や、投稿時点のバッジを表すものではない。kind 1やkind 0へ独自タグを追加せず、過去のポストカードにも現在の選択を反映する。バッジは発行者の意思を表す装飾として扱い、本人認証やNIP-05の検証済み表示とは分ける。

## 2. 関連NIPの仕様

### NIP-58: バッジのデータ

現行仕様はdraft / optional。次の4種類を使用する。[NIP-58公式仕様](https://github.com/nostr-protocol/nips/blob/master/58.md)

| kind | 名前 | 発行者・内容 |
| --- | --- | --- |
| 30009 | Badge Definition | 発行者が定義。必須のd、任意のname・description・image・thumb |
| 8 | Badge Award | 発行者が授与。1つのaで定義を参照し、1つ以上のpで受賞者を指定 |
| 10008 | Profile Badges | 本人が表示対象を選ぶ置換可能イベント。順序付きのa/eペア、またはセットへのa参照 |
| 30008 | Badge Set | dで識別するグループ。順序付きの定義・授与ペアを含む |

定義の参照は `30009:<発行者pubkey>:<d>`。定義は更新可能、授与は譲渡不可。表示ペアは隣接するa（定義）とe（授与ID）であり、対応のないタグは表示対象にしない。授与イベントのaが選択された定義と一致することを確認する。画像は1:1、imageは1024px、thumbは16〜512pxが推奨される。[NIP-58公式仕様](https://github.com/nostr-protocol/nips/blob/master/58.md)

旧Profile Badgesは `kind 30008 / d=profile_badges`。現行仕様はこれを10008相当として読み、新形式へ移行するよう求める。30008をすべて旧プロフィールとして解釈しない。[NIP-58公式仕様](https://github.com/nostr-protocol/nips/blob/master/58.md)

NIP-58は画面上の位置・表示件数・「代表バッジ」を定めていない。以下はToriNosの表示ルールとする。

## 3. UIと操作

### ポストカードの名前の右側

`NoteCard`のヘッダーは著者名・バッジを左寄せ、クライアント名・メニューを右寄せで同じ1行に並べる。バッジを投稿者に結び付く情報として読み取れる配置にする。名前とバッジの間は8dp、名前は短ければ内容幅、長ければ省略表示とし、バッジをカード右端へ押し出すためのSpacerは置かない。プロフィールアイコンの下に年・日付（MM/dd）・時刻（HH:mm）を縦に並べる。今年の年と今日の日付は省略し、端末のタイムゾーンで判定する。クライアント名・メニューは名前・バッジと同じ行の右端に置く。メニューの24dpとクライアント名の実測幅（最大64dp×文字倍率かつ行幅の25%）を先に確保し、長い名前・クライアント名は省略する。本文やメディアに重ねない。

- 有効な選択順に最大3個。画像は24dp、バッジ同士と最後のバッジから+Nまでの間隔は1dp。操作枠は画像幅24dp・高さ42dp、+Nは文字の実測幅・高さ42dpとする。リポスト時は名前行を24dpに縮め、リポスト表示と合わせてアイコンと同じ42dpのヘッダー内に収める。
- 上段の使用可能幅から、名前用の最低96dpと間隔8dpを差し引き、24dpの画像幅・1dpの間隔・+Nの実測文字幅から表示数を決める。大きな文字設定では名前の最低幅を増やし、バッジの枠数を減らす。残り幅を名前へ割り当て、長い名前は1行で省略する。
- 4枠あれば最大3個と「+N」、3枠なら必要に応じ2個と「+N」、2枠なら1個と「+N」。残りがなければ+Nは出さない。1枠だけで複数件ある場合は「+N」のみとし、Nは全有効件数とする。1件ならその画像を出す。枠を確保できない幅ではカード内のバッジを省き、プロフィールの一覧から確認できるようにする。
- Nは検証済みの表示対象の残り件数。未取得の参照を有効な件数として数えない。
- 個別タップは詳細シート、「+N」はその著者の表示バッジ一覧を開く。カードを開く操作とは別に扱う。
- リポストは元の投稿者のバッジを表示する。引用のバッジは引用著者に紐づけ、初期版の小さい引用プレビューには追加しない。
- 初期対象はフィード、プロフィールの投稿一覧、スレッドの共通NoteCard。記事専用カード・通知行は後続とする。

```text
┌─────────────────────────────────────────┐
│ アバター  投稿者名 [A][B][C] +2         │
│           12:34 · client              ⋮ │
│ 投稿本文                                │
│ リアクション等                          │
└─────────────────────────────────────────┘
```

### プロフィールの名前の下

自分・他ユーザーのプロフィールで、名前の行の直下に有効な表示バッジを選択順で横並びに表示する。画像は24dp、間隔は投稿カードと同じ1dp。件数を省略せず、画面幅を超えた分は横スクロールで確認する。

- 個別タップで詳細を開く。バッジがない場合は行を表示しない。
- アバターへの重ね表示は行わず、既存のアイコン編集ボタンを維持する。スクロール時の小さい固定ヘッダーにも重ねない。
- 自分の「バッジを管理」は名前の行の右端を維持する。他ユーザーの全件一覧ボタンも維持する。

### 詳細と管理

詳細は画像、名前、説明、発行者、受賞者、授与日時を表示する。発行者からプロフィールを開ける。名前なしはd、画像なし・画像取得失敗は汎用アイコンを使う。発行者の表示名が未取得なら短縮pubkeyを表示する。

自分のプロフィールでは名前の行の右端に「バッジを管理」ボタンを配置する。「バッジを管理」で「表示中」「受け取ったバッジ」を切り替える。未選択の授与を自動表示しない。表示追加、表示解除、上下移動、先頭へ移動を提供し、「保存」で一括反映する。表示解除は授与イベントの削除や返却ではなく、表示リストから外す操作。受信を拒否するプロトコルイベントは発行しない。

受賞者本人の画面でも他人の画面でも公開tagsだけを表示の情報源にする。暗号化contentは公開表示に転用しない。匿名利用は閲覧でき、保存は署名可能な本人のみ。

画像はContentScale.Fit、静止表示とし、thumbを必要な実ピクセルサイズ以上で最小の候補から選ぶ。なければimageを小さくデコードする。詳細表示で高解像度を読み込む。プロフィールや一覧のタップ領域は48dp相当を確保する。投稿カードは指定の1dp間隔を優先し、画像幅24dp・高さ42dp（リポスト時24dp）とする。読み上げ名は「バッジ名、発行者名」、一覧には件数も含める。

## 4. 正規化と検証

受信イベントは既存の`isValidEvent`でID再計算とSchnorr署名を検証してからキャッシュへ入れる。購読では`deduplicateEvents=false`とし、検証成功後にID重複を排除する。不正イベントが同じIDの正しいイベントを先に抑止しないようにする。

表示対象は次の条件をすべて満たすものとする。

1. 表示リストの作者が表示中のプロフィールpubkeyと一致する。
2. aのkindが30009、発行者pubkeyが64桁hex。dは最初の2つのコロン以降をそのまま取り、d内のコロンも保持する。
3. eで参照するイベントのIDが一致し、kindが8。
4. 授与イベントの唯一のaが表示ペアの定義アドレスと完全一致する。
5. 授与イベントのpubkeyが定義アドレスの発行者と一致する。
6. 授与イベントのpに表示対象のpubkeyが含まれる。
7. 定義イベントのkind・pubkey・dがアドレスと一致し、定義と授与に有効な削除要求を適用した結果、表示可能である。

画像・名前がないことは不正の理由にしない。同じ定義への授与が複数あっても表示は定義アドレス単位で重複排除し、最初の有効なペアを採用する。生イベントのタグ順・未知タグは別途保持する。

編集は隣接a/eペアまたはセット参照をタグのまとまりとして扱う。削除・並べ替えで元々孤立していたaとeが新たに隣接する場合は、間に説明用altタグを挿入して、未選択の参照が誤って有効なペアになることを防ぐ。元の未知タグやヒントは保持する。

参照の状態は`Resolving / Valid / Invalid / Unavailable / Deleted`に分ける。不一致はInvalid、取得の期限切れやリレー拒否はUnavailable。再試行可能な状態を不正授与と断定しない。正常なリスト取得で対象なしのEmptyと、リストを取得できないErrorも区別する。

削除要求は作者一致を必須とする。アドレス対象の削除は削除要求のcreated_atまでの版へ適用し、それより新しい定義は再び使用できる。授与の削除要求はそのイベントIDに適用する。これはToriNosのNIP-09表示対応であり、NIP-58に独自の取消イベントを追加するものではない。

## 5. 新旧プロフィールとセットの扱い

- 検証済み10008が存在すれば、空リストでも旧形式より優先する。空の10008を旧リストで埋め戻さない。
- 10008が取得できず旧イベントだけがある場合は旧形式を暫定表示する。取得失敗と新形式の不存在は区別して状態を持つ。
- 旧形式だけのプロフィールを本人が保存したときに10008を発行する。閲覧だけで移行イベントを発行しない。旧イベントは自動削除しない。
- 30008へのa参照はセットとして取得する。初期版は同じプロフィール作者のセットだけを展開し、他作者の参照は未対応として残す。この制限はアプリ方針でありNIPの必須条件ではない。
- セットの位置で中の有効なa/eペアを順に展開する。単独バッジと重複する定義は最初の有効な出現を採用する。
- セット内のセット参照は初期版では展開しない。循環や無制限の取得を避け、未対応項目として表示する。
- セット由来の項目は管理画面でまとまりとして扱う。セット全体の並べ替え・表示解除は可能、内部の編集は行わない。
- 初期版で編集できるのは公開選択リスト。既存contentは変更せず保持する。暗号化内の参照や未対応のタグを公開tagsへ移さない。

## 6. アーキテクチャと既存コードへの組み込み

kind 0の`NostrProfile`へバッジを埋め込まず、別の読み取り状態として管理する。

| 提案する要素 | 責務・配置 |
| --- | --- |
| BadgeAddress / BadgeSelection / BadgeDisplayItem | `badge/BadgeEvents.kt`。アドレス解析、タグのまとまりの保持・編集、授与検証、表示モデル |
| BadgeRepository | `badge/BadgeRepository.kt`。新旧の最新比較、セット展開、公開イベントキャッシュ、pubkey単位のobserve、取得の集約 |
| BadgeTransport | 既存NostrRepository.openSubscriptionを包み、Fetch / Liveとリレー結果を扱う。送信はpublishToRelaysWithResult(..., awaitAcceptance = true)を使い、成功・失敗リレーを返す |
| BadgeHost / rememberBadgeProfile | `badge/BadgeUi.kt`。描画中の著者に対する需要を登録・解除し、共通Repositoryの著者別状態を監視 |
| AccountBadgeStore | AccountSession所有。自分の受賞一覧、10008保存、送信箱、再送・競合処理。編集ドラフトは管理シートが保持 |
| BadgeStrip / BadgeAvatarOverlay / BadgeDetailDialog / BadgeListSheet | 表示・選択・並べ替え。取得・署名・送信をRepositoryとStoreへ委譲 |

`BadgeHost`がRepositoryをCompositionLocalで提供し、`NoteCard`と`ProfileHeader`は著者別の不変な表示リストを監視する。Composableは需要の登録と画面用StateFlowの監視だけを行い、カードごとのリレー購読は作らない。同じ著者のカードを参照カウントでまとめ、共通Coordinatorが100msで要求を集約する。画像は既存の画像リクエスト生成とデコード上限を再利用し、読込失敗時は汎用アイコンにする。

バッジ更新は該当pubkeyを使うカードだけへ差分通知する。本文解析やエンゲージメント集計を再実行しない。バッジ取得を初回フィード公開条件に加えない。プロフィールのバッジ行は検証済みの項目から表示する。

公開キャッシュも初期版ではAccountSession単位に分ける。匿名閲覧はBadgeHostの専用Repositoryを使用する。同じセッション内の画面はキャッシュを共有し、取得先リレー・自分の選択・送信箱をアカウントへ固定する。終了時に処理・購読をcloseし、遅延完了した前アカウントの結果を編集状態へ適用しない。

投稿カードのヘッダーは取得前からアイコンと同じ最低42dpを確保し、バッジがない場合も名前・クライアント名・メニューを縦中央に揃える。リポスト表示はヘッダー内の上段、名前・バッジ・クライアント名・メニューは下段に配置する。通常の文字サイズでは2段を42dp内に収め、文字拡大時は切れないよう高さを伸ばす。取得後のバッジ有無で高さを変えない。時刻は引き続きアイコンの下に表示する。一覧と詳細は同時に表示せず、詳細を閉じたら保持した一覧・編集状態へ戻る。

## 7. 取得・キャッシュ方針

カードの表示範囲と前後のプリフェッチ範囲の著者をまとめて取得する。自分の全授与の探索は管理画面を開いたときに行い、全タイムライン著者の授与一覧は探索しない。

| 段階 | NostrFilter相当 |
| --- | --- |
| 表示リスト | authors=[対象pubkey群], kinds=[10008] |
| 旧リスト | authors=[対象pubkey群], kinds=[30008], #d=[profile_badges] |
| 参照授与 | ids=[eタグのID群], kinds=[8] |
| 定義 | kinds=[30009], authors=[発行者], #d=[識別子] |
| セット | kinds=[30008], authors=[セット作者], #d=[識別子] |
| 自分の受賞探索 | kinds=[8], #p=[自分のpubkey]。ページ単位で取得 |
| 削除要求 | kinds=[5], authors=[対象イベント作者], #e=[ID群] または #a=[アドレス群]。別filterでOR検索 |

定義・セットは必要な作者とdの組をfilterとしてまとめる。authorsと#dを同時に複数指定したときの直積一致を、そのまま期待するアドレス集合と見なさない。リストを複数作者で取得するfilterにlimit=1を付けない。

受賞一覧はまず最新100イベントを取得し、「さらに読み込む」で過去へ進む。untilは境界秒を含めて再取得しIDで重複排除する。同じ秒にlimit以上ある場合は境界秒のlimitを増やして取得し、制限で取り切れなければ不完全と表示する。境界秒を無条件に1秒減らして同時刻の授与を落とさない。

基本は設定済みの読み取りリレー。取得済みのNIP-65情報と参照のリレーヒントを追加候補として用いる。ヒントは未信頼の入力として既存のURL検証・接続制限を通し、禁止リレーへ接続しない。任意のヒントだけに依存しない。

有限取得は既存SubscriptionBehavior.Fetchを利用し、正常EOSE、拒否、タイムアウトを分ける。取得できた有効イベントは部分成功でも反映するが、全取得失敗を「なし」としてキャッシュしない。取得処理の終了・画面離脱で購読を解放する。自分の表示リストはセッション中Liveで更新を監視し、他人は表示中の再取得と前面復帰で更新する。

初期版のパラメータ: 100msの要求集約、1バッチ30作者、共有取得は直列、取得期限10秒（外側の処理期限12秒）。表示リストと参照先は5分、正常取得で表示なしは1分、失敗は指数バックオフで再確認する。表示中の著者を1分ごとに確認し、前面復帰で再取得を予約する。未送信リストは30秒ごと・前面復帰時に再試行する。送信前には最新リストを再取得する。

初期版のメモリ上限: 参照されていないプロフィール状態は1,000件を超えたら破棄し、公開イベントキャッシュは5,000件で古い登録から破棄する。削除要求は別に保持して古いイベントの再取得で復活させない。1プロフィールの初回解決は先頭100ペア、セット取得は10件まで。「表示バッジをさらに取得」で解決範囲を100件ずつ増やせる。受賞探索は100件単位、同一秒の境界取得上限は2,000件とし、取り切れなければ不完全と表示する。取得上限は保有・選択件数の上限ではなく、保存タグを切り詰める理由にしない。

NIP-65追加候補は各作者2リレー、合計10リレーまで。授与のリレーヒントは合計4リレーまでとし、設定で無効にした接続先を追加候補へ戻さない。1取得のイベント上限は10,000件で、超過は正常な不存在・完全取得として扱わない。

初期版の他人向けキャッシュはメモリのみ。自分の最後に確認した公開リスト、未送信イベントとリレー受理状況はアカウント別LocalSettingsStorageへ保存する。

## 8. 表示選択の保存と競合

新規保存は自分の署名したkind 10008、公開tagsに隣接a/eペアを記録する。新規contentは空文字。既存イベントの編集ではcontent・未知タグ・未対応参照・リレーヒントを保持し、管理画面で明示的に操作した項目のみ変更する。全解除も空の表示リストを発行し、kind 5で表現しない。

1. 管理画面を開く際に読み書きリレーから新旧表示リストを取得する。結果は「イベントあり」「正常取得で新旧ともなし」「取得不完全・失敗」に分ける。取得先が1つ以上あり、全対象リレーで正常EOSEを受け、新旧ともなしなら「確認済み不存在」を基準として初回保存を許可する。イベントありでは基準イベントIDを記録する。確認済みイベント・不存在のいずれもなければ保存を有効にしない。
2. 編集は端末内ドラフト。保存時に最新を再取得する。
3. 最新の比較対象は確認済みリモートイベントと、端末で保存済みの未送信・一部受理イベント。NIP-01の時刻・ID比較で最も新しいものを編集基準にする。リレーに古い版だけが返ったことを理由に端末保存済みの選択を戻さない。別端末から基準より新しいイベントが取得された場合は全体を上書きせず、最新版とドラフトを提示して再編集する。「確認済み不存在」からイベントありへの変化も競合として扱う。送信前取得が不完全・失敗ならドラフトを保ち、再試行を案内する。
4. created_atは現在時刻と、確認済み・端末保存済みの最新時刻+1の大きい方。初回で基準イベントがなければ現在時刻を使う。極端な未来時刻の基準は自動的に追い越さず、競合として扱う。
5. 保存と送信箱更新はアカウント単位で直列化し、AccountSessionのsignerで署名する。前の保存Aが送信待ちでも保存Bを許可し、Bを端末へ永続化してから送信箱の現行イベントをBへ置き換える。署名・永続化失敗ならAを保持する。Bは新しいイベントなのでAの受理状況を引き継がず、書き込み先へ改めて送る。
6. 書き込みリレーへpublishToRelaysWithResult(event, targets, awaitAcceptance = true)を使い、BadgeTransportから成功・失敗リレー集合を返す。1つ以上のOK受理で「保存済み」、残りが失敗なら「一部リレーに未同期」。全失敗は「送信待ち」として再送する。書き込み先0件は保存成功とせず、送信先未設定を表示して端末保存済みのイベントを保持する。部分成功で例外を投げて結果を失うpublishToRelaysAndAwaitAcceptanceは使わない。
7. 再送は同じ署名済みイベントを使い、残りの送信先だけへ送る。受理結果の適用・送信箱の削除はsessionIdと現行イベントIDの一致を必須とする。B保存後にAのOKや失敗が届いても、Bの状態を変更しない。保存済みイベント自身の購読エコーは競合にしない。端末保存済みイベントより新しい別イベントを受信したら古い再送を打ち切り、送信箱の競合状態と編集ドラフトを保持して管理画面へ通知する。

送信箱保存後は自分の表示に反映し、同期状態を管理画面へ表示する。アカウント切り替え後の署名・送信はensureActiveで拒否し、保存キーは `badge_selection_v1_<ownPubkey>` とする。取得した全リレーの最新が世界全体の最新とは保証できず、送信直前の別端末更新との競合は残る。NIP-01の最新比較に従って収束し、ドラフトを黙って消さない。

## 11. バッジ取得の効率化

### 対象と完了条件

対象は初回表示の待ち時間と同一イベントの再取得。プロフィールのkind 0キャッシュへ混在させず、BadgeRepositoryと専用の取得コーディネーターで改善する。今回の実装範囲は受信時の段階反映、参照取得のキャッシュ・同時要求共有、リレー探索の並行化、著者バッチの並行処理。端末への永続化とフィードの先読みは独立した後続改善とし、この変更では追加しない。

初回の表示が遅いリレーのEOSEより先に更新されること、取得済みの授与・定義の再問い合わせが減ること、複数カードや著者から同じ参照を要求しても購読が共有されることを仮想時間テストで確認する。秒数の改善を実リレーで未計測のまま保証しない。

### 取得と反映

1. 10008／旧30008を受信した時点で署名検証し、最新版比較を経てキャッシュへ反映する。選択が変わった著者の参照取得を起動する。全対象リレーのEOSEは初回表示の開始条件にしない。
2. 本人・発行者の10002探索は既知の読み取りリレー／書き込みリレー／参照ヒントによる取得と並行する。追加の書き込みリレーが判明したら、そのリレーにも問い合わせる。無効化されたリレーと既存の候補数上限を維持する。
3. 表示リストの削除取得と、定義・授与・セット取得を並行する。到着した検証済みの定義・授与は逐次反映する。削除情報が届けば即時に除外し、削除墓標を保持する。表示可能と、削除を含む再確認完了を分ける。
4. 遅れて新しい表示リスト／空の10008が届いた場合も再計算する。旧形式だけが先に届いたことを理由に最新版を固定しない。
5. 著者30人のバッチを最大2個並行実行する。処理中の著者を待ち行列へ重複追加しない。共有した取得は表示に必要な参照用2枠とリレー探索・削除確認用2枠を分離し、合計最大4個同時。探索・確認が全枠を占有して表示を止めない。各購読のfilter上限は30を維持する。

### キャッシュと共有

- 取得キーはfilterと対象リレー集合。対象リレーが異なれば確認範囲も異なるため、同じ完了確認とは見なさない。
- 新しい画面の監視開始時も既存イベントから即時に表示状態を組み立てる。手動の再読み込みでは定義・セット・削除確認を強制更新する。完了済みの授与IDは再利用。定義は5分、セットは1分、削除問い合わせは30秒を期限とする。空の完全応答は30秒だけ保持。不完全応答・タイムアウトは完全な不存在としてキャッシュしない。
- 同じキーの実行中取得は共有し、署名検証済みのイベントを受信ごとに通知する。完了済み要求キャッシュは最大5,000キーかつ保存イベント参照合計5,000件とする。
- 無効イベントが先に同じIDで届いても正当な後続イベントを抑止しない。検証済みの同一イベントの再配信だけ検証・通知を省略する。
- 受信イベントの参照先索引から影響する著者だけ再計算し、逐次反映で全プロフィールを繰り返し走査しない。キャッシュ更新と状態再計算は短い同期処理で直列化し、並行取得が古い状態で表示を上書きすることを防ぐ。イベント本体・削除情報と取得結果の期限は独立させる。期限切れ時も確認済みの表示を残しながら再取得する。

### 保存前確認

自分の編集保存・送信前確認はプロフィール一覧の全対象リレー完了を要求する。表示側の早期反映や参照キャッシュを、最新確認済み／確認済み不存在の代用にしない。保存前の確認では定義・セット・削除問い合わせの期限を無視して再確認する。参照取得や削除確認が不完全なら保存の前提確認も不完全とする。授与イベントの本体はID固定だが、削除状態は毎回確認する。

### 設計レビュー

- 初期案の「最初のリレーで取得終了」は、遅れて届く最新版・削除・空の選択を落とすため不採用。表示だけ先行し、購読の完了まで受信を続ける。
- リレー集合を除外したキャッシュキーは、追加リレーを確認済みと誤認するため修正。
- filterのlimit=1を複数authorsへ適用すると他の著者を取りこぼす。今回その制限は追加しない。
- 同じIDの検証前の重複除外は不正イベントによる抑止を許すため不採用。
- 保存前確認まで通常の期限付きキャッシュで済ませる案は競合・削除の検知を弱めるため、強制再確認を別に指定する。
- 逐次反映中の未確認削除・参照失敗を「完全に取得済み」と表示しない。loading／partialと、保存に利用できるcompleteを区別する。

### 実装レビューと修正

1. 遅い探索・削除確認が全取得枠を占有すると早期表示できないことをテストで検出。参照用2枠と確認用2枠に分離し、定義と授与を同じチャンクに交互配置した。

4. 逐次反映による全著者の再計算を参照先索引による差分更新に変更し、キャッシュ更新と再計算を直列化。新規監視開始時のキャッシュ即時表示も追加。

## 12. 取得まわりの再レビュー（2026-10-02）

### 指摘内容

| # | 重要度 | 箇所 | 内容 |
| --- | --- | --- | --- |
| R1 | 高 | BadgeTransport / BadgeFetchCoordinator / BadgeRepository.request | 完了判定が「全対象リレーのEOSE」のみ。NIP-65追加候補・授与ヒントを含む対象のうち1つでも応答しないと`complete=false`となり、共有キャッシュに一切入らない。ID固定の授与も毎回再取得され、失敗扱いのバックオフ（10秒〜）が通常TTL（5分）より短いため取得頻度がむしろ増え、エラー表示も常時出る |
| R2 | 高 | AccountBadgeStore.loadAwards | `limit`はリレーごとに効くのに、全リレー合算の最古時刻を次の`until`にしている。密なリレーAと疎なリレーBが混在すると、Aの中間期間の授与を取得しないまま次ページへ進み、選択候補から欠落する |
| R3 | 中 | BadgeFetchCoordinator | 取得の所有者がキャンセルされると、同じキーを共有していた無関係な待機者も`CancellationException`で中断される。管理シートを閉じるとフィード側の自分のバッジ更新が中断され、エラー・取得時刻も更新されない |
| R4 | 中 | BadgeRepository.request | 取得中のpubkeyへの要求は`force`でも破棄される。「表示バッジをさらに取得」・再読み込み・前面復帰が取得中に来ると反映されない |
| R5 | 中 | BadgeRepository.refresh | NIP-65で判明した追加リレーへの問い合わせが、既知リレーの取得終了（最大12秒）を待ってから始まる。§11-2の並行方針と不一致 |
| R6 | 低 | BadgeRepository.ingest | 公開イベントキャッシュの追い出しが挿入順で、再利用しても順序が更新されない。表示中の著者の10008・参照先が追い出され、TTL切れまでバッジが消える |
| R7 | 低 | BadgeRepository.recompute / BadgeHost | 受信1件ごとに最大5,000件のスナップショット複製・索引作成・削除要求の全走査を行う。匿名閲覧のRepositoryはMainスコープで動くため、受信処理がメインスレッドに載る |
| R8 | 低 | BadgeRepository.deletions | 削除要求の保持に上限がない |

### 修正方針

1. **完了と再利用可能の分離（R1）**
   - `BadgeFetchResult`に、EOSEを返したリレー集合`answered`と、リレーごとの受信件数・最古時刻`pages`を追加する。同じイベントを複数リレーから受けた場合も各リレーの件数に数える（検証は初回のみ）。
   - IDだけを指定した取得（kind 8の授与）は、指定IDがすべて検証済みで見つかれば、他リレーの応答に関係なく完全とみなす。ID固定のイベントに新しい版は存在しないため。
   - 不完全でも、応答したリレーが1つ以上あってイベントを含む結果は「部分結果」としてキャッシュし、強制しない表示用取得で期限内に再利用する。戻り値の`complete=false`は保持するため、保存前確認（強制再確認）の代用にはならない。イベントなしの不完全結果は従来どおりキャッシュしない。
   - Repositoryは、表示リストの取得でどのリレーも応答しなかった場合だけを失敗としてバックオフとエラー表示に使う。部分取得は通常TTLで再確認し、`partial`だけを立てる。
2. **リレー単位のページ境界（R2）**: 受信件数が要求`limit`に達したリレーだけを「続きあり」とし、それらの最古時刻のうち最も新しいものを次の`until`にする。達していないリレーは取り切ったものとする。同一秒で境界が進まない場合の`limit`倍増（上限2,000）は従来どおり。不完全取得の場合は続きありのまま残す。
3. **共有取得のキャンセル分離（R3）**: 待機者は、所有者のキャンセルで中断された取得を検知したら、自分がキャンセルされていなければ同じキーを自分で取得し直す。
4. **取得中の要求の保留（R4）**: 取得中のpubkeyへの強制要求は待ち行列に保留し、現在の取得が終わったら実行する。ワーカーは取得中のpubkeyをバッチに入れず、バッチ終了時に保留があれば再び起動する。非強制の要求は、取得中の処理で満たされるので従来どおり破棄する。
5. **追加リレーの並行取得（R5）**: 既知リレーへの取得とNIP-65探索を並行に始め、探索が完了した時点で追加リレーへの取得を開始する。既知リレーの完了は待たない。
6. **参照中データの保護（R6）**: 再受信したイベントは最近使った順に更新する。追い出しでは、表示中（acquire中）の著者の表示リストと、その参照先（索引で判定）を対象外にする。
7. **索引による差分再計算（R7）**: キャッシュに、ID・アドレス・著者別10008/10002の索引と、削除要求の対象別索引を持たせる。再計算は対象著者に必要な参照だけを引き、全件スナップショットを作らない。匿名閲覧のRepositoryは`Dispatchers.Default`の専用スコープで動かし、破棄時にcancelする。
8. **削除要求の上限（R8）**: 削除要求は5,000件を上限に古いものから破棄する。墓標を破棄するときは、その対象イベントもキャッシュから除き、削除済みイベントだけがキャッシュに残って復活することを防ぐ。再取得すると対応する削除問い合わせも同時に行われる。

### 実装・レビュー・テスト

方針1〜8を実装した。実装後のレビューで次の2点を追加で修正した。

- 索引化の際、同じIDで内容の異なるイベントを置き換えなくなっていた（既存テストで検出）。同一内容の再受信だけを最近使った順の更新とし、内容が異なる場合は置き換える。
- リレーが大きい`limit`を独自の上限で切り詰めると、取り切ったと誤判定して同一秒の続きを止めていた。基本ページ（100件）以上を返したリレーは「続きあり」とする。100件未満で打ち切るリレーは取り切ったと区別できないため、既知の制限として残す。

仕様変更: 一部のリレーだけが応答しない取得では`error`を出さず、`partial`だけを立てる。エラー表示とバックオフは、表示リストの取得にどのリレーも応答しなかった場合に限る。

回帰テスト`BadgeFetchReviewTest`（8件）: 応答しないリレーがあっても参照を再利用し、強制確認では再取得する／全リレー無応答はエラー／密・疎なリレー混在のページ境界／上限で切り詰めるリレーのページ送り／取得中の強制要求の後続実行／探索で判明したリレーへの早期問い合わせ／表示中の著者の追い出し保護／墓標破棄時の対象除去。既存の`BadgeFetchEfficiencyTest`は、キャンセルが待機者へ波及しないこと、部分取得をエラーにしないことへ期待値を更新した。
