# 通常投稿の下書き一覧の読み込み 設計

作成日: 2026-10-13
状態: 要件確定。未実装
関連: `article-draft-list-and-edit-design.md`（6.2 時間切れで取得が止まる不具合）、`relay-unavailable-design.md`

## 1. 背景

記事下書きの一覧で、接続できないリレーや遅いリレーがあると読み込みが遅い問題を直した（`article-draft-list-and-edit-design.md`）。
同じ仕組みを使う箇所を調べたところ、通常投稿の下書き一覧（投稿シートの「下書き一覧」）にも近い問題があった。

## 2. 現状

- `DraftListSheet` は、下書き用に選んだリレー（`RelayStore.selectedMemoRelayUrl`、なければ先頭のリレー）の1つだけから取得する。保存先も同じリレー。
- `DraftMemoRepository.loadAll` は有限取得（8秒）の信号を、流れが閉じるまで受け取り続ける。`FetchCompleted` の結果は見ていない。
- そのため次のことが起きる。
  - リレーが EOSE を返さずに時間切れ・接続不可・CLOSED で終わっても、受け取れた分だけを正常な一覧として出す。1件も受け取れなければ「下書きはありません」になり、下書きが消えたように見える。
  - 有限取得が時間切れで終わったとき、購読の後片付けが止まる不具合（`article-draft-list-and-edit-design.md` 6.2）で、流れが閉じずに読み込み中のままになりうる。通信の層は直したが、受け手の側でも守る。
- 1リレーだけの取得なので、「最初に応答したリレーで先に一覧を出す」（記事下書きの L1）は当てはまらない。

## 3. 要件

| # | 要件 |
| --- | --- |
| P1 | `FetchCompleted` を受けた時点で受信を終える。流れが閉じなくても読み込み中のままにしない |
| P2 | リレーが EOSE を返さずに終わったとき、1件も受け取れていなければ「下書きはありません」と表示せず、取得できなかったことと「再取得」を表示する |
| P3 | EOSE を返さずに終わったが一部を受け取れたときは、その一覧を出し、「一部の下書きが表示されていないか古い可能性があります」と、リレー名を小さく添える |
| P4 | 取り直し中は、表示中の一覧を消さない（現状どおり） |

待つ時間（8秒）は変えない。接続できないと分かっているリレーは、通信の層の判定ですぐ「接続不可」で終わる。

## 4. 設計

- `DraftMemoRepository.loadAll` の戻り値を、下書きの一覧と「そのリレーから取り切れたか」（`complete`）、取り切れなかったときの理由を持つ型にする。
  `complete` は `FetchCompleted` で対象リレーが `Eose` のときだけ true。`FetchCompleted` が届かずに流れが閉じた場合も false。
- `DraftListState` に、取り切れなかったリレー（`incompleteRelay`）を持たせる。
  - 1件も受け取れず取り切れなかった: `error` に「下書きを取得できませんでした（リレー名）」を入れ、シートでは「再取得」ボタンを添える。
  - 一部を受け取れたが取り切れなかった: 一覧の上に小さな警告（`bodySmall`、記事下書きと同じ文面の形）を出す。
- 「再取得」は同じリレーで `load` をやり直す。

## 5. テスト（実装前に書く）

| 対象 | 確認すること |
| --- | --- |
| P1 | `FetchCompleted` の後も流れが閉じない偽の購読で、`loadAll` が返る |
| P2 | `FetchCompleted` が時間切れ・接続不可で、イベントなしのとき `complete = false`、ViewModel は `error` を出し一覧は空 |
| P3 | 時間切れでもイベントがあれば一覧を返し、`complete = false`。ViewModel は一覧と警告を出す |
| 正常 | EOSE なら `complete = true`、警告なし |

## 6. 実機での確認

- 下書き用のリレーが応答する通常の状態で、一覧が変わらず出ること。
