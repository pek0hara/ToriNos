# ジャーナル 月の一括取得 設計

作成日: 2026-10-09
状態: 実装済み（2026-10-09）。結果は 9章。
関連: `journal-refactor-design.md`（U3・U5、9.4 参照先の取得の見直し）

## 1. 背景

Android 実機（yabu.me 指定、有効4リレー）のログで、月を開いたときの取得を数えた。

| 操作 | ジャーナル本体の REQ | 届いたイベント | 所要時間 |
| --- | --- | --- | --- |
| 10月（9日分）を開く | 9（1日1回） | 16 | 約1.2秒 |
| 9月（30日分）を開く | 30（1日1回） | 66 | 約2.5秒（参照先を除く） |
| 9月、メンバー2人 | 30 | 約330 | 約4秒 |

1回の REQ で届くのは 0〜35件で、1日500件の上限（`DATE_LIMIT`）に比べてはるかに少ない。
REQ は前の日の結果を待ってから送るため、1日あたり 50〜100ms の往復がそのまま積み上がる。

もう1つ、件数の上限の扱いに穴がある。

- **U5**: 1日500件の上限に届いても、全リレーが EOSE を返せばその日を取得済みにする。
- **もらったいいねの月単位取得**は `limit=5000` で送っている。リレーの `max_limit`（NIP-11）が 500 なら
  500件しか返らないが、EOSE が来るので月全体を取得済みにする。残りは二度と取りに行かない。

## 2. 目的

1. 月の残りの日の取得（バックフィル）を、日ごとではなく範囲で1回の REQ にする。
2. 件数の上限に届いたら `until` を下げて続きを取り、取りこぼしを取得済みとして記録しない（U5 と、もらったいいねの穴を塞ぐ）。
3. 取得済みの記録（`JournalCoverage`）の意味は変えない。「その日・その種類・そのメンバーは全リレーから取り切った」。

## 3. 非目標

- 選択日の初回取得（`forDate`）は残す。開いた直後に、その日だけを先に出すため。
- 日付選択（`loadDate`）と日の更新は日単位のまま。
- エンゲージメント、参照先、プロフィールの取得。
- `JournalCoverage` のデータ構造。

## 4. 方式

### 4.1 範囲の取得計画 `JournalFetchPlanner.forRange`

```kotlin
fun forRange(
    days: List<LocalDate>,                                 // 月初〜今日（または月末）
    coverage: JournalCoverage,
    kinds: Set<JournalActivityKind>,
    members: Collection<String>,
    relayUrl: String?,
    clock: JournalClock,
): List<JournalFetchRequest>
```

- メンバーごとに「範囲内のどこかで足りない種類」の和を求め、同じ種類のメンバーを1つのリクエストにまとめる
  （`forDate` と同じまとめ方。普段は1本）。
- 各リクエストの範囲は、そのメンバーたちに足りない日がある最初の日から最後の日まで。
  `since` はその最初の日の 0:00、`until` は最後の日の 23:59:59。`dates` はその間の全日。
- 範囲内に取得済みの日が挟まっていても取り直す。結果は ID で重複を除くため害はなく、
  REQ を分けるより安い。選択日は普通、範囲の端（今日か月末）にあるため範囲から外れる。
- もらったいいねは別のリクエストにする（取得先が有効な全リレーで、フィルターも違うため）。
  現行の `monthReceivedLikes` をこの形に置き換え、`limit` をページの上限にそろえる。
- ページの上限 `PAGE_LIMIT = 500`。

### 4.2 打ち切りの検知（取得元）

`JournalFetchResult` に `truncatedAt: Long?` を足す。「`truncatedAt` より新しいイベントは全部届いた。
`truncatedAt` 以前は届いていないものがある」。null なら範囲全体が届いた。

`NostrJournalEventSource` は、リレーごと・フィルターごとに件数と最古の `created_at` を数え、
件数がしきい値に届いた組の最古の時刻の最大値を `truncatedAt` にする。

- しきい値は `EngagementFetcher` と同じ規則にする。リレーの `max_limit` が分かれば `min(max_limit, PAGE_LIMIT)`、
  分からなければ保守的に 100。リレー側の既定の上限が 500 より小さい可能性があるため。
  分からないリレーで 100件以上届いた場合、続きが空でも1回余分に取る。
- フィルターごとに数えるのは、`limit` がフィルターごとにかかるため。イベントがどのフィルターに当たるかは
  種類（`kinds`）で決める。計画が作るフィルターは、1つのリクエストの中で種類が重ならない
  （kind 1/6/16/7 と kind 1111、またはもらったいいねの kind 7 だけ）。テストで固定する。
- 数えるために、購読は `deduplicateEvents = false`、`replayCachedEvents = false` にする。
  他のリレーで受信済みのイベントを省かれたり、キャッシュの再生が混ざったりすると、
  そのリレーが返した件数が分からなくなるため（フィードの履歴取得と同じ理由）。結果は ID で重複を除く。
- 判定は純粋関数 `journalTruncatedAt(counts, threshold)` にし、テストで固定する。

### 4.3 ページの積み上げ `JournalRangePager`

範囲の取得を、`until` を下げながら繰り返す純粋な状態。

```kotlin
internal class JournalRangePager(request: JournalFetchRequest, clock: JournalClock, maxPages: Int) {
    /** 次に送るリクエスト。終わったら null。 */
    fun next(): JournalFetchRequest?
    /** 1ページの結果を受け取り、取り切れた日とその日のイベントを返す。 */
    fun accept(result: JournalFetchResult): JournalPageOutcome
    /** 終わった時点で、取り切れなかった日のイベント（取得済みにはしない）。 */
    fun leftovers(): List<NostrEvent>
}

data class JournalPageOutcome(val closedDates: List<LocalDate>, val events: List<NostrEvent>)
```

- ページの結果が未完了（タイムアウト・未応答）なら、そこで終える。そのページで届いたイベントは `leftovers` に回す。
- 完了で `truncatedAt == null` なら、残りの日をすべて「取り切れた」とする。
- 完了で `truncatedAt = B` なら、0:00 が `B` より後の日を取り切れたとする。`B` を含む日は保留し、
  次のページを `until = B` で送る（同じ秒のイベントを取りこぼさないよう `B` を含める。重複は ID で除く）。
- `B` が前のページの `until` から進まない（同じ秒に上限以上のイベントがある）、またはページ数が `maxPages`（20）に
  届いたら、そこで終える。残りの日は取得済みにしない。
- 保留中の日のイベントは、その日が取り切れたときにまとめて返す。
  更新（`replace`）では、取り切れた日の既存の行を消してから足すため、日の途中までのイベントを先に足してはいけない。

### 4.4 コントローラー

バックフィルは次の順にする。

1. もらったいいね（選んでいれば）: `forRange` のもらったいいねのリクエストをページ送りで取る。
2. それ以外: `forRange` の各リクエストをページ送りで取る。

ページごとに、取り切れた日を `request.copy(dates = closedDates)`、`complete = true` の結果として
既存の `applyResults` に渡す。こうすると、取得済みの記録・`replace` の削除・分類の処理を変えずに使える。
終わったときの `leftovers` は `complete = false`（取得済みにしない、消さない、足すだけ）で渡す。

世代の確認（`isCurrent(token)`）は各ページの後に行う。参照先はこれまでどおり、月の取得を終えてから1回で取る。

### 4.5 選択日の初回取得と日付選択

日単位の取得のまま残す。もらったいいねを月単位で取る場合は初回取得から外す、という現行の規則
（`willFetchMonthReceivedLikes`）も残す。

日単位の取得でも `truncatedAt` を見て、上限に届いた結果は未完了として扱う（足すだけで、取得済みにしない、消さない）。
選択日は取得済みにならないので、続くバックフィルの範囲に入り、ページ送りで取り切られる。
日付選択（`loadDate`）は月を開き直さないため、上限に届いた日はその場では取り切らず、次に月を開いたときに取る。

## 5. 期待する効果

| 操作 | REQ（変更前） | 変更後 |
| --- | --- | --- |
| 10月を開く | 9 | 2（選択日1、残りの範囲1） |
| 9月を開く | 30 | 2 |
| 9月、2人 | 30 | 2（2人は同じ種類が足りないので1本） |
| もらったいいね（月） | 1×4リレー | 1×4リレー（上限に届いたリレーがあれば続きを取る） |

## 6. 挙動の変化

- バックフィル中の表示が、1日ずつではなくページ単位で増える。ページは普通1つなので、月の残りの日がまとめて出る。
- 件数の上限に届いた日は取得済みにしないため、続きを取る（U5 の解消）。
- 日単位の取得で上限に届いた日も取得済みにしない（4.5）。

## 7. テスト

| 対象 | テスト |
| --- | --- |
| `forRange` | 足りない日の範囲、取得済みの日を挟む場合、メンバーのまとめ方、種類が重ならないフィルター、もらったいいねの別リクエスト |
| `journalTruncatedAt` | しきい値未満は null、届いた組の最古、複数の組は最大値、`max_limit` 不明時のしきい値 |
| `JournalRangePager` | 打ち切りなしで全日、打ち切りの日を保留して次のページ、未完了で終了、進まないときの終了、ページ数の上限 |
| `JournalController` | 月の残りが1回のリクエスト、続きのページで残りの日を取る、更新でページをまたぐ日を正しく置き換える、未完了の日は取得済みにしない |

## 9. 実装結果

### 9.1 実装

| 設計 | 実装 |
| --- | --- |
| 4.1 | `JournalFetchPlanner.forRange`。`monthReceivedLikes` と `MONTH_RECEIVED_LIKE_LIMIT` は削除した |
| 4.2 | `NostrJournalEventSource` が `journalFilterTallies` → `journalTruncatedAt`（しきい値は `journalPageThreshold`）で `truncatedAt` を出す |
| 4.3 | `JournalRangePager`（`journal/JournalRangePager.kt`）。ページ数の上限は 20 |

### 9.2 実機での前後比較（Android、yabu.me 指定、有効4リレー）

| 操作 | REQ（変更前） | 変更後 | バックフィルの時間（変更前 → 後） |
| --- | --- | --- | --- |
| 10月を開く | 9 | 2 | 約1.2秒 → 約0.1秒 |
| 9月を開く | 30 | 2 | 約2.5秒 → 約0.12秒 |
| 9月、メンバー2人（267件） | 30 | 2 | 約4秒 → 約0.35秒 |
| 9月のもらったいいね（240件） | 1×4リレー | 1×4リレー | 変わらず |

ページ送りは、一時的に `PAGE_LIMIT = 50` にしたビルドで実リレー相手に確かめた。9月は1ページ目 61件（kind 1 が 50件で打ち切り）、
`until` を下げた2ページ目 6件で取り切り、合計は上限 500 のときと同じ 84件だった。

### 9.3 レビューで確かめたこと

- **ページをまたぐ日の置き換え**: 更新で、前のページで届いた日の途中までの行を、その日を置き換えるときに消さない。
  `JournalRangePager` が取り切れるまで保留して返すことで防ぎ、`refreshReplacesADaySplitAcrossPagesOnlyOnceItIsComplete` で固定した。
- **取得元の集計**: 重複排除とキャッシュの再生を切ること、上限に届いたリレーの最古の時刻を `truncatedAt` にすることを
  `JournalEventSourceTest` で固定した（レビューで足した）。
- **テストの偽リレー**: 当初は上限を「超えたとき」だけ打ち切っていたが、実際のリレーは上限ちょうどを返す。
  上限に届いたら打ち切る形に直した。

### 9.4 残る制約

- `max_limit` が分からないリレーでは、1回に 100件以上届くと続きを1回余分に取る。日単位の取得（日付選択）で
  100件以上ある日は取得済みにならず、次に月を開いたときのバックフィルで取り切る。
- 同じ秒に上限以上のイベントがある、またはページ数の上限（20ページ、約1万件）に届いた月は、残りの日を取得済みにしない。
  その月を開くたびに取り直す。
- バックフィルの対象メンバーは始めた時点で決める。途中で隠した人の分も、その月は取り切る。

## 10. 月一覧の最初の表示（2026-10-09 追記）

### 10.1 観察（Android 実機の録画）

1. タブの切り替え中と、選択日（今日、0件）の取得が終わってから月の残りが届くまで、「この月・0件」「この月の投稿はありません」が出る。
   初期状態が `isLoading = false` で、選択日の取得が終わると読み込み中を解除していたため。
   リレーの設定を読み込む前に `loadMonth` が呼ばれたときも、読み込み中を解除していた。
2. リポスト元などの名前が16進で出て、後から差し替わる。
3. 一覧が先頭（10/01）で1コマ描かれてから、今日の位置（10/08）へ跳ぶ。位置合わせが最初の描画の後に動いていた。

### 10.2 方式

- `JournalState.initial` は `isLoading = true` で始める。リレーやメンバーがそろう前の `loadMonth` では読み込み中を解除しない。
- `isBackfilling` を足す。月の残りの取得・参照先の取得・名前がそろうまで（上限1秒）を含む。前の月の取得をやめたときも残らないよう、月を読み込むたびに戻す。
- 月一覧は `isBackfilling` が終わってから1回で出す（`journalListContent`）。日表示はその日の取得が終われば出す。件数も同じ条件で出す。
- 今月を開いたときの今日への位置合わせは、一覧の最初の配置の前に `requestScrollToItem` で予約する。その後の追いかけは今までどおり。
