# 参加中グループのタイムライン 設計

- 作成日: 2026-11-18
- ステータス: 実装済み。2026-11-27 に「スレッド」の絞り込みを追加（単体テスト済み。エミュレーターでは切り替えと空の表示だけ確認。Buzz の実データでの確認は未）
- 目的: チャットタブで、参加中のすべてのグループ（Buzz・標準の NIP-29）の投稿を1つの一覧で読めるようにする。Google Chat のホームのように、スレッドは「元の投稿 + 最新の返信」の1行にまとめ、最後に動きがあった順に並べる。
- 関連: `docs/nip29-buzz-design.md`（チャットタブと Buzz 対応の全体）。

## 1. 画面

チャットタブの上部（ヘッダーの下）に切り替えを置く。ヘッダーでリレー・コミュニティを選んでいるときだけ出す（「すべて」と DM では出さず、チャンネルの一覧を出す）。

```
[ チャンネル | タイムライン ]
```

- **チャンネル**: 今の一覧（チャンネルごとに1行）。既定。2026-11-27 に「グループ」から改名（作成の「新しいチャンネル」と合わせる。NIP-28 の方は「トピック」に改名）。
- **タイムライン**: 会話ごとに1行。範囲は選んでいるリレーの参加中のチャンネル。
- チャンネルのタブの上の左に絞り込みのチップ「# チャンネル」「💬 スレッド」（2.2）。既定はチャンネルとスレッドを混ぜて出す。
- 選んだ表示はアカウントごとに端末へ保存し、次に開いたときも使う（`chat.view.<pubkey>`）。

### 1.1 行（実際の投稿に近い形）

```
[#] welcome-everyone 💬
[avatar] 部長  14:44
         @ぺこ さん、ようこそ 👋 自己紹介・質問、気軽にどうぞ…（本文をそのまま。Markdown・画像も出す）
      ╰ [avatar] 部長  14:50
                 @N 修正しました。…
```

- 見出しはグループのアイコン（小）と名前。返信がある会話はスレッドの印を付ける。
- 元の投稿は、チャットの画面の発言と同じくアイコン・名前・時刻・本文（Buzz は Markdown と画像、標準はリンク付きの本文）。フォーラムの投稿・kind 11 は見出しを出す。
- 返信があれば、最新の返信を「╰」を付けて字下げし、同じ形（アイコンは小さめ）で出す。その下に「💬 返信 n件 ▸」（読めている返信の数）。
- 元の投稿が読めないときは「元の投稿を読み込めません」と出し、返信だけを出す。
- 会話の間は線で区切る。「今日」「昨日以前」で区切る（端末の日付で判定）。
- Buzz の画像は、グループの画面と同じく `/media/` に署名を付けて読む（外部署名器では押して許可）。
- 長い本文の畳み方は、チャンネルの画面のスレッドの表示（元の投稿 + 「╰」の最新の返信）と同じ。元の投稿は 80 文字・5 行（`BodyCollapse.Channel`）、最新の返信は 50 文字・3 行（`BodyCollapse.ReplyPreview`）で畳み、「もっと見る」で開く。
- 押したとき:
  - 返信のある会話、フォーラムの投稿、kind 11 → スレッド画面（`GroupThreadRoute`）。
  - 返信の無いチャットの投稿 → そのグループの画面（フォーラムのグループはフォーラムの画面）。
- 一番下に「さらに読み込む」。

### 1.2 グループの一覧の最新の発言

グループの一覧（「グループ」の表示）でも、最新の発言が Buzz のスレッドの返信なら、元の投稿の1行を上に出し、返信を「╰」を付けてその下に出す。ルートは一覧の読み込みのあとに `ids` で読み、端末の控え（`ChatListCache`）にも残す。読めなければ返信だけを出す（今までと同じ）。

## 2. 会話の単位

| 種類 | 会話のルート | 返信として数えるもの |
| --- | --- | --- |
| Buzz のチャット | `root`/`reply` の `e` タグが無い kind 9・40002 | `buzzThreadRootId` がそのルートの kind 9・40002 |
| Buzz のフォーラム | kind 45001 | kind 45003（`buzzThreadRootId`） |
| 標準のチャット | すべての kind 9（`q` 返信もスレッドにまとめず1行。返信先は読めていれば `replyTo` に入る） | なし |
| 標準のスレッド | kind 11 | kind 1111（`E` タグ） |

- 「最後の動き」= ルートと読めている返信の `created_at` の最大。
- 削除（作者の kind 5、管理者・リレーの kind 9005）と Buzz の編集（40003）は `GroupTimeline` と同じに反映する。ルートが削除された会話は出さない。
- ミュートした人の投稿は出さない。最新の返信がミュートした人なら、その前の返信を出す。ルートがミュートした人なら会話ごと出さない。
- Buzz の「スレッドから送信」したコピー（`buzz:sent-from-thread`）はトップレベルの投稿として出る（Buzz のチャンネルでもそう見えるため）。

### 2.1 bot を隠す（Buzz）

Buzz のコミュニティを選んでいるときは、一番上の見出し（「今日」か「昨日以前」）の右端に切り替えを出す（専用の行は取らない。投稿が無いときは右端に寄せた行に出す）。塗らずに文字だけで小さく出し、オフは灰色の「🤖 bot を表示中」、オンは色付きの「🤖 bot 非表示 · n ✓」。n は隠している投稿の数（表示の範囲の中で、削除・ミュートを除いた bot の投稿。`JoinedTimelineLoader.hiddenBotPosts`）。オンにすると bot の投稿を出さない。

- 最新の返信は人のものを出す。返信の数は bot の返信も数える（スレッドを開けば見えるので、開いたときの数と合わせる）。
- ルートが bot の会話は、人の返信があれば元の投稿（bot の投稿）ごと残す（何への返信か分かるように。押すとスレッドを開く）。人の返信が無ければ出さない。「最後の動き」は人の返信の時刻。こうして出す元の投稿は、隠している数 n に数えない。
- ミュート（ルートがミュートした人なら会話ごと出さない）とは扱いが違うので、`GroupTimeline.conversations(muted, hidden)` で分けて渡す。

- bot とみなす人（リレーごと）:
  - 読めたイベントのうち、エージェントの発言（kind 40002）の作者（`groupMessageAuthor`）。その人の kind 9 も隠す。
  - 参加中のグループのメンバー一覧（kind 39002、リレーの鍵の署名、最新のもの）で役割が `bot` の人。
- 読み直さず、読めているものから作り直す。オンにして行が減っても、続きは「さらに読み込む」で読む。
- 設定はアカウントごとに端末へ保存する（`chat.hideBots.<pubkey>`）。コミュニティごとには分けない。
- 標準の NIP-29 のリレーでは出さない（bot の印が無い。メンバー一覧は大きくなりうるので読まない）。
- kind 0 の `bot`（NIP-24）は見ない（プロフィールは後から届くので、行の作り直しの時機が別に要る）。

`GroupTimeline` に `conversations()` を足して、1グループ分の会話を作る。全グループ分をまとめて並べるのは `JoinedTimeline`（純粋な関数）が行う。

### 2.2 チャンネルとスレッドの一覧（2026-11-27）

Google Chat のホームと同じく、チャンネルのタブにチャンネルと「自分が関わっているスレッド」を混ぜて出し、上の左のチップで絞る。

```
[# チャンネル] [💬 スレッド]
[#] しょーもな                 21:50   ← チャンネル
[#💬] talk-雑談                 21:30   ← スレッド（アイコンの右下に印）
    (av) 元の投稿の1行…
    ╰ (av) 最新の返信（2行まで）
[🔒] dev-開発                   21:20
```

- チップ（`FilterChip`、`ChatListFilterChips`）: 何も選んでいなければ両方（`ChatListFilter.Both`、既定）。「チャンネル」はチャンネルだけ（今までの一覧）、「スレッド」はスレッドだけ。選べるのはどちらか一方で、選んでいるチップを押すと両方に戻る。アカウントごとに端末へ保存する（`chat.listFilter.<pubkey>`）。
- 出す場所: リレー・コミュニティを選んでいるときのチャンネルのタブと、チャンネルのある「すべて」（参加中の全リレーから集める）。DM の一覧とタイムラインのタブでは出さない。
- 混ぜ方（両方のとき）: 未読のチャンネルは今まで通り先頭。その下で、既読のチャンネルとスレッドを最後の動きの新しい順に混ぜる（`mergeChannelsAndThreads`。同じ時刻ならチャンネルが先）。「すべて」ではリレーごとの見出しの中で混ぜる。チャンネルの行がプレビューに出している投稿（最新の発言か、その上に出しているスレッドの元の投稿）のスレッドは、重ねて出さない（`threadsNotInChannelPreviews`）。
- 出すスレッド: スレッドの画面を開く会話（`JoinedTimelineEntry.opensThread`。返信のある会話、フォーラムの投稿、kind 11）のうち、自分が関わっているもの（`GroupConversation.involvesMe`）。
- 関わっている: 元の投稿か読めている返信（ミュートした人のものは除く）のどれかが、自分の投稿か、自分を `p` タグで指している。bot を隠して元の投稿を出していない会話でも、元の投稿を数える。
- スレッドの行: チャンネルと同じカード（`GroupRowItem`）で、アイコンの右下にスレッドの印（カードの色の縁で、アイコンと切り離す）。話題が主役なので、チャンネル名は小さい灰色の見出しにし、元の投稿を太めの1行目にする。最新の返信は「╰」で2行まで（`ChatTimelineRow.threadCard`）。返信の無いフォーラムの投稿・kind 11 は元の投稿だけ、元の投稿が読めなければ返信だけ。未読はチャンネルのものなので出さない。押すとスレッドの画面。
- 読み込み: タイムラインと同じ `JoinedTimelineLoader` を使い、スレッドを出しているときだけ読む（`ChatTabUiState.needsTimeline`）。既定で両方を出すので、チャンネルのタブを開くと読む。bot は隠さない（`threadRows`）。読めている範囲（リレーごとに新しい投稿から1ページ）の中で探すので、古いスレッドは「スレッド」だけにしたときの「さらに読み込む」で出る。
- 「スレッド」だけで無いときは「関わっているスレッドはありません」。
- チャンネルのページは、表示がまだタイムラインのとき（スワイプで移っている間）もスレッドを混ぜて描く（`channelPageShowsThreads`）。止まってから差し込むと、チャンネル→スレッドの順に出て見えるため（2026-11-28）。
- 未読のスレッド（Google Chat の太字）と、未読だけに絞る切り替えは、スレッドが未読を持たないので今回は入れない。

## 3. 読み込み

リレーごとに並行して読む。参加中のグループの一覧と各リレーの鍵（NIP-11 の `self`）は、今の一覧の読み込み（`ChatTabViewModel`）が持っているものを使う。

1. **最近の投稿**: `kinds` = 上の表の種類すべて、`#h` = そのリレーの参加中のグループID、`limit` = 100。
2. **続き**（1 で読めたものについて、1回の要求にまとめる）:
   - 返信のルートで、まだ読めていないもの: `ids`。
   - ルートへの返信（返信の数と最新の返信）: `#e` = ルートID（Buzz）、`#E` = ルートID（kind 1111）、`limit` = 500。
   - 削除と編集: kind 5・9005・40003、`#e` = 読めた投稿の ID。
   - 管理者（kind 39001、リレーの鍵の署名）: 9005 を誰のものとして認めるか。
   - Buzz ではメンバー一覧（kind 39002、同じフィルター）: 役割が bot の人（2.1）。
3. 一部のリレーが答えなくても、答えたリレーの分を出す。答えなかったリレーは行の上に「読めなかったリレーがあります」を出す（リレーの名前つき）。

### 3.1 リレーごとの範囲のずれ

リレーごとに `limit` 件を読むと、読めている期間がリレーで違う（よく動くリレーは数時間分、静かなリレーは数か月分）。そのまま混ぜると、よく動くリレーの古い部分が抜けたまま、静かなリレーの古い投稿が並んでしまう。

- `limit` いっぱいに返ってきたリレーについて、読めた最古の `created_at` を「そのリレーの下限」とする。
- 表示の下限 = 下限のうち最も新しいもの。「最後の動き」がこれより古い会話は、まだ出さない（`JoinedTimeline` で切る）。
- 「さらに読み込む」では、下限にかかっていたリレーだけを、そのリレーの最古を `until` にして読み足す（同じ秒を取りこぼさないよう、最古の秒を含める。`OlderPager` と同じ扱い）。

### 3.2 いつ読むか

- タイムラインに切り替えたとき、およびタイムラインを出したままタブに戻ってきたとき（今の一覧の `refreshJoined` と同じ時機）。
- 読み直しのときは前の結果を出したまま読み、そろったら差し替える。
- 読み込み中の表示はグループの一覧に合わせる。参加中の一覧を読み直している間とタイムラインを読んでいる間は、タブの上に線を出す。行が無いうちは行の形（スケルトン）を出し、「投稿がありません」は読み終えてから出す。
- 「読めなかったリレーがあります」は、読み込み中（参加中の一覧の読み直しを含む）は出さない。起動直後の接続前の失敗は、続く読み直しで消えるため。
- 配信（購読し続けること）はしない（初版）。

### 3.3 表示までの時間（2026-11-21）

開いてから行が出るまでが遅かった。原因は待ちが直列に重なっていたこと:

- 参加中の一覧の読み直し（`refreshJoined`、Buzz はリレーごとに 2〜4 往復）が全部終わってから、タイムラインを読み始めていた。
- リレーごとに「最近の投稿 → 続き（ルート・返信）→ 削除・編集・管理者」の 3 往復を順に待っていた。
- すべてのリレーが終わるまで 1 行も出さなかった。答えないリレーが 1 つあると、タイムアウト（10 秒）まで全体が待つ。

次のように変える。

1. **一覧の読み直しを待たない**: 一覧の読み直しを始めるときに、今わかっている参加中のグループ（前回の控え `ChatListCache` から戻したもの）でタイムラインも読み始める。読み直しが終わって、タイムラインに入れるグループ（`timelineGroups()`）が変わっていたときだけ、もう一度読む。同じグループで読み込み中なら取り消さない（起動直後は `refreshJoined` が何度か続けて呼ばれるため）。
2. **読めたリレーから出す**: リレーごとに 1 ページ（続きまで）読み終えたら、その時点で行を出す。表示の下限（3.1）は読み終えたリレーだけで決める（まだ答えていないリレーは下限にしない）。遅いリレーの分は後から差し込まれる。ただし前の結果を出しているとき（読み直し）は今までどおり、そろってから差し替える（行が減ったり並びが揺れたりしないように）。
3. **往復を減らす**: 続き（ルート・返信）と、1 ページ目の投稿についての削除・編集・管理者・メンバー一覧を同時に送る。続きで新しく読めた投稿（ページより古い返信・ルート）の削除・編集だけを後から読む（無ければ送らない）。行は後からの分を待ってから出す（削除した返信・ルートが一瞬出ないように）。

確認のため `[Timeline]` のログ（`PlatformLog.kt` の `isTimelineTraceEnabled`）で、一覧の読み直し・リレーごとの各往復の所要時間と件数・行を出した時刻を出す。

あわせて、起動直後に参加中の一覧（kind 10009）を読む前にグループ 0 件で「読み終えた」としていた（「投稿がありません」が一瞬出うる）のを、一覧を読み終え、一覧の読み直しも終わっているときだけ空と決めるようにした。グループの比較は並び順を無視する（集合で比べる）。

計測（2026-11-21、iOS シミュレータ、png.communities.buzz.xyz の 7 チャンネル、コールドスタートからタイムラインの行が出るまで、各 3 回）:

| | 1 | 2 | 3 |
|---|---|---|---|
| 変更前 | 6.7 秒 | 8.0 秒 | 8.4 秒 |
| 変更後 | 2.5 秒 | 4.6 秒 | 2.3 秒 |

残りの大半は 1 ページ目（`limit` 100）の答えを待つ時間（約 1.1〜1.3 秒）。一覧の読み直しと同じリレーに同時に聞くと、各往復が 0.2 秒から 1.3 秒ほどに延びることがある（変更後の 2 回目）。

### 3.4 読み込みの見直し（2026-11-28。実装済み・単体テスト済み、実機の計測は未）

#### 3.4.1 今の問題

チャンネルのタブに既定でスレッドを混ぜた（2.2）ので、タイムラインの読み込み（3 章）がチャンネルのタブを開くたびに走るようになった。

| | 今 | 問題 |
| --- | --- | --- |
| いつ読むか | チャットタブに入るたび（スレッド・チャンネルの画面から戻ったときも。`ChatTabScreen` の `LaunchedEffect(Unit)` → `refreshJoined()` → `refreshTimeline(force = true)`）と、バックグラウンドから戻ったとき | 毎回いちから読む。スレッドを開いて戻るだけで、リレーごとに 100 件と続き（ルート・返信 500 件・削除・編集）を読み直す。「すべて」では参加中の全リレー |
| 自分のスレッドの探し方 | 最近の投稿（リレーごとに 100 件）の中の、自分が関わっている会話（`isMyThread`） | 動きの多いリレーでは、少し前に自分が返信したスレッドがすぐ範囲から出て、一覧から消える |
| 古いスレッド | 「さらに読み込む」で全員の投稿をさかのぼる | 自分のスレッドを1つ探すのに、関係ない投稿を何百件も読む |

持ち方（`JoinedTimelineLoader` の中のリレーごとの `GroupTimeline`、会話のまとめ方・削除・編集・ミュート）は共通のままでよい。変えるのは**読む入口**と**読み直しの仕方**。

#### 3.4.2 自分が関わった投稿を狙って読む

リレーごとに、1（最近の投稿）と同時に次も読む（同じ要求にまとめる）。

- `kinds` = 上の表の種類、`#h` = 参加中のグループID、`authors` = [自分]、`limit` = 100。
- `kinds` = 同じ、`#h` = 同じ、`#p` = [自分]、`limit` = 100（メンションされた投稿。Buzz でリレーが署名し、先頭の `p` が作者のもの（`groupMessageAuthor`）も、作者が自分ならここで読める）。
- 読めたものは同じ `GroupTimeline` に入れ、続き（2）も同じように読む（返信のルートを `ids` で、ルートへの返信を `#e` / `#E` で）。
- これらは表示の下限（3.1 の `floor`）を決めない。タイムラインの行（`entries`）は今まで通り下限で切る（タイムラインに古い投稿が飛び飛びに混ざらないように）。関わっているスレッド（`myThreads`）は下限で切らない。
- 「スレッド」だけにしたときの「さらに読み込む」は、この2つを `until` でさかのぼる（全員の投稿はさかのぼらない）。両方のときの一覧では「さらに読み込む」を出さない（今まで通り）。
- 読めないもの: Buzz でリレーが署名し、作者が `actor` タグにだけあるもの（`actor` は1文字のタグではないので、リレーに問い合わせられない）。これは最近の投稿（1）に入っていれば出る。

#### 3.4.3 入るたびに全部読み直さない

`refreshTimeline(force = true)` の「いちから読み直す」をやめ、次のように分ける。

| きっかけ | 読み方 |
| --- | --- |
| 前回読み終えてから 60 秒以内にチャットタブに入った（スレッドから戻ったなど）、グループが同じ | 読まない（今の結果を出す） |
| それ以外でチャットタブに入った、バックグラウンドから戻った | **差分**: リレーごとに、前回読めた最新の `created_at` から 60 秒戻した `since` で 1 と 3.4.2 を読み、続き（2）は新しく読めた投稿の分だけ読む。削除・編集（kind 5・9005・40003）も同じ `since` と `#h` で読む（前に読んだ投稿の削除・編集も拾う） |
| 差分が `limit` いっぱいだった（間が空きすぎた）、前回から 30 分以上たった、グループが変わった、前回読めなかったリレー | そのリレーだけ、いちから読む（今まで通り） |

- 読んでいる間は前の結果を出したまま（今まで通り）。差分で増えた行は、読み終えたときに一度に足す。
- いちから読むリレーも、グループが同じなら、読み終えるまで前の結果を出しておく。リレーが答えなかったら（バックグラウンドから戻った直後など）前の結果を残し、「読めなかったリレー」だけを出す（2026-11-28、実機で一覧が空になったため）。グループの同じ・違うは並びによらず中身で比べる。
- いちから読んで何も答えなかったリレーは、2 秒待ってもう一度だけ読む（起動直後に初めて開いたときは前の結果が無いので、空の一覧にしない）。その間は読み込み中の表示のまま。一部でも読めたリレーは読み直さない。
- 「読み終えた時刻」と「最新の `created_at`」は、`JoinedTimelineLoader` のリレーごとの状態に持つ（端末には保存しない。アプリを起動し直したら、いちから読む）。

#### 3.4.4 今回やらないこと

- チャンネルの一覧の「各チャンネルの最新の発言」とタイムラインの読み込みの重複（同じ投稿を2回読む）。両方のつなぎ方が違う（チャンネルごとの最新 1 件と、リレーごとの最新 100 件）ので、3.4.2・3.4.3 のあとに計測してから決める。
- `rows`（タイムライン、bot を隠す）と `threadRows`（スレッド、隠さない）を1つにすること。
- 購読（新しい投稿をその場で足す）。

#### 3.4.5 確かめ方

- 単体テスト（`JoinedTimelineTest`）: 最近の 100 件に入らない自分の返信のスレッドが出る、メンションされたスレッドが出る、自分の投稿は下限で切られない（タイムラインには出ない）、差分の `since`、差分が `limit` いっぱいならいちから、60 秒以内は読まない、削除の差分で消える。
- 実機の計測（Android、`[Timeline]` のログ）: 変更の前後で「チャットタブを開く → スレッドを開く → 戻る」を 3 回くり返し、要求の数と読んだイベントの数を比べる。

### 3.5 スレッドの行を端末に控える（2026-11-28）

#### 3.5.1 今の問題

チャンネルのタブを開くと、チャンネルの行はすぐ出るが、スレッドの行は数秒あとから間に差し込まれ、チャンネルの行が下にずれる。

- チャンネルの行は前回の控え（`ChatListCache`）から戻すので、すぐ出る。
- スレッドの行（`threadRows`）はタイムラインの読み込み（`JoinedTimelineLoader`）からしか作らず、端末に保存しない（3.4.3）。起動し直すと、アカウントの準備・控えの復元を待ってから、リレーへの 2 往復（1 ページ目と自分の投稿 → 続き）を読み終えるまで出ない。

#### 3.5.2 やること

スレッドの行も前回の控えから出し、読み終えたら差し替える（チャンネルの行と同じ形）。

- **保存**: タイムラインを読み終えたとき（`publishTimeline(loaded = true)`）に、関わっているスレッド（`myThreads`）を `ChatThreadCache` に保存する（アカウントごと）。1 件に持つのは、グループ（リレー・ID）、種類（Buzz か）、ルートID、最後の動き、返信の数、ルートと最新の返信（イベント・作者・本文）。本文は 600 文字、件数は新しい順に 100 件までに切る。
  - 今回読んだリレー（答えたもの）の分は今回の結果で置き換え、それ以外のリレー（選んでいないコミュニティ、答えなかったリレー）の分は前回の控えを残す。
- **復元**: 一覧の控えを戻したあと、タイムラインをまだ読んでいなければ、控えのスレッドを `threadRows` に出す。選んでいるリレー（保存した選択）のものだけにし、ミュートした人のもの（ルートか最新の返信）は出さない。
- **差し替え**: 控えを出している間は、読めたリレーから出す途中経過（3.3 の 2）でスレッドの行を差し替えない（行が減ったり並びが揺れたりしないように）。読み終えたら差し替える。答えなかったリレーの分は控えを残す（3.4.3 と同じ考え方）。
- 押したときの動き（スレッドを開くか、グループを開くか）は、控えから戻したルート・最新の返信で今まで通り決める（`opensThread`）。

#### 3.5.3 やらないこと

- タイムライン（「タイムライン」のタブの行）の控え。
- 控えにある間に削除・編集されたもの: 読み終えたときに差し替わるまでは前の内容が出る。

#### 3.5.4 確かめ方

- 単体テスト（`ChatThreadCacheTest`）: 保存して戻すと同じ行になる（`opensThread`・`isMyThread`・最後の動き）、本文と件数が切られる、壊れた控えは空、置き換えるリレー・残すリレーの混ぜ方、同じスレッドは新しい方、並びは新しい順。
- 実機: 起動し直してチャンネルのタブを開いたとき、スレッドの行がチャンネルの行と同時に出て、読み終えても並びがずれないこと。

## 4. 初版でやらないこと

- 既読・未読の反映（タイムラインで読んでも、グループの未読は減らさない）。
- リアクションの表示。
- タイムラインからの返信・投稿。
- 端末への保存（開くたびに読む）。

## 5. チャンネルの画面の「スレッドへの返信」の行（Buzz）

古いスレッドに返信が付くと、グループの一覧のプレビューには返信が出るが、チャンネルの画面では上の方にある元の発言の「返信 n件」が増えるだけで見つけにくい。スレッドごとに1投稿（元の投稿 + 最新の返信）を、最新の返信を送った時刻の位置に差し込む。元の発言は元の位置にも残す（会話の流れを崩さない）。

```
╭ 💬 スレッドに新しい返信 ───────────────╮
│ [avatar] N  11月15日                     │
│          @しゅん Louisだれ？（本文そのまま）│
│      ╰ [avatar] 自分  22:41              │
│                 人格がある！             │
│      💬 返信 2件 ▸                       │
╰──────────────────────────────────────────╯
```

- 対象は Buzz のチャット（kind 9・40002 で `buzzThreadRootId` があるもの）。標準の NIP-29 とフォーラムには出さない。
- ルートと最新の返信の間の発言（チャンネルの並びの、ミュートを除いた発言）が5件以内（`THREAD_INLINE_MAX_BETWEEN`）なら枠を出さず、ルートの位置で「返信 n件」の上に最新の返信を「╰」を付けて出す（すぐ返信が付いたとき同じ投稿が2回並ばないように）。5件を超えたら、またはルートがチャンネルの並びに無ければ、下の枠を出す。
- 1スレッドにつき1投稿。形はタイムラインタブの会話の行（1.1）と同じ部品（`TimelinePost`）で、元の投稿はアイコン・名前・時刻・本文（Markdown・画像）、最新の返信は「╰」を付けて字下げ。薄い背景の枠で普通の発言と分ける。
- 押すとスレッドを開く（`openThreadRootId` = ルート）。
- 元の発言がチャンネルの読めている範囲より古いときは、`ids`（`#h` 付き）で読む（`GroupChatViewModel.scheduleThreadRoots`、返信が届いてから 300ms まとめて）。読んだものはチャンネルの並びには入れず、引用とスレッドの画面だけに使う（`GroupTimeline.addThreadRoots`）。このときスレッドの返信も `#e`（`#h` 付き、500件まで）で読み、返信の数をそろえる（読めている範囲より前の返信が数に入らないため。`GroupTimeline.addThreadReplies`、返信でないものは捨てる）。答えがそろわなかった分は、次に返信が届いたときに読み直す。読めるまでは「元の投稿を読み込み中…」と出す。
- 出さないもの: ルートが削除されたスレッドの返信、ミュートした人の返信、ルートがミュートした人のスレッドの返信、チャンネルへ送ったコピー（`buzz:copy-of` が指す返信。コピーの方が出る）。
- ミュートは `GroupTimeline.snapshot(muted)` の中で外す（最新の返信と数に入れない）。
- スレッドの画面では、ミュートした人の発言（ルート・返信とも）を外さずに、アイコン・名前・時刻はそのまま出し、本文以下（引用・プレビュー・リアクションなど）だけを赤字の「ミュートしています」に置き換える。押すとその発言だけ開く（開いた状態は画面を離れると戻る）。折りたたんでいる間は長押しのメニューを出さない。返信の数にも含める。チャンネルの画面・参加中のタイムラインには出さない。
- 行は長押しの操作を持たない（リアクション・返信はスレッドの画面で行う）。行のあとの発言は、同じ人でもアイコンと名前を出し直す。

## 6. テスト

- `GroupTimeline.conversations()`: Buzz のスレッドのまとめ、最新の返信、返信の数、ルートが無いとき、ルートの削除、フォーラム、標準の kind 9 と kind 11 / 1111、編集の反映、ミュート。
- `GroupTimeline.snapshot()`（Buzz）: 返信を時刻の位置に出す、スレッドごとに最新の1行、ルートが無いとき（`missingThreadRoots`）、別に読んだルートの引用と削除、コピーとの重複、ミュート、ルートの削除、標準では出さない。
- `ChatTabUiState`: 絞り込みを出す条件（リレー・チャンネルのある「すべて」、DM の一覧では出さない）、既定は両方、どちらか一方、タイムラインのタブでは混ぜない、読み込みが要るとき。`mergeChannelsAndThreads`: 新しい順に混ぜる。`threadsNotInChannelPreviews`: チャンネルのプレビューと重ねない。`ChatTimelineRow.threadCard`: 元の投稿と最新の返信、返信の無いとき、元の投稿が読めないとき、未読を出さない。
- `JoinedTimeline`: 読めたリレーから出す（遅いリレーを待たない・答えていないリレーは下限にしない）、続きと削除の同時読み、続きで読めた投稿の削除、複数グループの並べ替え、下限での切り捨て、「今日」の区切り、タップ先の判定、bot を隠す（40002 の作者・役割 bot、標準のリレーでは 39002 を読まない）、スレッドだけにする（自分の元の投稿・返信・`p` で関わっているか、返信の無い投稿は出さない、ミュートした人の返信は数えない）。
