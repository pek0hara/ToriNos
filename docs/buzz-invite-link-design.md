# Buzz の招待リンク（ToriNos から参加とログインまで） 設計

- 作成日: 2026-11-22
- ステータス: 段階1を実装済み（単体テストと Web 版のヘッドレス確認。アプリの実機・実在のコミュニティでの確認は未実施）。段階2以降は未実装
- 関連: [nip29-buzz-design.md](nip29-buzz-design.md) の 2.1・2.2・6.1、[buzz-admin-design.md](buzz-admin-design.md) の 2.4（招待の発行）、[buzz-community-sync-design.md](buzz-community-sync-design.md)（kind 10009 の暗号化項目）、[web-private-key-login-design.md](web-private-key-login-design.md)、[signer-abstraction-design.md](signer-abstraction-design.md)
- 目的: ToriNos で発行した1本のリンクから、受け取った人がアカウントを用意し、Buzz コミュニティへの参加まで迷わず終えられるようにする。

## 1. 背景

- ToriNos には、Buzz の招待の発行（管理シート、`POST /api/invites`）と、招待リンクを貼り付けて参加する流れ（規約への同意、NIP-98 付きの claim）がすでにある。
- 足りないのは次の3つ。
  - OS やブラウザからリンクで ToriNos を開く受け口。Android は LAUNCHER の intent-filter だけで、iOS にも URL scheme や Associated Domains が無い。
  - まだアカウントを持たない人を、鍵の作成から参加まで続けて案内する流れ。
  - ToriNos 用のリンクの発行。
- Web 版は GitHub Pages の `https://pek0hara.github.io/ToriNos/app/` で配信している（独自ドメインは無い）。

## 2. 基本の考え方

### 2.1 リンクで運ぶのは招待だけ

リンクに入れるのは、コミュニティ（リレーのホスト）と招待コードだけとする。秘密鍵、暗号化した鍵（ncryptsec）、リモート署名の接続情報（`bunker://`）は入れない。

- URL はトークの履歴、リンクプレビューのサーバー、ブラウザの履歴と同期に残る。Nostr の鍵は取り替えられないので、漏れると取り返せない。
- 発行者が相手の鍵を作れば、発行者はいつまでも相手になりすませる。
- 招待コードは漏れても「そのコミュニティに入られる」までで、期限と利用回数で範囲を絞れる。

鍵は本人の端末で作るか、本人が入れる。

### 2.2 繋ぐとは同じ鍵を使うこと

Buzz のメンバー資格は pubkey に付き、参加したコミュニティは kind 10009 の暗号化項目で同期される（buzz-community-sync-design.md）。Web で参加した人も、アプリで同じ鍵にログインすれば、招待をやり直さずにコミュニティが戻る。Web とアプリを繋ぐための専用の仕組みは、最初は作らない。

### 2.3 開いた端末で拠点を分ける

| | Web 版 | アプリ |
|---|---|---|
| 始めるまで | リンクを開けばすぐ | インストールが要る |
| 鍵の保管 | localStorage。iOS Safari は使わないと消え、アプリ内ブラウザは別の保管場所になる | Keychain / Keystore で安定 |
| 画像の添付・通知・パスワードマネージャ | なし | あり |
| PC | Web だけ | — |

このため、**スマホはアプリ、PC は Web** を拠点とする。利用者に Web かアプリかを選ばせず、入口ページが端末を見て振り分ける。

招待からの新規参加は、スマホではアプリだけで受け付ける。スマホのブラウザで新しく鍵を作る道は用意しない。これで、スマホの Web で鍵が消える問題と、スマホの Web からアプリへ移る手間の両方が起きなくなる。

### 2.4 リンクの種類

| 形 | 用途 | 配るか |
|---|---|---|
| `https://pek0hara.github.io/ToriNos/app/#join?relay=<host>&code=<code>` | 招待リンク。人に配る形はこれだけ | 配る |
| `torinos://join?relay=<host>&code=<code>` | 段階2で、入口ページの［アプリで開く］からアプリへ渡すときだけ使う | 配らない |

- `torinos://` を配らない理由: アプリが無いと何も起きず案内ページにも届かない、LINE・X・メールなどは独自スキームをリンクにしないことが多い、PC では開けない、iOS では同じスキームを登録した別アプリに横取りされうる。
- どちらの形も、コミュニティ（ホスト）と招待コードの組で持つ。Buzz の招待コードはコミュニティごとのもので、コードだけでは参加先が分からない（今の参加シートもコードだけの入力は断る）。
- 形は Buzz の `buzz://join?relay=…&code=…` に合わせ、アプリの中では同じ解析に通す。

## 3. 利用者ごとの動線

招待リンクは1種類で、開いた先の入口ページが案内する。

| 利用者 | 動線 |
|---|---|
| スマホ・アプリあり | 入口ページ → アプリ（段階1はコピーして貼り付け、段階2以降は直接開く）→ 参加シート → 参加 |
| スマホ・アプリなし | 入口ページ → リンクをコピー → ストア → インストール → 鍵の作成かログイン → ［招待リンクを貼り付け］→ 参加 |
| スマホ・アプリを入れられない | 「PC のブラウザでこのリンクを開いてください」と案内する |
| スマホの Web ですでにログイン済み | その人はスマホの Web を拠点にしているので、そのまま Web で参加させる |
| PC | Web でログイン（NIP-07・NIP-46・nsec）か鍵の作成 → 参加 → そのまま Web で使う |

例外の扱い:

- iPad の Safari は Mac として名乗るので PC として扱う。Android のタブレットはスマホとして扱う。
- 端末の判定は確実ではないので、入口ページの下に小さく「ブラウザで続ける（PC の方）」を残す。
- 端末を増やすとき（PC の Web からスマホのアプリなど）は、段階1では本人が nsec を入れるか、NIP-46 で同じ署名アプリにつなぐ。

この方針で一番の懸念は、インストールでの離脱と、インストール後に招待が切れること（ストアを経由すると招待は引き継げない）。入口ページでコミュニティの情報と招待されたことを見せてから入れる理由を伝え、リンクをコピーしておき、アプリの初回起動で貼り付けを目立たせる。

## 4. セキュリティの規則

- **招待コードは持参人払いの秘密として扱う。** ログ（`networkTraceLog`・`appLog`・クラッシュレポート）に出さない。OS から渡される URL や Intent にも同じ規則を当てる。
- **招待コードは URL のフラグメント（`#` の後ろ）に入れる。** サーバー、アクセスログ、Referer に出ない。Web では読み込んだらすぐ `history.replaceState` で URL から消し、履歴に残さない。
- **確認画面より前は何も送らない。** NIP-11 の取得は許すが、NIP-42 の AUTH、署名、claim は利用者が［参加する］を押すまで行わない。悪意のあるホストに pubkey を知られないため。
- **ホスト名をはっきり見せる。** ToriNos の招待リンクでは、リレーのホストに ASCII 以外の文字を受け付けない（IDN は `xn--` の形で書く）。似せたドメインに気づけるようにするため。ほかの規則は今の解析（nip29-buzz-design.md 6.1）と同じ。
- **受け付けるルートは `#join` だけ。** 戻り先の URL などのパラメータは持たない（オープンリダイレクトを防ぐ）。
- **自動で同意しない。** 規約と年齢の確認は必ず見せる。利用条件への同意（`UsageConsentDialog`）も飛ばさない。
- **参加するアカウントを確かめる。** 複数のアカウントがあるときは、黙って今のアカウントで参加しない。
- **鍵を作った場合はバックアップを先に済ませる。** Web ではパスキーでの保護と nsec のバックアップを、参加の前に必須にする。PC の Safari にも、使わないと保存データを消す制限があるため。
- **招待はメモリにだけ預かる。** ログインや鍵の作成が終わるまで、アカウントの切り替えでも消えないアプリ全体の場所（`pendingInvites`）に、期限（30分）付きで置く。端末には保存しない。参加シートへ渡した時点、鍵設定をキャンセルした時点、「招待を使わない」を押した時点で消す。文字列にしても招待コードは出さない。
  - 既知の制限: アプリが落ちると（Android で署名アプリへ切り替えている間のプロセス終了など）招待は消える。その場合はもう一度リンクを貼ってもらう。困るようならセキュアストレージへの保存を足す。
  - claim の応答が失われたときの再開は、今の journal の仕組みを使う。
- **独自スキームは横取りに注意する。** Android は `intent://` で package を指定して開くアプリを固定する。iOS の独自スキームは、同じスキームを登録した別アプリに取られうるので、使うかどうかを段階2で決める。

## 5. 段階

### 5.1 段階1: リンクで参加できるようにする

目的: 1本の招待リンクで、PC は Web で参加まで終わり、スマホはアプリを入れて貼り付けると参加できる。

リンクの形:

```
https://pek0hara.github.io/ToriNos/app/#join?relay=<host>&code=<code>
```

実装内容:

- 共通
  - `GroupInput` の解析にこの形を足す。
  - 招待コードがログに出ないことをテストで確かめる。
- 管理シート
  - 発行した招待から ToriNos のリンクを作り、表示とコピーができるようにする。リンクのホストは、応答の `url` のホストと一致するものだけを使う。
  - 「スマホの人はアプリ、PC の人はブラウザで参加できます」と注記する。
- Web の入口ページ（`#join`）
  - 読み込んだらすぐフラグメントを URL から消す。今の `initial-hash.js` は読み込みが終わると `#` を戻すので、`#join` だけは戻さない。
  - 端末を判定する。
  - スマホには、コミュニティの情報（NIP-11）、［リンクをコピーしてアプリで開く］、ストアへのリンク、「PC で開いてください」の案内、小さく「ブラウザで続ける」を出す。
  - スマホの Web ですでにログインしている人は、Web で参加させる。
- Web の参加の流れ（PC）
  - 確認画面: コミュニティ、ホスト名（punycode も）、［参加する］。
  - 未ログインなら、ログイン（NIP-07・NIP-46・nsec）か鍵の作成。鍵を作ったら、パスキーでの保護と nsec のバックアップを済ませる。
  - アカウントが複数あれば、参加するアカウントを選ぶ。
  - 規約への同意 → claim → 参加の確認 → チャットタブで開く（今の `BuzzJoinService`）。
  - ログインの途中だけ、招待をメモリに期限付きで預かる（4章）。
- アプリ
  - 鍵の作成やログインのあとに［招待リンクを貼り付け］を出す（初回起動とログイン画面）。iOS のペースト許可のダイアログを避けるため、クリップボードは自動で読まず、ボタンで貼り付ける。
  - チャットタブが隠れていても参加シートを開ける入口を作る。
  - 参加が終わったらチャットタブを表示する。

リリース: Web の配信と、アプリの更新（貼り付けの入口のため）。

完了の基準: PC でリンクを開いて、鍵の作成から参加まで終わる。スマホで、インストール、貼り付け、参加まで終わる。

### 5.2 段階2: アプリを直接開く

目的: アプリを入れている人が、入口ページのボタン1つでアプリの参加シートに進める。スマホをアプリだけにするので、コピーと貼り付けの手間がそのまま離脱に効く。そのため早めに入れる。

実装内容:

- Android: `torinos://join` の intent-filter。`onCreate` と `onNewIntent` でリンクを受け取る。
- iOS: 独自スキームを使う場合は URL Types と `onOpenURL`。使わない場合はコピーのまま。
- 共通: 受け取ったリンクを参加シートへ渡す。未ログインなら、ログインのあとに渡す。確認画面より前は何も送らない。
- 入口ページの［アプリで開く］: Android は `intent://…#Intent;scheme=torinos;package=com.nostr.torinos;end`、iOS は `torinos://join?…`（使う場合だけ）。アプリが開かなかったら、コピーとストアの案内に戻る。

リリース: アプリの更新と Web の配信。

完了の基準: アプリがあるスマホで、ボタンから参加シートを経て参加できる。アプリが無い場合は段階1の案内に戻る。

### 5.3 段階3: Universal Links / App Links

目的: リンクを踏むだけで、入口ページを経由せずにアプリが開く。

制約: 設定ファイルはドメインのルートの `/.well-known/` に置く必要があり、今のプロジェクトページ（`/ToriNos/` 以下）からは置けない。置き場所を次のどちらかに決める。

| 置き場所 | 長所 | 短所 |
|---|---|---|
| `pek0hara/pek0hara.github.io` リポジトリを作り、`.well-known` だけ置く | Web 版のオリジンが変わらない | 個人アカウント名のドメインに縛られる |
| 独自ドメインに移す | 見た目がよく、将来も自由 | オリジンが変わるので、今の Web 利用者の localStorage の鍵とパスキー（RP ID）が引き継げない。移すなら早いほど被害が小さい |

実装内容:

- `apple-app-site-association`（Team ID `2F7KXC2828`、`com.nostr.torinos.app`）と `assetlinks.json`（`com.nostr.torinos`、署名の SHA-256）。
- 専用の受け口 `/ToriNos/join` を静的ページで用意し、アプリが無ければ `app/#join…` へフラグメントごと送る。アプリで開くのはこのパスだけにし、`/ToriNos/app/` はアプリを入れている人でも Web で開けるようにする。
- Android: `autoVerify` 付きの intent-filter（`/ToriNos/join` だけ）。iOS: Associated Domains（`applinks:`）。
- リンクの形を `/ToriNos/join#…` に変え、古い `app/#join` も受け付け続ける。

限界: アプリ内ブラウザでは Universal Links が効かないことが多い。iOS では同じドメインの中のリンク遷移でも効かない。そのため段階2のボタンは段階3のあとも残す。

完了の基準: ブラウザやメッセージアプリでリンクを踏むとアプリが開く。効かない場合は段階2のボタンで代われる。

### 5.4 後回しにするもの

- **PC からスマホへの鍵の受け渡し。** 端末を増やすときに nsec を入れる手間を無くす。鍵を持つ側（PC）が一時鍵入りの QR を出し、スマホのアプリが読み、両者に出る確認番号を入力で照合してから、NIP-44 で暗号化した鍵を ephemeral イベントでリレー経由で送る。送る前にパスキーの解錠を求める。リンクを踏むだけで鍵が出ていくことが無いよう、鍵を持つ側から始める向きにする。
- **スマホのブラウザでの新規参加。** インストールでの離脱が問題になったら足す。PC の流れを流用し、アプリ内ブラウザの判定と案内、ホーム画面への追加の案内、バックアップの必須化を足す。
- **招待の一覧と取り消し。** Buzz に API ができたら。

| 預かった招待を、ログイン・新規登録のプロフィール・全画面の投稿が閉じてから参加シートへ渡す。未ログインなら鍵設定を開く | `AppSessionCoordinator.kt` |

| 鍵設定の画面の「招待を受け取りました」と「招待リンクを持っている」（貼り付け） | `ui/setup/KeySetupInvite.kt`、`ui/setup/KeySetupScreen.kt` |
| 設定の「チャット」にも同じ貼り付けの入口（チャットタブを隠していても参加できる） | `ui/settings/ChatSettingsSection.kt` |

| 管理シートで ToriNos のリンクと Buzz のリンクを並べて出す。Buzz の参加シートに参加するアカウントを出す | `ui/chat/ChatTabScreen.kt` |

確認したこと（2026-11-22）:

- 単体テスト: `ToriNosInviteLinkTest`（形・往復・別ホスト・クエリにコード・非 ASCII ホスト・重複・長さ）、`PendingInviteStoreTest`（期限・コード付きだけ・文字列にコードが出ない）。iOS シミュレーターのテスト一式が通ること。Android のビルド。
- Web 版をヘッドレス Chrome で、模擬の Buzz コミュニティ（NIP-11、規約、同意、NIP-98 を検証する claim、メンバーだけ通す AUTH）を相手に確認した。実リレーには接続していない。
  - PC: リンクを開く → URL から招待が消える → 招待の表示付きの鍵設定 → 鍵の作成（保存の印が必要）→ プロフィール → 参加シート（ここまで通信は NIP-11 と規約の取得だけ）→ 同意して参加 → claim（NIP-98 が一致）→ AUTH でメンバー → コミュニティが開く。
  - 招待コードが localStorage・sessionStorage・URL・配信サーバーのログ・コンソール・リクエストの URL のどこにも出ていない。
  - スマホ（Pixel 7 の UA）: 入口ページが出る。この画面では通信しない。コピーした中身が本番の招待リンクになっている。「このブラウザで続ける」で鍵設定へ進み、新規登録のあと最初の投稿の画面を挟まず参加シートが開く。
  - ログイン済みで、設定の「チャット」から招待リンクを貼ると参加シートが開く。

未確認・未決:

- アプリ（Android・iOS）の実機で、インストール直後に貼り付けて参加する流れ。
- App Store の URL が未定のため、iPhone の入口ページは「App Store で検索」の案内にしている（`TORINOS_APP_STORE_URL`）。Google Play の URL は `com.nostr.torinos` から作っている。

## 6. 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| リンクに nsec を入れる | 漏れると取り返せない。発行者が相手になりすませる |
| リンクに ncryptsec を入れ、パスワードを別経路で渡す | 発行者が鍵を知っている問題が残る。短いパスワードは総当たりできる |
| リンクに `bunker://` を入れる | 鍵が発行者側にあり、個人のアカウントに向かない。運営が管理する共用アカウントなら別途検討する |
| `buzz://` を ToriNos で受け取る | Buzz アプリとぶつかる。貼り付けでは今どおり受け付ける |
| インストール後の招待の自動引き継ぎ（deferred deep link） | 外部サービスが要り、招待コードを第三者に渡すことになる |

## 8. テスト

- リンクの解析: フラグメントの有無、不正なホスト、IDN、余計なパラメータ、Buzz の招待URLとの両立。
- 端末の判定: スマホ、iPad（PC 扱い）、Android のタブレット、アプリ内ブラウザ。
- 招待の預かり: 期限切れ、参加シートへ渡したら消えること、鍵設定のキャンセルで消えること。
- ログに招待コードが出ないこと（受け口、解析、参加の処理）。
- 段階2・3: 受け取ったリンクが参加シートへ渡ること、未ログインのときにログインのあとで渡ること、確認画面より前に AUTH も署名もしないこと。
- 通しの確認: Web 版をヘッドレスで、ローカルの buzz-relay を相手に、発行から参加まで。アプリは Android の実機とローカルの buzz-relay で。実在のコミュニティでの確認は、検証用の招待をもらってから参加と閲覧だけ行う。
