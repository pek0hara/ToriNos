# ToriNos アプリ要件

## 目的

ToriNos は Nostr を利用した日本語向け SNS クライアントである。ユーザーは公開タイムライン、フォロー中タイムライン、チャンネル、ステータスを閲覧し、Nostr 秘密鍵を登録した場合は投稿・返信・リアクション・リポスト・プロフィール編集などの書き込み操作を行える。

## 対象プラットフォーム

- Android
- iOS

書き込み機能は `isWriteSupported` が true のプラットフォームで提供する。秘密鍵の保存、画像選択、画像クロップ、クリップボード、パスワードマネージャ連携はプラットフォームごとの実装に委譲する。

## 利用者ロール

- 未ログイン利用者
  - 公開情報を閲覧できる。
  - 書き込み操作を開始した場合、鍵作成または既存秘密鍵インポートへ誘導される。
- ログイン利用者
  - Nostr 秘密鍵を端末に保存し、署名が必要な操作を実行できる。
  - 複数アカウントを保存し、切り替えられる。

## 主要ナビゲーション

- フィード
  - フォロー中フィードとグローバルフィードを表示する。
  - 投稿作成、通知ドロワー、検索、設定、プロフィールへ移動できる。
- チャンネル
  - Nostr チャンネル一覧を表示する。
  - チャンネル詳細、チャンネルメッセージ、チャンネル内スレッドを表示する。
- ステータス
  - NIP 系のユーザーステータスを一覧表示する。
  - ログイン中ユーザーはステータスを追加できる。
- プロフィール
  - 自分または他ユーザーのプロフィール、投稿、返信、リアクション、フォロー/フォロワーを表示する。
- 設定
  - アカウント、鍵、リレー、ミュート、NG ワード、カスタム絵文字を管理する。

## 機能要件

### アカウントと鍵

- 新しい Nostr 鍵ペアを生成できる。
- 既存の秘密鍵を `nsec1...` または hex 形式でインポートできる。
- 生成またはインポートした秘密鍵から公開鍵を導出し、端末に保存できる。
- Androidでは、ユーザーの操作により秘密鍵をGoogleパスワードマネージャへ保存できる。
- iOSでは秘密鍵をアプリ専用のiCloudキーチェーンへ保存・同期し、Appleの「パスワード」およびShared Web Credentialsとは連携しない。
- 初回鍵生成後、プロフィール初期設定を行える。
- 保存済みアカウントの一覧を表示し、アクティブアカウントを切り替えられる。
- 公開鍵をコピーできる。
- 秘密鍵は通常マスク表示し、明示操作で表示またはコピーできる。
- ログアウト状態はアカウント単位で管理し、ログアウト時は現在アカウントだけをログアウト済みにする。ほかに利用可能なアカウントがあればそのアカウントへ切り替え、なければ匿名閲覧状態へ遷移する。保存済みの秘密鍵は再ログイン用に残す。
- ログイン画面ではログアウト済みアカウントを個別に削除できる。iOSでは、削除対象アカウントについてアプリが作成したiCloudキーチェーンの同期バックアップも削除する。
- アカウント削除時は Damus と同様に、プロフィールを削除済み状態へ更新する kind 0 を有効なリレーへ送信し、その後端末内の秘密鍵を削除する。

### フィード

- グローバルフィードは選択中のグローバルリレーから kind 1 の投稿を取得する。
- フォロー中フィードはフォローリストに基づいて投稿を取得する。
- フィードは過去投稿のページング読み込みに対応する。
- フォロー中フィードで複数リレーを利用する場合、履歴カーソルをリレーごとに独立して管理し、応答しないリレーがあっても応答可能なリレーのページングを継続する。
- 1つの履歴購読に複数の論理フィルターを含む場合、ページ境界と取得上限をリレー・フィルター単位で管理し、一方のフィルターの進行によって他方の未取得イベントを飛ばさない。
- 複数フィルターを含む履歴購読が構造的に拒否された場合はフィルター別に再取得し、拒否されたフィルターだけを停止する。
- タイムアウト、切断、`CLOSED` では該当リレーの履歴カーソルを進めず、復旧後は最後に正常完了した位置から再取得する。
- 複数リレー由来の同一イベントはイベント ID で重複排除し、遅れて取得したイベントを時系列へ統合する。
- 空ページと `EOSE` を受信した場合だけ、そのリレーの履歴終端と判定する。短い非空ページ、タイムアウト、切断、`CLOSED` は終端と判定しない。
- NIP-01だけでは完全取得を証明できない同一秒の境界は未解決範囲として保持し、取得済みと偽らず、それより古い履歴のページングは継続する。
- 応答しないリレーしか残っていない場合は無限に読み込み中とせず、部分取得状態と再試行操作を表示する。
- 取得済み範囲、端末内の履歴保持、画面の表示ウィンドウを別に管理し、表示上限によるイベント削除を理由にリレーの取得カーソルを巻き戻さない。
- 受信した生イベントと、ミュート・NGワード・返信除外・リポスト変換後の表示イベントを分けて管理し、リポスト元のイベント ID を表示位置の基準として維持する。
- 表示対象外の投稿だけが続く場合も取得カーソルは正常に進める。ただし自動的な追加取得には上限を設け、上限後はユーザーの明示操作で再開する。
- バックグラウンド時間が5秒以内の場合、フィードの追加同期を行わず現在位置を維持する。
- バックグラウンド時間が5秒を超え10分以内の場合、現在位置を維持し、通常の過去方向カーソルとは独立したリレー・フィルター別ページングで空白期間を差分同期する。
- バックグラウンド時間が10分を超える場合、フィード固有のメモリ状態を破棄し、最新30件を取得して先頭へ戻る。アカウント、設定、プロフィール、画像等の永続キャッシュは維持する。
- 投稿ごとにプロフィール、返信数、リアクション数、絵文字別リアクションチップ、リポスト数を表示する。
- 返信、いいね、いいね解除、Unicode/カスタム絵文字リアクションの追加・解除、リポスト、リポスト解除、投稿削除を行える。
- リアクションがある投稿ではチップ末尾の追加ボタン、リアクションがない投稿ではいいねボタンの長押しから絵文字を選択する。
- 1ユーザーが1投稿に付けられるリアクションは1種類とし、選択済みの場合はほかのチップを無効化して追加ボタンを表示しない。選択中のチップは解除操作のためタップ可能とする。
- 自分がいいねまたは絵文字リアクション済みの場合は、いいねボタンを選択色で表示する。絵文字リアクション済みでは長押し選択を無効化し、通常タップで現在のリアクションを解除する。
- リアクション選択のクイックメニューではUnicode/カスタムを混在させた最近使ったリアクションを表示し、いいね用ハートは表示しない。「絵文字を選ぶ」から開く単一のアプリ内ボトムシートに、標準絵文字とカスタム絵文字を横断した検索、よく使う項目、カテゴリ別一覧を統合する。初期表示とカテゴリ導線は「履歴→カスタム絵文字→標準絵文字」の順とする。標準絵文字にはUnicode Emoji 17.0のRGI絵文字シーケンスを収録し、肌色違いは修飾なしのデフォルト1パターンだけを表示する。別の「すべて表示・検索」ダイアログは設けず、利用履歴も端末に保存する。
- 引用投稿、メンション、リンク、画像、カスタム絵文字を表示できる。
- ミュートユーザーと NG ワードに該当する投稿はフィルタリングする。

### 投稿と下書き

- 通常投稿と返信を作成できる。
- チャンネル内ではチャンネル文脈の返信タグを付けて投稿する。
- 画像を添付できる。
- 添付画像は選択、クロップ、削除できる。
- 投稿先リレー設定を投稿シートから確認・変更できる。
- 下書きを保存し、後から復元できる。

### 記事

- NIP-23 の kind 30023 の記事を一覧・著者別一覧・詳細画面で閲覧できる。
- 記事一覧の上部で、著者を「すべて／フォロー／自分」から選んで絞り込める。ログイン中の既定は「フォロー」とする。未ログイン時は「すべて」に固定し、切り替えを表示しない。
- 記事カードや詳細画面の `#タグ` をタップすると、そのトピックで一覧を絞り込める。詳細画面からは記事一覧へ戻って絞り込む。
- 記事カードの著者行をタップすると、その著者の記事一覧を開ける。著者別一覧ではトピックだけで絞り込める。
- 記事詳細では、記事へのリアクションの集計と、記事へ直接付いたコメントを古い順に表示する。コメントは NIP-22 の kind 1111 と、`a` タグで記事を参照する kind 1 の返信を対象とする。
- ログイン中は記事詳細から記事へのリアクションを送信・解除し、NIP-22 のコメントを投稿できる。記事へのコメント投稿後はスレッド画面へ遷移せず、詳細画面のコメント一覧を取り直す。
- ログイン中かつ書き込み対応プラットフォームでは、記事投稿画面を開ける。
- 記事投稿画面はダイアログではなく独立した全画面として表示する。
- タイトル、概要、Markdown 本文、カバー画像、トピックを入力できる。
- カバー画像は HTTPS URL 入力または画像選択・アップロードで設定できる。
- 選択した画像を Markdown 画像記法として本文へ追加できる。
- 編集画面とプレビュー画面を切り替えられる。
- 記事一覧で選択中の記事リレーへ kind 30023 を公開する。
- 公開成功後は作成した記事の詳細画面へ遷移する。
- 自分の記事は詳細画面から編集画面を開き、既存の `d` タグと `published_at` を維持して更新できる。
- 自分の記事は詳細画面から削除できる。記事用下書きは今後の対応範囲とする。

### スレッド

- 投稿詳細では返信、いいね、リポストをタブで表示できる。
- スレッド内から別の投稿詳細へ遷移できる。
- チャンネル由来のスレッドではチャンネル文脈を維持して返信できる。

### チャンネル

- チャンネル一覧を表示し、メッセージ数、最終活動、最新メッセージ、未読数、お気に入り状態を扱う。
- チャンネル一覧はページング読み込みに対応する。
- チャンネルを新規作成できる。
- チャンネル作成時はチャンネルメタ情報と初回本文を公開する。
- チャンネル詳細では kind 42 のメッセージを送受信できる。
- チャンネル所有者はチャンネルメタ情報を編集できる。
- チャンネルメッセージに対して返信、いいね、リポストを行える。
- チャンネルキャッシュを削除できる。
- お気に入り以外のチャンネルキャッシュを一括削除できる。
- お気に入り登録は、そのチャンネルのローカル保持件数上限を引き上げる(非お気に入り1チャンネル最大2,000件、お気に入りは最大20,000件。全チャンネル合計では最大50,000件)。
- 既読位置とスクロール位置は、チャンネルキャッシュの整理(prune)で削除しない。

### ステータス

- kind 30315 のステータスを表示する。
- ステータスにはタグ、本文、参照 URL、終了時刻を設定できる。
- 期限切れステータスは表示対象から除外する。
- ステータス画面でプロフィールへ遷移できる。

### プロフィール

- kind 0 のプロフィールを表示する。
- 名前、表示名、自己紹介、アイコン URL、バナー URL、NIP-05 アドレスを編集できる。
- アイコンとバナーは URL 入力または画像選択・クロップで更新できる。
- フォロー、フォロー解除を行える。
- フォロー数とフォロワー数を表示する。
- フォロー中/フォロワー一覧を表示し、一覧内検索ができる。
- プロフィール本文内の Nostr 参照を解決し、関連プロフィールを表示できる。
- ユーザーの参加リレー一覧を表示できる。

### 検索

- 検索リレーを利用して投稿検索とユーザー検索を行う。
- 検索結果は投稿タブとユーザータブで表示する。
- 検索実行時は選択中のタブに対応する検索だけを行う。ユーザー検索では投稿、返信、リアクション、リポスト、引用リポストを取得しない。
- 同じ検索語で未取得のタブへ切り替えた場合は、そのタブの検索を初回選択時に開始する。取得済みのタブへ戻っただけでは重複検索しない。
- 投稿検索とユーザー検索は、タブごとに読み込み中、取得済み、空結果、失敗の状態を独立して表示する。一方のタブの読み込み状態で他方の結果表示を妨げない。
- ユーザー検索は kind 0 を1回最大20件取得し、`EOSE`または8秒のタイムアウトで終了する。
- 投稿検索は kind 1 を1ページ最大30件取得し、ページング読み込みに対応する。各ページは独立した有限取得とし、30件取得して次ページが存在し得る場合も、ページの`EOSE`またはタイムアウト後は購読を閉じる。
- 新しい検索語で検索を開始した場合、以前の検索結果をクリアし、遅れて届いた以前の検索結果を現在の結果へ混ぜない。
- 投稿検索結果でも返信数、リアクション数、リポスト数を表示する。これらは接続リレー、取得期間、取得件数上限の範囲で得た値とし、Nostrネットワーク全体の厳密な総数は保証しない。
- 投稿検索結果の返信、リアクション、リポスト、引用リポストは、期間、フィルター単位件数、購読全体件数に上限を持つ有限取得とする。上限値は実機計測に基づいて調整可能な設定値として管理する。
- 検索画面が非表示になった場合は、プロフィール、投稿、返信、リアクション、リポスト、引用リポストに関する検索画面固有の購読と保留処理をすべて停止する。取得済み結果は保持し、画面へ戻っただけでは自動的に再検索しない。
- 検索画面を離れた後、検索由来のネットワーク受信、状態更新、共有リアクションキャッシュへの追加を継続しない。
- 検索の通信量と状態更新頻度は有効リレー数や検索回数に比例して無制限に増加させず、連続検索後もフィードのスクロール性能を低下させない。

検索の取得境界、購読終了、状態更新、計測の詳細は
[`search-performance-fix-plan.md`](./search-performance-fix-plan.md)を正とする。

### 通知

- ログイン中ユーザー向けに通知ドロワーを表示する。
- メンション、返信、リアクション、リポスト等の通知項目を表示する。
- 未読通知がある場合はフィード上で通知状態を示す。
- 通知を開いたときに既読化できる。
- 通知からユーザープロフィールまたは対象スレッドへ遷移できる。

### リレー設定

- 既定リレー一覧を持つ。
- リレー URL を追加・削除できる。
- リレー単位で有効/無効を切り替えられる。
- フォロー中フィード、グローバルフィード、チャンネル、アーティクル、ライブ、ステータスごとに利用リレーを選択できる。
- フォロー中フィードでは「すべてのリレー」を選択できる。
- リレー設定は端末に保存する。

### フィルタリング

- ミュートユーザー一覧を管理できる。
- NG ワード一覧を管理できる。
- 非公開ミュートリストを取得・保存し、ローカルミュート/NG ワードへ反映できる。
- ミュートや NG ワードはフィード、チャンネル等の表示に反映する。

### カスタム絵文字

- ローカルのカスタム絵文字一覧を管理できる。
- 公開絵文字セットを検索できる。
- 未登録カスタム絵文字をタップした場合、該当 shortcode を検索条件にして設定画面へ遷移する。
- テキスト表示時に登録済みカスタム絵文字を画像として表示する。

### リンクプレビュー

- 投稿本文から Web URL を抽出する。
- URL のタイトル、説明、画像などを取得し、リンクプレビューカードとして表示する。
- プレビュー取得に失敗した場合でも投稿本文の表示を妨げない。

## NIP 別機能要件

NIP 対応は、公式 NIPs リポジトリの kind/NIP 対応表を基準に整理する。ここでは ToriNos の利用範囲を「対応中」「部分対応」「計画/未対応」に分ける。

| NIP | 機能 | 対応状況 | ToriNos での扱い |
|---|---|---|---|
| NIP-01 | 基本プロトコル | 対応中 | イベント署名、`REQ`/`EVENT`/`EOSE`/`CLOSE`、kind 0 メタデータ、複数リレー購読・配信の基盤として扱う。 |
| NIP-02 | フォローリスト | 対応中 | kind 3 の `p` タグをフォロー一覧として取得・更新し、フォロー中フィード、フォロー数、フォロー/解除に使う。 |
| NIP-05 | DNS ベース識別子 | 部分対応 | プロフィールの `nip05` フィールドを表示・編集する。DNS 検証結果の表示は現時点では要件外。 |
| NIP-09 | イベント削除 | 対応中 | kind 5 を投稿、リアクション、リポスト、チャンネルキャッシュ削除要求などに使う。削除反映はリレー/クライアント側の対応に依存する。 |
| NIP-10 | テキストノートとスレッド | 対応中 | kind 1 の通常投稿を扱う。従来の kind 1 返信も `e`/`p` タグから読み取り、返信先判定、スレッド表示、返信数取得に使う。新規返信の投稿は NIP-22形式の kind 1111を使う。 |

## データ保存要件

- 秘密鍵は各プラットフォームの安全な保存先に保存する。
- リレー設定、選択中リレー、ミュート、NG ワード、カスタム絵文字、ステータス表示設定などはローカル設定として保存する。
- チャンネルメッセージとチャンネル一覧情報はローカルキャッシュできる。保持件数は非お気に入り1チャンネル最大2,000件、お気に入り1チャンネル最大20,000件、全チャンネル合計最大50,000件を初期値とする(実機計測後に見直す)。
- 起動時にチャンネルキャッシュを整理する。既読位置・スクロール位置・お気に入り状態はこの整理で削除しない。

## 非機能要件

- リレー接続は複数リレーへの WebSocket 接続を前提とする。
- 接続中リレーの増減に応じて購読を再送し、既存購読を維持する。
- 画面単位で購読を開始・終了し、不要な購読を閉じる。
- 初回読み込み、ページング、ライブ更新を区別し、重複イベントを抑制する。
- 有限取得は`EOSE`、タイムアウト、画面終了のいずれでも購読を確実に閉じ、次ページや別検索のために完了済み購読を残さない。
- ネットワークイベントが集中する処理では、受信ごとに画面全体の状態を発行せず、小さい時間窓または件数単位で更新をまとめる。
- 投稿、リアクション、リポストなどの操作は可能な範囲で楽観的 UI 更新を行う。
- ネットワークやリレーの一時的な失敗は画面全体のクラッシュにつなげず、ログ出力と局所的なエラー表示で扱う。
- 日本語 UI を基本とする。

## プッシュ通知

プッシュ通知バックエンドは [push-notification-durable-object-design.md](./push-notification-durable-object-design.md) にまとめる。アプリ全体要件としては、将来的に端末トークン登録、解除、メンション、返信、リアクション、リポスト通知を扱う余地を残す。DM通知は初期構成の対象外とし、NIP-17 / NIP-59に対応する際に別途プライバシー設計を行う。
