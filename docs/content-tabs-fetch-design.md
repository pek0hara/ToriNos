# 記事・チャンネル・ステータスの取得改善 設計

作成日: 2026-10-09
状態: 実装済み（2026-10-09）。結果は 8章。
関連: `article-tab-refactor-design.md`、`status-tab-refactor-design.md`、`subscription-architecture-design.md`、`Torinos_NIP28_channel_spec.md`

## 1. 背景（Android 実機の計測）

Android 実機（yabu.me 選択、有効4リレー: yabu.me / r.kojira.io / relay-jp.nostr.wirednet.jp / r.bitcoinhold.net）で、
`[Fetch]` ログ（`isFetchTraceEnabled`）を有効にし、次の操作を同じ手順で行って数えた。
フィードとバッジの取得は除いている。

| 操作 | 購読 | REQ（購読×リレー） | 受信イベント | 内訳 |
| --- | --- | --- | --- | --- |
| 記事一覧を開く | 記事 | 2 | 100 | 1ページ50件のはずが2ページ |
| 〃 | 一覧の件数 | 4 | 641 | **kind 5 が 612**、kind 7 が 29 |
| 記事を開く | 詳細の件数 | 4 | 約620 | **kind 5 が約600** |
| 〃 | 一覧の件数（下の一覧） | 4 | 約610 | ほぼ kind 5 |
| チャンネル一覧を開く | 最新発言 | **52** | 37 | チャンネル1件ごとに1 REQ、同時3本、約2.2秒 |
| チャンネルを開く | 10種類 | 60（10×6リレー） | 約200 | snowflare.cc で **CLOSED 3件**、wirednet で **同時購読の空き待ち 4件** |
| 〃 | 履歴 | 6 | 180 | snowflare.cc の30件は**取得を閉じた後に届いて捨てた**（STRAY 30） |
| ステータスを開く | ステータス | 1 | 200（上限） | 一般・音楽は102件、**残り98件は `security:scan:…` などの表示しない種類** |
| ステータスへ戻る | ステータス | 1 | 200 | 開くたびに同じ200件を取り直す |

リレーに直接問い合わせた比較（yabu.me、kind 30315）:

| 条件 | 件数 | 表示できる一般・音楽（期限内・本文あり） |
| --- | --- | --- |
| `limit=200`（現行） | 200 | 68 |
| `#d=[general,music]`、`limit=300` | 300 | 155 |

snowflare.cc の NIP-11: `max_subid_length: 50`、`max_filters: 10`。

## 2. 問題点

### 記事

- **A1 自分の取り消しを毎回200件取る。** 件数の取得（一覧・詳細とも）に `kinds=[5] authors=[自分] limit=200` を含めている
  （`ownRecentDeletionsFilter`）。対象を絞っていないため、記事に関係のない自分の削除イベントを全リレーから毎回200件ずつ受け取る。
  受信の9割以上がこれ。取り消しの判定に要るのは「今回受け取った自分のイベント」への削除だけ。
- **A2 開いた直後に2ページ目を取る。** 一覧の「もっと読む」の判定が、項目がまだ配置されていない
  （`totalItemsCount = 0`、`lastVisible = -1`）間も `-1 >= 0 - 4` で真になる。1ページ目の結果で `canLoadMore` が
  true になると `LaunchedEffect` が張り直され、配置前の判定で `loadMore()` が走る。
  記事一覧（ハブ）とユーザーの記事一覧の両方に同じ判定がある。

### チャンネル

- **C1 一覧の最新発言をチャンネルごとに取る。** `ch-list-activity` は1チャンネル1 REQ（`#e=[id] limit=1`）で、
  同時3本ずつ流す。50件超のチャンネルで52 REQ、約2.2秒。
- **C2 購読IDが長い。** `ch-meta-update-<16文字>-<セッション>-<リレー>` は55文字。
  snowflare.cc（チャンネルの推奨リレー）が `unsupported: too long subscription id` で拒否し、kind 41（メタデータ更新）、
  返信数、引用リポストがそのリレーから取れない。記事の購読ID（`article-engagement-<ms>-<hash>-<乱数>`）も54〜55文字。
- **C3 遅れて接続したリレーの履歴を捨てる。** 履歴は「最初の EOSE から1.5秒」で打ち切る。推奨リレーへの接続が
  1.1秒かかり、REQ を送った約0.4秒後に打ち切られた。届いた30件は購読外として捨てた。
- **C4 チャンネル画面の購読が多い。** 1チャンネルで常時8本（メタ、メタ更新、新着、返信数、リアクション、リポスト、
  引用リポスト、非表示、非表示の取り消し）を各リレーに張る。同時購読数の少ないリレー（wirednet: 16）では空き待ちになる。

### ステータス

- **S1 上限の半分を表示しない種類が占める。** `kinds=[30315] limit=200` を種類（`d`）で絞らずに取る。
  他のアプリが大量に出す種類（`security:scan:<uuid>` など）で上限が埋まり、表示できる一般・音楽が68件にとどまる。
- **S2 タブに戻るたびに全件取り直す。** 同じリレーに戻ったときは前回の結果を残して表示しているが、
  購読は `since` なしで200件を取り直す。

## 3. 目的と非目標

目的

1. 件数の取得で、関係のない自分の削除イベントを受け取らない（A1）。
2. 一覧を開いたときに要らないページを取らない（A2）。
3. チャンネル一覧の最新発言を少ない REQ で取る（C1）。
4. 購読IDを50文字以内にし、リレーに拒否されないようにする（C2）。
5. 遅れて応答したリレーの履歴も取り込む（C3）。
6. チャンネル画面の常時購読を減らす（C4）。
7. ステータスで表示できる件数を増やし、戻ったときは差分だけ取る（S1・S2）。

非目標

- フィードのエンゲージメント取得（`engagement-fetch-redesign.md` で対応済み）。
- NostrRepository の購読管理（接続待ちの REQ の扱い、購読ID の付け方の一律の変更）。
- 記事の件数の取り方そのもの（全リアクションを受け取って数える方式）。COUNT（NIP-45）への切り替えはしない。

## 4. 方式

### 4.1 A1 自分の取り消しは、受け取った自分のイベントに絞って後から確かめる

- 件数の取得（`articleEngagementFilters`、`articleListEngagementFilters`）から `ownRecentDeletionsFilter` を外す。
- 全リレーの取得が終わったら、受け取ったイベントのうち自分が作ったものの ID を集める
  （`ownEventIdsForDeletionCheck`）。1件以上あれば、`kinds=[5] authors=[自分] #e=[それらのID]` を全リレーへ1回問い合わせ、
  届いた削除を合わせて最後の集計を出す。自分のイベントがなければ問い合わせない。
- 取得の流れを `fetchArticleEngagementEvents(filters, ownPubkey, open, onSnapshot)` にまとめ、一覧と詳細で共有する。
  `open` を差し替えられるようにしてテストする（`fetchChannelEvents` と同じ形）。
- 途中の集計（リレーごとの EOSE のたび）は今と同じく出す。削除に対応しないリレーが古いリアクションを返した場合、
  確認が終わるまでの数百ミリ秒だけ自分のリアクションが残って見えることがある。多くのリレーは削除済みのイベントを返さないため、
  まれにしか起きない。
- 確認する ID は500件までにする（`limit` も500）。一覧の1バッチ（20記事）で自分のイベントが500件を超えることは想定しない。
- 確認の問い合わせが失敗・タイムアウトしても、受け取った分で集計を出す（今の「件数は補助表示」の扱いと同じ）。

### 4.2 A2 項目が配置されるまで「もっと読む」を判定しない

- 判定を純粋関数にする。

```kotlin
internal fun shouldLoadMoreArticles(
    lastVisibleIndex: Int,
    totalItemsCount: Int,
    canLoadMore: Boolean,
    isLoadingMore: Boolean,
): Boolean = totalItemsCount > 0 &&
    lastVisibleIndex >= totalItemsCount - LOAD_MORE_THRESHOLD &&
    canLoadMore && !isLoadingMore
```

- ハブとユーザーの記事一覧の両方で使う。

### 4.3 C1 最新発言を複数フィルターの1 REQ でまとめて取る

- 1 REQ に、チャンネルごとのフィルター（`kinds=[42] #e=[id] since=<保存済みの最新> limit=1`）を最大10本入れる。
  10は snowflare.cc の `max_filters` に合わせた控えめな値（NIP-11 の `max_filters` は大半のリレーが出さない）。
- `ChannelActivityQueue` に `takeBatch(max)` を足す。優先順位（表示中 → ★ → その他）は今と同じ。
  同時に流すのはバッチ2本まで。
- フィルターを作る処理を `channelActivityFilters(ids, sinceOf)` にしてテストする。
- 受け取ったイベントは、本文のチャンネルIDがバッチに含まれるものだけ反映する（今と同じ判定）。

期待: 52 REQ → 6 REQ。

### 4.4 C2 購読IDを短くする

- チャンネル画面: `ch-<種類>-<チャンネルIDの先頭12文字>-<セッションとリレーのハッシュ（36進）>`。
  最長は `ch-reply-count-` が無くなる（4.6）ため、`ch-meta-update` 相当も含めて40文字前後。
  作る処理を `channelSubscriptionKey(channelId, sessionKey, relayKey)` にし、全種類のIDが50文字以内であることをテストする。
- 記事: `articleSubscriptionId(prefix)` を `<prefix>-<乱数（36進）>` にする。50文字以内をテストする。

### 4.5 C3 EOSE のたびに打ち切りまでの待ちを延ばす

- `fetchChannelEvents` の `settleAfterFirstEoseMillis` を「最後に EOSE を受けてから」の待ちに変える。
  EOSE を受けるたびに待ちをやり直す。全リレーの完了、または購読全体のタイムアウト（10秒）で終わるのは今と同じ。
- 応答しないリレーが1件あっても、他のリレーが応答し終わってから1.5秒で終わる（今のテストは変えずに通る）。
- 待ちを延ばした結果、購読全体のタイムアウトに先に当たった場合も、EOSE を1件以上受けていれば成功として扱う。
  今の「最初の EOSE から1.5秒で成功」と同じ意味を保つため。EOSE が1件もなければ今どおり失敗。

### 4.6 C4 チャンネル画面の購読をまとめる

| 今 | 変更後 |
| --- | --- |
| `ch-meta`（kind 40 を ID で）、`ch-meta-update`（kind 41、kind 40 の受信後） | `ch-meta`（2フィルター、最初から両方） |
| `ch-reply-count`、`ch-react`、`ch-repost`、`ch-qrepost` | `ch-eng`（4フィルター） |
| `ch-hide`、`ch-unhide` | `ch-own`（2フィルター） |
| `ch-msg`、`ch-hist-*` | 変えない |

- 受け取ったイベントは種類で振り分け、各処理の今の検証（種類・対象ID・作成者）はそのまま使う。
  kind 42 は返信数と引用リポストの両方へ渡す（それぞれ自分の条件で判定する）。
- kind 41 が kind 40 より先に届いても、候補として持っておき kind 40 の受信時に解決する（`applyMetadataResolution` の現行の動き）。
- フィルターを作る処理（`channelMetaFilters`、`channelEngagementFilters`、`channelOwnHideFilters`）をテストする。

期待: 常時購読 8本 → 4本（メタ、新着、件数、非表示）。

### 4.7 S1 ステータスは表示する種類を絞って取る

```kotlin
internal fun statusFilters(since: Long?): List<NostrFilter> = listOf(
    NostrFilter(kinds = [30315], dTags = ["general", "music"], since = since, limit = 200),
    // 一般・音楽以外の種類を見つけるため、種類を絞らない分も少し取る。
    NostrFilter(kinds = [30315], since = since, limit = 50),
)
```

- `StatusSubscriptionGateway.subscribe` をフィルターのリストを受け取る形にする。

### 4.8 S2 同じリレーに戻ったときは差分だけ取る

- 前回の結果を使う場合（`reusingSnapshot`）、保持しているステータスの最新の `created_at` を `since` にする（同じ秒を含める）。
  自分のステータスの購読も同じ。
- 期限切れは端末側で判定しているため、差分だけでも表示は正しい。削除（本文を空にした置き換え）も新しいイベントとして届く。

## 9. ステータスの最初の表示（2026-10-09 追記）

### 9.1 観察（実機の録画）

1. タブの切り替え中（開始前、`Idle`）に「ステータスがありません」が約0.4秒出る。
2. 取得中は「ステータスを設定…」のカードごと読み込み表示に置き換え、一覧が出るとカードが戻る（上下に動く）。
3. 最初の1件が届いた時点で一覧を出し、名前は16進（`0c9b1e9f…`）のまま。後から名前とアイコンに差し替わる。
   プロフィールの取得は、イベントが届くたびに300ms待ち直してから依頼していた。
   さらに `StatusProfileGateway.ensureProfiles` は取得を依頼するだけで、届くのを待たない。

### 9.2 方式

- 自分のカードは常に出し、一覧の欄だけを読み込み中・空・一覧で切り替える（`statusListContent`）。開始前も読み込み中として扱う。
- 最初の表示は、EOSE の後に、受け取った人のプロフィールがそろうのを最大1秒待ってから出す（`revealAfterProfiles`）。
  それまでのプロフィールの依頼は EOSE でまとめて1回にする。待ちの上限を過ぎても取得は続け、届いた分は後から反映する。
- ゲートウェイは `awaitProfiles`（`ProfileRepository.awaitProfiles`）にし、届くまで待てるようにする。
- 途中でタブを離れて取得を止めたときは、その人たちを待ち行列に戻し、次に表示したときに取り直す。

### 9.3 結果

| 項目 | 変更前 | 変更後 |
| --- | --- | --- |
| 開いた直後 | 「ステータスがありません」が約0.4秒 | 読み込み中の表示 |
| 自分のカード | 消えて戻る | 動かない |
| 名前 | 16進で出て、後から差し替わる | 最初から名前で出る（アイコン画像の読み込みだけ後から） |
| タップから一覧が出るまで | 約1.2秒（名前は未取得） | 約1.45秒（名前つき） |

プロフィールの取得は EOSE から約0.45秒で終わる（77人、yabu.me）。
