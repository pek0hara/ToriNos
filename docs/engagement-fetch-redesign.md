# 付随情報（リアクション・返信・リポスト）の取得と集計の再設計

### 2026-10-16の実装更新

検索・チャンネルも共有EngagementStoreとPendingEngagementOperationsを利用する。EngagementEventClassifierはkind 1/1111/42の返信・引用を文脈で分類し、EngagementProjectionは閲覧リレー、受理イベントID、pendingの配送先を適用して表示を作る。Feed・Threadも同じ投影へ接続した。検索はsessionId付きのlocal commit sequenceにより停止中の自分の確定操作を回復する。チャンネルの件数はChannelEngagementBindingがstore/pendingのrevision一致を確認して公開する。[実装範囲と検証](./refactor-details/implementation-report.md)。


## 1. 対象と結論

状態: 2026-10-09 に段階1〜6を実装済み（11章）。フィードとポスト詳細（通常の投稿）が対象。残りは12章。
対象は、フィード（ホーム・プロフィール等の `FeedController`）とポスト詳細（`ThreadController`）が表示する
リアクション・返信・リポスト・引用の件数と、その取得に使う購読・通信層（`NostrRepository` / `NostrRelay` /
`SubscriptionStateMachine`）。

発端は「プロフィールの投稿のリアクション数（5）がポスト詳細（3）と合わない」不具合。
リレーへ直接問い合わせた実際の件数は3で、フィード側の二重計上だった。
その後の修正とレビューでも別の取りこぼし・二重計上が見つかり続けた。
Android実機の通信ログ（6章）でも、通信層に件数とは別の不備が複数見つかった。

結論は次の2点。

1. **件数を画面ごとの足し引きで持つのをやめる。** アカウント単位で共有する1つの保管場所に、
   投稿ごとのイベントをID集合として持ち、件数は表示時に集合から導出する。
   画面間の差分同期（`NoteCardSync`）と、画面ごとの既読IDによる重複排除を廃止する。
2. **「何を送ったか」を1か所で管理する。** 購読コマンドの送信は購読状態機械だけが決め、
   リレー接続側では保持・再送しない。あわせて、リレーごとの同時購読数とフィルターの上限を守る。

ファイルの分割や個別の分岐修正では、同じ種類の不具合が再発する（3章）。

## 2. 現行の構造

```text
FeedController（画面ごと。ホーム・自分のプロフィール・他人のプロフィール…で別インスタンス）
  ├─ 購読: 履歴取得（リレー×投稿20件ずつ×6区分）+ ライブ購読
  ├─ 重複排除: seenReactionIds 等（上限2000、古い順に破棄）
  ├─ 集計: EngagementAccumulator で件数を +1/-1
  └─ NoteCardSync を受けて詳細画面の値を反映

ThreadController（詳細画面ごと）
  ├─ 購読: 投稿＋返信へのリアクション等（limit 500 の Live 購読）
  ├─ 重複排除: seen*Ids（上限なし）
  ├─ 集計: 独自に件数を +1/-1
  └─ 閉じるときに NoteCardSync へ値を送る

ReactionEventStore（アカウント共通。リアクションのみ）
  └─ 受信した kind 7 を最大1万件保持。kind 5 で削除。新しい購読へキャッシュから再生する

NostrRepository / SubscriptionStateMachine
  └─ 購読ごと・リレーごとに送信済みフィルターを管理し、接続時に再同期

NostrRelay
  └─ 未接続中の送信メッセージを pendingMessages に保持し、接続後に送る
```

同じ「この投稿へのリアクション等」が、フィード画面ごと・詳細画面・キャッシュの3か所以上にあり、
それぞれ独立に取得・重複排除・集計している。

## 3. 問題の見直し

### 3.1 集計

| 問題 | 根拠 | 影響 |
|---|---|---|
| 件数を足し引きで持ち、中身（どのイベントを数えたか）と分離している | `EngagementAccumulator`、`ThreadController.handleReactionEvent` | 一度ずれると直す手段がない |
| 詳細画面の件数を絶対値でフィードへ上書きしていた（修正前） | `withCardSnapshot` | 上書き後に同じイベントを受信すると二重計上（今回の5≠3）。フィードだけが受け取った分は消える |
| 重複排除の既読IDに上限があり、古い順に捨てる | `MAX_SEEN_IDS = 2000` | 捨てた後に同じイベントが再送されると二重計上。取り消した自分のリアクションも再計上 |
| 自分の操作（楽観更新）と受信イベントが同じ件数に混ざる | `withEngagement` と `EngagementAccumulator` が同じ Map を更新 | 送信中に画面を離れる・同じイベントが別経路で届く等の組み合わせで食い違う |
| フィードは kind 6 だけ、詳細は kind 6/16 を数える | `EngagementPartition.Repost`、`ThreadController` の repost 購読 | 画面によって件数が違う |

作業ツリーには、この会話で入れた暫定修正がある（10章）。
暫定修正は個々の症状を止めたが、構造（画面ごとの保持・足し引き・差分同期）は残っている。

### 3.2 取得

| 問題 | 根拠 | 影響 |
|---|---|---|
| 履歴取得がリレーの件数上限で打ち切られても「取得済み」になる（修正前） | `EngagementPartition.filter` に limit・続き取得なし | 人気の投稿で件数が恒久的に少ない |
| 続き取得の判定がキャッシュ再生と購読内の重複排除の影響を受ける（暫定修正） | 履歴取得セッションには `ReactionEventStore` の再生も流れ、`deduplicateEvents = true` のためリレーが返した同じイベントは届かない | 「リレーが何件返したか」「最古の時刻」が正しく分からず、取りこぼし・余計な取得が起きうる |
| 詳細画面は投稿と返信へのリアクションを1フィルター（limit 500）で取っていた（修正前） | `scheduleReactionFetch` | 返信が多いと投稿自体の分が欠ける |
| 詳細画面はページングしない | `limit = 500` の Live 購読のみ | 500件を超えると欠ける |
| フィードと詳細が同じ投稿について別々に取得する | 2章の構造 | 通信の重複と、取得タイミングの違いによる件数差 |

### 3.3 通信層（Android実機ログ、6章）

| ID | 問題 | 根拠（ログ） | 影響 |
|---|---|---|---|
| D1 | 接続直後に同じREQを2回送る | 主要4リレーで接続時の再送が54件（yabu.me 13 / relay-jp 12 / r.kojira.io 15 / r.bitcoinhold.net 14）。2回目の応答が購読終了後に届き STRAY 238件。nostr.fediverse.jp は `Duplicate subscription ... Ignoring` を返す | 通信量の増加、リレー側の拒否、同時REQ上限の圧迫 |
| D2 | 一部のREQがリレーの制限に合わない | バッジ取得がバッジ定義（作成者＋d）ごとにフィルターを分け、1REQに十数件のフィルター。nostream.ocha.one: `must contain less than or equal to 12 items`、premium.primal.net: `arr too big`。また d が空のバッジ定義のフィルター（`#d: [""]`）を nostream.ocha.one が `"[5].#d[0]" is not allowed to be empty` で拒否する（空の d は NIP-01 上は正しいので、こちらの誤りではなくリレー側の制限） | そのリレーからはREQ全体が取得できず、10秒のタイムアウト待ち |
| D3 | NOTICE による拒否が購読に結び付かない | 上記の拒否はすべて NOTICE（購読IDなし）。該当購読は EOSE も CLOSED も来ず `TIMEOUT` で終わる（バッジ取得8件） | 画面の待ち時間が延びる。取得失敗の理由が分からない |
| D4 | リレーごとの同時購読数に上限がない | 同時に開いた購読数の最大: yabu.me 19、r.kojira.io 20、r.bitcoinhold.net 17、relay-jp 16。relay-jp が `ERROR: too many concurrent REQs` を19回返す | 拒否されたREQがどれか分からない。拒否された取得は欠ける、またはタイムアウト待ち |
| D5 | フィードの付随情報ライブ購読が起動直後に開き直しを繰り返す | 0.2秒間に `live open` 15回、`openSubscription aborted ... JobCancellationException`、同じ購読IDの REQ→CLOSE が4リレーへ繰り返し送られる | D4 を悪化させる無駄なREQ/CLOSE |
| D6 | 切断ログにキャンセルが「失敗」として出る | 一時接続の終了時に `WebSocket loop failed ... JobCancellationException` とスタックトレース | 実際の通信失敗と区別できない |

D1 は `subscription-architecture-design.md` 6.3 の「切断前のキュー済み REQ は世代番号が古ければ破棄する」
「キュー要素へ connection generation を追加する」が未実装であることによる（`PendingMessage` に世代がない）。
原因は2か所が「送ったもの」を別々に管理していることにある。
`NostrRelay` は未接続中のREQを `pendingMessages` に溜め、接続後に送る。
`NostrRepository` は接続通知を受けると全購読の状態を `onDisconnected`（`sentFilters = null`）に戻して再同期し、
同じREQをもう一度送る。初回接続でも再接続と同じ扱いになる。
`pendingMessages` は同じ購読IDのREQを1つにまとめるが、接続直後に溜まった分が先に送られると、
再同期のREQは別に送られる（ログでは2回目の応答が STRAY として届いている）。

D5 は `scheduleEngagementFetch` が投稿ごとに `engagementBatchJob` を取り消して作り直し、
ライブ購読が未作成のときは待たずに `subscriptions.open` を始めることによる。
次の投稿で取り消されるため、開きかけた購読が閉じられ、また開かれる。

D4 の NOTICE には購読IDがないため、どのREQが拒否されたかはログから特定できない（推測しない）。
`subscription-architecture-design.md` 19章で未検証の仮説としていた「購読が重なってリレーの上限に達する」は、
このログで実際に起きていることを確認した。

### 3.4 なぜ直すたびに不具合が出たか

集計・取得・通信のいずれも、**同じ事実を複数の場所が別々に持ち、差分で合わせている**。

- 件数: 画面ごとの Map、画面ごとの既読ID、共有キャッシュ、画面間スナップショット
- 取得済みかどうか: 画面ごとの `engagementHistoryStates` / `engagementCompletedPartitions`
- 送信済みのREQ: `SubscriptionStateMachine` と `NostrRelay.pendingMessages`

差分で合わせる仕組みは、どこか1つの取りこぼしや上限による破棄で食い違い、食い違いを検出・修復しない。
個別の修正はこの食い違いの一例を塞ぐだけになる。

### 3.5 既存設計との関係

- `subscription-architecture-design.md`（購読基盤）: desired/wire state の分離、EOSE 前の更新抑止、CLOSED の扱い、
  リレー別の並行バックフィル（11.3.2）は維持する。本設計は 6.3 の世代番号の実装（D1）と、
  13章・19章で扱っていなかったリレーごとの同時購読数とフィルター数の制限（D2・D4）を追加する。
  11.3（フィードのエンゲージメント）の画面ごとの履歴取得状態は、5.4 の共有 Fetcher に置き換える。
- `nip-compatibility-design.md`: リポストの kind と取得先、リアクションの規則はそちらに従う（9章の kind 16 の扱いもそこで決める）。

## 4. 設計方針

1. 事実は1か所に置く。画面はそれを読むだけにする。
2. 件数は保存しない。保存した集合から毎回導出する。
3. 集合への追加は何度行っても同じ結果になる（冪等）。重複排除のための別の記録を持たない。
4. 「どこまで取得したか」は、取得したデータと同じ寿命で同じ場所に持つ。片方だけ捨てない。
5. 通信は「何を送ったか」を状態機械だけが決め、リレーの制限（同時購読数・フィルター数・値の妥当性）を送信前に守る。
6. リレーの応答から確実に分かることだけで判断する。分からないもの（NOTICE の対象など）は推測せず、安全側（再試行・未完了）に倒す。

## 5. 新しい設計

### 5.1 付随情報ストア（EngagementStore）

アカウントセッション単位で1つ。フィード・詳細・今後は他画面も共有する。

```kotlin
/** 1つの投稿に付随するイベント。すべてイベントIDをキーにした集合。 */
data class TargetEngagement(
    val reactions: Map<String, NostrEvent>,     // kind 7
    val reposts: Map<String, NostrEvent>,       // kind 6 / 16
    val replies: Map<String, NostrEvent>,       // 直接の返信（kind 1 / 1111）
    val quotes: Map<String, NostrEvent>,        // q タグで引用した投稿
)

class EngagementStore {
    val changes: Flow<Set<String>>              // 変化した投稿ID
    fun snapshot(targetId: String): TargetEngagement?
    fun add(event: NostrEvent, sourceRelay: String?)   // 何度呼んでも同じ結果
    fun applyDeletion(deletion: NostrEvent)            // kind 5。作者が一致するものだけ
    fun retain(owner: Any, targetIds: Set<String>)     // 画面が表示・保持中の投稿を宣言
    fun release(owner: Any)
}
```

- 受信したイベントは、どの購読から来たものでもここへ入れる（`NostrRepository` の通常接続と一時接続の両方の受信口）。
  対象の投稿IDの判定（リアクションは最後の `e`、返信は `replyTargetId`、引用は `q`）はストアが行う。
- イベントごとに受信元のリレーを記録する（`ReactionEventStore` の `sourceRelayUrls` と同じ）。
  特定リレーのフィード（`FeedController(relayUrl = ...)`）は、現行どおりそのリレーから届いた分だけを数える。
- 削除（kind 5）は作者を確認して集合から外し、削除済みIDを覚える。後から同じイベントが届いても入れない。
  削除済みIDは対象投稿の保持と同じ寿命にする（上限で先に消えない）。
- `ReactionEventStore` はこのストアに統合する。キャッシュからの再生は不要になる（画面はストアを直接読む）。

### 5.2 件数の導出

```kotlin
data class EngagementSummary(
    val reactionCount: Int,
    val likeCount: Int,
    val customReactions: List<CustomReaction>,
    val unicodeReactions: List<UnicodeReaction>,
    val ownReactionIds: Map<String, String>,    // 自分のリアクション（いいね・絵文字）
    val repostCount: Int,                       // reposts + quotes
    val ownRepostId: String?,
    val replyCount: Int,
)

fun summarize(
    engagement: TargetEngagement,
    ownPubkey: String?,
    pending: PendingOperations,
    relayScope: Set<String>?,   // null なら全リレー。特定リレーのフィードはそのリレーだけ
): EngagementSummary
```

- 純粋関数。フィードのカードも詳細画面も同じ関数を使う。
- 画面の `UiState` から `reactionCounts` / `likeReactionCounts` / `customReactions` / `repostCounts` 等の Map を削除し、
  表示時（またはストア変化時に表示中の投稿だけ）に導出する。
- 計算量: 表示中の投稿数 × その投稿のイベント数。変化した投稿だけ再計算し、結果をキャッシュする。

### 5.3 自分の操作（楽観更新）

- 送信中の操作は `PendingOperations`（投稿ID → 操作）としてストアの外に別に持つ。アカウント単位で共有する。
- 表示は「集合から導出した値 ＋ 送信中の操作」。
  - 追加の送信が成功したら、署名済みイベントをストアへ入れてから操作を消す。
  - 取り消しの送信が成功したら、kind 5 をストアへ適用してから操作を消す。
  - 失敗したら操作を消すだけ（集合は変わっていないので戻す計算が要らない）。
- 送信中に画面を離れても、操作はアカウント単位なので他の画面にも同じ表示が出る。

### 5.4 取得（EngagementFetcher）

アカウント単位で1つ。画面は「この投稿たちの付随情報を表示したい」と `retain` で宣言するだけにする。

- **進捗**: 投稿 × リレー × 区分（リアクション、kind 1 返信、kind 1111 返信×2、リポスト、引用）ごとに
  `未取得 / 取得中 / 続きあり(until) / 完了 / 失敗(再試行時刻)` を持つ。
  ストアと同じ寿命で、投稿の保持が外れたら一緒に破棄する。
- **バッチ**: 同じリレー・同じ区分・同じ until の投稿をまとめて1フィルターにする（上限は 5.5 の制限から決める）。
- **続き取得**: 判定はそのリレーが返したイベントだけで行う。
  - 履歴取得の購読は `deduplicateEvents = false` にし、キャッシュ再生を行わない（ストアを直接使うので不要）。
  - 届いた件数が「要求した limit と NIP-11 の `max_limit` の小さい方」に達した区分は、最古の時刻から続きを取る。
    `max_limit` が分からないリレーでは、リレー側の既定上限が要求より小さい可能性があるため、
    保守的なしきい値（例: 100件）で続きを取る。続きが空なら1回の追加取得で終わる。
  - 同じ秒で埋まったら1秒前へ進める。until より新しいイベントを返すリレーは続きを取らず完了扱いにし、ログに残す。
- **ライブ**: 表示中の新しい投稿に絞った1本の購読。対象が変わったときだけ、一定時間まとめてから更新する（D5 対策）。
  開いている途中の購読を取り消さない（作成と更新を1つの直列キューで行う）。
- **詳細画面**: 同じ Fetcher に「この投稿と返信」を宣言する。フィードで取得済みの区分は再取得しない。
  投稿自体と返信は別バッチになるので、返信の件数で投稿の分が欠けない。
- **再取得の契機**: リレーの追加（そのリレーだけ未取得になる）、明示的な更新、復帰時の差分（ライブの since 以降）。

### 5.5 通信層の改修

- **REQ/CLOSE の送信は状態機械だけが決める（D1）**
  - 案A（推奨）: `NostrRelay` は未接続中の REQ/CLOSE を保持しない（EVENT の送信待ちは従来どおり保持してよい）。
    接続時の再同期で、まだ送っていない購読を1回だけ送る。初回接続と再接続を区別する必要がなくなる。
  - 案B: 既存設計 6.3 のとおり `PendingMessage` に接続世代を持たせ、古い世代の REQ/CLOSE を送信前に捨てる。
    変更は小さいが、「送ったもの」を2か所で持つ構造は残る。
  - どちらでも、「同一 `(subId, relay)` で未EOSEのREQが2本同時に存在しない」（既存設計17章）を実機ログの
    STRAY 件数で確認する。
- **リレーごとの制限を送信前に守る（D2・D4）**
  - NIP-11 の `limitation`（`max_subscriptions` / `max_filters` / `max_limit`）を `RelayInformationRepository` から使う。
    不明なときは保守的な既定値（例: 同時購読 10、フィルター 10、limit 500）。
  - 実機ログでは、起動後の定常状態でも主要リレーごとに約8本の購読が開いたまま（うちライブ6本:
    フィード、付随情報、引用、リポスト対象、バッジ、リレーリスト監視）。上限10ではほとんど余裕がないため、
    ライブ購読を用途ごとに分けず、リレーごとにまとめる（フィルターを合成した1本にする）ことも合わせて行う。
  - 同時購読数を超える REQ は送らずに待たせる（リレーごとの送信キュー。優先度: 表示中 > 先読み > バックグラウンド）。
  - フィルター数を超える REQ は分割する。同じ種類のフィルターは著者・IDをまとめて1つにする（バッジ取得の修正）。
  - 空の d のように、仕様上は正しいが拒否するリレーがある値は、ほかのフィルターと同じREQに入れず別REQにする。
    拒否されても他のフィルターの取得を巻き込まない。
- **NOTICE の扱い（D3・D4）**
  - 購読IDのない NOTICE は特定の購読に結び付けない。
  - `too many concurrent REQs` 等の既知の文言を受けたら、そのリレーの同時購読上限を下げ、
    応答のない購読を短い待ち時間で失敗扱いにして再試行キューへ戻す。
  - 文言の判定は一覧で持ち、未知の NOTICE はログに残すだけにする。
- **ログ（D6）**: キャンセルによる終了は失敗として記録しない。

### 5.6 画面との関係

```text
FeedController / ThreadController
  ├─ 表示・保持する投稿IDを EngagementFetcher.retain() で宣言
  ├─ EngagementStore.changes を購読し、表示中の投稿だけ summarize() で再計算
  └─ いいね等の操作は EngagementActions（PendingOperations + 送信）へ委譲
```

- `FeedController` から付随情報の購読・既読ID・集計を取り除く。
- `ThreadController` も同様。詳細画面のリアクション一覧（誰が何をしたか）はストアの集合をそのまま並べる。
- `NoteCardSync` は廃止する（同じストアを見るので同期が不要）。

### 5.7 保持と破棄

- 投稿の保持は画面ごとの `retain(owner, ids)` の和集合。どの画面も保持しなくなった投稿は、
  集合・削除済みID・取得進捗をまとめて破棄する。
- 容量の上限（例: 保持投稿数）を超えるときも、投稿単位でまとめて捨てる。次に表示されたら取り直す。
  「件数だけ残って中身がない」「中身はないのに取得済み」という状態を作らない。
- アカウント切り替えでストア・Fetcher・送信中の操作ごと破棄する。

## 8. テスト計画

テストを先に書き、失敗を確認してから実装する。

- **ストア**: 同じイベントを何度入れても1件。削除後に同じイベントが届いても入らない。作者が違う kind 5 は無視。
  保持を外すと集合・削除済みID・進捗がまとめて消える。
- **導出**: いいね・カスタム絵文字・Unicode絵文字・リポスト（6/16）・引用・返信の件数。自分のリアクション状態。
  送信中の追加・取り消しを重ねた表示。送信の成功・失敗後の表示。
- **Fetcher**: リレー×区分ごとの進捗。limit に達したら続きを取る。同じ秒で埋まったら1秒前へ。
  until を守らないリレーで止まる。キャッシュの影響を受けない（リレーの件数だけで判定）。
  リレー追加でそのリレーだけ取り直す。フィードと詳細が同じ投稿を重ねて取得しない。
  ライブ購読は対象の連続変化でも開き直さない（D5 の回帰テスト）。
- **通信層**: 未接続中の REQ が接続後に1回だけ送られる（D1）。同時購読数を超えると待つ（D4）。
  フィルター数超過の分割と空の値の除外（D2）。NOTICE で上限が下がり、応答のない購読が再試行される（D3）。
- **画面**: 今回の不具合の再現（詳細で数えた後に同じイベントが届く → 3件のまま）を、
  ストア経由の構成で回帰テストとして残す。

- `EngagementFetcher` を複数の画面（利用者）で共有できるようにした（`register` / `activate` / `deactivate` /
  `track` / `forget` / `release`）。どの利用者も追跡しなくなった投稿の進捗だけを捨て、利用者が1つでも動いている間は購読する。
  本番では取得先リレーごとに1つ（`SharedEngagementFetchers`、メインスレッドで動かす）。
  ポスト詳細（通常の投稿）は自前のリアクション・リポスト・引用の購読をやめ、共有の取得を使う。
  表示中の投稿と返信はライブ購読で優先する。引用がストアに入ったら、その引用の付随情報も取る。
  チャンネルのスレッドはチャンネルのリレーから個別に取る従来の方法のまま。
- リポストの取得を kind 6 と 16 にした（NIP-18。9章の未決事項）。
- 他の画面が先に受信したイベントはその画面の購読に届かないため、表示する人のプロフィールを導出時に求めるようにした
  （詳細画面のいいね一覧が公開鍵のままになっていた）。
- 段階1の修正C（詳細画面で表示中の投稿のフィルターを分ける）で、引数名が表示中の投稿IDを隠し、
  直前に予定した投稿を「表示中の投稿」として分けていた。チャンネルのスレッドに残る経路で直した。
- テスト: 送信中の操作の共有（4件）、フィードと詳細が同じストアから同じ件数を出すこと（3件）、
  取得の共有（4件: 履歴取得が1回になる、他の画面が表示中なら追跡を続ける、最後の画面が止まるまでライブ購読を続ける、
  受信がストアと動いている画面へ届く）。スナップショット前提のテストはストア経由のテストに置き換えた。

実機（Android）で、元の不具合の手順を確認した: プロフィールの1件目「子どもがハイハイレース…」は
「いますぐおおきく 1・🤙 2・合計3」、ポスト詳細も同じ値で、いいね一覧は3人（3001・たけし・淀川）、
戻ったプロフィールも同じ値（リレーの実数3と一致）。

## 12. 残っていること

- `ReactionEventStore` は統合していない。通知（`receivedReactions`）と、他の画面の購読へのキャッシュ再生がまだ使う。
  付随情報の履歴取得はキャッシュ再生を切っているので、件数には影響しない。
- チャンネル・記事・ジャーナル・通知・検索の付随情報は、それぞれの仕組みのまま（7章で対象外とした）。
- チャンネルのスレッドは共有の取得を使わない（チャンネルのリレーを使うため）。件数はストアから導出する。
- `PendingEngagementRegistry` はアカウントを削除しても空にしない。送信中の操作は送信が終われば消えるので、残るのは空の入れ物だけ。
- relay-jp は公開上限8に対し7件目で拒否することがある。D3 の処理で上限を下げて回復する。
- 実機確認で、ポスト詳細（ナビゲーションメニュー内）から端末の戻るキーで戻れないことがあった。画面左上の ← では戻れる。
