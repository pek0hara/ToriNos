## 共通の設計規則

1. 構造を抽出する変更と、不具合修正・挙動変更を別の変更にする。R1の完了判定、R3の削除反映、R4の欠落検知、R6の再送時のイベント再利用は挙動変更としてテストする。
2. 画面の状態は画面の寿命、アカウント依存操作は `sessionId` の寿命、公開イベントは共有ストアの保持契約に従う。
3. コルーチンの終了時は購読・監視・retainを解放する。キャンセルを通常の失敗へ変換しない。
4. 接続世代、セッション世代、画面要求世代を混用しない。古い結果の適用は、処理開始時の識別子と所有者を確認して拒否する。
5. 新しいDI基盤やモジュール分割を前提にしない。コンストラクタと小さいインターフェースで依存を渡す。
6. データ保存形式は原則維持する。変更が必要になった場合は読み込み互換と失敗時の復旧を別途設計し、暗黙に移行しない。

## 変更単位と取り込み条件

各設計書の移行手順を1段階ずつ取り込む。旧経路と新経路を同じ操作で同時に動かさず、比較が必要な場合は読み取り専用の比較に限定する。購読・署名・送信・保存を二重実行しない。

変更箇所の既存テストと、各設計書の追加ケースを実行する。通信・セッション・コルーチンに関わる変更はiOSシミュレータとWasmで確認し、Androidのコンパイルと端末の切断・復旧・画面往復・アカウント切り替えを確認する。描画変更は文字サイズとメディアを含む [`regression-test.md`](../regression-test.md) も実施する。

[レビュー記録のAC-01〜16](./review-cycles.md#横断受け入れ条件)は、各回で見つかった競合を含む取り込み条件とする。詳細設計の既存テスト項目と合わせて実行する。

今回の自動検証結果は[実装記録](./implementation-report.md)を参照する。実機回帰・性能計測は未実施であり、自動検証の成功と区別する。

## 実装後の文書管理

確定した通信契約は購読・取得失敗方針、入力の寿命はアカウントセッション、集計はエンゲージメント、表示と保持はフィード、チャンネル公開はチャンネル仕様へ反映する。各文書の導入状況も更新する。

この詳細設計は実装用の一時文書である。すべての移行・確認と恒久文書への反映が終わった後、上位設計とともに削除し、`docs/README.md` のリンクを整理する。
