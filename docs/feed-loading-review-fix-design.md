## 3. 守る性質

前回の修正方針の3章を引き継ぎ、次を加える。

1. 未解決境界（`coverageGaps`）には、リレーが実際に返却上限で切った秒だけを記録する。
   リレーが返せる分をすべて返した秒は記録しない。
2. 表示0件ページの自動継続上限は、新しく受信した投稿がすべて隠れたページだけで数える。
   ほかのリレーから受信済みの投稿しかないページは数えない。
3. 初回の状態（`Empty` / `Failed`）は、応答しないリレーを待ち続けずに決まる。
   決まった後も取得は裏で続け、投稿が届けば一覧を出す。
4. ほかのイベントに埋め込まれて届いた投稿は、検証してから表示し、`canonicalEvents` に入れる。
5. 保持上限は通常履歴（過去方向）の取得だけを止める。新着方向の取得はライブ受信と同じ扱いにする。

## 5. 末尾が1秒だけのリレーを「未取得あり」と誤判定する（P1）

### 5.1 現象

`advanceCursor()` は、要求の `until` と同じ秒の投稿しか返らなかったとき、次のように振り分ける。

| 条件 | 現行の扱い |
|---|---|
| `size < limit` かつ `size < largestPrevious` | 取りきった。前の秒へ進む |
| `size >= limit` かつ `limit < maxPageSize` | 要求数を倍にして同じ秒を取り直す |
| それ以外 | 未解決境界として記録し、前の秒へ進む |

あるフィルターでリレーが投稿を1件しか持っていないと、1ページめは1件、2ページめ（`until` がその1件の秒）も
同じ1件になる。`1 < 1` が偽なので3行めに落ち、未解決境界になる。全件が同じ秒にある場合も同じになる。

一番よく起きるのは復帰時の差分取得である。`since` は保持中の最新投稿の時刻を含むので、
新着がなければその1件だけが返る。一時テストで次を確認した。

- 復帰1回につき、1リレーあたり有限REQが3本出る（`until=now`、`until=最新`、`until=最新-1`）。
- `coverageGapCount=1` が残り、「同じ時刻の投稿に未取得の範囲があります」が表示される。
- 差分取得が完了扱いにならず、`feedSyncs` に残る（`startFeedSync()` の完了判定で `coverageGapCount > 0` のため）。

3つめにより、次の復帰では前回の `since` を引き継ぐ。補完の範囲は24時間で打ち切られるが、
それまで復帰のたびに広がっていくと考えられる（未確認）。

### 5.2 原因

「短いページがリレーの返却上限によるものか」を、そのフィルターで観測した最大件数（`largestPage`）だけで判定している。
1件しか観測していなければ、1件のページを上限によるものと区別できない。

ただし `until` は「その秒以前のすべて」を指す。境界秒の投稿しか返らず、件数がリレーの返却上限より少なければ、
リレーはその秒も、それより古い投稿もすべて返している。足りないのは「返却上限がいくつか」の情報である。

### 5.3 方針

リレーの返却上限の推定値 `relayCap` を次の順で決め、`size < relayCap` なら取りきったとみなす。

1. NIP-11の `limitation.max_limit` が分かっていれば、その値（ジャーナルと同じ `RelayLimits.maxLimit` を使う。取得を待たない）。
2. そのフィルターで観測した最大件数（`largestPage`）。
3. どちらもなければ（または2が下限より小さければ）、下限 `MIN_ASSUMED_RELAY_CAP`。

判定表は次のとおりにする。

| 条件 | 扱い |
|---|---|
| `size < requested.limit` かつ `size < relayCap` | 取りきった。`until = oldest - 1`（`oldest == 0` なら終端） |
| `size >= requested.limit` かつ `limit < maxPageSize` | 要求数を倍にして同じ秒を取り直す（現行どおり） |
| それ以外 | 未解決境界として記録し、前の秒へ進む（現行どおり） |

`MIN_ASSUMED_RELAY_CAP` の初期値は **10** とする。理由：

- 既存テスト `cappedRelayBoundaryIsRecordedWithoutFutileExpansion`（上限20のリレー）は、2が20になるので現行どおり未解決境界になる。
- 返却上限を10件未満にしている実リレーは、これまでの実機ログで見ていない。

coordinatorに `relayCapOf(url): Int?` を引数で渡し、テストでは差し替えられるようにする。

### 5.4 確認するケース

- 投稿1件のリレー：初回→復帰で、有限REQが1ページめ＋前の秒の空ページで終わり、`coverageGapCount=0`、差分取得が `feedSyncs` から消える。
- 全件が同じ秒の5件のリレー：未解決境界にならない。
- 上限20のリレーで同じ秒に20件以上：現行どおり未解決境界になる（既存テスト）。
- NIP-11で `max_limit=5` のリレーが同じ秒の5件を返す：未解決境界になる。
- 復帰を2回繰り返しても、2回めのREQの `since` が1回めより古くならない。

## 6. 重複だけのページを「表示0件」と数える（P1）

### 6.1 現象

`finishPage()` は、正常に終わって `visibleAdded == 0` のページを `emptyVisiblePages` に数え、5ページ続くと
`requiresExplicitLoadMore` にして自動読み込みを止める。`visibleAdded` は「保持に新しく加えた件数のうち、
隠れていない件数」なので、ほかのリレーから受信済みの投稿だけのページも0になる。

一時テストで、6リレーが同じ30件を返すと、初回の読み込み直後に `requiresExplicitLoadMore=true` になることを確認した。
単一著者のプロフィールのフィードのように、どのリレーも同じ投稿を持つ場合に起きやすい。

### 6.2 原因

「隠れた投稿だけだった」と「すでに持っている投稿だけだった」を区別していない。
返信を出さないフィードでは返信を保持に加えないので、`added` でも区別できない。

### 6.3 方針

- `commitHistoryPage()` で、ページの各投稿が保存の前から `historyStore` にあったかを数え、
  `FeedPageCommitResult.Committed` に `newlyStored`（このページで初めて保存した件数）を加える。
  リポストは表示ID（`sourceDisplayId`）ではなくイベントIDで数える。
- `finishPage()` の判定を次のように変える。

| ページの内容 | `emptyVisiblePages` | 自動継続（`skipInvisible`） |
|---|---|---|
| `visibleAdded > 0` | 0に戻す | しない |
| `visibleAdded == 0` かつ `newlyStored > 0`（新しい投稿がすべて隠れた） | 1増やす | 上限まで続ける |
| `newlyStored == 0`（重複だけ、または空） | 変えない | しない |

重複だけのページで自動継続しないのは、そのリレーがほかのリレーと同じ範囲を取り直しているだけで、
続けても表示が増える見込みがないためである。表示境界より遅れているリレーの追いつき（`behindRevealed`）は、
この判定と関係なく現行どおり行う。

### 6.4 確認するケース

- 6リレーが同じ30件を返す：`requiresExplicitLoadMore=false` のまま、末尾までスクロールすると次のページを取りにいく。
- 返信だけのページが5回続く：現行どおり止まる（既存テスト）。
- 返信だけのページと重複だけのページが交互に来る：返信だけのページだけを数えて5回で止まる。
- ミュートした著者だけのページ：隠れた投稿として数える。

## 7. 応答しないリレーで初回状態が決まらない（P2）

### 7.1 現象

`publishState()` の `isInitialFetchSettled` は、全リレーが「初回ページ完了・停止・失敗回数が上限」のいずれかになるまで偽である。
通常の履歴取得は `maxFailures = Int.MAX_VALUE` なので、タイムアウトし続けるリレーが1本あると永久に偽になる。

- 投稿が0件のプロフィールやハッシュタグで、`Empty` にならずスケルトンが続く。
- 全リレーに届かないときも、`Failed` にならずスケルトンが続く。

投稿があれば一覧が出て `ContentReady` になるので、この問題は「結果が空」のときだけ見える。

### 7.2 方針

- 初回の状態を決めるときだけ、`failureCount >= INITIAL_SETTLE_FAILURES` のリレーを確定済みに数える。
  取得の再試行（`maxFailures`）は変えず、裏で続ける。
- `INITIAL_SETTLE_FAILURES` の初期値は **2** とする。タイムアウト10秒＋待ち2秒＋10秒で、
  最長およそ22秒で状態が決まる。
- 判定に使う失敗には、`TimedOut`・接続失敗・CLOSED（再試行可）を含める。認証待ち（`RetryAfterAuth`）は含めない。
  署名器の承認を待っている間に `Empty` を出さないためである。
- `Empty` / `Failed` を出した後に投稿が届いたら、現行どおり `ContentReady` に変わる
  （`assembleFeedState()` が一覧の有無で決める）。

### 7.3 補足

`Failed` の表示から手動更新すると、`startRelayHistory()` が新しいcoordinatorを作るので失敗回数は0に戻る。
この動きは変えない。

### 7.4 確認するケース

- 2リレーのうち1つが空で完了、もう1つが2回タイムアウト：`Empty` になる。
- 2リレーとも2回タイムアウト：`Failed` になる。
- `Empty` の後に遅れたリレーから投稿が届く：一覧が出る。
- 認証待ちのリレーが1つ残っている：`Empty` にしない。

## 8. リポストの埋め込み投稿を検証しない（P2）

### 8.1 現象

`appendRepostedEvent()` は、kind 6 の `content` をそのまま元の投稿として一覧に出し、`canonicalEvents` も上書きする。
リポストする人が任意の pubkey・本文で投稿を作って埋め込めば、その人の発言として表示される。
その投稿をこちらがリポストすると、`repost()` は `canonicalEvents` の内容を埋め込むので、捏造した内容を再配布する。

通知（`NotificationTarget`）とIDでの取得（`EventByIdFetcher`）では `isValidEvent` で検証している。フィードだけ抜けている。

### 8.2 範囲

この章は「ほかのイベントに埋め込まれて届いた投稿」に限る。リレーから直接届いたイベントの署名検証は、
リレーを信頼する現行の前提に関わるので、この文書の対象にしない（13章）。

### 8.3 計測

`isValidEvent` は署名検証（schnorr）とIDのハッシュ計算をするので、メインで同期的に呼べるかを先に測る。
Android実機とiOS実機で、1件あたりの時間を `FeedTrace` に出して確かめる。

| 1件あたり | 方式 |
|---|---|
| 0.2ms以下 | A：`appendRepostedEvent()` の中で同期的に検証する |
| それより大きい | B：受信時に計算用ディスパッチャで検証し、結果を待ってから取り込む |

Bでは、履歴ページは受信時（`onEvent`）に検証を始め、確定（`onPageCommit`）の前にそのページ分の検証を待つ。
`onPageCommit` は今は suspend ではないので、Bを選ぶ場合は確定処理を suspend にする変更が要る。

### 8.4 方針

- 埋め込み投稿を使う条件：
  1. `isValidEvent` が真。
  2. `e` タグがあれば、最後の `e` タグのIDと埋め込み投稿のIDが一致する。
- 条件を満たさなければ、`content` が空のリポストと同じ扱いにする（`e` タグのIDで元の投稿を取りにいく）。
  `e` タグもなければ捨てる。
- `canonicalEvents` には検証を通った投稿だけを入れる。
- 検証済みのIDを `MAX_SEEN_IDS` 件まで覚え、同じ投稿の複数のリポストで検証を繰り返さない。

### 8.5 確認するケース

- 正しい署名の埋め込み：現行どおり表示する。
- 本文を書き換えた埋め込み（IDが合わない）：表示せず、`e` タグのIDで取得する。
- IDは合うが署名が違う：同上。
- `e` タグと埋め込みのIDが違う：同上。
- 捏造された埋め込みの後に、こちらがその投稿をリポスト：リレーから取った正しい内容で送る。

## 9. ライブ購読の `since` が端末の現在時刻ちょうど（P3）

### 9.1 現象

ライブ購読は `since = 端末の現在時刻` で開く（`startRelayHistory()` と、再開時の `subscribeLiveFeed()`）。
端末の時計が進んでいる、または投稿者の時計が遅れていると、購読直後に投稿された `created_at < since` の投稿がライブで届かない。
その後に新しい投稿を保持すると、次の差分取得は保持中の最新時刻からなので、取りこぼした投稿は拾われない。

### 9.2 方針

- ライブ購読の `since` を `now - LIVE_SINCE_OVERLAP_SECONDS` にする。初期値は既存の
  `LIVE_RESUME_OVERLAP_SECONDS` と同じ **60秒** とし、定数を1つにまとめる。
- 初回の表示境界（`historyFloor`、`historyRevealOldestAt`）は変えない。重なりで届いた古い投稿は保持され、
  表示境界がそこまで進んだときに出る。
- 重なりで同じ投稿が履歴とライブの両方から届くが、現行どおりIDで重複を除く。
- `newPostCount` は「一覧の先頭より新しい投稿」だけを数えるので、重なりで届いた投稿を新着と数えない。

### 9.3 確認するケース

- 購読の30秒前の投稿がライブで届く：保持され、表示境界がそこまで進めば一覧に出る。
- 履歴とライブの両方で同じ投稿が届く：一覧に1件だけ出る。
- 先頭にいないときに重なりで古い投稿が届く：新着の件数に数えない。

## 10. 保持上限で差分取得も止まる（P3）

### 10.1 現象

差分取得のcoordinatorにも `canRequest = { !historyStore.limitReached }` を渡している。
ライブ受信だけで保持が5,000件に達した長時間のセッションでは、復帰しても離れていた間の投稿を取らない。
「端末で保持できる履歴の上限に達しました」は出るが、「再試行」ボタンは上限中は押せない。

### 10.2 方針

- 差分取得（全リレー・リレー単位とも）の `canRequest` は常に真にする。通常の履歴取得だけ現行どおり止める。
- 差分取得の確定後も、ライブ受信と同じく保持を削る。`appendLiveEvent()` の削る処理を
  `trimHeldEventsIfNeeded(protect: Set<String>)` に切り出し、両方から呼ぶ。
  表示中・表示待ちの投稿を守る規則は現行どおり。
- 差分取得は `MAX_FEED_SYNC_EVENTS`（500件）の予算で打ち切られるので、上限中に取っても増え方は抑えられる。
- 表示：上限中でも差分取得の失敗（`pendingGapCount > 0`）には「再試行」を押せるようにする。

### 10.3 確認するケース

- 保持上限に達した状態で復帰：差分取得のREQが出て、新着が一覧に出る。
- そのとき保持件数は上限＋余裕分を超えない。表示中の投稿は削られない。
- 上限中の通常の「もっと読む」は、現行どおりREQを出さない。

## 11. 一覧の組み直しで全件を走査する（P3）

`flushPendingTimelineEvents()` と `rebuildFilteredEvents()` は、保持中の全件をミュート・NGワードでフィルタして並べ替える。
`updateEvents()` も呼ぶたびに `eventSortTimes` を全件コピーする。どちらもメインで動き、新着のまとめ反映（150ms）ごとに走る。

まだ計測していないので、先に次を測る。

- 保持が5,000件、NGワードが50語のときの、`updateEvents()` の呼び出し1回のメインスレッドでの時間（Android実機・iOS実機）。
- ライブ受信が多い時間帯に、1分あたり何回呼ばれるか。

1回が数ms以上で、受信が続くとスクロールが重くなるなら、次を検討する（この文書では決めない）。

- フィルタの結果を投稿ごとに覚え、ミュート・NGワードが変わったときだけ全件を判定し直す。
- 並べ替え済みの一覧に、新しい投稿を挿入するだけにする。
- `eventSortTimes` のコピーをやめ、変更のたびに作る読み取り専用の写しを渡す。

## 12. 実機確認

[`regression-test.md`](./regression-test.md) の手順に加え、次を確認する。
リアクションを誤って送らないよう、フィードの投稿はタップしない。

- 投稿の少ない著者のプロフィールを開き、別のタブへ移って戻る：警告が出ず、REQが増え続けない（通信ログで確認）。
- 同じ投稿を持つリレーを6本以上有効にした状態で、末尾までスクロールする：「もっと読む」なしで読み込みが続く。
- 投稿のないハッシュタグを、応答しないリレーを含めて開く：おおよそ25秒以内に空の表示になる。

### 12.1 エミュレータでの確認結果（2026-11-16）

Android 35 のエミュレータで、ログインしない状態（グローバルは yabu.me、プロフィールは有効な3リレー）で確認した。

| 確認 | 結果 |
|---|---|
| 9章：ライブ購読が基準時刻の60秒前から始まる | 確認。重なりで届いた1件は、履歴側で受信済みとして除かれた |
| 5章：新着のない復帰で、差分取得が未解決境界を残さず完了する | 確認。境界秒の1件だけのページで前の秒へ進み、差分取得が完了した |
| 6章：同じ内容を返すリレーの重複ページで、読み込みが止まらない | 確認（3リレー）。6本以上での上限到達は、リレーを足せないので未確認 |
| 8章：埋め込みのリポストが、実際の署名検証を通って表示される | 確認。プロフィールで5件のリポストがすべて検証を通り、「がリポスト」の表示が出た |
| 7章：投稿のないフィードが空の表示になる | 未確認。投稿のないプロフィールを開く経路が画面になく、ハッシュタグのフィードも使われていない |
| 10章：保持上限での差分取得 | 未確認。5,000件に達するまで使い続ける必要がある |

確認の中で見つけた2点を直した（14章の最後の2項目）。直した後に同じ操作をもう一度行い、
新着のない復帰の差分取得が1リレーあたり2本で終わること、プロフィールで満杯の重複ページから
先読みしないことを確かめた。

## 13. 対象にしないもの・未決事項

- **リレーから直接届いたイベントの署名検証**：現行はリレーを信頼し、フィードの投稿を検証していない。
  悪意のあるリレーは任意の投稿を出せる。検証するかは、8.3の計測結果と合わせて別に決める。
- **24時間を超えて離れた後の穴**：最新ページだけを取る（`LatestPage`）ので、古い保持分との間に穴が空いても表示されない。
  意図どおりか、一覧に「ここから先は未取得」の印を出すかを決める。
- **5.3の `MIN_ASSUMED_RELAY_CAP`**：10で足りるかは、実機で各リレーのNIP-11を見て確かめる。

## 14. 実装時の判断

- **5章**：直したのは境界秒の誤判定だけで、境界秒の取り直し自体は残した。短い1ページめで前の秒へ
  直接進めばREQが減るが、境界秒を取り直す現行の安全側の動きを変えることになるので見送った。
  新着のない復帰は、1ページめと境界秒の取り直しの2本になる（次の秒の空ページは、下の「範囲外のREQ」の修正で出なくなった）。
- **6章**：要求数に満たない重複ページでは続きを取ることにした（6.3の表の3行めを変更）。境界秒の取り直しは
  必ず短い重複ページになり、そこで止めると「もっと読む」が何も増やさずに終わるためである。
  自動継続の上限（`emptyVisiblePages`）には数えず、リレーごとに `MAX_CATCH_UP_PAGES`（3ページ）までにする。
  満杯の重複ページ（他のリレーと同じ範囲を返しただけ）では続きを取らない。最初は満杯でも続きを取る実装にしたが、
  エミュレータで、同じ内容のリレーが「もっと読む」のたびに次のページを先読みしていたので改めた。
  空のページは現行どおり「表示0件」として数える。
- **7章**：認証待ち（`RetryAfterAuth`）のリレーは、現行でも停止（`suppressed`）として確定済みに数えている。
  7.2の「認証待ちは含めない」は実装していない。認証待ちのリレーしか残っていなければ、現行どおり状態が決まる。
  差分取得のcoordinatorは `settleAfterFailures = 3` を渡し、完了判定を現行（3回失敗）のままにした。
- **8章**：実機の計測を待たず、検証を計算用ディスパッチャで行ってから一覧に加える方式にした（8.3のAでもBでもない）。
  メインスレッドを止めず、確定処理を suspend にする変更も要らない。検証済みのIDは同期的に加える。
  代わりに、検証待ちのリポストはページ確定時の表示件数に数えない。リポストだけのページは「表示0件」と
  数えられ、続きを1ページ多く取ることがある。
  テストの投稿は署名を持たないので、埋め込みのリポストを使うテストは `validateEmbeddedEvent = { true }` を渡す。
- **9章**：重なりは `subscribeLiveFeed()` の中で引く。呼び出し側が渡す基準時刻（表示境界と同じ値）は変えていない。
- **10章**：削る処理は `trimHeldEventsIfNeeded()` に切り出した。差分取得ではページの確定ごとに呼ぶ。
- **範囲外のREQ（エミュレータで発見）**：差分取得で境界秒の取り直しの後、`until` が `since` より前になる、
  必ず空のREQを送っていた。カーソルを進めた結果 `until < since` になったフィルターは、その場で取りきったものとする。
