# お気に入りユーザー設計

作成日: 2026-10-01。状態: 設計案（未実装）。

## 1. 目的と範囲

特定のユーザーを非公開のお気に入りに登録し、同じNostrアカウントで利用する端末間で同期する。

会話で合意した方針は「対象はユーザー」「非公開を標準」「端末間同期」。以下の画面配置・識別子・同期規則は、その方針に基づく提案。

- フォローしていないユーザーも登録できる。登録・解除では通常のフォロー一覧を変更しない。
- 初期版はアカウントごとに1つの非公開リストを扱う。公開切り替えや複数カテゴリは設けない。
- 登録一覧からプロフィールを開ける。タイムラインの並び替え、専用フィード、通知の優先設定は今回の範囲に含めない。
- 記事・チャンネル・絵文字のお気に入りとは別の状態として管理する。

## 2. Nostrでの保存形式

[NIP-51](https://github.com/nostr-protocol/nips/blob/master/51.md)のFollow sets（kind 30000）を使い、項目は自分宛てのNIP-44暗号文としてcontentに保存する。同じアカウント・kind・dで更新する。

| 項目 | 値 |
| --- | --- |
| kind | `30000` |
| d | `torinos-favorite-users`（固定） |
| 公開tags | `[["d", "torinos-favorite-users"]]` |
| content | `[["p", "<pubkey>"]]`形式のJSON配列を、自分宛てにNIP-44暗号化したもの |
| 取得filter | authors=自分のpubkey、kinds=[30000]、#d=[torinos-favorite-users] |

「お気に入りユーザー」はアプリ内で表示する名称とし、初期作成時にtitleやdescriptionは発行しない。10021はリスト自体をお気に入りにする種類であり、今回の保存先には使わない。

暗号化前の例:

```json
[
  ["p", "<ユーザーAの64桁hex公開鍵>"],
  ["p", "<ユーザーBの64桁hex公開鍵>"]
]
```

- 公開鍵は小文字の64桁hexに正規化し、重複を排除する。新規項目は末尾に追加する。
- 最後の1件を解除した場合も、暗号化した`[]`を発行する。イベントの削除では表現しない。
- 他のdのFollow setsを取り込んだり書き換えたりしない。
- 同じdの最新イベントに公開pタグが含まれる場合は、非公開の前提と一致しないため自動編集を停止し、互換性エラーを表示する。黙って公開項目を消したり公開方式を引き継いだりしない。
- 既存の非pタグ、暗号化内の未知タグ、既存pタグの付加情報は保持する。解除対象のpタグだけを削除する。
- 新規発行はNIP-44のみ。初期版でNIP-04の旧暗号文には対応せず、読めないイベントを空リスト扱いしない。

NIP-51形式を使うため他クライアントが解釈できる余地はあるが、専用dをToriNosのお気に入りとして認識する保証はない。

## 3. 非公開の意味

リレーに公開されるのは、作成者、kind、d、更新時刻、暗号文とそのサイズ。お気に入りにした相手の公開鍵を公開tagsに入れない。

リストの存在・更新の事実まで隠す設計ではない。同じ秘密鍵を使える端末・アプリは復号できる。プロフィール取得など通常の通信の秘匿は、この機能では扱わない。

端末内キャッシュは既存のアカウント別LocalSettingsStorageに保存する。初期版では端末内の暗号化を追加せず、「非公開」はリレーへ送るリスト項目の暗号化を指す。お気に入りの公開鍵一覧・復号したcontent・秘密鍵をログに出さない。

## 4. 画面と操作

### 登録・解除

他ユーザーのプロフィールに星ボタンを追加する。選択状態はアカウントセッションの共有StateFlowから表示し、画面ごとに別の状態を持たない。

- 未登録: 「お気に入りに追加」。登録済み: 「お気に入りを解除」。
- タップ後、端末への保存成功をもって一覧・星を更新し、同期を予約する。通信完了を待たず次の操作ができる。
- 保存失敗なら操作を確定せずエラーを表示する。送信失敗なら端末の変更を保持し、再試行する。
- 初回説明は「お気に入りは非公開で保存され、同じアカウントの端末間で同期されます」。
- 自分自身・未ログイン状態では星ボタンを表示しない。

### 一覧

自分のプロフィールから「お気に入り」を開く。登録順の逆順で最近追加した人を上に表示する。行にはアイコン、表示名、識別情報、解除ボタンを置き、行タップでプロフィールへ遷移する。

プロフィール未取得でも公開鍵で行を表示し、既存のProfileRepositoryで段階的に補完する。解除はフォロー・ミュートへ影響させず、ミュートしたユーザーも管理のため一覧には残す。

一覧には再読み込み操作と同期状態を表示する。

| 状態 | 表示例 |
| --- | --- |
| キャッシュ読込中 | 読み込み中 |
| 最新イベント取得中 | 同期中 |
| 端末保存済み・未送信 | 同期待ち |
| 1つ以上の送信先で受理・残り再送中 | 一部のリレーに未同期 |
| 全送信先で受理 | 同期済み |
| 取得・暗号化・署名・送信失敗 | エラーの説明と再試行 |

初回取得に失敗しキャッシュもない場合は「読み込めませんでした」と表示し、「お気に入りはいません」と区別する。他ユーザーのプロフィールにはお気に入り一覧・件数を表示しない。

## 5. アカウント単位の構成

既存のAccountSessionを所有者とし、セッション終了時に購読・同期ジョブを終了する。

| 提案する要素 | 責務 |
| --- | --- |
| FavoriteUsersRepository | 確認済みリスト、未送信操作、画面用状態、アカウント別永続化 |
| FavoriteUsersEventCodec | タグの解析・保持・追加・解除。暗号化はAccountSignerに委譲 |
| FavoriteUsersSync | 最新取得、復号、未送信操作の適用、署名、送信、再試行 |
| FavoriteUsersTransport | NostrRepositoryを使った取得・受理結果の取得。テストで差し替え可能にする |
| FavoriteUsersScreen / ViewModel | 一覧と操作、プロフィール情報の補完 |

既存のAccountSigner.encryptToSelf / decryptとNip44を再利用する。PrivateMuteListStoreの暗号化経路、EmojiPreferenceSyncの前面復帰・送信箱は参考にするが、その同期アルゴリズムをそのままコピーしない。

保存キーは`favorite_users_cache_v1_<ownPubkey>`。以下を1つのスナップショットとして直列に保存する。

- 最後に採用したイベントと、その公開・非公開タグ。
- 未送信操作（操作ID、追加/解除、対象pubkey、操作順）。
- 署名済み送信イベント、そこへ反映した操作の境界、リレー別受理状況。
- 状態のrevision。同期結果を適用するとき、署名後に発生した操作を消さないために使う。

画面向け一覧は「確認済みリストに未送信操作を順番に適用した結果」から導出する。未送信操作は最後の希望状態へ圧縮できるが、確認前の解除を単なる集合差分として捨てない。

## 6. 同期手順

### 取得

起動時、アプリ前面復帰時（前回取得から60秒以上）、一覧の再読み込み時、再接続後、送信前に取得する。前面利用中は専用リストの更新も購読する。

受信イベントは署名、作者、kind、dを検証する。[NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md)に従いcreated_atが最大のもの、同時刻ならidが辞書順で小さいものを最新候補とする。キャッシュや未完了の自分の送信イベントより古いイベントは採用しない。

最新候補の復号・構造検証に失敗した場合は、自動送信を停止し、キャッシュと未送信操作を保持する。古い復号可能イベントに戻って最新を上書きしない。

正常に取得が完了したリレーが1つ以上ある場合にのみ、送信前取得を成功と扱う。全リレーのタイムアウト・切断は「リストが存在しない」と区別する。応答しないリレーがある場合は完全な最新性を保証できず、再接続時に再取得する。

### 追加・解除と送信

1. 端末操作を操作ログに保存し、画面へ反映する。オフラインでも利用できる。
2. 350ms程度のデバウンス後、同期用Mutexの下で最新イベントを取得する。
3. 最新の復号済みリストへ、未送信の追加・解除を順番に適用する。取得が失敗した場合は送信を保留する。
4. 操作を含んだスナップショットを自分宛てに暗号化し、署名する。created_atは端末時刻と既知最新イベント時刻+1の大きい方とする。極端な未来時刻のイベントでは自動更新を止める（許容範囲は実装時に既存ポリシーと合わせる）。
5. 発行イベントと反映済み操作の境界を永続化してから、アカウントの書き込みリレーへ送る。
6. リレーのOK受理を確認する。1つ以上の受理で当該スナップショットを確認済みの候補にできるが、他の送信先は再試行対象として残す。受理後の操作ログ整理・候補更新は同じ保存で行う。
7. 署名・送信中に追加された操作は未送信のまま残し、次の送信へ進める。

通常のフォローkind 3、お気に入りFollow sets参照kind 10021は発行しない。リストが未作成で操作もなければ、ログインしただけでは空イベントを作らない。

### 送信失敗・再起動

未送信操作とリレー別受理状況を永続化する。再試行は30秒を初期値とし、失敗が続く場合は間隔を広げる。

再接続や再起動時は、保存した古いイベントを無条件に再送せず、先に最新を取得する。新しいリモートイベントがあれば、それを基準に未確認操作を再適用して作り直す。既に確認済みの変更を古い送信箱から復活させない。

リモート更新が未完了の自分のイベントより新しい場合、古いイベントの残りの送信先は破棄する。未確認の操作だけを残す。未完了イベント自体が最新なら、そのイベントを同じIDで残りのリレーへ再送できる。

アカウント切り替え後に古いセッションの結果を新しい画面・保存キーへ反映しない。署名・復号・送信前と、応答適用前にAccountSession.ensureActiveを確認する。

## 7. 複数端末の競合と限界

初期版はNIP-51のリスト全体を置換する方式とし、NIP-01の最新イベント選択に従う。

送信前の取得と未送信操作の再適用によって、既に取得できた別端末の変更は保持する。例: 別端末でAを追加済み、自端末でBを追加した場合、最新を取得できればA+Bを送る。

ただし、両端末が同じ旧リストを読み、ほぼ同時に別々の追加を送信すると、後で採用されるイベントによって一方の変更が失われる可能性がある。同じユーザーへの追加と解除も、採用されたイベントの状態が優先される。完全に無損失な同時編集は保証しない。

取得済みの古いリストとの単純な和集合は行わない。解除したユーザーを復活させるため。無損失な同時編集が要件になった場合は、操作イベント・解除履歴を含む別の同期方式を改めて設計する。

## 8. 容量・異常時の扱い

- 暗号化前のJSONは、既存Nip44実装の上限65,535バイト以内にする。件数だけで判定せず、保持する未知タグも含めて実サイズを検証する。
- 上限を超える追加は確定せず、削除操作は可能にする。既存の項目を自動で切り捨てない。
- キャッシュ破損を空リストで上書きせず、リレーからの復元を試みる。読めない保存データは復旧のため残す。
- 暗号化・署名が利用できない状態では公開保存へフォールバックしない。

## 9. 実装時の検証項目

1. 公開tagsにお気に入り対象のpタグがなく、別アカウントの鍵ではcontentを復号できない。
2. フォロー外のユーザーを登録でき、追加・解除でkind 3が変わらない。
3. 最後の解除が暗号化した空配列として別端末へ反映される。
4. 起動直後の操作、オフライン操作、再起動後の操作再送で未送信変更を失わない。
5. 取得失敗とリスト不在、復号失敗と空リストを区別し、自動上書きを防ぐ。
6. 署名・送信中の追加操作を受理結果が巻き戻さない。
7. 別端末の既知の変更へ未送信操作を再適用でき、解除を和集合で復活させない。
8. 同時刻イベントの比較、署名不正、別d、公開pタグ混在を扱える。
9. 部分受理後の再起動、古い送信箱、新しいリモート更新の組合せで古いリストを再送しない。
10. アカウント切り替え中の遅延応答と保存処理が他アカウントへ混ざらない。
11. プロフィール未取得の行、空状態、エラー、同期中、アクセシビリティのラベルを確認する。

## 10. 実装順

1. イベントcodec、未送信操作の適用、キャッシュとその検証。
2. AccountSession配下のrepository・同期・送信箱と同期シナリオの検証。
3. プロフィールの星、本人用のお気に入り一覧、ナビゲーション。
4. 対応するプラットフォームで起動・前面復帰・2端末同期・オフライン復旧を確認。

この文書では設計のみ追加し、アプリの実装は変更しない。
