# Buzz コミュニティ内の検索 設計

- 作成日: 2026-11-22
- ステータス: 改訂（2026-11-22、ToriNos 独自の一致方式へ。初版の公式モバイル版準拠は iPhone 実機で確認済み）
- 目的: 選んでいる Buzz コミュニティの中で、メッセージ・チャンネル・人を検索できるようにする。リレーの検索は公式と同じ窓口を使い、リレーが苦手な一致（語の途中、日本語の文の途中）は ToriNos が手元で補う。
- 対象: Buzz のコミュニティだけ。標準の NIP-29 リレーには出さない（NIP-50 に対応しているとは限らず、作者の解釈も違うため）。
- 調査対象（2026-11-22 時点の main）:
  - [block/buzz](https://github.com/block/buzz) `0e7fd48`
    - モバイル版（Flutter）: `mobile/lib/features/search/search_provider.dart`、`search_page.dart`、`search_page/message_tile.dart`、`recent_searches_provider.dart`、`name_match.dart`、`shared/relay/relay_session.dart`（`searchProfiles`）、`shared/relay/nostr_filters.dart`（`searchUsers`）
    - リレー: `crates/buzz-relay/src/handlers/req.rs`（WebSocket の NIP-50）、`api/bridge.rs`（`/query` の検索）、`api/profiles.rs`（`/profiles/search`）、`crates/buzz-search/src/query.rs`、`migrations/0008_fresh_install_search_allowlist.sql`
  - [block/buzz-app](https://github.com/block/buzz-app) `4363e10`（デスクトップ）: `src/app/shell/useSearchMessages.ts`、`parseSearchOperators.ts`、`shared/search-debounce.ts`
- 関連: `docs/nip29-buzz-design.md`（Buzz の全体）、`docs/buzz-presence-design.md`（NIP-98 の REST）

## 1. 公式の実装

### 1.1 リレー側

- 全文検索は Postgres の FTS。`search_tsv = to_tsvector('simple', content)` で、索引に入る kind は **0・9・40002・45001・45003** だけ。
- WebSocket の REQ に `search` を付けると NIP-50 の検索になる（`handlers/req.rs`）。
  - 同じ REQ の中で `search` の有るフィルターと無いフィルターを混ぜると `CLOSED`（`error: mixed search and non-search filters not supported`）。
  - 結果は関連度順（`ts_rank_cd`、同点は新しい順）で送られ、EOSE で終わる一度きりの購読（ライブ配信はしない）。
  - WebSocket では `search_mode`・`search_sort`・`page` は使えず、常に全文（`websearch_to_tsquery`）・関連度順。
  - `#h` を付けるとそのチャンネルだけ。無ければ、読めるチャンネル全部（＋チャンネルに属さないイベント）。
  - 当たったイベントは改めて読める範囲か確かめてから返す（検索で読める範囲は広がらない）。
- HTTP の `POST /query`（NIP-98 必須）でも同じ検索ができ、こちらは `search_mode: "prefix"`（最後の語を前方一致）、`search_sort: "newest"`（NIP-11 の `supported_extensions` に `buzz-search-sort` があるとき）、`page` が使える。デスクトップ版はこちらを使う。
- 件数の上限（2026-11-21 時点）:

| 取り方 | 1回の上限 | 続き |
| --- | --- | --- |
| 検索・`POST /query` | 500 件（既定 100） | `page`（1〜1000）。オフセットは `(page - 1) × limit` |
| 検索・WebSocket（全文） | 1,000 件 | 無し |
| 普通の取得・WebSocket | 1,000 件 | `until` でさかのぼる |

  前方一致・関連度順は、当たりの新しい 1,000 件だけを並べる（`PREFIX_RANK_WINDOW`）。それより古い当たりは出ない。
- `POST /profiles/search`（NIP-98 必須）: 本文 `{"query": 1〜100文字, "limit": 1〜100, "page"?}`。`name`・`display_name`（と認証済みの名前）だけを前方一致で探し、名前の一致を先に並べる。応答は kind 0 と kind 30382 のイベントの配列。古いリレーは 404 / 405。

### 1.2 モバイル版（ToriNos が合わせる相手）

| 項目 | 内容 |
| --- | --- |
| 入口 | 検索画面（ホームのタブ / ボタン）。開いたらすぐキーボードを出す |
| 入力 | 1文字ごとに検索し直す。**300ms** 止まってから送る。前の検索の答えは捨てる（世代番号） |
| 絞り込み | すべて / メッセージ / チャンネル / 人 のチップ。表示だけを切り替え、検索はいつも3つとも行う |
| メッセージ | WebSocket の REQ `{"kinds":[9,40002,45001,45003],"search":<入力>,"limit":20}`。`#h` も `search_mode` も付けない。関連度順のまま出す。続きの読み込みは無い |
| チャンネル | 手元のチャンネル一覧（参加中 + 公開ディレクトリ）を名前で順位付け（下の 1.3）。DM は除く。アーカイブ済みと、`#` だけの入力では参加中のものだけ。最大 **8** 件 |
| 人 | `/profiles/search`（`limit` 24）。404 / 405 なら 5 分間は NIP-50（`{"kinds":[0],"search":…,"limit":…, "search_mode":"prefix"}` を `/query` へ）。自分は除く。最大 **8** 件 |
| メッセージの行 | アバター、名前、相対時刻、「Message in `#チャンネル`」（DM は「Direct message」）、本文2行（512文字を超える本文は書式を解釈しない） |
| メッセージを押す | フォーラム投稿（45001）はその投稿のスレッド。それ以外はチャンネルを開く（発言の位置へは飛ばない） |
| 最近の検索 | 入力が空のときに出す。最大 **6** 件、新しい順、大文字小文字を無視して重複を消す。決定（キーボードの検索）と、結果を押したときに記録。「消去」で全部消す。コミュニティとアカウントごとに端末へ保存 |
| 空のとき | 「メッセージ・チャンネル・人を検索」。結果が無ければ「'…' に一致するものはありません」 |

### 1.3 チャンネル名の順位（`name_match.dart`、デスクトップの `matchName` の移植）

入力は小文字にし、先頭の `#` を外す。名前も小文字にして比べ、良い順に:

0. 完全一致
1. 先頭が一致
2. 途中の語の頭で一致（直前が文字・数字でない）
3. 途中の一致
4. 文字が順に現れ、それぞれのまとまりが語の頭から始まる（`tlp` → `team-launch-planning`）
5. 文字が順に現れる

どれでもなければ外す。入力の空白は比べるときに無視する（4・5）。アーカイブ済みは +0.5。同順位なら参加中を先に（参加中どうしは一覧の順）、未参加は名前順。

### 1.4 デスクトップ版

- `/query` で `search_mode: "prefix"`（最後の語を前方一致）。最後の語が 3 文字未満なら送らず「短すぎる」と出す。引用符の語句・`-語` の除外があれば全文。
- 1 ページ 20 件。結果の末尾の「Show more messages」を押すたびに次の 20 件（スクロールでは読まない）。AI の並べ替えが使えるときは最初だけ 60 件。
- `from:` `in:` `after:` などの演算子、チャンネル内の検索もある（ToriNos では扱わない）。
- どれも 1 回ごとに NIP-98 の署名が要る。

### 1.5 公式の弱いところ（実機で確認）

- 「Open」で「明日！OpenSatsの申請…」が出ない（モバイル版の全文一致は語全体の一致だけ）。前方一致なら当たる。
- 日本語は空白・記号で区切られた語ごとに索引されるので、文の途中（「申請」）はどちらの方式でも当たらない。
- 「明日」は「！」で区切られて独立した語になっていたので、全文一致で当たった。

## 2. ToriNos の一致方式

リレーの検索（過去すべて、語の一致・前方一致）と、手元の部分一致（最近の発言、文の途中も当たる）を合わせる。

### 2.1 リレーの検索

| 条件 | 送り方 | 最初 | 続き |
| --- | --- | --- | --- |
| 確認なしで署名できる、最後の語が 3 文字以上、語句・除外が無い | `/query`・前方一致 | 50 件 | 「さらに表示」で 500 件ずつ |
| 確認なしで署名できる、それ以外（最後の語が短い、語句・除外がある） | `/query`・全文一致 | 50 件 | 同上 |
| 外部の署名器 | WebSocket・全文一致 | 500 件 | 無し（ページごとに署名の確認が出るため） |

- 入力が止まってから 300ms 後に送る。前の検索は取り消す。
- `/query` が失敗したら WebSocket の全文一致（500 件）で探し直す。
- 続きのオフセット: 最初の 50 件の後は `limit 500` の `page 1, 2, …` を読み、出したものは重ねて出さない（`page 1` の先頭 50 件は捨てる。ページの大きさをそろえないとオフセットがずれるため）。
- 返事が頼んだ数に満たなければ続きは無い。
- 前方一致と全文一致の両方は送らない（前方一致は全文一致の当たりを含むので、通信が増えるだけ）。

### 2.2 手元の部分一致

- 画面を開いたら、入力の前に裏で最近の発言を読む: 1 回の REQ に
  - `{"kinds":[9,40002,45001,45003],"limit":500}`
  - `{"kinds":[5,9005,40003],"limit":500}`（削除と編集）
- 「さらに表示」を押すたびに、いちばん古い発言の時刻を `until` にして 500 件ずつさかのぼる（2.1 の続きと同時に）。黙って読み続けない。
- 削除: kind 5 は作者本人のもの、9005 はリレーが受け付けたもの（管理者だけが送れる）を反映し、出さない。編集: 作者本人の最新の 40003 の本文で探し、出す。
- 照合用の本文は読み込み時に一度だけ作る: Markdown を平文に → 2.3 で正規化。
- 入力のたびに（300ms 待たずに、1 文字から）全件を線形に照合する。2,000 件・約 100 万文字でも数ミリ秒の見込み。索引は作らない。
- 照合: 入力を空白で語に分け、すべての語が含まれるもの（`-語` は含まないもの、`"` は外す）。語ごとの良さ: 語全体（前後が文字・数字でない）0、語の頭 1、途中 2。行の良さは語の良さの最大。
- 同じコミュニティを 5 分以内に開き直したら、前回の分を使い、それより新しい発言だけを読む（アカウントのセッションの間、メモリだけに持つ）。

### 2.3 文字の正規化（手元の照合とチャンネル名）

- 小文字にする。全角英数・記号（U+FF01〜FF5E）は半角に、全角空白は空白に。
- カタカナ（U+30A1〜30F6）はひらがなに。
- 漢字の読みは扱わない（辞書が要る）。

### 2.4 結果のまとめ方

- 手元の当たりを先に（良さ → 新しい順）、そのあとにリレーの当たりで手元に無いもの（リレーの順）。
- リレーの答えは下に足すだけなので、手元の当たりの行は動かない。
- 同じ発言は1つ。表示の作者・本文・開く先は初版と同じ（3.2）。
- 末尾の「さらに表示」は、リレーに続きがあるか、手元の読み込みがまださかのぼれる（前回 500 件そろった）ときに出す。

### 2.5 人とチャンネル

- チャンネル: 名前の順位（1.3）を、2.3 で正規化した名前と入力で行う。
- 人: 確認なしで署名できるときは `/profiles/search`（初版どおり）。外部の署名器のときは、コミュニティのメンバー一覧（kind 13534）の人の手元のプロフィールの `name`・`display_name` を 2.3 で正規化して部分一致。メンバー一覧が無いコミュニティは WebSocket の kind 0 の全文一致。

### 2.6 通信量

| | 初版 | 改訂 |
| --- | --- | --- |
| 開いたとき | チャンネル一覧 1 回 | チャンネル一覧 1 回 + 最近の発言 1 回（約 0.5MB） |
| 入力が止まるたび | メッセージ 1 回（20 件）+ 人 1 回 | メッセージ 1 回（50 件）+ 人 1 回（外部の署名器は人 0 回） |
| 入力のたび | なし | 手元の照合だけ |
| 「さらに表示」 | なし | リレー 500 件 + 手元 500 件 |

## 3. 画面（初版から変わらないところ）

### 3.1 入口

- チャットタブで Buzz のコミュニティを選んでいるとき、ヘッダーに検索ボタン。`BuzzSearchRoute(relayUrl)` を開く。
- 戻る・スワイプで閉じる。結果から開いた画面から戻ると結果が残る。
- 上部は戻るボタン + 丸い検索欄（BasicTextField。TextField を上部バーのタイトルに入れると高さが足りず文字が切れた）+ 横にスクロールするチップ。

### 3.2 メッセージの行と開く先

- `h` がちょうど1つのものだけ。作者は `groupMessageAuthor`（リレー署名は `actor`）。本文は平文 2 行（512 文字を超える本文は先頭だけ）。
- 45001 → その投稿のスレッド、45003・スレッドの返信 → ルートのスレッド、それ以外 → チャンネル（フォーラムならフォーラム）。

### 3.3 最近の検索

- `chat.buzzSearch.recent.<pubkey>.<relayUrl>`。決定・結果を押したときに記録、6 件、大文字小文字を無視して重複を消す。

## 5. テスト（commonTest `chat/BuzzSearchTest.kt`・`BuzzSearchCorpusTest.kt`）

- 正規化（大文字・全角・カタカナ）。
- 手元の照合: 部分一致、複数語、除外、語全体・語の頭・途中の良さ、並べ方。
- 控え: 削除（本人の 5、9005）、本人の最新の編集、他人の編集は無視、さかのぼりの `until`、重複。
- 送り方の選択（2.1 の表）、`/query` の本文（`search_mode`・`page`）、続きのオフセット。
- まとめ方: 手元が先、リレーの重複を除く。
- 名前の順位・最近の検索・当たりの解釈（初版のテスト）。

## 6. 対象外

- デスクトップ版の演算子、チャンネルの中だけの検索、AI の並べ替え。
- 発言の位置へ飛ぶこと。
- 標準の NIP-29 リレーでの検索。
- 漢字の読みでの検索、2,000 件より古い発言の文の途中（「さらに表示」を押した分だけ広がる）。
