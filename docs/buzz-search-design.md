# Buzz コミュニティ内の検索 設計

- 作成日: 2026-11-22
- ステータス: 実装済み（単体テストまで。実在の Buzz コミュニティ・実機での確認は未実施）
- 目的: 選んでいる Buzz コミュニティの中で、メッセージ・チャンネル・人を検索できるようにする。公式アプリ（特にモバイル版）と同じ送り方・同じ結果になるようにする。
- 対象: Buzz のコミュニティだけ。標準の NIP-29 リレーには出さない（NIP-50 に対応しているとは限らず、作者の解釈も違うため）。
- 調査対象（2026-11-22 時点の main）:
  - [block/buzz](https://github.com/block/buzz) `0e7fd48`
    - モバイル版（Flutter）: `mobile/lib/features/search/search_provider.dart`、`search_page.dart`、`search_page/message_tile.dart`、`recent_searches_provider.dart`、`name_match.dart`、`shared/relay/relay_session.dart`（`searchProfiles`）、`shared/relay/nostr_filters.dart`（`searchUsers`）
    - リレー: `crates/buzz-relay/src/handlers/req.rs`（WebSocket の NIP-50）、`api/bridge.rs`（`/query` の検索）、`api/profiles.rs`（`/profiles/search`）、`crates/buzz-search/src/query.rs`、`migrations/0008_fresh_install_search_allowlist.sql`
  - [block/buzz-app](https://github.com/block/buzz-app) `4363e10`（デスクトップ）: `src/app/shell/useSearchMessages.ts`、`parseSearchOperators.ts`、`shared/search-debounce.ts`
- 関連: `docs/nip29-buzz-design.md`（Buzz の全体）、`docs/buzz-presence-design.md`（NIP-98 の REST）

## 1. 公式の実装

### 1.1 リレー側

- 全文検索は Postgres の FTS。`search_tsv = to_tsvector('simple', content)` で、索引に入る kind は **0・9・40002・45001・45003** だけ。
- WebSocket の REQ に `search` を付けると NIP-50 の検索になる（`handlers/req.rs`）。
  - 同じ REQ の中で `search` の有るフィルターと無いフィルターを混ぜると `CLOSED`（`error: mixed search and non-search filters not supported`）。
  - 結果は関連度順（`ts_rank_cd`、同点は新しい順）で送られ、EOSE で終わる一度きりの購読（ライブ配信はしない）。
  - WebSocket では `search_mode`・`search_sort`・`page` は使えず、常に全文（`websearch_to_tsquery`）・関連度順。
  - `#h` を付けるとそのチャンネルだけ。無ければ、読めるチャンネル全部（＋チャンネルに属さないイベント）。
  - 当たったイベントは改めて読める範囲か確かめてから返す（検索で読める範囲は広がらない）。
- HTTP の `POST /query`（NIP-98 必須）でも同じ検索ができ、こちらは `search_mode: "prefix"`（最後の語を前方一致）、`search_sort: "newest"`（NIP-11 の `supported_extensions` に `buzz-search-sort` があるとき）、`page` が使える。デスクトップ版はこちらを使う。
- `POST /profiles/search`（NIP-98 必須）: 本文 `{"query": 1〜100文字, "limit": 1〜100, "page"?}`。`name`・`display_name`（と認証済みの名前）だけを前方一致で探し、名前の一致を先に並べる。応答は kind 0 と kind 30382 のイベントの配列。古いリレーは 404 / 405。

### 1.2 モバイル版（ToriNos が合わせる相手）

| 項目 | 内容 |
| --- | --- |
| 入口 | 検索画面（ホームのタブ / ボタン）。開いたらすぐキーボードを出す |
| 入力 | 1文字ごとに検索し直す。**300ms** 止まってから送る。前の検索の答えは捨てる（世代番号） |
| 絞り込み | すべて / メッセージ / チャンネル / 人 のチップ。表示だけを切り替え、検索はいつも3つとも行う |
| メッセージ | WebSocket の REQ `{"kinds":[9,40002,45001,45003],"search":<入力>,"limit":20}`。`#h` も `search_mode` も付けない。関連度順のまま出す。続きの読み込みは無い |
| チャンネル | 手元のチャンネル一覧（参加中 + 公開ディレクトリ）を名前で順位付け（下の 1.3）。DM は除く。アーカイブ済みと、`#` だけの入力では参加中のものだけ。最大 **8** 件 |
| 人 | `/profiles/search`（`limit` 24）。404 / 405 なら 5 分間は NIP-50（`{"kinds":[0],"search":…,"limit":…, "search_mode":"prefix"}` を `/query` へ）。自分は除く。最大 **8** 件 |
| メッセージの行 | アバター、名前、相対時刻、「Message in `#チャンネル`」（DM は「Direct message」）、本文2行（512文字を超える本文は書式を解釈しない） |
| メッセージを押す | フォーラム投稿（45001）はその投稿のスレッド。それ以外はチャンネルを開く（発言の位置へは飛ばない） |
| 最近の検索 | 入力が空のときに出す。最大 **6** 件、新しい順、大文字小文字を無視して重複を消す。決定（キーボードの検索）と、結果を押したときに記録。「消去」で全部消す。コミュニティとアカウントごとに端末へ保存 |
| 空のとき | 「メッセージ・チャンネル・人を検索」。結果が無ければ「'…' に一致するものはありません」 |

### 1.3 チャンネル名の順位（`name_match.dart`、デスクトップの `matchName` の移植）

入力は小文字にし、先頭の `#` を外す。名前も小文字にして比べ、良い順に:

0. 完全一致
1. 先頭が一致
2. 途中の語の頭で一致（直前が文字・数字でない）
3. 途中の一致
4. 文字が順に現れ、それぞれのまとまりが語の頭から始まる（`tlp` → `team-launch-planning`）
5. 文字が順に現れる

どれでもなければ外す。入力の空白は比べるときに無視する（4・5）。アーカイブ済みは +0.5。同順位なら参加中を先に（参加中どうしは一覧の順）、未参加は名前順。

### 1.4 デスクトップ版との違い（ToriNos は採らない）

デスクトップは `/query`（HTTP）で前方一致・ページ送り・`from:` `in:` `after:` などの演算子・チャンネル内の検索を持つ。どれも 1 回ごとに NIP-98 の署名が要る。ToriNos は外部の署名器（NIP-46・Amber）でも使えるよう、メッセージはモバイル版と同じ WebSocket の NIP-50 にする（AUTH 済みの接続に REQ を送るだけで、新しい署名が要らない）。

## 2. 日本語の検索について（公式と同じ制約）

リレーは `simple` 設定の FTS なので、語の区切りは空白と記号だけ。日本語の文は空白が無いと1語として索引される。

- 「検索機能をつけたい」という発言は、`検索機能をつけたい` という1語になる。`検索` では当たらない（全文検索は語の完全一致）。
- 当たるのは、語全体を入れたとき、または空白・記号で区切られた語（英数字の語、`、` `。` で区切られた部分など、Postgres のパーサーが区切る所）。

これはリレー側の仕様で、公式アプリでも同じ結果になる。ToriNos 側で補うと「公式と同じ結果」でなくなり、全件を読む必要もあるので補わない。検索画面のヒントに「日本語は語の区切り（空白・句読点）までを1語として探します」と書く。

## 3. ToriNos での作り

### 3.1 画面と入口

- チャットタブで Buzz のコミュニティを選んでいるとき（`selectsBuzzCommunity`）、ヘッダーの右に検索ボタン（虫めがね）を出す。
- 押すと新しいルート `BuzzSearchRoute(relayUrl)` を開く。戻る・スワイプで閉じられ、結果から開いたチャンネルから戻ると検索の結果が残る（公式と同じ）。
- 画面: 戻るボタン + 検索欄（開いたらフォーカス）、その下に「すべて / メッセージ / チャンネル / 人」のチップ、結果の一覧。

### 3.2 メッセージ

- 送るもの: `NostrFilter(kinds = [9, 40002, 45001, 45003], search = 入力（前後の空白を除く）, limit = 20)` を、そのコミュニティのリレーだけへ一度きりの取得で送る（`fetchFiniteEvents`、10秒）。
- 一時接続では NIP-42 の認証ができないので、取得の間は常時接続の側に置く（`ChatAccount.keepingRelay`、既存の作成・名簿の読み込みと同じ）。
- 届いた順（関連度順）を保つ。`h` がちょうど1つあるものだけを出す（開く先のチャンネルが決まらないものは出さない。デスクトップと同じ）。
- 作者は `groupMessageAuthor`（リレーが署名したものは `actor`）。
- 本文: 40002 は JSON の `content`、ほかは content。Buzz の Markdown を `chatListPreview` と同じ要領で平文にし、2行まで。512文字を超える本文は先頭 512 文字の平文にする（公式と同じ上限。書式の解釈を省く）。
- チャンネル名: 手元のチャンネル情報（3.3）から引く。DM は「DM」、分からなければチャンネル名を出さない。
- 押したとき:
  - 45001（フォーラム投稿）→ その投稿のスレッド。
  - 45003（フォーラムのコメント）・スレッドの返信（`buzzThreadRootId` がある 9 / 40002）→ ルートのスレッド。
  - それ以外 → チャンネル（フォーラムならフォーラムの画面）。
  - 公式モバイル版は返信でもチャンネルを開くが、ToriNos のチャンネル画面は発言の位置へ飛べず、スレッドの返信はチャンネルに出ないので、見つけた発言が見える画面（スレッド）を開く。

### 3.3 チャンネル

- 画面を開いたとき、そのコミュニティのチャンネル情報を読む。
  1. 先にチャット一覧の控え（`ChatListCache`、参加中のチャンネルと名前）で出す。
  2. リレーから kind 39000（リレーの鍵の署名、limit 300）と、自分が入っている kind 39002（`#p` = 自分）を読み、置き換える（`ChatTabViewModel.refreshBuzz` と同じ読み方）。答えがそろわなければ控えのまま（無いと決めつけない）。
- 候補: `hidden` でなく、種類が Hidden でないもの。DM は除く。参加中か、未参加なら一覧に出る（公開）もの。アーカイブ済みは参加中のときだけ。
- 1.3 の順位で最大 8 件。入力が `#` だけなら参加中だけ。
- 押したらチャンネル（フォーラムならフォーラムの画面）を開く。

### 3.4 人

- 秘密鍵・パスキーでログインしている（確認なしで署名できる）とき: `/profiles/search`（`{"query":…,"limit":24}`、NIP-98）。404 / 405 なら、そのリレーは 5 分間 3.4 の NIP-50 にする。
- それ以外（外部の署名器）と、上の代わり: WebSocket の REQ `{"kinds":[0],"search":…,"limit":24}`（NIP-50 の全文検索。`search_mode` は WebSocket では使えないので付けない）。1回ごとに署名を求めないため。
- kind 0 だけを使う（30382 の認証済みの名前は今は使わない）。同じ人は新しい kind 0 だけ。自分は除き、最大 8 件。
- 行: アバター、名前、`@name`（あれば）。押したらプロフィールを開く（`onUserClick`）。
- 失敗しても画面にエラーは出さない（公式と同じ。人の検索は補助）。

### 3.5 入力と状態

- 入力のたびに 300ms 待ってから、メッセージと人を検索し、チャンネルを並べ直す。新しい入力が来たら前の検索は取り消す（`Job.cancel` と世代番号の両方で、遅れた答えを捨てる）。
- 前後の空白を除いて空なら、結果を消して「最近の検索」を出す。
- 読み込み中は、結果の下に回転するものを出す。メッセージ・人がどちらも終わるまで。
- メッセージの検索が失敗したら（リレーが答えない・`CLOSED`）「メッセージを検索できませんでした」と「再試行」を出す。チャンネル・人の結果は出したまま。

### 3.6 最近の検索

- 保存先: `LocalSettingsStorage` の `chat.buzzSearch.recent.<pubkey>.<relayUrl>`（改行区切り）。アカウントとコミュニティごと。
- 記録: キーボードの検索ボタンで決定したとき、結果のどれかを押したとき。最大 6 件、新しい順、大文字小文字を無視して重複を消す（新しい書き方を残す）。
- 入力が空のときに一覧で出し、押すとその語で検索する（入力欄にも入れる）。「消去」で全部消す。

## 5. テスト

`commonTest` の `chat/BuzzSearchTest.kt`:

- 名前の順位: 完全一致・先頭・語の頭・途中・語の頭のまとまり・順に現れる・外れ、`#` の除去、空白の無視、並べ方（アーカイブ +0.5、参加中が先、未参加は名前順、8 件まで、`#` だけなら参加中だけ）。
- 最近の検索: 先頭に入る、大文字小文字の重複を消す、6 件まで、空は記録しない、保存形式の往復。
- メッセージの当たり: `h` が無い・2つあるものは出さない、関連度順を保つ、40002 の本文、リレー署名の `actor`、開く先（45001 / 45003 / 返信 / トップレベル / フォーラムのチャンネル）、長い本文の切り詰め。
- 人の応答: kind 0 以外を除く、同じ人は新しいもの、自分を除く、8 件まで、壊れた JSON は空。
- フィルター: メッセージと人の REQ の形（`#h` も `search_mode` も付けない）。

## 6. 対象外

- デスクトップ版の演算子（`from:` `in:` `before:` など）、前方一致、新しい順、ページ送り、チャンネルの中だけの検索（どれも `/query` の NIP-98 が要る）。
- 発言の位置へ飛ぶこと（チャンネル画面に仕組みが無い。公式モバイル版も飛ばない）。
- 標準の NIP-29 リレーでの検索。
- 日本語の部分一致（2 章）。
